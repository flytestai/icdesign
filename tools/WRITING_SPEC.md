# 课程写作规范（面向零基础）

这份规范是硬约束。写（或改）任何 `content/*.md` 前先读完，交付前用 `python tools/audit.py --bad` 自检。

## 一、读者是谁

- **完全零基础**：没进过芯片公司，不知道什么是 netlist、不知道 shell 是什么；英语只到四级，看到 `insertion delay` 会卡住。
- 他们的目标很具体：**能在面试里讲清流程、能在公司里照着脚本跑起来、能看懂报告上的红字**。
- 所以：**先讲清"这是什么、为什么需要它"，再讲"命令怎么写"**。顺序反了，读者就云里雾里——这也是原站最大的问题。

## 二、每一课必须有的结构（块语法，块结束都是单独一行 `:::`）

```markdown
---
id: 03-13-xxx        # 不改，由维护者统一编号
no: "37"
stage: 3
title: 中文标题
en: English Title
hours: 3
minutes: 40
tags: [标签]
summary: 一句话说清这一课解决什么问题
status: live
---

## 章节标题 {#anchor}

正文（见第三节的深度要求）

:::goal 一句话目标
能用一句话说出这一课学完你会做什么（动词开头，可验收）。
:::

:::scene 场景标题
一个具体的工作场景：谁、在什么阶段、手里有什么文件、被什么问题卡住。要具体到"周一早上 leader 让你……"这种程度。
:::

:::term Insertion Delay | 插入延迟
从时钟源到某个触发器时钟端的实际延迟。英文首次出现必须给中文，并用一句大白话解释。
:::

:::pitfall 坑的标题
现象 → 原因 → 怎么避免/怎么查。写真实报错或真实现象，不要写"注意安全"这种空话。
:::

:::lab 动手标题
可验收的动手任务：给输入、给步骤、给"做到什么程度算过"。
:::

:::quiz
问题|答案
（至少 4 道，答案要能自洽，不要"略"）
:::

:::check
- 过关项（能自己复述/能跑出某个结果）
:::
```

- `:::term` 每课 **≥3 条**，自动进术语表。
- `:::quiz` 每课 **≥4 题**，自动进题库。
- `:::sandbox basic|text|proc | 提示语` 是浏览器内模拟终端，只能在 Linux/命令类课程用。
- 每课至少 **1 个 `:::scene`**（工作场景）和 **1 个 `:::lab`**（可验收练习）。

## 三、深度要求（这是重点，不是凑字数）

| 指标 | 下限 | 说明 |
|---|---|---|
| 正文字数 | **≥ 900 汉字 / 学时**（3 学时课 ≥ 2700 字，不含代码） | 现在的课普遍只有 300 字/学时，太薄 |
| 每章 | ≥ 300 字 + 1 个类比或手算例子 | 一章只写两三句等于没写 |
| 每章 | 至少 1 处"**工作中怎么用**" | 说清这一步在项目里由谁做、做完交给谁、做错了会怎样 |
| 术语 | 首次出现的英文都要给中文 | `skew（偏斜）`、`utilization（利用率）` |

写法要求：

1. **先类比，再定义，再命令**。触发器讲成"照相机"、时钟树讲成"自来水管网"、DRC 讲成"违建"——类比之后立刻给严格定义，别停在类比。
2. **数字要能算**。能给公式就给公式（如 `slack = required − arrival`、通道宽度 = 引脚数 × 间距），并带一次手算。
3. **报错要真**。写工具真实的报错首行（如 `**ERROR: (IMPSR-2019): Cannot find library`），并解释每个词。
4. **不要空话**。"非常重要""需要注意"这类句子删掉，换成具体判断标准。
5. **句子短**。一段不超过 4 行，多用列表和表格。中文标点，代码和命令用反引号。

## 四、代码块规范

```bash
# 作用：把最差的一条路径捞出来，只保留 slack 和路径名
# 用法：在 pnr/ 目录下执行；timing.rpt 是 report_timing 的输出
grep -E "slack" timing.rpt | sort -k3 -n | head -5
```

- **每个代码块第一行必须是注释**：这块代码干什么、在哪个目录跑、依赖什么文件。
- **每一行命令都要有解释**：行尾 `# 说明`，或在代码块后逐条讲。
- 长脚本要分节注释（`# ---- 第一步：读库 ----`）。
- Tcl / Shell / Python 都要标语言，让页面能高亮。
- **绝不编造工具输出**。没在课程环境验证过的，写"课程环境跑不了这一步，真实项目里你会看到……"，并说清依据。

## 五、事实纪律

- 工具命令、参数、报错码写你确定的部分；不确定就写判断依据，不要造。
- 学时、工艺节点、单元数量这类数字，如果来自课程环境实测就标注"实测"，否则标注"典型值"。
- 课表没覆盖但工程上必须知道的（如 antenna、ERC），可以写，但要标明"课表外补充"。

## 六、禁止

- 禁止改 front-matter 里的 `id` / `no` / `stage`（编号由 `tools/_renumber.py` 统一排）。
- 禁止在正文里写 HTML（除 `:::svg` 块）。
- 禁止复制粘贴同一段话到多课；重复内容合并到一课，别处引用课号。
- 禁止把"这一课很重要"当开头。

## 七、自检

```bash
python tools/audit.py --bad     # 结构缺失、代码没注释、术语/自测不足
python tools/build.py           # 能构建就说明语法没错
```
