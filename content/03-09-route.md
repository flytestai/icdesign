## 布线的两步 {#two-steps}

:::goal 学完这一课，你能拿到一份布线结果后，用三份报告判断它能不能交出去；DRC 清不干净时，能判断该继续修布线还是回退改布局。
:::

搬家时司机不会一上来就决定"停第 3 排第 7 个车位"。他先看导航：走哪条高速、从哪个出口下、进小区走哪个门。到了小区门口，才决定具体停哪个车位。

布线（routing）也是这么两步：

- 第一步叫**全局布线**，决定"大致走哪条通道、上哪一层金属"；
- 第二步叫**详细布线**，决定"具体占哪一根轨道、在哪里打 via"。

前一步错了，后一步再努力也布不下；后一步不做，前一步只是一张草图。

| 对比项 | 全局布线 | 详细布线 |
|---|---|---|
| 决策粒度 | 层、通道、大致走廊 | 具体轨道、具体 via |
| 输出 | 每条 net 的层分配 + 各区域轨道占用 | 可以直接送去制造的版图 |
| 失败表现 | overflow > 0（这块地方根本塞不下） | DRC 违例、open（画错了） |
| 耗时（典型值） | 几分钟 | 几十分钟到几小时 |
| 出问题该找谁 | 回 floorplan / placement | 就地增量重布 |

为什么不合成一步？因为解空间是组合爆炸的：一条通道有 100 根轨道、要过 130 根线，逐根去试是天文数字。先做粗粒度的"层与通道分配"，把问题缩小到"某条通道里 130 选 76"，才有解。

:::term Global Route | 全局布线
只决定每条网络走哪一层、穿过哪些区域（gcell），不决定具体轨道。它的产出是"可行性判断"：如果某个区域的走线需求超过供给，这一版布局就布不通，必须回去改布局。
:::

:::term Detail Route | 详细布线
在全局布线给出的走廊里，把每根线放到具体的 track 上，并在换层处打 via，同时满足间距、宽度、via 规则。DRC 违例绝大多数在这一步产生、也在这一步被修掉。
:::

:::term Track | 轨道
每一层金属上，走线只能落在等间距的格线上，这些格线就是 track。track 的间距叫 pitch（节距）= 最小线宽 + 最小间距。

一个区域能过多少根线，等于它能容纳多少条 track。**拥塞的本质就是"要走的线比 track 多"。**
:::

:::term Via | 通孔
连接相邻两层金属的垂直通道。换层必须打 via，一根线换两次层就多两个 via。via 本身要满足"包边"（enclosure）规则，也就是上下层金属要比 via 多出一圈，这是 via 类 DRC 的主要来源。
:::

不同层有不同分工，这是布线能收敛的前提（下面是 7 层工艺的典型分工，具体层数看你的工艺）：

| 层 | 主要用途 | 为什么 |
|---|---|---|
| M1 | 单元内部走线、引脚引出 | 最细，电阻大，只适合短距离 |
| M2~M4 | 局部信号 | 数量多，够密，适合短中距离 |
| M5~M7 | 长线、时钟主干 | 线宽大、电阻小，跑得远 |
| 顶层厚金属 | 电源/地 | 载流能力强，也方便打电源 via |

```tcl
# 作用：Innovus 里把"两步"拆开跑，方便在中间就看拥塞
# 用法：place 完成后执行，SDC 已 source；层号按你的工艺改
setRouteMode -earlyGlobalMaxRouteLayer M6   ;# 全局布线最高只用到 M6，M7 留给电源
globalRoute                                  ;# 第一步：只分配层和通道，输出草图
reportCongestion -hotSpot                    ;# 草图阶段就能看出哪块会堵，别等 detail 跑完
detailRoute                                  ;# 第二步：落到具体轨道和 via，同时修 DRC
```

ICC2 把这两步包在一个 `route_auto` 里，log 里会分别打印 global route 和 detail route 的阶段。想只跑前半段，用阶段参数限定（不同版本参数名有差异，动手前先 `man route_auto` 确认）。

:::scene 周一早上，6000 条 DRC
你接手一个万门设计，周五要交布线 review。周一跑完 `route_auto`，屏幕最后一行是"完成"，你松了口气，随手 `check_routes`：

```
Total number of DRCs: 6000
```

6000 条里 95% 是同一个形状：某个单元的引脚出不来线（pin access）。leader 问你三个问题：这 6000 条是布线没跑对，还是布局没留够空间？再加五轮增量能不能清掉？如果不能，要回退到哪一步？——这三个问题，就是这一课要你能答的。
:::

## `route_auto` 返回 0，不等于布完了 {#not-done}

写过程序的人都知道：编译器退出码 0，只说明"语法没报错"，不说明"程序算得对"。布线命令的返回值是同一回事——**它只说明这条命令跑完了、没崩**。

布通和布好之间，隔着五件事：

1. **退出码不管 DRC。** 工具认为"我把该连的都连上了"就返回成功，剩下几十条间距违例，要你另外数（`check_routes`）。
2. **`route_auto` 优先保连通。** 引脚挤在一起时，它的第一选择是"先连上"，把一个引脚绕出去，代价是挤到隔壁网络——于是产生 spacing/short。
3. **布线不管时序。** 布完才有真实 RC，"连得上"和"跑得够快"是两件事。布线前的延迟是估算值，布线后才是真的。
4. **天线、密度、LVS 都不在它的判定里。** 这三项要单独查，任何一项红都不能送厂。
5. **局部修补会带来新违例。** 你修 A 点的 spacing，可能把 B 点的线挤歪，所以"跑一次就干净"这件事，在大设计上基本不成立。

所以判断"布完了"要用四个硬条件，不看退出码：

| 硬条件 | 怎么查 | 通过标准 |
|---|---|---|
| 没有开路 | `check_routes` 或 `check_lvs` 看 opens | 0 |
| DRC 清零 | `check_routes` 看 DRC 总数 | 0，或有书面 waiver 清单 |
| 天线清零 | 天线检查报告 | 0 |
| 时序有快照 | `report_qor` / `report_timing` | 有 WNS/TNS 数字，能和布局后基线对比 |

一句话记住：**`route_auto` 是把线画上去，不是把线画对。**

:::pitfall 看到"完成"就去睡觉，第二天发现 DRC 6000
现象：命令返回 0，log 最后一行是完成信息，你以为收工了。
原因：返回值和结果质量是两回事，DRC 要单独数。
处理：把"跑完 → 数 DRC → 出三份报告"写成一个脚本固定下来（本课后面的 lab 就是这个），不要靠人记。
:::

## 五类 DRC：成因、修法、谁负责 {#drc}

DRC 不是"工具算错了"，是**你画出来的版图真的违反了工厂的制造能力**。工厂不会听你解释，所以必须清零。

先记住五类，这五类覆盖了实际项目的 95% 以上：

| 类型 | 报错长什么样 | 成因 | 修法 | 谁负责 |
|---|---|---|---|---|
| Short（短路） | `Net A shorted to Net B` | 两根不同网络的线碰上；常见于拥塞区和引脚出口 | 局部重布；挪单元；加通道 | 布线 + 布局 |
| Open（开路） | `Net A has unconnected pin` | 线没连到引脚；via 漏打；线被别的线切断 | 查引脚是否被电源轨挡住，重布该 net | 布线 |
| Spacing（间距） | `Metal2 spacing < 0.07` | 同层两条线距离小于规则；局部密度过高 | 局部重布；降局部密度 | 布线（根因常在布局） |
| Width / Notch（线宽/缺口） | `Metal1 width < 0.065` | 线太细；为了避让缩了线；NDR 没生效 | 让工具加宽；检查 NDR 是否作用到该 net | 布线 |
| Via（通孔） | `Via enclosure < 0.02` / `Via count < 2` | via 包边不足；via 数量不够（EM 与良率要求） | 加倍 via；换 via array；检查 via 规则 | 布线 |

```
Spacing 违例示意（同层两条线距离小于规则）

  ━━━━━━━━━━━━━━━
        ↕ 0.08µm   ← 规则要求 0.10µm，差 0.02 就是违例
  ━━━━━━━━━━━━━━━
             ↑ 修法：把下面那根线往下推 0.02µm，或换一层走
```

三类最容易搞混的，单独说清：

**Short 和 Spacing 的区别。** Short 是两根线真的连上了，电学上就是同一个节点，功能直接错，LVS 也会报；Spacing 是没连上，但靠得太近，制造时可能粘连或者击穿。前者是"已经错了"，后者是"可能会错"。修 Short 必须动线，修 Spacing 有时只要挪 20nm。

**Open 最容易被误判成"工具没布"。** 打开版图看，线明明画到了引脚边上，为什么还报 open？多半是引脚被电源轨（power rail）盖住，或者上一层金属挡住了出线口，工具画的线其实没接触上。这类要查单元摆放和引脚方向，不是加布线轮数能解决的。

**Via 类违例不是"多打几个孔"那么简单。** 除了包边，还有"每个 via 至少 2 个 cut"（可靠性）、"via array 必须规则排列"（光刻）这些要求。电源网络上的 via 尤其容易踩，因为电流大、数量多。

:::note 引脚访问冲突不是第六类，它是成因
你会在报告里看到 `pin access` 这个词，它不是一种独立的 DRC 类型，而是 short/open/spacing 的**根因**：一个 `AOI222_X1` 六个引脚挤在 0.76×1.4µm 的框里，周围单元摆得太密，线就出不来。

判断方法：把 DRC 按坐标画到版图上，如果违例**成簇**出现在多引脚单元周围，就是 pin access；如果是零散分布，才是普通的绕线问题。前者必须回布局，后者可以增量磨。
:::

读 DRC 报告有个固定顺序，别一条条看：

1. **按类型分组**：先看哪一类最多（短路的优先级永远最高，因为它意味着功能错）；
2. **按坐标聚簇**：把违例投到版图上，看是"几个大簇"还是"均匀撒开"；
3. **挑最大的簇下手**：一个簇往往对应一个根因，修一个簇能消掉几百条。

:::pitfall 反复跑增量，DRC 卡在 156 下不去
现象：`route_detail -incremental` 跑了六轮，DRC 从 6000 降到 156 就再也不动了。
原因：剩下的都是 pin access，根因在布局——单元太密、多引脚单元周围没留出线通道。布线只能在给定空间里找解，空间不够它不是万能的。
处理：回布局端打开 pin density aware、重跑 place + legalize + refine，再回来布线。我们在课程环境验证过：同一套布线参数，布局改对之后 DRC 能从 6000 直接归零（完整曲线见第 22 课）。
:::

## 增量布线：一轮一记录 {#incremental}

增量布线（incremental routing）的意思是：**保留已经布好的线，只重布有问题的那一小块**。它的价值是快——全量重布几小时，增量一轮几分钟。

但它有个前提：**你必须知道每一轮发生了什么**。否则你会在"跑了十轮还是 300 条"的状态里出不来，也不知道该停还是该回退。

三条纪律：

1. **一轮只做一件事。** 这一轮就修 DRC，别顺手改约束、别顺手换单元尺寸——那会让增量变成事实上的全量，还查不出是哪一步引入的新违例。
2. **每轮前后各记一次数。** 跑之前记 DRC 数、WNS、时间；跑之后立刻再记一次，写进同一个 csv。
3. **连续两轮数字不变就停。** 不变说明不是"还能收敛"，是结构性问题（拥塞或 pin access），加轮数只是烧机器。

```tcl
# 作用：ICC2 里跑增量布线，每轮存一份报告、往 csv 里追加一行记录
# 用法：在 pnr/ 目录下、block 已打开；先建好 rpt/ 目录
set fh [open rpt/route_rounds.csv w]                                    ;# 建记录文件，覆盖上一次的
puts $fh "round,drc,wns,note"                                           ;# 表头：轮次/DRC 数/setup WNS/备注
for {set i 1} {$i <= 10} {incr i} {
  route_detail -incremental true                                        ;# 只重布有问题的局部，保留已布好的线
  redirect rpt/drc_$i.rpt { check_routes }                              ;# 每轮一份独立报告，别覆盖
  set txt [read [set f [open rpt/drc_$i.rpt r]]]                        ;# 读回报告文本
  close $f
  regexp {Total number of DRCs\s*:\s*(\d+)} $txt -> n                   ;# 从报告里抠出 DRC 总数
  set w [get_attribute [get_timing_paths -delay_type max -max_paths 1] slack]  ;# 顺手记一条最差 setup
  puts $fh "$i,$n,$w,"                                                  ;# 每轮追加一行，趋势一眼可见
  puts "@@@ round $i  DRC=$n  WNS=$w"                                   ;# 屏幕上也打一行，跑的时候就能看
  if {$n == 0} { break }                                                ;# 归零就退出，别白跑
}
close $fh                                                               ;# 关文件，否则最后一轮不落盘
```

为什么一定要留这份 csv：汇报时你能拿出"6000 → 156 → 119 → …"的曲线，而不是"我跑了十轮就好了"。曲线还能证明一件事——**哪一轮开始不降了**，那才是真正需要改布局的时刻。

:::pitfall 把增量循环当成万能药
现象：写了 `for` 循环跑二十轮，每轮都"修好了几条"，总量却不动。
原因：增量只能修"局部资源还够"的违例；一旦根因是拥塞，它每修一条就挤坏另一条，总数守恒。
处理：看 csv 的斜率。前几轮下降快、后面每轮只降个位数，就该停手去查拥塞热点，而不是把轮数改成 50。
:::

## 手算：一条通道能过几根线 {#hand-calc}

拥塞不是玄学，可以提前算出来。

假设某条通道宽 20µm，用 M3 走线，M3 的 pitch 是 0.2µm（线宽 0.1 + 间距 0.1，典型值）：

- 理论轨道数 = 通道宽 ÷ pitch = 20 ÷ 0.2 = **100 条**；
- 扣掉穿过的电源/地各 2 条 → 100 − 4 = **96 条**；
- 再留 20% 给 via 阵列和绕线拐弯（dogleg）→ 96 × 0.8 ≈ **76 条可用**。

现在看需求：这一条通道要过 130 根 net。

`overflow = 需求 − 供给 = 130 − 76 = 54`

意思是：**有 54 根线无论如何都过不去**，不管你跑多少轮增量。

两种解法，代价完全不同：

| 解法 | 怎么算 | 代价 |
|---|---|---|
| 加宽通道 | 需要 (130 ÷ 0.8 + 4) × 0.2 ≈ 33µm，即把 20µm 加宽到 34µm | 芯片面积增加 14µm × 通道长度 |
| 降需求 | 把这 54 根挪到 M4 走，或者把部分单元挪走 | 可能把拥塞搬到别处，要复查 |

那 20% 的余量不是随便留的。一条线从 A 点到 B 点，不会笔直走完全程：出引脚要拐一下、遇到障碍要绕、换层要打 via 占掉上下两层的空间。经验上这部分损耗在 15%~25%，所以算法里先扣掉。

换个层再算一遍就更能说明问题：同样是 20µm 宽的通道，如果改用 M5（pitch 0.4µm，典型值），理论轨道只剩 50 条，扣掉 4 条电源再留 20% 余量，可用约 37 条。**同一块地方，层选错，容量差一半。** 这也是为什么"放开高层"常常是四条拥塞解法里最便宜的那一条。

算完你就明白：**拥塞是几何问题，先算再改，比跑十轮增量便宜得多。**

## 拥塞：四个成因与诊断顺序 {#congestion}

DRC 是"已经画错了"，拥塞是"根本画不下"。两个指标先分清：

| 指标 | 定义 | 红线 |
|---|---|---|
| overflow | 某区域需要的 track 数 − 实际可用 track 数 | > 0 就是拥塞 |
| congestion % | 该区域 track 占用率 | > 90% 高危，> 100% 一定布不通 |

四个成因，从便宜到贵排：

1. **层分配不合理。** 该上高层的长线被限制在低层，几百根线挤在 M2。改一个 `max routing layer` 就可能解决。
2. **引脚密度过高。** 多引脚单元（AOI/OAI/MUX）成片堆在一起，每个单元都要向外引 6~10 根线，局部轨道被瞬间抽干。
3. **宏单元通道太窄。** 两个 macro 之间只留 5µm，但那里要过 3000 根线。这是 floorplan 的账，布线改不了。
4. **整体利用率过高。** 标准单元占了 85% 的面积，剩下的通道根本不够。这是最贵的修法——降利用率意味着面积变大、线变长、成本上升。

诊断顺序**必须**是这样，别跳步：

```tcl
# 作用：先看热点在哪，再判断是 floorplan 还是 placement 的问题
# 用法：全局布线之后就可以跑；输出热点坐标和 overflow 数值
reportCongestion -hotSpot          ;# 列出 overflow 最大的若干区域（Innovus）
reportCongestion -overflow         ;# 按 gcell 打印 overflow 分布，配 -hotSpot 一起看
```

看到热点之后，用形状判断根因：

| 热点的形状 | 说明问题在 | 先改什么 |
|---|---|---|
| 沿宏单元边界连成一条 | floorplan：通道不够 | 加宽通道、加 halo、调整宏朝向 |
| 芯片中央一大片均匀 | placement：利用率太高 | 局部降密度、开 pin density aware |
| 小簇状，落在多引脚单元区 | placement：引脚密度 | 打散这类单元、换低引脚数的单元 |
| 沿某一层边界整齐出现 | 层分配 | 放开高层、改 max routing layer |

:::pitfall 一拥塞就降利用率
现象：DRC 清不掉，把利用率从 0.7 降到 0.55，DRC 果然降了。
代价：芯片面积涨 27%，线变长，功耗跟着涨，成本直接上去。
正确顺序：先试便宜的——挪宏单元、加通道、打散多引脚单元、放开高层。这四样都不行，最后才降利用率，并且要写进评审记录，说明为什么必须付这个代价。
:::

## 天线效应：为什么会产生，三种修法 {#antenna}

芯片制造是一层一层刻出来的。刻蚀金属时用等离子体，长金属线就像一根天线，把电荷收集起来。

正常情况下电荷会沿导线流走。但如果这根线只连到晶体管的**栅极**，而栅极下面是绝缘的氧化层——电荷没地方去，越积越多，电压升高到一定程度就把氧化层击穿。击穿是永久的，芯片直接报废。

工艺厂因此规定一个比例（典型量级，具体看工艺手册）：

`antenna ratio = 接在栅上的金属面积 ÷ 栅氧化层面积`

超过阈值（常见 300:1 到 500:1）就是违例。注意这个比例是**按层、按刻蚀步骤**分别算的：一根线在 M2 上很长、到 M5 才接到栅，那 M2 那一步也会被算一次。

三种修法，代价递增：

| 修法 | 做法 | 为什么有效 | 代价 |
|---|---|---|---|
| 跳层（layer jumping） | 在长线中段打 via 上高层，走一段再下来 | 把同层金属面积摊到两层，每层都低于阈值 | 多两个 via，占布线资源 |
| 改布线 | 换一条更短的路，或换层走 | 直接减少接在栅上的金属长度 | 可能引入新拥塞，要复查 DRC |
| 插二极管 | 在栅附近加一个反向二极管，给电荷一条泄放通路 | 电荷从二极管走掉，不经过氧化层 | 面积增加、漏电增加、要库支持、LVS 要认这个器件 |

优先顺序：**先跳层 → 再改布线 → 最后插二极管**。因为前两个不动网表、不加器件，后一个要改网表，还会带来漏电和 LVS 的新问题。

```tcl
# 作用：Innovus 里检查并修天线违例
# 用法：详细布线之后执行；先看有多少条，再决定修法
verifyProcessAntenna                       ;# 按工艺规则算 antenna ratio，列出违例 net
setNanoRouteMode -drouteFixAntenna true    ;# 让详细布线在重布时顺手做跳层修天线
ecoRoute                                   ;# 只对违例 net 做局部重布，不动其他线
```

ICC2 里天线修复是布线过程的一部分（叫 antenna fixing），默认会尝试跳层；开关在 route 的应用选项里，不同版本名字不同，用 `get_app_options *antenna*` 查当前版本的确切名称。检查报告随 `check_routes` 一起出。

:::pitfall 修完天线，DRC 涨了 200 条
现象：跑完 antenna fixing，天线违例归零，DRC 从 12 涨到 212。
原因：跳层要打 via，via 一多就撞上 via 包边和 via 间距规则；改布线还可能把线挤到邻居身上。
处理：天线和 DRC 是**互相拉扯**的，修完天线必须再数一次 DRC，放进同一个循环里收敛。别以为修完天线就结束了。
:::

## 布线后必出的三份报告 {#reports}

布完线，你要交出去的不是"我跑完了"，是三份能被人复核的报告。

| 报告 | 命令 | 看哪个数 | 不合格怎么办 |
|---|---|---|---|
| DRC 数 | `check_routes > rpt/drc.rpt` | `Total number of DRCs` | 按类型分组，先修簇；根因在布局就回退 |
| 时序快照 | `report_qor` + `report_timing -max_paths 50` | WNS、TNS、违例条数 | 与布局后基线比，恶化超 10% 就要查原因 |
| 天线 | `verifyProcessAntenna` | 违例 net 数 | 跳层 / 改线 / 插二极管 |

再加一份可选的连通性报告（`check_lvs` 或 `verifyConnectivity` 看 opens、floating），因为你**永远要确认"没有开路"比"DRC 是 0"更优先**——一条开路的线，DRC 可能完全不报。

三份报告的使用方式有一条铁律：**必须和上一阶段基线对比**。单独一个"WNS = −0.05ns"说明不了任何问题；"布局后 +0.12，布线后 −0.05"，说明布线吃掉了 170ps，这才是要找的东西。

:::note 课程环境的一组参考数据
同一个万门设计，时序驱动流程和纯物理流程的布线结果可能差三个数量级：前者首轮 DRC 可能就是 0，后者首轮几千条。差别不在布线参数，在于前面有没有做时序驱动的布局和引脚密度感知。

完整的两组数据、以及一条 6000→0 的逐轮收敛曲线，在第 22 课。这里只需要记住结论：**布线阶段的 DRC 数量，很大程度是布线之前就决定了的。**
:::

## 交付前的检查清单 {#checklist}

本节这张表是"把布线结果交出去"的自检，不是"送厂"的自检（送厂的十项在第 23 课）。

| # | 检查 | 判据 | 为什么 |
|---|---|---|---|
| 1 | 数据库已存盘 | 有明确命名的 `.enc` / block 存点 | 后面每一步出问题都要能退回 |
| 2 | opens = 0 | `check_routes` 或 `check_lvs` | 开路比 DRC 更致命，功能直接错 |
| 3 | DRC 为 0 或有 waiver | `check_routes` 总数 | 带着几千条往下一阶段走，等于把债滚大 |
| 4 | 三份报告齐全 | DRC / 时序 / 天线各一份文件 | 口头说"跑过了"没法复核 |
| 5 | 报告带版本与时间 | 文件名含轮次或日期 | 优化后旧报告全部作废，混用会看错 |
| 6 | 天线违例已处理 | 违例 net 数 = 0 | 送厂才发现，要重出 GDS |
| 7 | log 与脚本已归档 | run 脚本 + 完整 log 在同一目录 | 别人复现你的结果，靠这个 |
| 8 | 已知问题写清楚 | waiver 清单 + 原因 | 不写，下一个人会以为是漏修 |

第 5 条最容易被忽略。同一天跑三次布线、三个 `drc.rpt` 互相覆盖，等你回头找"哪一版是干净的"，只能靠猜。**报告命名是工程习惯，不是强迫症。**

## 交给下一课：OptRoute 在布线后修什么 {#optroute}

布线一结束，时序一定会变，而且多数是变差。原因很朴素：布线前工具用"估算线长"算延迟，估算往往偏乐观；布线后线真的绕了弯、换了层，RC 变大，延迟就上去了（典型值：net delay 增加 10%~30%）。

估算有多乐观，可以用一个具体例子感受：布线前工具按"两点直线距离 × 单位电阻电容"算，一条 200µm 的线估成 200µm；实际走线为了绕开宏单元，可能变成 320µm，还多换了两次层，多出四个 via 的电阻。延迟按长度线性涨 60%，再叠加 via 电阻，实际可能比估算高 70%。**这就是"布线前必须留 100~150ps 余量"的算术依据。**

所以布线之后还有一轮优化，用真实 RC 重新修 setup/hold/DRV。这一轮不在这课讲，因为它的重点不是"怎么布线"，而是"怎么在已经布好的版图上做取舍"，那是第 22 课（OptRoute）的内容。

两边分工记清楚：

| 这一步 | 本课（Route）负责 | 第 22 课（OptRoute）负责 |
|---|---|---|
| DRC | 把线画对，消掉画错的违例 | 优化动作引入的新违例，再收敛一次 |
| 时序 | 只出快照，不改 | 用真实 RC 修 setup / hold / DRV |
| 天线 | 检查 + 跳层/改线 | 优化后再复查一次 |
| 手段 | 重布、跳层、加通道 | 换单元尺寸、插 buffer、局部重布 |

本课只需记住一条纪律：**布线前 WNS 要留 100~150ps 余量**，不然布线后一波新违例，等于白跑一轮。

## 交给下一课：ChipFinish 收的四件事 {#finish}

布线跑完，版图并不是"成品"。它现在的状态是：标准单元行里有空隙、金属层大片空白、芯片边缘什么都没有、也没有经过签核级 DRC/LVS。这四件事归第 23 课（ChipFinish），这里只说清边界，避免你误以为布完就能送厂。

| 还缺什么 | 一句话说明 | 详见 |
|---|---|---|
| 填缝 | 标准单元行的空隙要填 filler，否则阱和电源轨不连续 | 第 23 课 |
| 铺平 | 每层金属密度要达标，否则化学机械抛光后表面不平 | 第 23 课 |
| 包壳 | seal ring 防切割裂、pad 供封装打线 | 第 23 课 |
| 验证与交付 | 签核级 DRC/LVS、GDS/OASIS、给下游的报告与说明 | 第 23 课 |

你需要在本课就建立的意识是：**布线的 DRC 数和金属密度，直接决定 ChipFinish 要跑几轮**。布线阶段把密度留得太极端（某层 90%、另一层 10%），收尾时就得靠大量 metal fill 去补，而 metal fill 又会反过来影响时序。这笔账在布线时就要开始算。

四件事的顺序也不能乱：先填缝（filler 会改局部电容，要在时序复查之前做完），再铺平（metal fill 会加耦合），最后才做签核级 DRC/LVS 和出图。顺序反了，等于每做一步就把前一步的验证结果作废。

## 工作中怎么用：Route 在项目里的位置 {#in-work}

**谁做**：数字后端工程师（PR 工程师）。大设计通常一人负责一个 block，顶层由资深工程师做集成。

**输入是什么**：CTS + OptCts 之后的数据库、SDC、工艺的 layer/track 定义（tech lef）、布线规则（NDR、天线规则）。

**输出交给谁**：交给 OptRoute（第 22 课）继续收敛，再进 ChipFinish（第 23 课）。同时要给 STA 工程师一份时序快照，告诉他"这是布线后的真实延迟"。

**评审看什么**：三个数——DRC 是否为 0 或有明确 waiver、WNS/TNS 与布局后基线的差值、天线违例数。任何一个说不清来源，评审都会打回。

**做错会怎样**：布线是整个流程里 runtime 最长的一步（几小时到一天）。如果带着布局的根因去布线，你会花掉一天跑出一个 6000 条 DRC 的结果，然后再花两天做无效的增量。**所以布线前的检查比布线本身值钱**：先确认利用率、引脚密度、宏通道这三件事，再按回车。
