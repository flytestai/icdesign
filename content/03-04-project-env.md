## 先有环境，再谈操作 {#why}

:::goal 能说出 work / scripts / data / library / report / logs 六个目录各放什么；能在服务器上建出这套结构并说出为什么脚本必须进 scripts；能说出 Run 命名的三要素；能解释 Queue 集群解决了什么问题、一个 run 为什么可能跑三四天、等待期间该干什么。
:::

课上有一句提醒很实在：**实际工作几乎不用图形化桌面，全是开终端进目录干活。** 所以你入职后第一批动作往往不是"跑工具"，而是：

1. 登录（VNC / ssh）；
2. 找到项目目录；
3. 建自己的 work 目录；
4. 确认 scripts / data / library 在哪。

**这四步做错，后面所有命令都会写错路径。**

## 六个目录，各管一件事 {#dirs}

```
/proj/<项目名>/          ← 也可能在 ~/work/<项目名>/
├── work/               ← 你的工作目录：跑工具、放 run 的现场
├── scripts/            ← 脚本（Flow）：所有 tcl、makefile、配置文件
├── data/               ← 数据：网表、def、sdc 等输入
├── library/            ← 库：lef / lib / rc tech / 内部库
├── report/             ← 报告：每个阶段吐出的时序、面积、DRC 报告
└── logs/               ← 日志：工具跑批的输出
```

| 目录 | 放什么 | 谁产生 |
|---|---|---|
| **work** | run 目录、临时文件、调试现场 | 你 |
| **scripts** | 所有脚本（**也叫 Flow**） | 你 / 团队 |
| **data** | netlist、def、io file、sdc | 上游 release |
| **library** | tech lef / cell lef / lib / rc tech / 内部库 | 库组 / 工艺厂 |
| **report** | 时序报告、面积报告、DRC/LVS 报告 | 工具 |
| **logs** | 运行日志 | 工具 |

:::term Flow | 流程脚本
一个项目里"把九道工序串起来自动跑"的脚本集合（一堆 tcl + 配置文件），放在 `scripts/` 下。**新人最重要的自学材料不是文档，是 Flow**——它写明了每一步用什么命令、什么参数、按什么顺序。
:::

:::tip 为什么脚本必须放 scripts，不能放 work
- work 是"现场"，会被反复清空重建；
- scripts 是"资产"，要进版本库（git/svn）、要被同事 review、要能复现。

**把脚本写在 work 里，等于把唯一一份图纸放在会被推平的工地。**
:::

:::pitfall 在公共目录里直接动手
**现象**：`rm -rf *` 清一下目录，把别人的 run 删了；或者两个人在同一个 `work/` 里互相覆盖文件。

**原因**：账号可能是共用的（课上专门提醒过这点），或者你的 work 目录里有别的同学留下的内容。

**做法**：
1. 先 `ls -la` 看清里面有什么、属主是谁（`ls -l` 第三列）；
2. **有别人的东西，就在 work 下自建一个以自己名字命名的目录**（如 `work/weizhen/`），不要清空公共目录；
3. 删除前先 `ls` 确认，再删**具体文件名**，永远不要对着通配符按回车。
:::

## 终端：多窗口 + 改名，效率差一倍 {#terminal}

文档给的两个技巧，看着小，实际天天用：

| 操作 | 作用 |
|---|---|
| **`Ctrl+Shift+T`** | 新开一个终端标签页（同一个窗口里多任务） |
| **双击终端标题栏** | 给这个终端改名（如 `Run1`、`Debug-ALU`） |

为什么要改名？因为你可能同时开着：

- 一个窗口在**跑 run**（要跑几小时，不能动）；
- 一个窗口在 **debug**（查报告、试命令）；
- 负责多个模块时：`ALU-Run`、`ALU-Debug`、`IOU-Run`……

**标题不清，半小时后就分不清哪条命令发到哪个环境里了**——把命令敲进正在跑批的窗口，是最容易让人崩溃的事故之一。

## Run：一个 run 就是一个"从头跑一遍的版本" {#run}

:::term run | 一次完整运行
针对某一版数据/某一版配置，把流程从头跑一遍（或从某个阶段跑到底），看结果有没有变好。**一个 run 对应一个目录、一份 log、一套报告。**
:::

命名规范（文档建议）：**日期 + 改动内容**。例如：

```
run_1025_base            ← 10月25日，基线
run_1026_halo2           ← 加了 macro halo 2um
run_1027_density70       ← 密度从 85% 降到 70%
```

为什么必须带日期和内容？因为**一个 run 在集群上可能跑两三天**，一周后你自己都想不起来"run_1027 到底改了什么"。命名是给未来的自己看的。

## Queue：把耗时的事丢给集群 {#queue}

:::term Queue | 队列 / 集群
项目组的服务器集群把机器资源切成若干队列（如 `normal`、`abc`）。你把任务提交进去，调度器排队分配机器执行。**所有"自动跑"的步骤都走这条路。**
:::

为什么必须用集群？因为 PR 的自动流程**极耗资源、极耗时**：

- 一个五六百万门的大模块，**从 placement 结束跑到 CTS 出结果，可能要 3~4 天**；
- 这种任务不可能挂在你自己的登录节点上跑（会把机器拖死，也违反规定）。

典型工作方式：

```
      你手动做完 floorplan / 摆好 memory / 设好约束
                     ↓
      把任务提交进 Queue（跑 place → cts → route → 报告）
                     ↓
      集群排队、分配机器、自动跑（几小时到几天）
                     ↓
      你看 log、看 report，判断好坏，改参数，再提交
```

## 多版本并行：Try 机制 {#try}

Memory 摆哪儿没有唯一答案（取决于数据流、通道、时序），所以标准做法是**同时试几版**：

```
FLP1（memory 靠左）   ┐
FLP2（memory 分两排）  ├─→ 依次/并行提交 Queue → 比较结果 → 选最好的一版做 Final
FLP3（memory 靠上）   ┘
```

:::tip 等待期不是空转
run 要跑三天，这三天你该干什么？文档的答案是：**分析上一批 run 的结果，加新约束，再提交一批。**

形成循环：

**提交 → 分析（看 congestion / density / timing）→ 调参数 → 再提交**

这样机时永远不空，你的方案也在持续变好。**干等着看进度条，是新人最浪费的三天。**
:::

:::pitfall 提交完就不管，任务被 Killed
**现象**：以为在跑，两天后一看 status 是 `Killed`（被杀）或早就中断了，白等两天。

**原因**：常见三种——
1. **内存/资源超限**（核数给太多、或模块太大）；
2. **license 拿不到**（排队时被别的任务抢走）；
3. **脚本报错提前退出**（前面几步就失败了，后面根本没跑）。

**做法**：提交后**定期查状态**（`bjobs`/`qstat` 之类，看项目用什么调度器），并第一时间看 log 尾部有没有 ERROR。**跑批的第一原则是"确认它真的在跑"。**
:::

:::lab 建一套自己的项目目录
在练习终端（或真机）里，从零建出这套结构，并验证每一步：

```bash
# 1. 先看清当前在哪、有什么（永远先看再动）
pwd
ls -la

# 2. 建自己的 work 目录（用自己名字，避免和共用账号冲突）
mkdir -p work/$(whoami)/run_1025_base

# 3. 建其余五个目录（-p 表示父目录不存在就一起建）
mkdir -p scripts data library report logs

# 4. 看一眼最终结构（tree 没装就用 ls -R）
ls -R . | head -30

# 5. 建一个 run 目录，并让 log 落在 logs/ 下（输出同时上屏和进文件）
cd work/$(whoami)/run_1025_base
echo "run start: $(date)" | tee ../../logs/run_1025.log

# 6. 检查目录属主与权限（确认没动到别人的东西）
ls -ld ../../work ../../work/*
```

验收标准：目录结构建对、run 目录名带日期与内容、log 能落到 `logs/` 下、能说出六个目录各放什么。
:::

:::quiz
work / scripts / data / library / report / logs 各放什么？| work 是你的 run 与调试现场；scripts 放所有流程脚本（Flow）；data 放网表/def/sdc 等输入；library 放 lef/lib/rc tech/内部库；report 放各阶段报告；logs 放运行日志。
为什么脚本不能写在 work 目录里？| work 是会被反复清空重建的现场，scripts 是要进版本库、要被 review、要能复现的资产；写错地方等于图纸放在会被推平的工地。
发现 work 目录里有别人的内容怎么办？| 不要清空公共目录；在 work 下自建以自己名字命名的目录，避免冲突；删除前先 ls 确认属主与内容。
Run 命名应该包含什么？为什么？| 日期 + 改动内容；因为一个 run 可能跑两三天，一周后要靠名字回忆改了什么。
Queue / 集群解决什么问题？| 把极耗资源、极耗时的自动流程（place→cts→route）丢到集群排队执行，不占用登录节点；你只做手动的 floorplan 与结果分析。
一个大模块从 place 到 cts 出结果大概要多久？| 五六百万门的规模，可能 3~4 天。
多版本 Try 机制是什么？等待期间该做什么？| 同时/依次提交多版 floorplan 比较结果择优；等待期应分析上一批结果、加新约束、再提交，形成"提交→分析→再提交"的循环。
提交后必须关注什么？| 任务状态（是否被 Killed）、资源与 license、log 尾部有没有 ERROR；跑批第一原则是确认它真的在跑。
:::
