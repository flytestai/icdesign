## 十二个坑 {#twelve}

:::goal 学完这一章，你能在动手之前说出至少八个"这一步最容易错在哪"，并知道对应的一条命令或一个文件名。
:::

这些坑的共同点：**代价都在半天到一周，而避免成本只有一分钟。** 每条都按"现象 → 原因 → 怎么避免"写，避免方法都具体到命令或文件名。

### 1. 不存盘就跑下一步

**现象**：跑完 placement 直接进 CTS（时钟树综合），工具崩了或者你想回退，发现上一个可用状态是四小时前。

**原因**：`saveDesign` / `save_block` 没执行，或者存了但被后一步覆盖。

**怎么避免**：每个阶段结束必须存，文件名带阶段和序号：`saveDesign db/03_place_01.enc`（Innovus）或 `save_block -as top db/03_place_01`（ICC2）。**序号只增不改**，出事能回退到任意一版。

### 2. 用 `rm -rf` 清目录

**现象**：想清 `run/` 下的临时文件，手滑打成 `rm -rf run /*`，空格让命令变成"删 run 和根目录下所有东西"。

**原因**：路径里带空格、变量没加引号、没有先看再删。

**怎么避免**：

```bash
# 作用：安全清空一个目录的内容，防止变量为空或手滑
# 用法：先注释掉 rm 那行跑一次 ls，确认清单对了再放开
DIR=./run
ls -la "${DIR}/"                    # 先看清楚要删什么
rm -rf "${DIR:?}/"*                 # ${DIR:?} 在 DIR 为空时直接报错退出
# 说明：${VAR:?} 是"变量为空就中止"，这是防手滑的最后一道闸
# 说明：通配符放在引号外面，否则不会展开
```

### 3. 约束没读对就开始优化

**现象**：跑了四小时 `place_opt`，打开报告发现时钟周期是 2.0ns，而规格是 2.5ns；或者某个模块整片 unconstrained。

**原因**：SDC 版本不对、时钟名写错、SDC 读在 `link_design` 之前（约束静默失效，见 05-02）。

**怎么避免**：优化前固定跑两条，看输出再继续：

```tcl
# 作用：优化前的两道闸，任何一条不对就停下来
# 用法：读入 SDC 之后、place_opt 之前
report_clocks                                    ;# 周期、名字、源端口逐个对规格书
check_timing -include {unconstrained_endpoints no_clock}  ;# 两项都必须为 0
# 说明：report_clocks 里少一个时钟，就有一整片逻辑没被约束
# 说明：这一步花 30 秒，能省掉四小时白跑
```

### 4. 利用率定太高

**现象**：`setPlaceMode -place_global_util 0.85`，看起来"省面积"，结果 detail route 布不通，DRC（设计规则检查）几千条，越修越拥塞。

**原因**：利用率是"单元面积 / 核心面积"，但布线需要通道。0.85 意味着只剩 15% 给线和空隙，标准单元密集区根本挤不下。

**怎么避免**：第一版定 0.60~0.65，跑完看拥塞图和 pin density 再逐步加。**面积是谈出来的，不是一次定死的。**

### 5. 宏单元通道没算

**现象**：两个 SRAM 之间按默认间距 5µm 摆，布线时那一带全是 DRC 和开路。

**原因**：通道宽度要按"出线数 × 间距"算（见 03-03），不是按"看起来够宽"。

**怎么避免**：先数每个 macro 边上有多少信号要出来，`通道宽度 = 出线数 × 线间距 × 层数系数`，再加 halo（`create_halo`）挡住标准单元。

### 6. 跳过 CTS 直接布线

**现象**：place 之后直接 `routeDesign`，hold 违例 −10ns 级别，插了几千个 delay cell 还是收不掉。

**原因**：没有时钟树，时钟是理想的，skew 为 0；真实时钟一上来，hold 全线崩。

**怎么避免**：CTS 是 hold 收敛的前提，不能跳。顺序永远是 place → CTS → post-CTS opt → route。

### 7. 先修 hold 再修 setup

**现象**：先花两天修 hold，修完发现 setup 全崩；回头修 setup，插的 buffer 又把 hold 搞坏，来回两三轮。

**原因**：修 setup 的动作（upsize、插 buffer）会改变数据路径延迟，hold 跟着变；反过来修 hold 插的 delay cell 也会拖慢 setup。

**怎么避免**：**setup → hold → 复验**。setup 用面积换时间，hold 用时间换稳定，顺序反了就是互相拆台。

### 8. 网表和 SPEF 不同版本

**现象**：PT 报 `Cannot find port`，或者时序结果和 PR 里差 0.3ns，怎么都对不上。

**原因**：netlist 是周三导的，SPEF 是周五提的，中间改过版图。两个文件的实例名对不上。

**怎么避免**：导出时用同一条命令、同一个时间戳：

```tcl
# 作用：把网表和 SPEF 绑成一对，文件名带同一个时间戳
# 用法：在 PR 工具的 shell 里执行，两条命令不要隔夜
set TS [clock format [clock seconds] -format %Y%m%d_%H%M]
write_verilog netlist/top_${TS}.v        ;# 导出网表，文件名带时间戳
write_spef    spef/top_${TS}.spef        ;# 紧接着导出 SPEF，同一时间戳
# 说明：时间戳放文件名里，谁和谁是一对，一眼就能看出来
# 说明：再算一次 md5 写进 README，防止文件被后续运行覆盖
```

### 9. LVT 用太多

**现象**：时序一紧就把单元全换 LVT（低阈值电压，low-Vt），WNS 好看了，漏电涨 3~5 倍，功耗签核被打回。

**原因**：LVT 靠降低阈值电压换速度，代价是亚阈值漏电指数上升。全芯片换等于把静态功耗翻几倍。

**怎么避免**：LVT 占比控制在 10%~20%，只给关键路径。换完跑一次 `report_power`，看 leakage 涨了多少。

### 10. DRC 卡在几百条就乱调参数

**现象**：DRC 从 6000 降到 800 之后卡住，于是开始调 spacing、调 density、调 route effort，结果涨回 2000。

**原因**：剩下的是孤例，批量调参数只会引入新问题。

**怎么避免**：先分类统计再动手：

```bash
# 作用：把 DRC 按规则类型和区域聚类，找出主要矛盾
# 用法：对 Calibre 的 results 文件做统计
grep "^" drc.results | awk '{print $1}' | sort | uniq -c | sort -rn | head -10
# 说明：第一列是规则名，先看哪条规则占大头
grep "M1.S.1" drc.results | awk '{print $2, $3}' | cut -d. -f1 | sort | uniq -c | sort -rn | head
# 说明：再按坐标聚类，看是不是集中在某个区域
```

### 11. 报错只看最后一行

**现象**：屏幕最后一行是 `OPT-041`，你顺着它查了两小时，没结果。

**原因**：最后一行是"结果"，真正的病因在前面。`OPT-041` 往往只是"优化失败"，上面五行的 `NEX-018 no valid parasitic` 才是原因。

**怎么避免**：**往上翻，找第一条 ERROR。** 第一条之后的错误多半是它的连锁反应。

你会反复遇到的三类报错，长这样：

:::fig term-error | 三个高频报错的会话摘录：每个报错的前半句是现象、后半句才是原因。重点练这个拆读习惯——和第 11 坑"往上翻找第一条 ERROR"配合，排查速度会快很多。
:::

从图里要看出什么：**报错不是读一遍就过，是拆成两半读**。前半句告诉你"什么坏了"，后半句告诉你"为什么坏"，方向定错就白查。

### 12. 改完不记录

**现象**："我记得改过 utilization" —— 改成多少？哪一版？和谁比的？全想不起来。

**原因**：改动只存在脑子里，没有落到文件。

**怎么避免**：每次运行写一个 `README.txt`（不是随手记，是固定模板）：改了什么、为什么、结果如何。模板见"交接的习惯"一章。

:::term Regression | 回归
把一整套流程脚本化，每次改动后全量重跑一遍，对比关键指标有没有变差。

这是把"手工调参"变成"工程"的关键手段：**没有回归，你永远不知道这次改动是变好还是变坏，只知道"看起来好了"。**
:::

## 排错方法论 {#debug}

:::goal 学完这一章，你能用四种方法把"不知道哪错了"缩小到"就是这一行"，而不是靠猜。
:::

遇到问题，按这个顺序走，不要跳：

1. **看第一条错误**，不看最后一条。
2. **确认输入**：网表、库、约束、脚本版本对不对。
3. **缩小范围**：能不能用更小的设计复现？
4. **对比基线**：和上一次成功的运行比，改了什么？
5. **二分验证**：把流程切一半跑，看问题在哪一半出现。

### 方法一：二分法

把流程按阶段切成两半：只跑到 place 就停，看问题是否出现。

- 出现了 → 问题在 place 之前（读库、读网表、约束）。
- 没出现 → 问题在 place 之后（CTS、route、opt）。

然后再把有问题的那一半切一半。**一千行的流程，十次二分就能定位到一行。**

同样的思路可以用在"设计规模"上：整个芯片跑不出来，就先跑一个模块；模块也不行，就跑一个 counter。

### 方法二：最小复现

:::term Minimal Reproducible Case | 最小复现
用尽可能小的输入（最少的单元、最短的脚本）重现同一个错误。能复现，说明问题是环境/流程问题；不能复现，说明和规模或特定数据有关。
:::

一个真实例子：某项目 `place_opt` 报 `OPT-041`。用公司自带的 counter 小设计（几十个单元）跑同一套脚本，同样报错——**立刻排除"设计太大"这个方向**，转向环境检查，最后发现是没读 TLU+ 寄生模型。

**最小复现的价值在于：它把"可能性"从几十个砍到两三个。**

### 方法三：对照实验

只改一个变量，其他全部保持上一版不变。

| 做法 | 结果 | 能得出什么 |
|---|---|---|
| 只改 utilization 0.65→0.70 | DRC 从 800 涨到 1500 | 利用率是主因 |
| 同时改 utilization、density、buffer 列表 | DRC 从 800 涨到 1500 | 什么都得不出 |

:::term Baseline | 基线
一次"已知良好"的完整运行结果，包含脚本版本、输入文件、所有关键指标。任何新实验都要和它比。

没有基线，你说"变好了"没有依据；有基线，你能说出"WNS 好了 0.1，DRC 多了 20，净收益为正"。
:::

### 方法四：日志时间线

工具日志里每一行都有时间戳（或至少有序号）。把"最后一条开始"和"第一条 ERROR"之间的内容抽出来，就是案发现场。

```bash
# 作用：从一份几千行的日志里提取案发现场
# 用法：在 run 目录下执行，log 是工具重定向出来的日志
grep -n -m1 -E "^\*\*ERROR|^Error" run.log          # 第一条错误在第几行
# 说明：-m1 只要第一条，-n 给行号；后面的错误多半是连锁反应
sed -n "$(( $(grep -n -m1 -E '^\*\*ERROR|^Error' run.log | cut -d: -f1) - 10 )),+15p" run.log
# 说明：打印第一条错误前后各十行，这就是案发现场
grep -nE "^#|^##|Start|Finish|Elapsed" run.log | tail -20
# 说明：看各阶段耗时，哪一步突然变慢，往往就是问题所在
```

**时间线还能回答"是不是卡住了"**：某一步正常 3 分钟，这次跑了 40 分钟，说明它在反复迭代或死循环，不是"机器慢"。

:::scene 一个真实的排错过程
现象：ICC2 `place_opt` 报 `OPT-041`。

- 第 1 步：往上翻日志，发现 `NEX-018 no valid parasitic`。
- 第 2 步：确认输入 —— NDM 有 timing view，但没读 TLU+。
- 第 3 步：缩小范围 —— 用 counter 小设计试，同样报错，说明是环境问题不是设计问题。
- 第 4 步：对比基线 —— 上一版流程没读寄生，也能跑（因为没开 place_opt）。
- 第 5 步：补 `read_parasitic_tech` + `set_parasitic_parameters`，通过。

**整个过程 40 分钟，其中 30 分钟花在"往上翻日志"和"缩小范围"。**
:::

:::pitfall 一上来就怀疑工具
现象：结果不对，第一反应是"工具算错了"，于是换版本、重装 license、找 AE。

原因：工具出错确实会发生，但概率远低于"输入不对"。而且一旦你认定是工具问题，就不会再去查脚本。

怎么避免：先做三件事——确认输入版本、用最小复现跑一遍、和基线对比。三件都排除了，再怀疑工具。**怀疑工具的成本很高（换版本要重跑全流程），排在最后。**
:::

## Review 该准备什么 {#review}

:::goal 学完这一章，你能用一页纸在五分钟内讲清"目标、现状、差异、下一步"，并接住五个必问。
:::

被 review 时，组长通常按这个顺序问：

| 顺序 | 问题 | 你要能给出 |
|---|---|---|
| 1 | 设计规模？ | 单元数、面积、利用率、macro 数量 |
| 2 | 现在什么状态？ | 做到哪个阶段，卡在哪 |
| 3 | 关键指标？ | WNS/TNS、DRC 数、面积、功耗 |
| 4 | 最大的风险？ | 哪条路径最紧、哪个区域最拥塞 |
| 5 | 下一步计划？ | 具体动作 + 预计耗时 |

**准备一页纸，四块内容**：

```text
【目标】本版要做到：WNS ≥ 0、DRC = 0、面积 ≤ 230×230µm
【现状】WNS −0.12、TNS −0.8、DRC 42、面积 222.5×222.2µm
【差异】离目标差：setup 两条路径（u_dp 41 级逻辑）、DRC 42 条（集中在 M4）
【下一步】① 两条路径换 LVT，预计 +0.07（今天）
          ② DRC 按区域聚类，先修 u_dsp 东侧（明天）
          ③ 若仍差 0.05，走 waiver 并报风险评估（周四）
```

四块里最重要的是**差异**：目标和现状之间差什么、差多少、为什么。很多人只讲"我做了什么"，不讲"还差什么"，review 就变成了流水账。

讲的时候**结论先行**：第一句话说"这版能过/不能过，差在哪"，然后再展开。不要从"我先做了 floorplan"讲起。

一个对照：差的开场是"这周我主要做了三件事，第一是 floorplan 的宏单元调整，第二是电源规划……"；好的开场是"这版过不了，WNS 差 0.12，卡在 u_dp 的 41 级逻辑上，我需要前端帮忙拆流水"。**后者三十秒就让人知道要不要介入。**

## 交接的习惯 {#handoff}

:::goal 学完这一章，你能交出一份"别人照着能跑起来"的包，并说清哪三件事最容易漏。
:::

交接的本质是：**让一个不认识你的人，在不问你的情况下，重现你的结果。**

### README 五要素

```text
# top PR 交接（2026-11-22）
1. 怎么跑：cd pnr && ./run_all.sh        # 无参数，无交互，跑完在 run/ 下出结果
2. 输入在哪：syn/netlist/top.v、constraints/top.sdc、lib/（版本见 versions.txt）
3. 产物在哪：run/<时间戳>/ 下的 def、spef、rpt/
4. 已知问题：3 条 max_transition 违例已 waiver，原因见 waiver.txt
5. 上次结果：单元 12026、面积 222.5×222.2µm、WNS +0.12、DRC 0
```

五行字，能省对方两小时。缺任何一行，对方都要来问你一次。

### 脚本可重跑

三个条件，缺一个就不叫"可重跑"：

- **无交互**：不能有 `read -`、不能等用户输 y/n。所有参数从文件读或从命令行传。
- **路径可控**：输入用绝对路径或相对脚本位置的路径，不能依赖"我在哪个目录执行"。
- **幂等**：跑第二遍不会因为"目录已存在"或"文件已存在"而失败（该 `mkdir -p` 就 `mkdir -p`，该覆盖就覆盖）。

### 数据可追溯

:::term Traceability | 可追溯
任何一个结果，都能回答"用哪个脚本、哪版输入、什么时候、在哪台机器跑出来的"。

最小要求：脚本进版本管理（git）、输入文件带版本号或时间戳、每次运行的日志保留、关键产物算 checksum。
:::

一个够用的目录结构：

```text
prj/
├── scripts/         # 脚本，进 git；不放大文件
├── constraints/     # SDC，进 git
├── lib -> /pdk/...  # 库用软链接，记录指向
├── run/20261122_1400/   # 每次运行一个时间戳目录
│   ├── run.log
│   ├── rpt/
│   └── README.txt   # 这次改了什么、为什么
└── versions.txt     # 库、工具、PDK 的版本
```

交接包的目录骨架，推荐照这个来搭：

:::fig pr-dir | 推荐的项目目录结构，右边是四条配套规矩。重点看第一条"脚本要能从头重跑"——上面 README 五要素和这个目录树是一套：怎么跑对应 scripts/，产物在哪对应 run/<时间戳>/，已知问题对应 README.txt。
:::

从图里要看出什么：**目录结构就是交接文档的物理形态**。README 里写的每一行，都能在目录里指到一个具体位置，接手的人才不用来问你。

## 怎么写周报 {#weekly}

:::goal 学完这一章，你能写出一份"全是数字、没有形容词"的周报，让组长三十秒看完。
:::

周报不是日记，是**决策材料**。组长看周报只想回答三个问题：进度到哪、有没有卡住、要不要我出手。

### 用数字说话

| 差 | 好 |
|---|---|
| 本周继续优化时序，进展顺利 | WNS 从 −0.35 收到 −0.12，TNS 从 −2.4 收到 −0.8，还剩 2 条 |
| DRC 修了很多 | DRC 从 812 降到 96，剩余集中在 M4，u_dsp 东侧占 71 条 |
| 和前端沟通了逻辑深度问题 | 已和前端确认：u_dp 的 41 级逻辑可拆成两级流水，下周三给新网表 |
| 功耗有点高 | 总功耗 1.82W（目标 1.70W），其中 leakage 0.41W，LVT 占比 28% 超标 |

差别在哪：**数字能比较、能定决策、能追责；形容词不能。**

### 一个够用的模板

```text
【本周目标】WNS ≥ −0.10，DRC ≤ 100
```

:::quiz
为什么排错要看第一条错误而不是最后一条？|后面的错误常常是第一条引起的连锁反应，修了第一条其余的往往自动消失。
`rm -rf "${DIR:?}/"*` 里的 `:?` 是什么作用？|变量为空时直接报错退出，防止 `DIR` 没设值时命令变成删除当前目录或根目录。
网表和 SPEF 版本不一致会有什么现象？|PT 报找不到端口/引脚，或时序结果完全不合理；必须同一次导出、文件名带同一时间戳。
为什么第一版利用率不要定到 0.85？|布线需要通道，0.85 只剩 15% 给线和空隙，标准单元密集区布不通；先 0.60~0.65 再逐步加。
二分法和最小复现分别解决什么问题？|二分法定位"问题在流程的哪一半"，最小复现定位"是不是环境/流程问题而非规模问题"。
没有 baseline 会怎样？|你无法判断一次改动是变好还是变坏，只能说"看起来好了"，也无法量化收益。
review 一页纸的四块内容是什么？|目标、现状、差异、下一步；其中"差异"最重要，要说清差什么、差多少、为什么。
交接的 README 五要素是什么？|怎么跑、输入在哪、产物在哪、已知问题（写根因）、上次关键指标。
周报里"卡在哪"和"需要谁"为什么最值钱？|它们让组长知道要不要介入、该找谁；没有这两行，周报只是汇报，不是决策材料。
:::
