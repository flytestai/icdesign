## 课程导入：从启动到可恢复的设计 {#use-intro}

这一课安排两个课时，但目标只有一个：**让你能把一个设计导进 Innovus，证明它导对了，并且随时能恢复回来。**

听起来简单，实际是新手最容易卡住的地方——不是命令不会敲，而是**不知道敲完对不对**。

| 课时 | 内容 | 结束时你应该能 |
|---|---|---|
| **第 1 课时** | 从终端启动、认界面、分清「看见」与「选中」 | 独立启动一次、看懂版图区在显示什么、能用属性窗口核对一个实例 |
| **第 2 课时** | 准备输入、按对照表导入、用证据验证、保存与恢复 | 把 40nm 案例导进来、用五类证据证明导对了、存盘并恢复 |

两个课时用的是**同一个 40nm 案例**（`leon`）。不换设计，是因为换设计会引入新的变量——你要先确认流程本身跑得通，再换自己的数据。

:::note 阅读方式
如果你已经有 Innovus 环境：可以边看边做，每节末尾都有验收动作。
如果你暂时没有环境：每节都写了「无工具也能做」的读图练习，按文字和图也能学会判读。

两课时之间不需要重启工具——第 1 课时结束时保存的会话，第 2 课时直接接着用。
:::

## 第一课时：从 Linux 终端启动并留下日志 {#period-1}

第一件事不是打开工具，是**学会怎么启动、并且让这一趟留下记录**。

:::note 为什么强调「留下日志」
Innovus 的启动参数里有一个 `-log`。不写日志，这一趟跑完就什么都没有了——出了错无法回溯，成功了也无法复现。

这是工程习惯问题，不是命令问题。所以放在第一课时第一节讲。
:::

### 启动前确认三件事

在敲 `innovus` 之前先确认：①当前目录对不对（后面所有相对路径都基于它）；②License 是否可用（没有会卡在启动阶段）；③输入文件是否可读（路径写错的话启动成功但导入失败）。

:::fig innovus-doc-01.png | 原文图 01 · Linux 项目目录与终端中的 work 目录示例，不是 Innovus 主界面
:::

:::note 这张图该看什么
这是 Linux 终端，不是 Innovus 主界面。它展示的是启动前的**工作目录环境**。

要看的是 `pwd` 显示的当前路径——它决定了所有相对路径的基准。实际项目里通常每个 run 一个独立目录。图中能看到 `data/`、`library/`、`logs/`、`reports/`、`scripts/` 等目录，以及创建 `work/` 的示例。

**不要照图使用 `root` 或照跑 `start.sh`**，那只是一种可能的目录组织方式。
:::

### 启动命令

```bash
pwd ; ls                      # 先确认位置和目录内容
command -v innovus            # 确认工具在 PATH 里
innovus -help                 # 确认本版本支持哪些参数
innovus -log use_lesson01.log # 正式启动，指定日志名
```

三个要点：`-log` 记录全程输出，`-files` 启动后自动跑脚本，`-cpus` 指定核数。九个选项的详细解释见后文[「九个常用启动选项」](#options)。

**版本要从启动横幅或日志里看，不要把 `command -v` 返回的路径当版本号。** 到 `innovus ...>` 提示符后才进入 Innovus 命令环境——项目 Tcl 命令要在这里输入，不是在 Linux shell 输入。

:::pitfall 起不来先按现象分流
- **找不到命令**：核对项目环境和 `PATH`；
- **许可证报错**：记录原文，走团队支持流程；
- **无法开窗**：核对是否在获准的图形会话。

首次上手**不要加 `-files`**——否则启动故障和脚本故障会混在一起，不知道是哪个错了。
:::

### 第一课时的验收

启动成功的最低标准：看到 `innovus>` 提示符，并且日志文件开始有内容（日志名和实际位置以这次启动结果为准）。

:::

:::note 这张图该看什么
已载入设计的 Innovus 20.1 主界面。三个层次：①标题栏显示版本（20.1）和设计路径；②菜单栏按工序排列（File 到 Help）；③中间黑底是版图区，右侧是控制区。

### V/S 列：这一节最该记住的东西

:::fig innovus-doc-05.png | 原文图 05 · 三种视图入口和右侧 V/S 列：V 控制可见，S 控制可选
:::

:::note 这张图该看什么
三种视图入口和右侧的 V/S 列。**V 控制可见（Visible），S 控制可选（Selectable），两者独立。**

| V | S | 结果 |
|---|---|---|
| 开 | 开 | 看得见，能选中（正常状态） |
| 开 | 关 | 看得见，**选不中** |
| 关 | 关 | 看不见，选不中 |

**为什么这个设计重要**：排查问题时经常需要「看得见但不想误选」。比如看宏之间的通道宽度，关掉 Standard Row 的 V，行线消失通道清楚；但行线消失了就选不中行了。

**「隐藏不等于删除」**：关掉 V 只是不显示，对象还在。
:::

### 跟做顺序：适配全图 → 缩放局部 → 切换 V/S → 核对属性

旧版资料记载的快捷键：`f` 适配全图、`z` 放大、`Shift+z` 缩小、`q` 打开对象属性。**但要先查本版本的菜单或快捷键设置**——不同版本可能不同，而且快捷键需要焦点在版图区才生效。若不一致，用菜单或工具提示，不要反复试按。

1. **适配全图**：菜单 Fit 或按 `f`。看图先 fit 一次，否则可能在某个角落放大到看不见全局；
2. **缩放局部**：框选放大一个区域，最后回到全图；
3. **切换 V/S**：找到目标类别（如 `Instance`），保持 V 开、暂关 S，观察「看得见但选不中」；再打开 S，清除旧选择后重选；
4. **核对属性**：选中已知实例，通过属性入口（`q`）查看，记录**实例名**和**引用单元名**，用 Design Browser 或项目清单交叉核对。

:::tip 选到 net 和选到 instance，属性窗口完全不同
新手常犯的错：以为选中了单元，实际选中的是连线。

**区分方法**：instance 有「引用单元名（cell name）」、net 有「连接端点列表」。先核对对象类型，再决定要不要改。
:::

:::note 没有环境怎么练
空会话无法演示对象选择。可以**先读图**，等第二课时导入之后再补做这一节的动手部分。

有已获准载入的同一案例只读设计或个人副本才动手——不要在生产设计上试。
:::

### 界面分四块（旧站示意图，与本节对照阅读）

旧站用的是 ASCII 示意图，和上面基于真实截图的讲解是**同一件事的两种讲法**。示意图的价值在于把结构简化了：

```
┌────────────────────────────────────────────────────────────┐
│  菜单栏 File / Edit / View / Design / Timing / ...          │
├──────────────────────────────────────────────┬─────────────┤
│                                              │  右侧面板    │
│           版图显示区（Layout View）           │  ├ Design   │
│                                              │  ├ Physical │
│   · 左边是 Design Browser（层次树）           │  └ Timing   │
│   · 中间是芯片版图，滚轮缩放、中键平移         │             │
│                                              │             │
├──────────────────────────────────────────────┴─────────────┤
│  命令行（Command Line）：所有 Tcl 命令在这里敲               │
├────────────────────────────────────────────────────────────┤
│  输出窗（Log / Console）：命令的返回、warning、error 都在这 │
└────────────────────────────────────────────────────────────┘
```

**四个地方必须会用**：①版图区（`f` fit、滚轮缩放、中键平移，看图先 fit）；②命令行（界面点一遍然后去 log 抄命令，是学命令最快的路）；③输出窗（warning 和 error 在这里，**别忽略 warning**，很多「结果莫名其妙」的根因就藏在几百行 warning 里）；④Design Browser（层次树，找 instance/net 从这里搜）。

:::note 示意图和真实截图的差异
示意图里画的「命令行」和「输出窗」是独立两个框，真实界面里它们通常在同一个控制台窗口里上下滚动。

看真实截图（图 09）时，命令区在版图区下方或独立窗口。结构一样，布局可能不同。
:::

## 第一课时：桌面练习与验收 {#use-start-check}

没有工具也能做的练习，检验「看见 vs 选中」这个模型有没有建立起来。

:::lab 无工具也能做：读图和排错
**练习一：判断状态**
右侧面板看到 `Instance` 的 V 打了勾、S 没打勾。回答：①版图区能看到 instance 吗？②能用鼠标点中一个 instance 吗？③如果这时执行「删除选中对象」会发生什么？

**练习二：定位问题**
同事说他「选中了一个单元，但属性窗口显示的字段不对，没有 cell name 这一项」。最可能的原因是什么？他应该怎么确认？

**练习三：找命令**
他在界面上点了一个按钮完成了「适配全图」。他想知道对应的命令是什么。最直接的方法是什么？
:::

:::quiz
V 和 S 两个开关分别控制什么？关掉 V 之后还能选中该对象吗？| V 控制可见（Visible），S 控制可选（Selectable）。关掉 V 之后对象不可见，也就不能选中。
为什么工具栏截图（图 02–04）不能当作「功能界面」？| 它们拍的是工具栏上的图标入口，点开之后才是工具窗口。把入口当界面会误解功能的样子。
图中没看到 `innovus>` 提示符，命令在哪里敲？| 在终端或独立的控制台/命令窗口。版图区只显示图形，不接收命令输入。
想看清两个宏之间的通道宽度，但行线太密挡住视线，怎么操作？| 把 Standard Row 的 V 关掉，行线消失通道清楚。但关掉后也选不中这些行，要看清又要能选就只关 S。
选中对象后属性窗口没有 cell name 字段，最可能是什么原因？| 选中的是 net 而不是 instance。两类对象属性字段不同，先核对对象类型。

## 第二课时：为同一个 40nm 案例准备输入 {#period-2}

第一课时解决「怎么用工具」，第二课时解决「怎么把数据导进去、怎么证明导对了」。仍然用同一个 40nm 案例 `leon`，不换工艺、不换设计。

把项目发布清单当作对照表，先填写「输入路径、发布版本、预期结果」，再开一个**干净会话**。原图 08 的 `leon` 是历史资料中的顶层实参；上机以手头同一案例的发布清单为准，**不凭截图猜路径、库名或电源网名**。

:::

:::note 这张图该看什么
导入准备与操作的对照示意图（**明确标注为教学示意，不是 Innovus 实机截图**）。左侧是准备清单，右侧是对应操作。

### 准备清单：五项必须核对

| 准备项 | 上机前核对 |
|---|---|
| **门级网表与顶层** | 网表可读，顶层名和大小写以网表及发布清单为准；记下预期端口/实例规模以及一个可抽查的实例 |
| **Tech LEF 与 Cell/Macro LEF** | 来自同一 40nm 发布；按项目清单排列，Tech LEF 在前；核对标准单元及用到的宏是否有物理定义 |
| **MMMC 配置及其依赖** | 核对各分析视图、Liberty、RC 技术数据、SDC 和配置内引用的实际路径；记下预期视图、时钟或合理的无时钟预期 |
| **电源/地网与可选 DEF** | 按项目指定的电源域和网名填写，**不能默认 VDD/VSS**；仅在项目要求接续已有物理数据时才用同一发布的 DEF |
| **环境与留档** | 核对授权、项目指定版本、可读输入和可写个人 run 目录；约定日志、报告和检查点名称。不复制或分享受限资料 |

:::pitfall 三个最容易出错的准备项
1. **网名想当然**：设计里可能是 `VDD_CORE` / `VSS_CORE`，不是 `VDD` / `VSS`。写错的话电源规划阶段找不到网络；
2. **LEF 顺序错**：Tech LEF 必须在 Cell LEF 之前。顺序错了工具不知道该工艺有哪些层，所有单元都找不到；
3. **MMMC 路径失效**：配置里写的是绝对路径，换机器就失效。要检查每个引用的文件是否真的存在。
:::

### 为什么用同一个案例

换设计会引入新变量：新的库、新的约束、新的命名规范。一旦出问题，你不知道是流程不对还是数据不对。**先用已知能跑通的案例把流程走通**，再换自己的数据——这是工程上排查问题的基本原则。

## 第二课时：按对照表配置并导入 {#use-import}

导入不是「敲一条命令」，是「按对照表逐项确认」。

### 导入脚本的基本结构

```tcl
# 1. 定义（换项目只改这一段）
set DESIGN   leon
set NETLIST  ./data/leon.v.gz
set LEF_TECH ./lef/tech.lef
set LEF_CELL ./lef/cells.lef
set LIB      ./lib/xxx_ss.lib
set SDC      ./sdc/leon.sdc

# 2. 读取
read_lef   $LEF_TECH
read_lef   $LEF_CELL
read_netlist $NETLIST
read_lib   $LIB
read_sdc   $SDC

# 3. 核心操作
init_design

# 4. 保存
saveDesign ./db/leon_init.enc

# 5. 输出报告
report_design_summary > ./rpt/init_summary.rpt
```

这个五段式结构（定义 → 读取 → 核心 → 保存 → 输出）和 [PowerPlan 那课](/lesson/03-06-powerplan/)讲的流程脚本结构是同一套。**换项目只改第 1 段**，其余不动。

### 导入顺序为什么不能乱

```
read_lef (tech)  →  先有工艺层定义
read_lef (cell)  →  再有单元物理定义（依赖 tech）
read_netlist     →  逻辑连接
read_lib         →  时序信息
read_sdc         →  约束
init_design      →  建立数据库
```

**Tech LEF 必须在 Cell LEF 之前**——Cell LEF 里引用的层名要在 Tech LEF 里定义过。

`init_design` 放在最后：它把所有已读入的数据「固化」成一个设计数据库。在它之前读的东西都只是「准备材料」。

## 第二课时：用证据验证，再保存并恢复 {#use-verify-restore}

**这一节是整课最重要的部分。** 因为「导入成功」和「导入正确」是两回事。「先验再存」是这一节的全部要点。

:::fig innovus-use-verify-guide.svg | 导入验证与恢复示意图 · 不是 Innovus 实机截图
:::

:::note 这张图该看什么
导入验证与恢复的示意图（**明确标注为教学示意，不是实机截图**）。左侧是证据检查顺序，右侧是保存与恢复的对应关系。

### 三类证据：缺一类都不算导对

| 检查项 | 看哪些证据 | 不符合时先查什么 |
|---|---|---|
| **设计身份与链接** | 用 Design Browser 或汇总报告核对顶层、端口/实例规模、一个实例及其引用单元 | 网表发布版、顶层名、缺失的 LEF/时序库定义 |
| **约束与视图** | 核对预期 MMMC 视图是否启用，时钟名、周期和单位是否相符 | MMMC 的分析视图绑定、SDC 路径、约束引用的端口 |
| **日志与设计检查** | 读**第一条有因果关系的异常**及上下文；区分本阶段预期的提示与真正的阻断项 | 先处理未解析引用、缺库、错误顶层或必需视图缺失 |

:::pitfall 最常见的「假成功」
导入没报错、版图区有图形，但：

- **约束被忽略了**：SDC 读了但没生效，所有路径变成「无约束」，时序报告全是 0；
- **只启用了默认视图**：MMMC 配置没读进去，只有一套环境，其他模式根本没检查；
- **电源网名不对**：后面 powerplan 报一堆 unconnected。

这三个都**不会报 error**，只能靠上面三类证据主动查。

而且**修正输入后要从干净会话重跑并留新日志，不要覆盖原 run**——否则前后对比就没有基线了。
:::

### 保存与恢复

三项符合项目预期后，在**个人可写目录**用一个尚未使用的基名保存：

```tcl
saveDesign $checkpoint_path
```

记录同一次保存生成的**入口和配套数据**（例如 `.enc` 与 `.enc.dat`，后者可能是目录）。搬运时要保留配套数据与所需依赖，只搬一个文件是恢复不了的。

```tcl
# 方式 A：直接 source 入口
source $checkpoint_path

# 方式 B：用 restoreDesign 指定配套数据和真实顶层
restoreDesign $checkpoint_dat $top_name
```

:::

`source ...enc` 恢复命令在提示符上的样子。**注意：这张图只显示命令，不显示执行结果**——不能从这张图推断恢复是否成功。

判断恢复成功要靠：日志无 error、设计摘要与保存时一致、抽查实例能定位到。

`restoreDesign ...enc.dat leon` 命令。同样**只显示命令，不显示执行结果**。

保存后只搬 .enc 文件不搬 .enc.dat 会怎样？| 恢复不了。.enc.dat 可能是目录且包含配套数据，只搬入口文件缺少依赖。搬运时要保留配套数据。

## 为什么是 Innovus / ICC2 {#tools}

数字后端的主流工具就两家：**Cadence 的 Innovus** 和 **Synopsys 的 ICC2**。

| | Innovus | ICC2 |
|---|---|---|
| 厂商 | Cadence | Synopsys |
| 命令语言 | Tcl（`dbGet` 系） | Tcl（`get_*` 系） |
| 数据库 | .enc | Milkyway / ND |
| 强项 | 布局布线优化、时序驱动 | 与 Synopsys 生态（DC/PT）集成 |

**为什么要学两套**？因为不同公司、不同项目用的不一样。而且**方法论是共通的**——学会了 floorplan 的判据，换工具只是换命令。

这套课程先讲 Innovus，因为它的 GUI 更直观、命令更接近「看得见的操作」。ICC2 在阶段四单独讲。

:::note 不要纠结「学哪个更有前途」
工具是手段，方法才是本事。

一个懂「为什么这个 floorplan 不行」的人，换哪个工具都能干活；一个只会点按钮的人，换版本就废了。
:::

## 第一步：启动与确认版本 {#start}

```bash
innovus
```

最简启动。但工程上很少这样用——因为这样启动既没有日志，也没有预加载脚本。

**确认版本**：启动后第一件事是看版本。

```tcl
version
```

或者在 GUI 的 Help → About 里看。**不要把 `command -v` 返回的路径当版本号**——那只是可执行文件的位置。

**为什么版本重要**：不同版本的命令参数可能不同（某些参数被废弃或改名）；默认行为可能不同（比如默认的优化力度）；已知 bug 不同。

:::tip 把版本记进日志
在脚本开头加一行：

```tcl
puts "Innovus version: [version]"
```

这样日志里就有版本记录，出问题时能确认「是不是版本差异导致的」。
:::

## 九个常用启动选项 {#options}

这一节逐条讲 `innovus` 的启动参数。每个都说明「它解决什么问题」和「不加会怎样」。

### 1. `-log`：把这一趟的全部输出记下来 {#log}

```bash
innovus -log innovus.log
```

**作用**：把标准输出重定向到文件。**不加会怎样**：输出只在终端里滚过去，关掉就没了。出了问题无法回溯，成功了也无法复现。

**这是最该加的一个参数**，没有之一。

:::tip 日志文件名带上时间戳
```bash
innovus -log innovus_$(date +%Y%m%d_%H%M).log
```
这样每趟一个独立日志，不会互相覆盖。回溯问题时能精确找到「那次」的日志。
:::

### 2. `-files`：启动后自动跑脚本 {#files}

```bash
innovus -files run.tcl
```

**作用**：启动完成后立即执行指定脚本。**用途**：把「导入 + 设置」封装成脚本，一条命令完成启动和初始化。**不加会怎样**：启动后是空会话，要手工敲命令或 `source` 脚本。

:::pitfall 首次上手不要加 -files
如果启动本身有问题（环境、license、图形会话），加 `-files` 会把启动故障和脚本故障混在一起，不知道是哪个错了。

**先确认能正常启动，再考虑自动化。**
:::

### 3. `-no_gui`：不开图形界面，快得多 {#nogui}

```bash
innovus -no_gui -files run.tcl
```

**作用**：不启动图形界面，只在命令行运行。**为什么快**：GUI 要渲染图形、维护窗口状态，跑长时间批处理时是纯开销。**不加会怎样**：默认开 GUI，在无图形环境的服务器上会失败。

### 4. `-wait`：等 license 再启动 {#wait}

```bash
innovus -wait 60 -log innovus.log
```

**作用**：如果 license 暂时不可用，等待指定秒数而不是立刻退出。**用途**：多个任务排队时避免频繁失败重启。**不加会怎样**：license 被占用时立刻报错退出。

### 5. `-cpus`：多核启动 {#cpus}

```bash
innovus -cpus 4
```

**作用**：指定使用 4 个 CPU 核心。**为什么重要**：布局布线是计算密集型，多核能显著缩短 runtime。

:::pitfall 核数不是越多越好
核数超过 license 允许的数量会被拒绝；超过物理核心数会导致抢核，反而更慢。

而且**不是所有步骤都能并行**——某些算法本质上是串行的，加核没用。

**经验**：先用默认值跑一次记录 runtime，再逐步加核对比，找到收益拐点为止。
:::

### 6. 启动后调整核数：setMultiCpuUsage {#setcpu}

```tcl
setMultiCpuUsage -localCpu 8
```

**作用**：在**已启动的会话里**调整核数，不用重启。**什么时候用**：启动时没指定，跑到某一步发现太慢，想在当前会话加速。**注意**：这个设置对**后续**的操作生效，已经在跑的任务不会变快。

### 7. `-help`：不知道参数就查 {#help}

```bash
innovus -help
```

列出所有启动参数。**记不住参数时最该做的事**——不要凭印象猜。

### 8. `help *关键字*`：按关键字搜命令 {#helpsy}

```tcl
help *clock*
```

**作用**：在 Innovus 提示符下按关键字搜索命令。**用途**：只记得「大概和 clock 有关」，不记得确切命令名。这比翻文档快得多。

### 9. Tab 键补全 {#tab}

在命令行敲命令的前几个字母，按 Tab 补全。**为什么重要**：Innovus 的命令名很长（`set_ccopt_property`、`report_ccopt_clock_tree`），手敲容易错。Tab 补全既快又不会拼错。

:::tip 补全 + help 组合用法
1. 敲 `set_ccopt` 按 Tab，看有哪些候选；
2. 选中一个后加 `-help` 看参数；
3. 按需填参数。

这个循环比查文档快得多，而且不会用错参数。
:::

## 界面分四块认识 {#gui}

这一节和前面[「认主界面」](#use-interface)讲的是同一件事，但用的是结构示意图。**建议两处对照着看**：示意图给你结构，真实截图给你细节。

:::note 已在第一课时详述
主要内容已并入[第一课时：认主界面](#use-interface)，这一节保留作为快速回顾。
:::

四个区域的作用再强调一次：

1. **版图区** —— 看设计。`f` 先 fit，再看局部；
2. **命令行** —— 所有操作都能敲。**界面点一遍，去 log 抄命令**，是学命令最快的路；
3. **输出窗** —— warning 和 error 在这里。**别忽略 warning**；
4. **Design Browser** —— 层次树。找 instance、net 从这里搜。

:::tip 最有效的学习循环
1. 在界面上点一个按钮完成操作；
2. 去 log 或命令历史里找对应的 Tcl 命令；
3. 记下来，下次直接敲命令。

**为什么有效**：界面操作降低学习门槛，命令记录积累可复用资产。做一两次这个循环，比读十页文档收获大。
