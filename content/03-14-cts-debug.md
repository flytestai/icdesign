## 三角：三个指标为什么不能同时最优 {#triangle}

:::goal 学完这一课，你拿到一份不达标的 CTS 报告，能按固定顺序判断问题出在树结构、单元、还是上游布局，并说清每一次修改要拿什么换什么。
:::

上一课讲的是"约束怎么写对"。这一课讲另一件事：**约束写对了，指标还是不达标，怎么办。**

先说清一个前提：CTS 没有"全都变好"的操作。skew、latency、功耗三个数被同一批物理量绑在一起——buffer 的数量、级数、尺寸。改动其中任何一个，三个数一起动。

用一个类比。你要把水送到一栋楼的每个房间，水压要一致（skew 小）、要快（latency 短）、水泵要省电（功耗低）。想让每个房间水压一致，就在管路上多加减压阀和增压泵（多插 buffer）；泵一多，水在路上走的时间变长（latency 涨），电费也涨（功耗涨）。三个目标在物理上就是互相拉扯的。

:::term Global Skew | 全局偏斜
整棵树里，最晚到达的叶子与最早到达的叶子之间的时间差。

它回答的是"这棵树整体平不平"。全局 skew 大，通常意味着某几条大分支之间延迟不均，问题在树的中上层。
:::

:::term Local Skew | 局部偏斜
物理上相邻的两个叶子（比如同一个 row 上相距几十微米）之间的到达时间差。

它回答的是"近处的叶子对得齐不齐"。局部 skew 大，问题通常在叶子这一级——负载不均、单元太弱、某个 leaf 带了太多触发器。
:::

这两个数必须分开看，因为它们的病根完全不同。全局大而局部正常，说明树的分支结构有问题；局部大而全局还行，说明叶子级有问题。**看错这一个区分，后面全错。**

| 目标 | 常用手段 | 代价 |
|---|---|---|
| skew 变小 | 多插 buffer、加平衡级、换大驱动 | latency 变长、功耗上升、面积上升 |
| latency 变短 | 减级数、root 移到中心、加大驱动 | skew 变大、transition 变差 |
| 功耗变低 | 少插 buffer、用小单元、leaf 降 NDR | skew 变大、transition 变差 |

### 手算：多插 500 个 buffer 到底多花多少电

这是 review 里最常被问、最少有人算过的一笔账。

条件：时钟 500MHz（周期 2ns），核心电压 1.0V，一个时钟 buffer 的等效开关电容约 35fF（含自身输入电容和一段短线）。

```
单个 buffer 动态功耗 = C × V² × f
                    = 35e-15 × 1.0² × 500e6
                    = 17.5 µW
加短路功耗约 20%     ≈ 21 µW
500 个             = 500 × 21µW = 10.5 mW
```

一个万门级设计总功耗常在 120~150mW。10.5mW 就是 **7%~9%**。这还没算它带来的面积和布线资源。

再看 latency 的代价：多插 3 级，每级 80ps，insertion delay 就多 240ps。接口时序的预算里，这 240ps 是硬吃掉的。

所以"多插 buffer 把 skew 压下去"从来不是免费的。**在看到"skew 还差 40ps"时，先问一句：为了这 40ps，我愿意付 10mW 吗？** 多数时候答案是不愿意——40ps 可以用 useful skew 借，或者干脆承认这个指标该放宽。

## 诊断顺序：五步，不许跳 {#order}

新手最常见的动作是：看到 skew 超标，直接改 `target_skew`，重跑，再看。这个循环能跑一整天，因为它在**改结果，不是找原因**。

正确的顺序是自下而上——先确认树本身长什么样，再确认问题在哪一层，最后才动约束。

### 第一步：看树结构

```tcl
# 作用：先看树的规模，判断"是不是工具在乱插"
# 用法：CTS 之后立刻执行；重点看级数、buffer 数、buffer/leaf 比
report_clock_tree -summary > rpt/dbg_tree.rpt    ;# 级数、buffer 数、max/min latency
```

读三个数：

- **级数（levels）**：万门级设计通常 5~7 级。超过 9 级说明树太深，latency 一定长。
- **buffer/leaf 比**：正常 0.2~0.4。接近 1 说明工具在疯狂插，多半是目标太紧或单元太弱。
- **max/min latency 差**：这个差就是全局 skew 的上界。

树长什么样，版图上先扫一眼：

:::fig innovus-cts | 时钟树综合后的版图：绿色线条是从时钟源一路分叉到每个触发器的时钟网络，绿点是工具插入的缓冲器。重点看有没有一条分支明显比别的长、是否绕开了宏单元——第一步"看树结构"要抓的就是这种形状，报告里的级数和 buffer/leaf 比是对它的量化。
:::

从这张图里要看出什么：形状在版图上、数字在报告里，两处一起看才能排除"工具在乱插"；只看数字不看形状，会漏掉"某条分支绕路"这种一眼可见的问题。

如果这一步就看到 buffer/leaf 接近 1，后面不用看了，先回去放宽 `target_skew`。

### 第二步：看 skew 分布

```tcl
# 作用：分清是全局问题还是局部问题
# 用法：先看全局，再看最差的那几对叶子在哪
report_clock_timing -type skew > rpt/dbg_skew.rpt   ;# 全局/局部 skew 与最差叶子对
```

这份报告要给两个答案：**全局 skew 是多少、最差那一对的局部 skew 是多少、这两个叶子在哪个坐标。**

判断规则很硬：

| 现象 | 结论 |
|---|---|
| 全局大、局部小 | 分支之间不均，问题在树的中上层 |
| 全局还行、局部大 | 叶子级问题，看负载和单元 |
| 两个都大 | 先修局部（叶子级便宜），再看全局 |

### 第三步：看 transition 违例分布

```tcl
# 作用：确认电气质量，因为 transition 不准时延迟计算本身就是错的
# 用法：在 skew 分析之后；看违例集中在 trunk 还是 leaf（-type 的取值各版本略有差异）
report_clock_timing -type transition > rpt/dbg_tran.rpt
```

如果违例集中在 leaf，通常是单元太弱或负载太重；集中在 trunk，通常是驱动不够或 NDR 不足。**transition 有违例时，前面两步看到的 skew 数字都不可信**——工具是按错的延迟算的平衡。

### 第四步：看是不是上游造成的

到这一步还没找到原因，就要怀疑 floorplan 和 placement 了。三个检查：

```tcl
# 作用：量宏单元通道，确认时钟线有没有被迫绕路
# 用法：和 floorplan 的通道估算值对比；小于估算值一半就是可疑
dbGet [dbGet -p top.insts.name u_sram0].box          ;# 宏单元坐标框
reportCongestion -hotSpot > rpt/dbg_cong.rpt         ;# 拥塞热点，看是否压在通道上
```

再加一个几何检查：拿最差那对叶子的坐标，量它到 root 的直线距离，再和 `report_clock_tree` 里的 latency 折算出的等效长度比。**绕线长度超过直线距离两倍，就是 floorplan 的问题，不是 CTS 的问题。**

### 第五步：才动约束

前四步都有结论了，才知道该改哪个数：

| 前四步的结论 | 该改什么 |
|---|---|
| 级数 >9、buffer/leaf >0.8 | 放宽 `target_skew` |
| 局部 skew 大、leaf 单元偏小 | 提高 leaf 最小尺寸 |
| transition 集中在 leaf | 提高 leaf 驱动 或 降 leaf NDR |
| 绕线是直线两倍 | 回 floorplan，不在 CTS 里解 |
| 某分支天生短 | 用 useful skew，不动树 |

:::scene 周四晚上，第三天改参数还是 380ps
项目在流片前四周，CTS 目标是全局 skew 120ps。你跑出来 380ps。第一天你把 `target_skew` 从 80ps 收到 50ps，buffer 从 1800 涨到 2600，skew 375ps。第二天你把 leaf 单元从 X4 全换成 X8，skew 360ps，功耗涨了 6mW。第三天你怀疑 NDR 给太满，把 leaf 降到默认规则，skew 385ps。

三天里你改了三个参数，skew 一动不动。leader 走过来看了一眼你的屏幕，说："别调了。先告诉我 380ps 是哪两个叶子之间的差，它们在版图上的哪个位置。"

你打开 `report_clock_timing -type skew`，第一次认真看最差那一对的坐标——两个触发器都在 SRAM 右侧那条 8µm 的缝旁边。**问题从来不在约束里。**
:::

## 三种典型病症 {#symptoms}

### 病症一：全局 skew 大，局部正常

现象：全局 300ps，抽查几个相邻叶子对，局部只有 30ps。

病根：根到各大分支的延迟不均。常见三种成因：

1. **root 位置偏。** 时钟根放在芯片左下角，到右上角的分支要多走 600µm。这一段线的延迟差就是 skew。
2. **分支级数不同。** 左边分支 6 级，右边分支 8 级，每级 80ps，天然差 160ps。
3. **某个分支被宏单元挡住绕路。**

全局 skew 大，本质就是这张图里两端的差被拉大了：

:::fig wave-skew | skew 的形成：同一个时钟源，因为走线长短不同，到达两个触发器的时间不一样。重点看 B 比 A 晚的那一段——病症一要做的第一件事，就是回答"这段差是哪一条分支贡献的"，而不是急着改 target_skew。
:::

从这张图里要看出什么：skew 是两端之差，压它只有两条路——把长的分支缩短（回上游），或把短的分支加长（补级、借 skew），改全局目标哪条都不沾。

判断方法：看 `report_clock_tree` 里每条一级分支的 latency，把差值列出来。差值集中在某一条分支上，就是那条分支的问题。

处理：先看能不能调 root（回到 floorplan）；不能调就让工具在短的分支上补级——但这一步要算账，补 2 级就是 2×80ps 的 latency 和几百个 buffer。

### 病症二：局部 skew 大

现象：全局 120ps 看着还行，但某几个相邻叶子之间差 150ps。

病根通常在叶子级，三种：

1. **负载不均。** 一个 leaf buffer 带 8 个触发器，隔壁那个带 20 个。带 20 个的 transition 差、延迟长。
2. **单元太弱。** leaf 清单里混进了 X2，带 15 个触发器时延迟比 X4 多 100ps。
3. **一个 leaf 跨了两个 row。** 触发器分居上下两行，走线要多拐一次。

判断方法：找到最差的那对叶子，看它们各自的 driver 是哪个单元、fanout 是多少。两个 driver 尺寸不同、fanout 差一倍，就是负载问题。

处理：优先均衡 fanout（让工具重做 leaf 分配），其次换单元。**局部问题不要用改全局目标的方式解决**——那等于用大锤敲一颗螺丝。

:::pitfall 用全局目标去修局部 skew
现象：某几个相邻叶子差 150ps，你把 `target_skew` 从 80ps 收到 40ps，全树 buffer 从 1800 涨到 2400，那几个叶子还是差 140ps，其它地方的 skew 倒是从 90ps 降到了 60ps。

原因：局部 skew 来自那两个 leaf 的负载差和单元尺寸差，是叶子级的物理事实。全局目标只能让工具在别处多插 buffer，改不了这两个 leaf 的驱动能力。

怎么查：把最差那两个叶子的 driver 单元名和 fanout 列出来。两者 fanout 差一倍以上、或一个是 X4 一个是 X8，就确认是叶子级问题。

怎么修：让工具重做 leaf 分配（把负载摊平），或者把弱的那一个换成同尺寸单元。改完只看那两个叶子的局部 skew，不要看全局数字。
:::

### 病症三：latency 特别长

现象：skew 达标（80ps），但 insertion delay 2.4ns。

病根：树太深或绕线太远。

先算一笔：2.4ns 的 latency，在 2ns 周期里意味着什么？对芯片内部路径，launch 和 capture 两端都有 latency，可以部分抵消；但对输入接口，数据从片外来、时钟在片内绕 2.4ns，接口时序直接崩。所以**顶层设计的 latency 目标往往不是"越小越好"，而是"接口能接受"**。

判断：`report_clock_tree` 的级数 >8，或者 root 到最远叶子的绕线长度 >1500µm（40nm 量级，典型值），就是树太深。

处理：减级数（换大驱动、提高单级 fanout）、把 root 挪到几何中心、或者把一个大时钟域拆成两个子树。**这三件事有两件要回 floorplan。**

:::term OCV | On-Chip Variation，片上偏差
同一片芯片上，不同位置的晶体管和连线，延迟会有微小差异。工艺越先进，这个差异占比越大。

latency 越长，OCV 带来的绝对偏差越大——2.4ns 的路径按 5% 算就是 120ps 的不确定度，1.2ns 的路径只有 60ps。**这是"latency 越短越好"的第二个理由，与接口时序无关。**
:::

## useful skew 的边界：能借多少，怎么还 {#boundary}

useful skew 的原理和三条纪律在《OptCts：时钟树做完只是开始》里讲过。这里只讲边界——**什么时候能借、最多借多少、借完怎么还。**

### 能借多少：一个三选一的公式

借用的量受三个约束，取最小值：

```
可借量 = min( 下游最差 slack − 50ps,
              该端点 hold 余量 − 20ps,
              周期 × 10% )
```

三个项分别在防三件事：

- 第一项防"救了这条路径、弄坏下游"。捕获端的时钟推迟，以它为起点的所有下游路径都少同样的时间。
- 第二项防"把 setup 违例换成 hold 违例"。捕获时钟推迟，这条路径的 hold 要求也跟着推迟。
- 第三项是工程经验：单次借用别超过周期的 10%，超过就说明这条路径的设计本身有问题，该改逻辑而不是借时间。

### 手算一次：70ps 是怎么来的

条件：周期 2.0ns，某条 setup 违例路径差 60ps。捕获端所在触发器，下游最差 slack 120ps，自身 hold 余量 90ps。

```
第一项：120 − 50 = 70ps
第二项： 90 − 20 = 70ps
第三项：2000 × 10% = 200ps
可借   = min(70, 70, 200) = 70ps
```

借 70ps 之后：这条路径的 setup 从 −60ps 变成 +10ps（勉强过）；这个触发器的 hold 余量从 90ps 降到 20ps；下游最差 slack 从 120ps 降到 50ps。

**三个数同时变差，只是没变负。** 这就是借用的本质：不是创造余量，是搬运余量，而且搬运过程有损耗（安全余量）。

### 借了之后 hold 怎么还

hold 的账必须在借的时候就记下来，不能等布线后再算。

借出 70ps 之后，这个端点的 hold 余量只剩 20ps。布线会让数据路径变慢、时钟路径也变慢，净效果通常是 hold 再掉 30~50ps。也就是说，**借完的当下就要预留"布线后修 hold"的预算**。

还债的方式只有两种：

| 还法 | 做法 | 代价 |
|---|---|---|
| 给数据路径加延迟 | 在短路径上插 delay cell | 每条路径 1~3 个单元，面积 + 功耗 |
| 把捕获时钟推回去 | 减小借用（等于没借） | setup 回到违例 |

算一下第一种的代价：一条 hold 违例路径插 2 个 delay cell，每个约 3µm²，20 条路径就是 120µm²。对比"多插 500 个 buffer"的 10mW，这个代价小得多——所以**借 skew 修 setup、再用 delay cell 还 hold，通常是划算的**。前提是借之前就算清楚了。

### 什么时候不能用

五条红线，碰一条就别借：

1. **该端点 hold 余量 < 100ps。** 借 70ps 直接变负，你是把问题挪了个位置。
2. **该触发器在扫描链上。** 扫描移位时（shift）时钟频率低，但 hold 检查照样做，而且扫描链的 hold 违例极难修——你不能随便在扫描路径上插 delay cell。
3. **跨时钟域的发射端。** 借的 skew 只在同一个时钟域内传递，跨域的路径不认这个账。
4. **输入输出接口路径。** 接口时序按端口 latency 算，你在这里借，等于改了整个接口的基准。
5. **后面没有 ECO 空间的设计。** 借完 hold 一定要还，还不了就是负 hold 进签核。

:::pitfall 借了 skew 却没记 hold 的账
现象：CTS 后借用 skew 修掉 40 条 setup 违例，setup WNS 从 −0.08 变 +0.02。布线后 hold 冒出 60 条违例，最差 −0.12ns。

原因：借用的那 40 个端点，hold 余量本来就只有 60~90ps，借走 50~70ps 之后只剩 10~20ps。布线的延迟变化一吃，全变负。

处理：借之前把每个端点的 hold 余量列成表，借多少、剩多少、布线预算留多少，写进交接记录。**没有这张表，就不要借。**
:::

## 一份问题定位表 {#table}

下面这张表是这一课的核心。现象按"看到的第一个数"归类，往右查原因、验证命令、处理手段。

| # | 现象 | 最可能原因 | 验证命令 | 处理 |
|---|---|---|---|---|
| 1 | 全局 skew 大、局部正常 | 根到各分支延迟不均 | `report_clock_tree` 看各一级分支 latency | 调 root 位置或补平衡级 |
| 2 | 局部 skew 大（相邻叶子） | 负载不均或 leaf 单元太弱 | 看最差叶子的 driver 与 fanout | 均衡 fanout、提高 leaf 尺寸 |
| 3 | latency 长但 skew 达标 | 树太深或绕线太远 | 级数 >8，或 root 到叶子 >1500µm | 减级、root 居中、拆子树 |
| 4 | transition 违例集中在 leaf | leaf 驱动不足 | `report_clock_timing -type transition` | 提高 leaf 最小尺寸 |
| 5 | transition 违例集中在 trunk | 驱动不够或 NDR 不足 | 同上，看违例所在的级 | 换大驱动、trunk 上 2w2s |
| 6 | buffer/leaf 比接近 1 | `target_skew` 太紧 | 对比目标值与实际达成值 | 放宽到周期 3%~5% |
| 7 | 某时钟域单独超标 | 该域 root 偏或负载特殊 | `report_clocks` + 分组报告 | 单独建组、单独给目标 |
| 8 | 布线后 skew 又变差 100ps+ | NDR 没生效、绕线变长 | 量实际线宽，看绕线长度 | 修 NDR 属性、改通道 |
| 9 | hold 大面积违例 | ideal 切 propagated 后暴露 | `report_timing -delay_type min` | 交给 OptCts，先看是否相邻叶子 |
| 10 | 两路 MUX 的 latency 差很大 | 共享段在妥协 | 分模式各跑一次报告 | 缩短共享段、分组建树 |

用这张表的方法：**从上往下逐行排除，不要跳行。** 第 1 行和第 2 行的区分最重要，因为它决定了后面所有动作的方向。

## 什么时候必须回退 {#rollback}

CTS 阶段有个诱惑：什么问题都想在 CTS 里解。但有三类问题，CTS 里怎么调都是白费力气，必须回退到 floorplan 或 placement。

**判据一：局部 skew 超标的叶子在物理上聚成一团。**
如果 60% 的违例叶子集中在 100µm × 100µm 的区域内，那不是树的问题，是那块地方的 placement 密度或宏单元通道有问题。CTS 只能在那块地方插 buffer，插多少都不解决"没有走线空间"。

**判据二：root 到某分支的绕线长度超过直线距离两倍。**
这说明时钟线在绕障碍。绕障碍的成本是固定的，CTS 无法消除。要么挪宏单元，要么把 root 挪到障碍的另一侧。

**判据三：同一分支的 max/min latency 差超过周期的 8%，且级数已经 ≥8。**
级数到 8 还在加，说明这条分支的延迟是物理距离造成的，不是平衡算法能解决的。再加级只会让 latency 更长、OCV 更悲观。

三条判据命中任意一条，正确动作是：**停下来，写一页说明（现象、数据、判断依据），交给做 floorplan 的人。** 继续在 CTS 里调，是把一天的问题拖成三天。

算一笔账就明白为什么不能恋战：在 CTS 里调参数，一天能试三四组，每组半小时，但成功率很低——因为你改的是结果不是原因；回退改 floorplan 加重跑 place 和 CTS，两天能出一版干净数据，一次到位。**两天的确定性，好过三天的碰运气。**

回退时交出去的东西要具体：一张标了坐标的违例分布图、一份通道宽度对比表（实际 8µm，估算 30µm）、一句话结论。只带一句"skew 下不来"，对方只会让你再调两天。

## 一个完整的 debug 案例 {#case}

下面是课程里反复用到的那个例子，从 380ps 到 95ps，每一步都写清看什么、得出什么结论。报告数值是示例，用来讲怎么读；真实项目的数字会不同，但形状一样。

### 第 1 步：树结构

```text
# 示例输出：report_clock_tree -summary（数值为示例）
Clock   Sinks   Buffers  Levels  MaxLat(ns)  MinLat(ns)
clk     5860    1700     7       2.10        1.72
```

结论：buffer/leaf = 0.29，正常，不是乱插；级数 7，正常。**但 max/min 差 380ps**，这就是那个 skew。树本身没病，问题在分支之间。

### 第 2 步：skew 分布

```text
# 示例输出：report_clock_timing -type skew（只摘最差三对）
Launch        Capture        Skew(ns)  Distance(um)
u_core/U8821  u_core/U9104   0.380     42
u_core/U8823  u_core/U9110   0.362     55
u_dsp/U2201   u_dsp/U2240    0.110     38
```

结论：最差两对的叶子彼此只隔 42µm 和 55µm，但 skew 380ps——**这不是"相邻叶子对不齐"，是两个相距 42µm 的叶子分别属于两条延迟差很大的分支。** 第 3 名只有 110ps，说明问题是局部的两条分支，不是全树。

### 第 3 步：追这两条分支

```tcl
# 作用：把最差的那两个叶子各自的路径打出来，比较经过了几级、走了多长
# 用法：CTS 之后执行；按叶子追路径的选项各版本不同（-to / -pin），敲前 man 一次
report_clock_tree -to [get_pins u_core/U8821/CK] > rpt/dbg_path_a.rpt
report_clock_tree -to [get_pins u_core/U9104/CK] > rpt/dbg_path_b.rpt
```

两个文件对比：一条 6 级、总长 1180µm；另一条 9 级、总长 1960µm。**多出来的 3 级和 780µm，就是 380ps 的来源。**

问题变成：为什么这一条要多走 780µm？

### 第 4 步：量通道

```tcl
# 作用：量两个 SRAM 之间的实际间距，和 floorplan 的估算值对比
# 用法：box 输出顺序是 llx lly urx ury，单位 µm
dbGet [dbGet -p top.insts.name u_sram2].box    ;# 例：{420.0 180.0 620.0 580.0}
dbGet [dbGet -p top.insts.name u_sram3].box    ;# 例：{628.0 180.0 828.0 580.0}
```

两个 box 的 x 方向间距 = 628 − 620 = **8µm**。而按引脚数估算，这条通道该留 30µm（下一课会给完整算法）。时钟线要穿过去，8µm 里挤不下带 NDR 的时钟线，只能从上方绕出去再绕回来——正好多 780µm。

**结论：380ps 里约 300ps 是绕线造成的，改约束救不了。**

### 第 5 步：回退与验证

动作：把这条通道加宽到 32µm（挪 u_sram3 向右 24µm），重跑 place 和 CTS。

```text
# 示例输出：修完之后的同一张表
Clock   Sinks   Buffers  Levels  MaxLat(ns)  MinLat(ns)
clk     5860    1664     6       1.58        1.49
```

结果：skew 从 380ps 降到 90ps，latency 从 2.10ns 降到 1.58ns，buffer 还少了 36 个。**一个通道宽度，同时改善了三个指标。**

这就是为什么这一课要把"看树 → 看分布 → 看上游"的顺序定死：如果第 1 步就去调 `target_skew`，你会得到 2600 个 buffer 和 375ps，永远走不到第 4 步。

## 工作中怎么用：debug 是交付物的一部分 {#in-work}

**谁做**：PR 工程师。debug 的时间通常占 CTS 阶段的一半以上，但它在计划里往往被低估成"跑完看一下报告"。

**怎么记录**：每次 debug 留一份四行记录——看到什么现象、查了哪条命令、得出什么结论、做了什么动作。这份记录的价值不在当时，在两周后有人问"这个通道为什么是 32µm"时，你能直接翻出来。**没有记录的 debug 等于没做。**

**交给谁**：CTS 结论要交给两个人。给 STA 一份时钟树汇总（latency、skew、各分支延迟），因为签核用的就是这些数；给 floorplan 负责人一份"通道不足"的清单，如果 debug 结论是回退。

**评审看什么**：不看"skew 达没达标"，看"超标的那部分解释清楚了没有"。一个 200ps 的 skew，如果能说清 150ps 来自某条通道绕线、50ps 来自叶子负载，这个设计是可接受的；说不清，哪怕只有 120ps 也不该放行。

**做错会怎样**：在 CTS 里硬压一个上游造成的 skew，代价是几百个 buffer、几毫瓦功耗，以及布线阶段同样的绕线问题再爆一次——因为绕线不会因为你在 CTS 里多插了 buffer 就消失。

:::quiz
全局 skew 和局部 skew 的病根有什么不同？|全局大是树中上层分支之间延迟不均（root 偏、级数不同、绕线）；局部大是叶子级问题（负载不均、单元太弱、跨 row）。
为什么 CTS 诊断要先看树结构再看 skew？|因为树结构能立刻排除"工具乱插"这一类原因。buffer/leaf 接近 1 或级数超过 9 时，skew 数字本身没有分析价值，先改约束。

useful skew 可借量的三项约束是什么？|下游最差 slack 减 50ps、该端点 hold 余量减 20ps、周期的 10%，三者取最小。
借 70ps 之后 hold 的账怎么算？|该端点 hold 余量直接少 70ps；预留 30~50ps 的布线恶化预算；不够就在短路径上插 delay cell 还，每条 1~3 个单元。
哪五类端点不能借 skew？|hold 余量低于 100ps、扫描链上的触发器、跨时钟域的发射端、输入输出接口路径、后面没有 ECO 空间的端点。
局部 skew 违例的叶子聚成一团，说明什么？|说明问题在 placement 密度或宏单元通道，不在时钟树。CTS 只能插 buffer，解决不了没有走线空间的问题，必须回退。
报告显示 latency 2.4ns 但 skew 只有 80ps，要不要继续压 skew？|不要。应先处理 latency：它吃接口时序、放大 OCV。压 skew 会让 latency 更长。
debug 记录为什么必须留？|因为结论要能被复现和交接。两周后有人问"这条通道为什么 32µm"，没有四行记录就只能重跑一遍。
