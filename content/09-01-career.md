## 简历：一行字要回答三个问题 {#resume}

:::goal 学完这一章，你能把任何一条经历改写成"做了什么 / 怎么做的 / 结果如何"的一句话，并删掉所有形容词。
:::

后端简历最容易犯的错：写成流程说明书。

```
❌ 参与 IPA 项目后端设计，使用 Innovus 完成 floorplan、placement、CTS、routing。
```

这句话的问题不是不真实，是**没有信息**：多大规模？遇到什么问题？你做了什么判断？结果如何？面试官读完，脑子里没有任何画面。

### 三个问题，一行字答完

一条合格的简历 bullet（条目），必须同时回答：

1. **做了什么**：设计类型 + 规模 + 工艺。规模是单元数、macro 数、频率。
2. **怎么做的**：你采取的具体动作，最好带一个"因为……所以……"的判断。
3. **结果如何**：一个可比较的数字。前后对比最好。

公式：

```
做了什么（设计 + 规模 + 工艺） + 遇到什么问题 + 你做了什么动作 + 量化结果
```

改成：

```
✅ IPA 图像加速器（9390 单元 / 6 个 SRAM / 40nm）后端实现：
   floorplan 阶段重排宏单元通道（10µm→20µm），布线 DRC 从 6000 降至 0；
   全流程 21.7 分钟收敛，WNS +1.00ns，面积 222.5×222.2µm。
```

一句话里有规模、有动作、有因果、有数字。**面试官会顺着"为什么 10µm 不够"往下问——这就是你要的，让他问到你准备过的地方。**

:::term STAR | 情境-任务-行动-结果
Situation / Task / Action / Result。面试答题和写简历都用这个结构。

关键在 A 和 R：**你具体做了什么动作，带来了什么可量化的变化。** 没有 A 和 R 的 STAR，只是 S 和 T，等于在讲背景。
:::

### 五组对照：差在哪，怎么改

| 差 | 好 | 差在哪 |
|---|---|---|
| 负责 CTS，优化了时钟树 | CTS：全局 skew 从 380ps 压到 86ps，buffer/leaf 比 0.28，insertion delay 1.42ns | 没有数，看不出"优化"了多少 |
| 使用 PrimeTime 进行时序分析 | PT 签核 4 个 corner，清掉 37 条 setup 违例，最终 WNS +0.08 / TNS 0 | 工具不是能力，"查出什么、修到什么程度"才是 |
| 熟悉 Linux 和脚本 | 用 Tcl 把 6 个场景的回归从手工 3 小时压到 12 分钟，脚本在 git 上可复跑 | "熟悉"无法验证，"压到 12 分钟"可以 |
| 解决了 DRC 问题 | 通道从 10µm 加到 20µm，DRC 6000→0，面积只增 2.3% | 没有取舍就不叫"解决"，叫"碰巧好了" |
| 参与流片 | 负责 top 集成与 chipfinish，tapeout 前 DRC/LVS 清零，输入版本记录完整 | "参与"是最弱的动词，说清你负责哪一块 |

五组对照的共同规律：**差的那一栏全是"工具 + 流程名"，好的那一栏全是"数字 + 取舍"。**

### 三条硬规则

- **一页**。应届和三年以内，超过一页说明你不会删。项目多的，只留两个最深的。
- **倒序**。最近的在最上面。面试官只看前三分之一。
- **不要写"精通"**。写了就会被打穿。写"用过什么、做到什么程度"，让对方判断。

:::pitfall 简历写"精通"，面试被问穿
现象：简历写"精通 STA"，面试官问"说说 CPPR 在什么情况下加不回来"，答不上来。

后果比"不会"更糟：面试官会开始怀疑你简历上其他每一条。

怎么避免：把"精通/熟悉/了解"全部删掉，换成事实。"用 PT 跑过 4 个 corner 的签核，能读 full_clock_expanded 报告定位 skew 来源"——这句话本身就说明了水平，不需要形容词。
:::

## 项目描述模板 {#project}

:::goal 学完这一章，你能用"背景-职责-手段-结果-数字"五段式写出一个项目的完整描述，并加一行复盘。
:::

简历上是一行，面试时要展开成三分钟。展开的结构固定为五段：

| 段 | 内容 | 长度 |
|---|---|---|
| 背景 | 什么芯片、什么工艺、多大规模、你的角色 | 2 句 |
| 职责 | 你负责哪几个阶段，边界在哪 | 2 句 |
| 手段 | 遇到的关键问题 + 你的动作 + 为什么这么选 | 4~5 句 |
| 结果 | 关键指标 + 和目标的对比 | 2 句 |
| 数字 | 规模、频率、WNS/TNS、DRC、面积、功耗 | 一行 |

```text
### IPA 图像加速器后端实现（40nm, 9390 cells, 400MHz）
- 背景：6 个 SRAM 的图像加速器，我负责 floorplan 到 chipfinish 全流程
- 职责：floorplan、电源规划、placement、CTS、route、signoff 自检
- 手段：
  1. Floorplan：6 个 SRAM 靠边对齐、pin 朝内，按出线数算通道宽度（20µm），加 halo
  2. 电源：ring + stripe 覆盖，via 阵列补齐，静态 IR 预估 3.8%
  3. CTS：skew 目标 80ps，实际 62ps；buffer/leaf 控制在 0.3 以内
  4. 布线：route_auto + route_opt + 局部增量修 DRC
- 结果：DRC 0、open net 0、WNS +1.00ns、hold −0.07ns、FM 2560/2560 等价
- 复盘：第一版通道只有 10µm，DRC 6000；改到 20µm 后首轮即 0，面积只增 2.3%
```

**最后一行"复盘"最有价值**：它证明你不是照流程点按钮，而是理解了因果。面试官听到"第一版为什么错、改了什么就好了"，基本就能判断你是真做过。

一个技巧：把"复盘"写成一句可迁移的经验，比如"通道宽度要按出线数算，不能按视觉间距"。**这句话可以在面试里被复用十次。**

## 20 道高频面试题 {#questions}

:::goal 学完这一章，你能对每道题先说出考点，再给出三句话以内的答案要点，而不是背一段课文。
:::

下面每道题给"考点 + 参考答案要点"。**背要点，不要背原句**——原句在紧张时一定会忘，要点能自己组织语言。

### 概念类

| 问题 | 考点 | 参考答案要点 |
|---|---|---|
| setup 和 hold 的区别 | 时序基础 | setup 检查"下一个时钟沿之前数据是否已经稳定"，跨一个周期；hold 检查"同一个沿之后数据是否保持不变"，在同一沿附近。setup 违例可以降频救，hold 不能。 |
| 为什么降频救不了 hold | 公式理解 | hold 的式子里没有周期：`T_logic ≥ T_hold + skew`。降频只把捕获沿往后推，hold 检查仍在同一沿附近，竞争关系不变。 |
| skew 是什么，越大越好还是越小越好 | 时钟树 | 同一时钟到不同触发器的时间差。不是越小越好：太小要插大量 buffer，功耗面积上升；适当留 skew 可以做 useful skew 抢时序。目标按周期的 5%~10% 给。 |
| 时序预算怎么分 | 系统思维 | 周期 = CK→Q + 逻辑 + setup + skew + uncertainty + margin。逻辑通常占 60% 左右，margin 留 10%~15% 给布线恶化和后期改动。关键是加总必须等于周期。 |
| OCV、CPPR、AOCV 的区别 | 悲观度 | OCV 是统一 derate，一刀切；CPPR 把公共时钟路径被 late/early 各算一次的虚假悲观加回来；AOCV 按级数和距离查表，深路径 derate 更小，比 OCV 准也没那么悲观。 |
| false path、multicycle、max_delay 的区别 | 例外约束 | false path 完全不查；multicycle 放宽到 N 拍（hold 要配套 N−1）；max_delay 用绝对时间代替周期。三者都能让违例消失，所以每条都要有书面依据。 |

### 流程类

| 问题 | 考点 | 参考答案要点 |
|---|---|---|
| 为什么必须做 CTS | 时钟树 | 不建树时钟是理想的、skew 为 0，hold 完全没暴露；真实时钟一上来 hold 全线崩。CTS 还负责波形质量（transition）和 NDR。 |
| 利用率定多少，为什么 | floorplan | 第一版 0.60~0.65。布线需要通道，0.85 只剩 15% 给线和空隙，密集区布不通。跑完看拥塞再逐步加。 |
| 宏单元怎么摆 | floorplan | 靠边、对齐、pin 朝内、按出线数算通道、加 halo。还要考虑电源走线和信号流向，别把 macro 摆在芯片正中间切断通道。 |
| 电源规划怎么做 | 功耗完整性 | ring 包边、stripe 按电流密度铺、via 阵列补齐、关键模块加 decap。判据是静态 IR < 3%~5%、动态 < 8%~10%、EM 无违例。 |
| ECO 流程是什么 | 签核闭环 | PT 出 ECO 清单（动作/目标/参数/预期收益）→ 人工筛物理可行性 → PR 应用 → 局部布线 → 重新导出 netlist+SPEF → PT 复算。通常 2~3 轮收敛。 |

### 工具类

| 问题 | 考点 | 参考答案要点 |
|---|---|---|
| PT 和 PR 自带 STA 的区别 | 签核 | 立场不同（判断 vs 优化）、输入不同（冻结数据 vs 当前数据库）、精度不同（真 SPEF + 全 OCV）、可复现性不同。PR 的数只能算施工估算。 |
| Innovus 和 ICC2 的区别 | 工具广度 | 数据组织不同（.enc vs NDM+block），命令能一一对应，方法论相同。说清"换工具两周能上手"比背命令列表有用。 |
| 怎么修 setup 违例 | 优化手段 | 优先级：换更强驱动/换 LVT → 缩短线长（改 floorplan/加约束）→ 重构逻辑/加流水 → useful skew → 降频（最后手段，是产品决策不是技术手段）。 |
| 怎么修 hold 违例 | 优化手段 | 插 delay cell、调 skew（让捕获时钟晚到）、删多余 buffer、降驱动。hold 不能靠降频，必须清零。 |

### 排错类

| 问题 | 考点 | 参考答案要点 |
|---|---|---|
| 时序突然变差怎么定位 | 排错 | 先对比基线：约束变了吗、库 corner 换了吗、网表/SPEF 版本对吗、时钟从 ideal 切到 propagated 了吗。四项排除完再看设计本身。 |
| DRC 清不干净怎么办 | 排错 | 先分类统计（按规则名）+ 区域聚类（按坐标），判断是系统性问题还是孤例。孤例逐条修，系统性问题回去改 floorplan 或布线策略。 |
| 网表和 SPEF 不匹配的现象 | 流程 | 报找不到端口/引脚，或时序结果完全不合理。根因是两次导出不同步，规矩是同一条命令、同一时间戳导出。 |

### 综合类

| 问题 | 考点 | 参考答案要点 |
|---|---|---|
| 你做过最难的一个问题是什么 | STAR + 深度 | 选一个"有诊断过程"的：现象 → 你怀疑了什么 → 怎么排除 → 最后根因 → 结果。一定要有排除过程，只讲结果听起来像编的。 |
| 如果给你一个更高频的规格，你怎么做 | 迁移能力 | 先算预算：周期少了多少，逻辑预算还剩多少级；再判断是结构问题（拆流水）、实现问题（换 LVT/加 pipeline）还是约束问题。给出取舍，不要只说"优化"。 |

:::note 答题的一个通用结构
任何技术题都可以用三句话：**是什么 → 为什么重要 → 我实际怎么用**。

比如问 CPPR："它是把公共时钟路径被重复计算的悲观量加回来；不加会让 WNS 偏悲观 0.05~0.1ns；我在签核脚本里默认打开，并在报告里核对 `clock reconvergence pessimism` 那一行。"

第三句是分水岭——有第三句的人，是真做过。
:::

## 模拟面试怎么练 {#mock}

:::goal 学完这一章，你能用"录音 + 计时 + 自评表"完成一次 30 分钟的模拟面试，并找出三个具体改进点。
:::

三步，每步 20 分钟：

1. **自我介绍（2 分钟）**：一句话背景 + 一个项目 + 一个亮点。不要从大学讲起。
2. **项目深挖（10 分钟）**：对方会问"为什么这么做""如果改条件会怎样"。**答不上来就说"这块我当时没深入，我的理解是…"，别编。**
3. **基础题抽查（8 分钟）**：上面 20 题随机抽 5 道。

### 必须录音

不录音的模拟面试，等于没练。因为你对自己说话的印象，和真实听起来差很远。

回听时只查三件事：

| 检查点 | 具体听什么 | 合格标准 |
|---|---|---|
| 口头禅 | "然后""就是说""那个" | 每分钟不超过 3 次 |
| 时长 | 自我介绍是否超 2 分钟 | 1分40秒 ~ 2分钟 |
| 有没有数字 | 每个项目是否至少 3 个数字 | 规模、频率、WNS/DRC 各一个 |

### 计时

用手机秒表，每段到点就停，不要"再讲两句"。**面试的时间感是练出来的**：练过的人知道 2 分钟能说多少字（约 400 字），没练过的人一开口就讲了 5 分钟。

### 自评表

每次模拟后填一张，三次之后看趋势：

| 项 | 1 分 | 3 分 | 5 分 | 自评 |
|---|---|---|---|---|
| 结构 | 想到哪说到哪 | 有 STAR 但不完整 | 背景-动作-结果清晰 | |
| 数字 | 全是形容词 | 有一两个数 | 关键结论都有数 | |
| 深度 | 只讲流程 | 能讲一个判断 | 能讲取舍和替代方案 | |
| 诚实 | 不懂装懂 | 会说"没深入" | 会说"没深入 + 我的推测 + 怎么验证" | |

**"诚实"这一项最容易被忽略，也最影响评价。** 面试官不怕你不会，怕你编——编了就没法判断你的真实水平。

:::pitfall 面试时说"我们团队"
面试官只关心**你**做了什么。

错误："我们做了 floorplan 优化。"
正确："我负责 floorplan，具体做了三件事：算通道宽度、调宏单元朝向、加 halo。结果 DRC 从 6000 降到 0。"

**把"我们"换成"我"，把动作说具体。** 如果真是团队做的，就说"这部分是团队做的，我负责其中 XX"——边界清楚比抢功更加分。
:::

## 投递与谈薪 {#apply}

:::goal 学完这一章，你能排出"准备-投递-面试-offer（录用意向）"的时间线，并在被问期望薪资时给出不伤谈判的答法。
:::

### 时间线

| 阶段 | 做什么 | 注意 |
|---|---|---|
| 提前 3~6 个月 | 补项目、刷基础题、整理简历 | 项目比刷题重要，一个能讲深的项目顶十个 demo |
| 提前 1~2 个月 | 投 3~5 家练手（不是最想去的） | 先用不重要的面试练手感 |
| 面试期 | 每面完当天记下被问的题 | 同一道题第二次答得更好，就是进步 |
| offer 期 | 比较总包，不只看月薪 | 月薪 × 月数 + 签字费 + 股票 + 补贴 |

:::term Referral | 内推
由公司内部员工把你的简历直接递给 HR 或用人经理。命中率通常高于海投，因为简历不会被系统筛掉。

找内推的正确方式：说明你投哪个岗位、附上简历、一句话说清匹配点。不要只发一句"在吗"。
:::

### 渠道

| 渠道 | 特点 |
|---|---|
| 内推 | 命中率最高，优先找师兄师姐、前同事 |
| 招聘网站 | 量大但竞争激烈，简历要针对 JD（职位描述）改关键词 |
| 公司官网 | 大厂必投，流程正规 |
| 猎头 | 三年以上经验更有效 |

:::term JD | 职位描述
Job Description。招聘方写的岗位要求。投递前逐条对照，把简历里的词改成 JD 里的词（比如 JD 写"功耗完整性"，你就别只写"IR drop"）。这不是造假，是让对方三秒内看懂你匹配。
:::

### 多个 offer 怎么沟通

三条原则：

1. **诚实**：说有其他流程在进行，不要说"我手上有五个 offer"（会被要求证明）。
2. **给时间**：请对方给一个明确答复期限（通常一周），同时告诉另一家你的时间点。
3. **不虚构**：不要编造一个高薪 offer 去压价。背景调查和圈子都很小。

正确说法："我这边还有一家在流程中，预计下周三给答复。我对贵司这个岗位更感兴趣，能否在本周五前给我一个大概的范围？"

### 被问期望薪资怎么答

三步：

1. **先问区间**："这个岗位的预算区间大概是多少？"——很多 HR 会直接给，给了你就有了锚点。
2. **报区间不报单点**：给一个下限是你真实能接受的区间。单点报价要么被压，要么直接出局。
3. **说总包**："我看的是总包，月薪、签字费和股票能不能一起说一下？"

:::term Total Compensation | 总包
一年内的全部现金与非现金收入：月薪 × 发放月数 + 绩效奖金 + 签字费（sign-on）+ 股票（分几年归属）+ 补贴。

比较 offer 必须用总包，且要问清股票的归属年限和兑现条件——"纸面 40 万"和"四年归属、每年 25%"是两回事。
:::

**具体数字不要问别人要，也不要信"统一价"。** 后端薪资因城市、年限、公司类型差异很大，同一岗位在不同城市可能差一倍。正确做法是查同城同年限的公开区间，给自己定一个"低于多少不去"的底线，谈判时守住底线、放开上限。

## 面试官最怕听到的三句话 {#redflags}

:::goal 学完这一章，你能在面试中避开三句"一出口就掉分"的话，并知道该换成什么。
:::

### 第一句："这个我没做过，是别人负责的"

问题不在"没做过"，在"把边界划得太干净"。面试官会想：那你在这项目里到底负责什么？

换成："这块不是我负责的，但我了解它的接口。我的理解是……如果要我接手，我会先确认 XX。"

**展示的是"可迁移"和"愿意补位"，不是"与我无关"。**

### 第二句："我们一直都是这么做的"

这句话等于说"我没有判断，只是执行"。面试官最怕招一个"照着脚本点按钮"的人。

换成："我们当时的做法是 XX，原因是 YY。如果条件变了（比如频率更高），我会改成 ZZ。"

**有理由、有替代方案，才叫工程判断。**

### 第三句："随便，都行，没什么难点"

问"最大的难点是什么"，答"没什么难点"，面试官只有两种解读：项目太水，或者你没参与核心。

换成："最难的是 XX，当时卡了三天，最后发现是 YY，用 ZZ 解决的。"

**难点不是暴露短板，是展示你的诊断能力。** 一个讲不清难点的项目，在面试官眼里等于没做过。

:::scene 面试前一晚，你在改简历
明天上午十点面试，你打开简历，发现第一条写着"参与 SoC 后端设计，负责 P&R（布局布线）全流程"。

这句话在面试官眼里等于什么都没说。你要在半小时内把它改成三行：规模（多少单元、什么工艺、多少 MHz）、动作（你做的三个具体决定）、结果（WNS/DRC/面积各是多少）。

改不出来，说明你还没想清楚自己做过什么——**这比任何技术题都致命。**
:::

**任务**：产出一条能直接放进简历的项目 bullet，以及一段 2 分钟的自我介绍录音。

**步骤**：
1. 选你最深的一个项目，写下四个数：单元数、工艺、频率、WNS（或 DRC）。
2. 写三个"你做的决定"，每个配一句"为什么"。
3. 按公式拼成一句话，控制在 60 字以内。
4. 用手机录 2 分钟自我介绍，回听并填自评表（结构/数字/深度/诚实）。
5. 重录一遍，对比第一版删掉了哪些废话。

**过关标准**：bullet 里有规模、动作、数字；录音时长 1分40秒~2分钟；自评表四项都不低于 3 分。**做不到就再录一遍，这是唯一有效的练法。**
