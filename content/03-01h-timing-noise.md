## 按阶段读 Setup 和 Hold {#timing-stages}

:::fig innovus-practice-h.svg | 原创教学示意图 · 同一条路径，用不同报告回答问题
:::

:::note 课程来源
本讲是网站原创专题；钉钉目录第 12 项仅用于确定主题与顺序，不转载原文、项目参数或图片。可另看上传 Word 整理的 [CTS 时序检查](/lesson/03-08-cts/#source-05) 和 [时序 ECO](/lesson/03-11-eco/#source-03)。
:::

Setup 要求数据在捕获边沿前及时稳定，Hold 要求数据在捕获边沿后不能过早改变。布局后通常用理想时钟和估算寄生；先核对约束，再找过长逻辑链和高延迟网，此时 Hold 只作初筛。CTS 后改用传播时钟：把发射与捕获时钟延迟单独列出来，不能把偏斜造成的变化误认成数据线变慢。布线后用提取寄生做签核，记录端点、检查类型、路径组、模式、库角和 RC 角，再逐项比较发射、数据、捕获、时钟不确定度与库约束的贡献。

本例输入为同一小模块 `si_lab` 的布线后数据库、逻辑网表、功能／扫描 SDC、慢快时序与噪声库、对应角的耦合寄生，以及固定的降额和 SI 分析配置。下方报告是原创合成摘录，不是 PrimeTime 实测或命令。复查时各版寄生都从各自数据库生成；不要拿新网表配旧 SPEF。开始前排除未约束端点、断传播时钟及关键网寄生漏回标，否则裕量可被错误放大。

## 分清负载、边沿和扇出 {#design-rules}

Max Cap 检查驱动端负载电容，Max Tran 检查边沿转换时间，Max Fanout 通常按库定义的负载值累加，不一定等于引脚数量。每项都写下实际值、限制、引脚、边沿和场景；不能只看违规网名，也不能把 `ps`、`fF` 和扇出值混用。对宏输入转换超限，先核对宏接收模型的限值、驱动能力、长线和其他支路。不要试图放大宏内部的标准单元；若考虑分支或缓冲，还需留意布线效果、保持时间和驱动后新增负载。

本例 `u_mem/REQ` 的上游驱动实际负载为 29 fF、限值 35 fF，扇出负载为 3.0、限值 8.0，只有入宏端边沿在功能慢角超限。线路是否被耦合拖慢要靠提取与详细时序确认；“边沿慢，所以一定要换驱动”是尚未验证的假设。

## 用 PrimeTime Noise 找到主要施扰网 {#primetime-noise}

用 PrimeTime SI 查噪声前，确认模型、供电状态和含耦合电容的寄生都正确加载；报告缺少受害端不代表没有噪声。对稳定受害网的毛刺，读取引脚、极性、峰值、脉宽、接收判据和主要施扰网，并在版图追并行段。对切换受害网的串扰延迟，另看包含串扰的 STA 路径、施扰网同向或反向切换及活动时间窗。两类检查用的是不同受害状态，毛刺峰值不能替代时序增量，也不要直接相加不同窗口的最坏施扰峰值。

## 建立多场景基线：定位同一段耦合 {#practice-step-04}

功能 Setup 路径从 `u_req_ff/Q` 到 `u_mem/REQ`，受害网是 `req_data`，其 M4 段与 `burst[2]` 的 M4 长直线相邻。耦合清单把 `burst[2]` 列为最大贡献者，时序报告也显示反向切换窗口重叠；源到受害端的主数据段需要先查这里。下面的毛刺检查给出相应脉宽对应的接收限值；同一线路在功能模式可触发毛刺检查，也可在不同窗口触发串扰延迟分析。

```text
合成功能慢角基线（场景 FUNC_SS_RCmax，非命令）
path u_req_ff/Q -> u_mem/REQ, Setup
arrival=831 ps; required=811 ps; slack=-20 ps
included SI delay delta on req_data: +25 ps
u_mem/REQ rise transition=128 ps; limit=110 ps
victim req_data ; aggressor burst[2] ; Ccouple pair=9.0 fF
quiet-low receiver: +89 mV at 32 ps; limit=75 mV at 32 ps
```

根因证据要能互相支持：同一条物理并行段有较大的成对耦合，且施扰翻转与功能路径的关键窗口重叠。若版图上虽平行但窗口互斥，应先核对该模式的活动条件和约束，不拿几何外观替代时序证据；若报告来源的逻辑网与物理网不一致，则先确认映射与寄生版本。

## 只调整一段走线，再重新提取 {#practice-step-05}

保存基线，在可用轨道上把受害网的一段 M4 走线局部平移一轨以增大间距，允许这段为接回两端而产生短折线；保留驱动、接收端、周围网络、时钟和 SDC。选轨同时看另一侧有没有新施扰体以及改线是否引入几何或天线问题。受害网变快可能降低 Hold 裕量；在功能慢角只盯着 Setup 正负，很容易漏掉功能快角或扫描快角的问题。

```text
合成多场景前后对比（裕量 ps；同一分析设置）
scene             check   scope                         before  after
FUNC_SS_RCmax     Setup   u_req_ff/Q -> u_mem/REQ         -20     +5
FUNC_FF_RCmin     Hold    u_req_ff/Q -> u_mem/REQ         +14     +6
SCAN_SS_RCmax     Setup   affected-cone worst            +27     +24
SCAN_FF_RCmin     Hold    affected-cone worst            +10     +7
FUNC_SS_RCmax: SI delay +25->+6 ps; path arrival 831->806 ps
FUNC_SS_RCmax: req transition 128->103 ps (limit 110 ps)
FUNC receiver: +89 mV @32 ps (limit 75) -> +57 mV @24 ps (limit 81)
```

## 用数值差复核修复逻辑 {#practice-step-06}

功能 Setup 的要求时间保持 811 ps，抵达提前 25 ps，其中 SI 延迟增量减少 19 ps，剩余 6 ps 来自本例局部线路非 SI 延迟下降。不能把全部改善都归因于串扰，也不必假设增距总能缩短非 SI 延迟。受害网对应的成对耦合降到 3.6 fF；噪声的接收限值随脉宽变化，修后 24 ps 的毛刺应与该脉宽的 81 mV 比，不直接沿用基线的 75 mV。最紧的正裕量只有 5 ps，如果项目另有大于 5 ps 的签核余量，该修复仍不合格。

每个相关场景用修前同样的时钟传播、降额、例外路径处理和预先定义的项目门槛复查。扫描行是受影响逻辑范围的最坏路径，不一定还是功能路径的端点组合；做归因时要按同一端点配对，看整体有无新问题时再比较最坏路径和受影响范围。

若修后重新展开路径，先对照端点选中的触发边沿、发射和捕获时钟渐变、公共时钟段处理以及时钟不确定度。固定这些分析配置不等于报告里的每个分项都应相同；只有确认线路改动没有牵动时钟树、同步关系或活动窗口，才能把差值集中解释到数据路径。快速核对可同时保留一份关闭串扰的对照报告，用它分辨基础 RC 和动态干扰的贡献；正式验收仍用项目规定的含串扰签核结果。

若快角原来的 Hold 裕量靠近零，建议同时检查受害网在两种稳定电平下的毛刺和相邻新受害端，并观察该场景最短路径是否换了起点。这样即使眼前这条路径通过，也不会漏掉另一段被挤到更近轨道、因耦合变化而退化的新路径。

## 复查与回退清单 {#practice-step-07}

- 核对 SDC、RC 和库配对，确认耦合寄生已回标；保留修前后版图与两套报告，记录被移动的线段和相邻网络。
- 复跑连通性、DRC、天线及相关角的 Setup、Hold、噪声和三类设计规则；扩大到潜在的新受害网，并按项目要求做全量回归。
- 若 Hold 从正变负、宏输入边沿仍超限，或者几何／噪声新违例无法消除，恢复旧路线及其配套寄生，校验复原报告后再单独试换层或缓冲，不能改约束遮住退化。

## 小练习：判断一笔时序修复能否合入 {#timing-check}

:::quiz
Hold 由负转正但 Setup 由正转负，且宏输入转换仍超限，能合入吗？|不能；比较数据和时钟分项，再在相关场景回归 Setup、Hold、转换和受影响的串扰。
为什么毛刺变小不能证明 SI 时序问题已经解决？|毛刺检查稳定受害网，串扰延迟检查切换受害网，两者要分别用噪声及带 SI 的路径报告验证。
为什么不能用修前同一毫伏阈值判定所有修后的毛刺？|接收判据可能与脉宽及极性相关，应与改善后波形匹配的报告限值比较。
:::
