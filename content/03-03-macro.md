## 宏单元为什么难 {#why}

:::goal 学完这一课，你能用"引脚数 × 出线数 ÷ 层数 × 间距 + 电源走廊 + 余量"算出一条通道该留多宽，按四条硬规则摆完宏单元，再用七项检查判断这一版能不能进布局。
:::

先做个类比。搬家时书可以随手塞进任何缝隙，衣柜不行——它大、重、门朝哪边开是定死的，进门还得先拆门框。标准单元是书，宏单元（macro）是衣柜。

宏单元是预先设计好的整块功能：SRAM、ROM、PLL、ADC、模拟 IP。在后端眼里它是个黑盒子，你只能"摆"，不能"改"。

三个"硬"决定了它难摆。

**第一，尺寸大。** 40nm 下一颗 512×64 的 SRAM，面积在 0.1~0.3mm² 量级（典型值）。一颗万门级设计的 core 可能只有 0.08mm²——**一个 SRAM 比整个标准单元区还大**，这在真实项目里很常见。

**第二，引脚多且集中。** 一颗 SRAM 有 150~250 个引脚，而且全挤在一条边上。标准单元的引脚是"撒"在面上的，宏单元的引脚是"排"在一条线上的，后者的线密度高一个数量级。

**第三，位置固定。** 形状、尺寸、引脚坐标都写在 LEF 里。它能做的只有 90° 翻转，不能拉伸、不能裁角、不能被工具重排。

还有第四个隐形成本：**它周围的地不能用**。为了防止标准单元贴上来堵住引脚出口，宏单元四周要留一圈保护边（halo）。这圈地算进 core 面积，却放不了标准单元。

所以宏单元的"实际占地"比它的外框（bbox，bounding box）大：

```
实际占地 ≈ (W + 2h) × (H + 2h)，h = 单边 halo 宽度
```

手算一次。一颗 100µm × 200µm 的 SRAM，halo 每边 8µm：

```
实际占地 = (100 + 16) × (200 + 16) = 116 × 216 = 25056 µm²
外框面积 = 100 × 200 = 20000 µm²
倍数     = 25056 ÷ 20000 = 1.25  →  多占 25%
```

**做面积预算时漏掉这 25%，是后面利用率失控的第一个原因。** 六个这样的 SRAM，账面 12 万 µm²，实际吃掉 15 万 µm²。

:::term Macro Pin | 宏单元引脚
宏单元对外连接的物理接入点，坐标固定在 LEF 里。SRAM 的数据/地址/控制引脚通常集中在一条边，电源引脚在另一条边或贯穿整个高度。

引脚朝哪边由摆放方向决定：`R0` 时朝东，翻转后就朝西。**摆之前必须确认"这一侧的引脚朝哪"，摆完必须看图确认。**
:::

:::scene 周一早上的三个问题
SRAM 刚摆完，review 会上组长只问三句：

1. "这两个 SRAM 之间留了多宽？"——你答"大概 10µm"。他问："算过吗？"
2. "`u_sram2` 的 pin 朝哪边？"——你说"默认的"。他让你开飞线，结果线从 SRAM 背面绕出来，兜了 400µm。
3. "halo 加了吗？"——你说"布局工具会自动避让吧"。他打开图形界面，标准单元正贴着 SRAM 引脚边缘。

这三个问题对应这一课的三块内容：通道怎么算、朝向怎么定、halo 怎么加。答不出来，说明你只是把宏单元"放上去了"，并没有"摆"。

真实代价是这样的：这一版进布局，布线跑到 70% 卡住，回头挪 SRAM，前面 8 小时布局 + 3 小时 CTS 全部作废。**宏单元摆错不是"改一个坐标"，是"重跑三天"。**
:::

**工作中怎么用**：宏单元摆放是 floorplan 阶段 PR 工程师的活，但决定权不全在你——连接关系来自前端和架构，封装与模拟团队会指定某些 IP 必须靠某条边。你的职责是"在给定约束下把空间需求算出来"。输出物是一版 floorplan 数据库加一张通道宽度表，交给布局和 CTS。

## 通道要留多宽：一个能用的估算 {#calc}

先给结论，再拆开推。通道宽度由三块拼成：

```
通道宽度 = 信号占用 + 电源走廊 + 余量
信号占用 = (引脚数 × 每引脚出线数 ÷ 可用层数) × 线间距
```

三个因子逐个解释：

- **每引脚出线数**：一个引脚平均接几根线。纯数据引脚 1 根，带测试或双向的 2 根，控制引脚可能 3 根。不确定时按 2 根估，偏保守。
- **可用层数**：这条通道方向上有几层金属真的能走。40nm 常见配置是 M1~M6，但 M1 基本只做单元内部连线，M6 以上留给电源，实际可用往往只有 3~4 层。
- **线间距（pitch）**：一根线加它必须留出的间距。40nm 大约 0.2~0.3µm（典型值），具体查工艺的 `tech LEF`。

手算一条"大通道"。两个大 SRAM 面对面，两侧合计朝通道出 128 个信号引脚（每侧 64），平均每引脚 2 根线，4 层可用，pitch 0.28µm，余量 25%，通道里还要走两条电源条：

```
信号线数     = 128 × 2 = 256 根
单层线数     = 256 ÷ 4 = 64 根
信号宽度     = 64 × 0.28 = 17.92 µm
加 25% 余量  = 22.4 µm

电源条       = 每条 8µm 宽 + 两侧各 2µm 间距 → 8 + 2×2 = 12 µm
两条 + 中间 3µm 间隔 = 12 × 2 + 3 = 27 µm

走线区小计   = 22.4 + 27 ≈ 49.4 µm  （信号 + 电源，还没算逃逸和 halo）
```

先记住这个 49.4。工具默认给 10µm，差五倍——这就是"按默认值摆"必然翻车的原因。但它还不是最终答案，下面两项还要加上去。

这个加法长什么样，图里画出来了：一条通道其实是"信号 + 电源 + 逃逸"三段拼起来的。

:::fig fp-channel | 两个 SRAM 面对面、引脚都朝内，中间那条通道要同时容纳三样东西。下面的色条把加法拆开：信号段、电源走廊、余量。重点看每一段占多少比例。
:::

从图里要看出什么：**通道宽度不是一个数，是一笔账**。报"留了 30µm"没人能判断对不对，报"信号 18 + 电源 12 + 余量 5"才有人能挑错。评审时被问"能不能窄一点"，你要能指出窄的是哪一段、为什么不能动。

**反向校验**（review 时最容易被追问的一步）：用轨道数验一遍。

```
通道给的单层轨道数 = 22.4 ÷ 0.28 = 80 根
实际需要           = 64 根
余量               = 80 ÷ 64 = 1.25  ← 正好是前面那个 25%
```

两个方向算出来是同一个数，说明公式没写错。**对不上就一定是口径用错了**：把总宽当信号宽、把 M1 算进可用层数、或者把引脚数重复计了两次。

还有一个常被漏掉的修正项：**出线要错开**。128 个引脚挤在两侧各 200µm 的边上，每根线不能直着出去，得在通道里拐到不同轨道，这个动作叫出线逃逸（escape）。逃逸区至少要吃 1 条轨道/引脚：

```
逃逸占用 = 128 × 1 × 0.28 ÷ 4 层 ≈ 9 µm
```

所以**走线区**的下限是 `49.4 + 9 = 58.4µm`，实战取 60µm。还有一项 halo 没算——它加在走线区外面，见规则四。**估算值永远向上取整到布线网格**，别写 58.4。

:::term Pin Pitch | 引脚间距
相邻两个引脚中心的距离。它决定一个引脚占多宽的边，也间接决定逃逸能走几根线。

SRAM 的 pin pitch 常见 0.5~4µm（典型值），比布线 pitch 大一个数量级。所以引脚本身不是瓶颈，**引脚之间的出线空间才是**。
:::

:::term Escape Routing | 出线逃逸
引脚上的线先垂直离开宏单元边缘、再拐进通道的那一小段。所有线都挤在宏单元的边上，必须逐层错开，否则一出头就短路。

逃逸区宽度通常按"1~2 条轨道 × 引脚数 ÷ 层数"估。它是通道宽度里最容易被忘掉的一块。
:::

:::term Flyline | 飞线
工具把每根连线的两个端点用直线连起来画在版图上，不管中间有没有障碍。

它不精确（不绕障碍、不分层），但**判断"摆得对不对"最快**：线短而平行是好的，线长而交叉成蜘蛛网说明连接紧密的模块被摆远了。
:::

**工作中怎么用**：这张通道宽度表要在 floorplan review 前交上去，每个宏单元一条通道、一个数字、一行算式。评审时不看图画得好不好看，只看"这个数怎么来的"——所以算式必须能当场复现。

## 摆放的四条硬规则 {#rules}

四条规则按"违反后的修复代价"排序。

### 规则一：出 pin 方向朝外

这里的"外"指标准单元区，不是芯片边缘。宏单元贴边放时，引脚必须朝里。两种判断方法：打开 LEF 看 PIN 的坐标和方向；或者在图形界面里开飞线，看线从哪一侧出来。

朝向代码容易记混：

| 代码 | 实际效果 | 常见误用 |
|---|---|---|
| `R0` | 原样 | 引脚在左、你希望朝右，却没翻 |
| `MY` | 沿 Y 轴镜像（左右翻） | 引脚左右对调，上下不变 |
| `MX` | 沿 X 轴镜像（上下翻） | 引脚上下对调，左右不变 |
| `R180` | 转 180° | 引脚跑到对角，最容易摆错 |

记一句就够：**`MY` 管左右，`MX` 管上下**。摆完开飞线看一眼，不要相信记忆。判断标准很硬：飞线如果从宏单元的"背面"绕出去，就是朝向错了。

### 规则二：通道方向一致

同一条通道两侧的宏单元，引脚都朝这条通道，让线直着穿过去。最忌讳两条通道十字交叉——交叉点四面来线，是拥塞的绝对热点。

```
✅ 一字通道                      ❌ 十字交叉
┌────┐   ┌────┐                ┌────┐
│RAM │──▶│RAM │                │RAM │
└────┘   └────┘                └────┘
   通道直穿，线不拐弯              ↓ 四面来线
┌────┐   ┌────┐                ┌────┐
│RAM │──▶│RAM │                │RAM │
└────┘   └────┘                └────┘
```

如果布局逼得你只能做十字，就把交叉那一小段通道加宽 30%，并在交叉点上盖一块硬禁放区，把标准单元赶走，让布线有地方换层。

### 规则三：电源对齐

宏单元的电源引脚（VDD/VSS）要和全局电源网格的电源条（stripe）对齐。不对齐的后果有两种：加一段短接线接过去（多一组通孔，多一个电迁移弱点），或者整条 stripe 改道（影响全片电源规划）。

做法：先知道 stripe 的间距（比如 20µm）和起始坐标，摆宏单元时让电源引脚落在 stripe 上。同一列宏单元宽度一致时，一条 stripe 能笔直打穿所有宏单元，这是最省事的情况。

```tcl
# 作用：把三个同尺寸 SRAM 沿左边缘对齐摆成一列，让电源引脚落在同一条竖直 stripe 上
# 用法：floorPlan 之后执行；坐标单位 µm，原点在 die 左下角；y 步进 = 宏单元高度 + 通道宽度
placeInstance u_sram0 40  60  MY    ;# 左下角 (40,60)，MY 让原本朝左的引脚翻到右侧
placeInstance u_sram1 40 260  MY    ;# y = 60 + 180(高) + 20(这两颗小 SRAM 的通道) = 260，x 保持 40
placeInstance u_sram2 40 460  MY    ;# 按同一节拍继续排，三个 x 对齐形成笔直通道
```

`x` 全为 40，保证三个宏单元的电源引脚在同一条竖直线上；`y` 的步进是"高度 + 通道宽度"，保证通道宽度处处一致——宽度忽宽忽窄的地方，布线工具会往宽处堆线，窄处反而空着。

### 规则四：留出 halo / keepout

halo 加在"走线区"外面，所以它不占走线区的宽度，而是让**两个宏单元外框之间的距离**变大。取每边 10µm：

```
摆位间距 D = 走线区 + 2 × halo
           = 58.4 + 2 × 10
           = 78.4 µm  →  取 80µm

若 halo 压到 5µm：D = 58.4 + 10 = 68.4  →  取 70µm
```

这里有个口径问题，review 时一定会被问：**"两个 SRAM 之间留多宽"说的是走线区还是外框间距？** 走线区是 58，外框间距是 78，差 20µm。报数时先说口径，再报数字。

halo 给太小（比如 2µm）标准单元会贴上来，把引脚出口堵死；给太大则白扔面积。经验值是走线区的 1/6~1/8，且不低于 5µm。

```tcl
# 作用：给宏单元四周加保护边，并把通道里的电源走廊钉成硬禁放区
# 用法：placeInstance 之后执行；-halo 的四个数对应 左 下 右 上（不同版本可能只收一个统一值，敲前 man 一下）
createPlaceBlockage -type halo -inst u_sram0 -halo {10 10 10 10}   ;# 通道左侧的宏单元，四边各 10µm 不放单元
createPlaceBlockage -type halo -inst u_sram1 -halo {10 10 10 10}   ;# 通道右侧，与左侧对称
createPlaceBlockage -type hard -box {266 60 293 640} -name pwr_corr ;# 通道中段 27µm 宽（两条 stripe + 间距），禁止摆放
checkPlace                                                          ;# 立刻检查有没有实例落在 halo 里
```

不想建 blockage，也可以让布局工具自己留位：

```tcl
# 作用：等价写法——不画 halo，直接告诉布局工具给这些实例四周留空
# 用法：place_opt_design 之前执行；数值单位 µm
setPlaceMode -place_global_module_padding {u_sram0 10 u_sram1 10}  ;# 每个实例四周各留 10µm
```

ICC2 里的对应写法（坐标格式不同，别照抄）：

```tcl
# 作用：ICC2 里等价的"硬禁放区 + 实例保护边"
# 用法：ICC2 中 floorplan 之后执行；boundary 是 {{llx lly} {urx ury}}，和 Innovus 的 box 顺序不同
create_placement_blockage -type hard -boundary {{266 60} {293 640}} -name pwr_corr  ;# 电源走廊禁放
set_keepout_margin -type hard -outer {10 10 10 10} [get_cells u_sram0]             ;# 实例四周 10µm 保护边
# 有些教材把上面这条写作 set_inst_halo，含义相同：给实例加保护边；参数名以 man 为准
```

:::term Placement Blockage | 摆放禁区
明确告诉工具"这块地不许摆标准单元"的区域。三种常见类型：硬禁放（hard，永不许摆）、软禁放（soft，工具可以临时借用）、部分禁放（partial，按百分比限制密度）。

它和 halo 的区别：halo 是**跟着某个实例走**的一圈缓冲；blockage 是**画在坐标上**的一块地，和实例无关。
:::

**四条规则里哪条最容易违反？** 朝向。因为它不报错——`checkPlace` 会说"完全合法"，只有飞线和时序报告会告诉你不对劲。所以第四条之后还要加一步：**摆完立刻开飞线看十秒**。

**工作中怎么用**：四条规则里，靠边和对齐是"摆法"，朝向和 halo 是"约束"。实际做法是先用脚本按列摆好（对齐），再逐个调朝向（看图），最后批量加 halo。顺序反了会返工——用 `-inst` 建的 halo 会跟着实例走，用 `-box` 画的不会，宏单元一挪，画的那块就留在原地挡路。

## 四个禁忌：出错什么样、怎么查 {#taboo}

上面讲的是"应该怎么做"，这一节反过来讲"做错了会看到什么"。四个禁忌，按被发现的难度从易到难排：

| 禁忌 | 出错后的现象 | 怎么查（具体动作） | 修法 |
|---|---|---|---|
| **出 pin 朝内**（本该朝内却朝了外） | 飞线从 macro 的背面绕出去，那条 net 的长度是直线的 2~4 倍；经过它的路径 net delay 占比异常高 | 开飞线，只显示连到这颗 macro 的 net，看线的**第一段**往哪走；或 `dbGet` 取它的 pin 坐标，和 net 另一端坐标比方向 | 用 `MY`/`MX` 翻过来，翻完再开飞线确认 |
| **通道方向不一致**（两条通道十字交叉） | 拥塞热点精确落在交叉口那一个 bin；`reportCongestion` 的单点 overflow 特别高；via 数异常 | `reportCongestion -hotSpot` 抄下热点坐标，对照 floorplan 看是不是两通道交点；再看该处 density 是否正常（正常就说明是走线交叉，不是单元太多） | 改成一字通道；必须交叉时把交叉段加宽 30%，并在交叉点盖硬禁放区 |
| **电源不对齐** | macro 电源引脚不在 stripe 上：`checkPGConnectivity` 报 unconnected；IR 热点出现在 macro 四个角 | 把电源网格和 macro 电源引脚**同时显示**，逐列目测；`verifyPowerVia` 看该处 via 覆盖率是否为 0 | 平移 macro 让 pin 落在 stripe 上；或调 stripe 的 `-start_offset`；临时短接线只当应急，不当方案 |
| **没留 halo** | 标准单元贴着 macro 引脚摆进来，布线时 macro 四周一圈 DRC；pin access 失败 | `checkPlace` **不会报错**（几何完全合法），要看 place 后的密度图有没有单元紧贴 macro 边；也可以对比"加 halo 前后"的 `report_area` | `createPlaceBlockage -type halo` 或 `setPlaceMode -place_global_module_padding`；加完必须重算利用率 |

四条里前两条"看一眼"就能发现，后两条必须"算"或者"叠图对"。所以检查顺序应该是：

1. **朝向**（10 秒）：开飞线，扫一眼有没有从背面出来的线。
2. **通道**（5 分钟）：`dbGet` 量相邻 macro 的间距，和估算表逐个对。
3. **电源**（5 分钟）：叠两层图，看 pin 落没落在 stripe 上。
4. **halo**（2 分钟）：跑 `checkPlace` + 看密度图边缘。

**为什么按这个顺序？** 因为前两项改起来是"翻个方向、挪个坐标"，后两项改起来要动电源规划和面积账。先做便宜的检查，能让贵的检查少做几遍。

:::pitfall 四个禁忌同时犯，但只查出一个
现象：改完朝向，飞线正常了，但布线 DRC 还是 3000 条。以为是布线参数问题，调了两天没效果。

原因：四个禁忌会互相掩盖。朝向错了，飞线绕远，看起来"通道很挤"；其实是朝向造成的假拥塞，把真问题（通道太窄）盖住了。

怎么处理：**按顺序一次查完四个，不要查一个改一个。** 每查完一项记一个数（朝向：几条线异常 / 通道：最窄多少 / 电源：几个未连 / halo：几处贴边），四个数都有了再决定改哪个。一次只改一个变量，否则你不知道是哪一项起了作用。
:::

## 三种典型摆法：条状、环形、岛屿 {#patterns}

规则讲完，还剩一个选择题：这些宏单元**整体排成什么形状**。工程上常见三种，没有优劣，只有适用场景。

先看一个真实例子——下面这张就是"环形"摆法的样子。

:::fig innovus-floorplan | 四角各一块 SRAM，中间留完整标准单元区，外侧一圈是 IO。重点看四条边上的宏单元是怎么"围"出一块连续区域的，以及四角附近的通道为什么最宽。
:::

从图里要看出什么：**摆法决定了通道的拓扑**。环形把通道分成四条边，每条边单独算宽度；四角是两条边交汇的地方，最容易拥塞，所以角上的通道要额外加宽。换成条状就是一条长通道，换成岛屿就是好几条短通道——通道的数量和方向，是三种摆法最本质的区别。

三种摆法放在一起对比：

| 摆法 | 长什么样 | 适合什么设计 | 主要风险 |
|---|---|---|---|
| 条状（strip） | 所有宏单元排成一条或两条带，贴一边 | 宏单元少（≤6 个）、尺寸相近 | 带太长，另一侧的逻辑要跨全片 |
| 环形（ring） | 沿四边各排一排，中间留完整标准单元区 | 宏单元多（8~20 个）、形状不一 | 四个角的通道交汇，最易拥塞 |
| 岛屿（island） | 按数据流分几群，每群靠近自己的逻辑 | 多模块 SoC、有明确子系统边界 | 群与群之间的通道要单独算 |

```
条状                      环形                      岛屿
┌────────────────┐      ┌────────────────┐      ┌────────────────┐
│ ███ ███ ███    │      │ ██          ██ │      │ ██    ██       │
│                │      │                │      │  ↑数据流A  ↑B  │
│   标准单元区    │      │   标准单元区    │      │   ██    ██     │
│                │      │ ██          ██ │      │    ↑C     ↑D   │
└────────────────┘      └────────────────┘      └────────────────┘
```

选择依据有两条，按顺序问：

1. **数据流在哪？** 宏单元和哪块逻辑交互最多，就往那块逻辑旁边放。这条压倒一切——形状好看但线要跨全片，等于白摆。
2. **还剩多少完整区域？** 标准单元需要一个连续的、能形成长 row 的区域。环形和岛屿都会把区域切碎，碎片区放不下大单元，利用率会掉 3~5 个百分点。

条状最容易做对，所以新项目常从它起步；宏单元超过八个之后，条状会拉得太长，才转环形或岛屿。

:::term Island Placement | 岛屿式摆放
把宏单元按功能/数据流分成几群，每群靠近它服务的逻辑区，群与群之间留宽通道。

它把"一条大通道"拆成"多条小通道"，每条都要单独按本课的公式算宽度——**岛屿摆法的通道数量多，最容易漏算**。
:::

**工作中怎么用**：摆法在 floorplan 评审时就要定下来，并写进脚本注释（"采用环形，四角通道各留 45µm"）。中途从条状改环形等于坐标全废。评审时如果被问"为什么不用岛屿"，回答"数据流集中在一个方向，岛屿会把一条通道拆成四条、每条都要更宽，反而更费面积"。

## 摆完的自检清单 {#checklist}

七项检查，十分钟能跑完。跑不完就别进布局。

```tcl
# 作用：七项自检里能脚本化的五项；第 4、6 项（朝向、电源对齐）只能看图，见下文
# 用法：Innovus 里逐条执行；输出重定向到 rpt/ 存证，结果写进交接记录
checkPlace                        ;# ① 合法性：重叠、越界、站点对齐、落在 blockage 里的实例
checkFPlan -reportUtil            ;# ② 整体规划：宏单元是否在 core 内、利用率是多少
dbGet [dbGet -p top.insts.name u_sram0].box   ;# ③ 量坐标：输出 {llx lly urx ury}，用来自查通道宽度
report_area                       ;# ④ 面积：标准单元面积 + 宏单元面积，和综合报告对得上吗
reportCongestion -hotSpot         ;# ⑤ 拥塞预判：此时还没布线，只能看早期估计，有热点就记下来
```

`checkPlace` 通过时输出是"没有违例"这类汇总；有违例时它会逐条列出实例名和原因。**课程环境跑不了完整流程，真实项目里你会看到类似这样的行**（不同版本措辞不同）：

```
Placement violation: instance u_core/u_alu/U1203 overlaps blockage pwr_corr
```

读到这一行要知道三件事：哪个实例、违反了哪条规则、被哪块区域挡住。修法不是删 blockage，而是把这个实例挪走或让工具重跑局部布局。

| # | 检查项 | 通过标准 | 不通过先怀疑什么 |
|---|---|---|---|
| 1 | 重叠/越界 | 0 条 placement violation | 坐标算错、朝向翻转后外框变了 |
| 2 | 落在禁放区 | 0 条 blockage violation | halo 太宽、blockage 坐标写反 |
| 3 | 通道宽度 | 每条 ≥ 估算值，无 <10µm 的窄缝 | 没算通道、按默认间距摆 |
| 4 | 朝向 | 飞线全部从宏单元朝内一侧出发 | `MY`/`MX` 用反 |
| 5 | halo | 每个宏单元四周都有，宽度 ≥5µm | 只加了 padding 没加 blockage，或反过来 |
| 6 | 电源对齐 | 宏单元电源引脚落在 stripe 上 | 摆了 macro 才想起电源，顺序反了 |
| 7 | 利用率 | 与目标差 <3 个百分点（含 halo） | 面积预算漏了 halo 那 25% |

前六项是"几何对不对"，第七项是"账算没算对"。**几何错能改，账错会一路错到布线**——利用率虚报的设计，后面每一步都会以为"还有空间"。

第 4 项（朝向）和第 6 项（电源对齐）没有可靠的单条命令，只能开图形界面看：打开飞线看线的第一段方向，把电源网格和宏单元电源引脚同时显示、逐列目测。所以放在最后人工确认——这两项也是最容易漏的。

自检里最容易糊弄过去的是第 3 项。别用眼睛估，用坐标算：

```bash
# 作用：从 checkPlace 前的坐标快照里量出相邻宏单元的真实间距
# 用法：把 dbGet 的输出粘进 boxes.txt，一行一个 "llx lly urx ury"，按 y 排序后逐对相减
awk '{print $2, $1, $3, $4}' boxes.txt | sort -n | \
awk 'NR>1 {gap = $2 - prev_urx; if (gap < min || NR==2) min = gap; prev_urx = $4} END {print "最小通道:", min, "um"}'
# $1..$4 = llx lly urx ury；先按 lly 排序，再拿当前 llx 减上一个 urx 得到水平间距
```

**工作中怎么用**：这七项要在进 place 之前跑完，输出贴进交接记录：日期、数据库版本、七个数字。下次有人问"这版 floorplan 靠不靠得住"，你拿得出证据，而不是"我记得检查过"。

## 一个真实的数字 {#real}

课程环境里，我们在一套 45nm 开源库上跑过一个万门设计：9390 个标准单元、6 个 SRAM。第一版没算通道，直接按工具默认间距摆（SRAM 之间 6µm）：

- 布线 DRC：**6000 条**（课程环境实测）
- 红色拥塞区：**5 处**，全部落在 SRAM 之间的缝里

改成"按出线数算走线区（20~50µm）+ halo + 对齐 + 朝向修正"之后，同一套布线参数：

- 布线 DRC：**0 条**
- 红色拥塞区：0 处

**这不是优化出来的，是摆对了自然就通了。**

再看面积账（估算，按上面 6 个 SRAM 的典型尺寸推）：

| 项目 | 占 core 面积 | 说明 |
|---|---|---|
| 6 个 SRAM 外框 | 约 18% | 账面数 |
| 加 halo 后 | 约 22% | 实际占地，多出 4 个点 |
| 5 条通道 | 约 8%~10% | 只放线，不放单元 |

**用 4% 的面积换掉 6000 条 DRC，这笔账在任何项目里都划算。** 反之，为了省 4% 面积把通道压到 6µm，后面要用两三天返工来还。

还有一个更值得记住的比例：这 6 个 SRAM 的引脚加起来约 1200 个，占全部连线端点的比例不到 5%，但它们集中在 5 条通道上——**通道里的线密度是标准单元区内部的 5~6 倍**（估算）。面积上它是"低效用地"，走线上它是全片最挤的地方，这个反差就是宏单元难摆的本质。

**工作中怎么用**：报这组数要带口径和代价。"6 个 SRAM 占 18% 面积"是布局选择，"通道不够导致 6000 条 DRC"是它的账单——两个数并列摆出来，评审才听得懂你为什么坚持要那 80µm。只说"间距太小会拥塞"，没人会批你多用 4% 面积。

:::pitfall 宏单元贴太近，布线阶段无解
现象：布线跑到 70% 卡住，日志里出现类似这样的提示（不同版本措辞不同）：

```
Routing congestion detected in region (1200, 800) - (1800, 1400)
```

打开拥塞热图，红色区域正是两个 SRAM 之间那条 6µm 的缝。

原因：通道宽度是布局阶段定死的物理量，布线只能在既有空间里绕。空间不够时，工具能做的只有"拆线、换层、绕远"，结果就是一大堆 DRC 和天线违例。

处理：只有两条路——挪宏单元（重跑布局 + CTS，8 小时起），或者接受一堆 DRC 然后一条条手工修（通常修不干净，最后还是要挪）。

**结论：floorplan 阶段多花 30 分钟算通道，能省后面 8 小时。**
:::

:::pitfall halo 加了，但利用率没重算
现象：加了 halo 之后 `checkFPlan` 说利用率 78%，而你的目标是 62%。布局一跑，标准单元被挤到更远的角落，原来宏单元旁边的拥塞消失了，却在 core 的另一侧冒出新的红色区域。

原因：halo 吃掉的是"可用 row 面积"，分母变小，利用率自然上升。你没重算，工具就按 78% 的真实密度去摊，只能把单元往剩余空间里硬塞。

处理：加完 halo 先 `report_area` + `checkFPlan -reportUtil` 重算一遍；如果利用率超过 75%，要么减 halo（但不能低于 5µm），要么承认 die 尺寸不够、回去改 floorplan。**拥塞不会消失，只会搬家。**
:::

:::pitfall 朝向用反，飞线绕半圈
现象：`checkPlace` 全绿，布局也正常，但 `u_sram2` 相关的路径时序特别差，飞线图上它的线绕了 400µm 才出来。

原因：这颗 SRAM 的引脚本来在左侧，你想让它朝右，用了 `MX`（上下翻），结果引脚还是在左边，只是上下颠倒了。引脚朝着 die 边缘，线必须贴着边缘绕过去。

处理：记住 `MY` 管左右、`MX` 管上下；摆完开飞线，看线是否从宏单元朝内的一侧出发。判断标准不是"看起来对不对"，是"线的第一段方向对不对"。
:::

:::lab 动手：算一遍你自己的通道
**任务**：给定条件算通道宽度，写成命令，并用自检确认。

**给定**：两个 SRAM 面对面，两侧合计朝通道出 128 个信号引脚，每引脚 2 根线，4 层可用，pitch 0.28µm，余量 25%，通道内两条 8µm 电源条（两侧各 2µm 间距，条间 3µm），另需 9µm 逃逸空间，两侧各 10µm halo。

```bash
# 作用：算通道宽度，并验证"层数减半会怎样"
# 用法：任意目录 python3 直接跑；改 layers 看结果变化
python3 - <<'EOF'
pins, per_pin, layers, pitch, guard = 128, 2, 4, 0.28, 1.25   # 引脚数、每引脚出线、层数、线距、余量系数
nets = pins * per_pin                                          # 这条通道要过的信号线总数
sig  = nets / layers * pitch * guard                            # 信号需要的宽度
pwr  = (8 + 2 * 2) * 2 + 3                                      # 两条电源条 + 两侧间距 + 条间间隔
esc  = 9                                                        # 逃逸区（按 1 轨/引脚估出来的）
print("信号 %.1f + 电源 %.1f + 逃逸 %.1f = %.1f um" % (sig, pwr, esc, sig + pwr + esc))
print("层数改 2 层时信号宽度 %.1f um" % (nets / 2 * pitch * guard))
EOF
```

**预期**：`22.4 + 27.0 + 9.0 = 58.4µm`；层数改 2 层后信号宽度翻倍到 44.8µm（总宽 80.8µm）。

**再走一步**：把这几个数写成命令并自检。

```tcl
# 作用：按算出的走线区 58µm、摆位间距 80µm 摆两个 SRAM，加 halo，并检查合法性
# 用法：Innovus 里 floorPlan 之后执行；坐标按 200µm 宽的 SRAM 推
placeInstance u_sram0 40  60  MY                        ;# 左列，引脚朝右（朝通道）
placeInstance u_sram1 320 60  MX                        ;# 右列，x = 40 + 200(宽) + 80(摆位间距)，引脚朝左
createPlaceBlockage -type halo -inst u_sram0 -halo {10 10 10 10}   ;# 通道侧各留 10µm
checkPlace                                              ;# 期望：0 条 violation
```

**过关标准**：能说出三件事——58.4µm 里信号、电源、逃逸各占多少；为什么层数从 4 减到 2 后信号部分正好翻倍（22.4→44.8）；以及 58.4 和 78.4 这两个数分别在说什么（走线区 vs 摆位间距），为什么报数前必须先说口径。
:::

:::quiz
宏单元和标准单元最本质的三个区别是什么？|尺寸大（可能超过整个标准单元区）、引脚多且集中在一条边、位置和形状固定（只能 90° 翻转，不能改）。
为什么算宏单元面积时要额外加 halo？|halo 是宏单元四周不许放标准单元的缓冲带，它占 core 面积但不承载单元；不加会让面积预算偏小 20% 以上，后面利用率失控。
通道宽度公式里"÷ 可用层数"是在算什么？|把总走线需求平摊到几层金属上。层数越多，同一宽度能过的线越多，通道就可以窄；层数减少，通道必须按比例变宽。
手算：128 个引脚、每引脚 2 根线、4 层、pitch 0.28µm、余量 25%，信号部分要多宽？|256 根 ÷ 4 = 64 根/层，64 × 0.28 = 17.92µm，乘 1.25 得 22.4µm。
为什么通道里要先算电源走廊再算信号？|两者抢同一块地。先定电源，剩下的才是信号可用宽度；顺序反了会来回改，而且电源条位置被迫偏移会影响全片电源网格。
`MY` 和 `MX` 分别翻哪个方向？|`MY` 沿 Y 轴镜像，左右对调；`MX` 沿 X 轴镜像，上下对调。
为什么朝向摆错时 `checkPlace` 查不出来？|因为朝向错在几何上完全合法——单元不重叠、不出界、落在站点上。只有飞线图和时序报告能暴露"线绕远了"。
halo 加宽之后利用率上升，说明什么？|说明可用 row 面积变小了。要么减 halo（不低于 5µm），要么承认 die 不够，回 floorplan 改尺寸。
