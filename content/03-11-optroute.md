## `route_auto` 返回 0，不代表布线做完了 {#why}

:::goal 学完这一课，你能设计一个可回退的布线收敛循环：每轮记 DRC、时序和耗时，判断"还在收敛"还是"该停手回退"，并说清三种优化模式各自的代价。
:::

`route_auto`（Innovus 里对应 `routeDesign`）跑完，log 最后一行通常是"完成"。但这时报告里至少有四类问题：

| 问题 | 典型数量 | 后果 |
|---|---|---|
| DRC 违例 | 几十到几千 | 签核不过，必须清零 |
| setup 恶化 | 新增几十条 | 真实线延迟吃掉了布线前的估算余量 |
| 串扰（crosstalk） | 通常还没检 | 信号互相干扰，功能可能出错 |
| 天线违例 | 几十条 | 栅氧化层可能被击穿，工厂要求修 |

为什么"完成"不等于"做完"，拆开看这条命令干了什么就清楚了：

1. 它先做全局布线，给每条 net 分配层和通道；
2. 再按分配结果把线落到具体 track 上，换层处打 via；
3. 最后对局部冲突做修补，**修补的优先级是"先连通"**。

所以它的成功标准是"每条 net 都有路径"，不是"每条 net 都合法"。DRC 要你另外数，天线要另外查，时序要另外出快照——这三件事都不在它的判定里。

本课与第 20 课的分工：第 20 课讲布线本身（两步分工、五类 DRC、拥塞与天线的原理），本课讲**布完之后怎么收敛、什么时候必须认输回退**。

:::scene "不是已经布通了吗，怎么还有 6000 个 DRC"
第一次看到 `Total number of DRCs: 6000` 会以为工具坏了。

其实这很正常：全局布线只保证"每个连接有路可走"，详细布线才把线真的画在轨道上。6000 条里绝大多数是同一类形状——**引脚访问冲突**（pin access），一个单元的多个引脚挤在一起，线出不来。

更麻烦的是：这 6000 条里有 95% 你加多少轮增量都清不掉，因为根因在布局。你要做的第一件事不是"再跑一轮"，是判断"这批违例的结构是什么"。
:::

:::term DRC | Design Rule Check，设计规则检查
工艺厂规定的一堆"物理上不许这样画"的规则：两条线不能太近、线不能太细、不能有缺口、换层必须打 via 且要包边。

DRC 违例不是工具算错，是**你画出来的版图真的超出了工厂的制造能力**。所以必须清零，不能靠解释。
:::

## 五类 DRC，认清成因才知道怎么修 {#types}

先复习一遍（各类的完整成因、修法和示意在第 20 课，这里只列判定要点）：

| 类型 | 英文 | 典型报错 | 成因 | 修法 |
|---|---|---|---|---|
| 短路 | short | `Net A shorted to Net B` | 两根不同网的线碰上，多发生在拥塞区 | 局部重布，必要时挪单元 |
| 开路 | open | `Net A has unconnected pin` | 线没碰到引脚、via 漏打、线被切断 | 查引脚遮挡，重布该 net |
| 间距 | spacing | `Metal2 spacing < 0.07` | 同层两条线距离不足 | 增量重布；根因是密度就回布局 |
| 宽度 | width / notch | `Metal1 width < 0.065` | 线太细、有缺口、NDR 没生效 | 让工具加宽，检查 NDR 作用范围 |
| 通孔 | via | `Via enclosure < 0.02` | via 包边不足、cut 数不够 | 加倍 via、换 via array |

:::note 引脚访问冲突是成因，不是第六类
报告里会出现 `pin access` 字样，但它不是独立类型，而是 short / open / spacing 的**根因**：多引脚单元周围没有出线空间。

识别方法：把违例投到版图上，**成簇**出现在多引脚单元周围就是 pin access；零散分布才是普通绕线问题。前者必须回布局，后者可以增量磨。
:::

:::term Pin Access | 引脚访问
详细布线从单元引脚"出线"的那一小段路径。引脚越密、周围单元越挤，可用的出线方向越少，于是出现 short、open 或 spacing 违例。

它是布局问题在布线阶段的显形，不是布线算法不够努力。
:::

到 OptRoute 阶段，你要先分清手里这批 DRC 是**谁造成的**：

| 来源 | 特征 | 该谁修 |
|---|---|---|
| 布线阶段没修干净的 | 从 `route_auto` 第一份报告就在，数量大、成簇 | 先判断根因；pin access 类回布局 |
| 优化动作引入的 | 优化前 0、优化后几十条，零散分布在被改过的单元附近 | OptRoute 的增量重布 |
| 规则本身没设对 | 同一层同一类型反复出现，位置随机 | 改 NDR / 规则，别修版图 |

判断方法很土但有效：**每次优化动作前后各存一份报告，做差集**。没有基线，你永远说不清这 200 条是谁弄出来的。

## 三种 OptRoute，代价差很多 {#modes}

| 模式 | Innovus | ICC2 | 改什么 | 耗时 | 主要风险 |
|---|---|---|---|---|---|
| 只修 DRC（增量） | `routeDesign -incremental` | `route_detail -incremental true` | 只重布违例附近的一小块 | 分钟级 | 反复修同一处，数量守恒 |
| 修时序（优化） | `optDesign -postRoute` | `route_opt` | 换单元尺寸、插 buffer、局部重布 | 十几分钟到一小时 | 会引入新 DRC，须再收敛 |
| 全量重布 | `routeDesign` | `route_auto` | 推倒重来 | 最长（小时级） | 前面所有局部修复作废 |

三种模式的本质区别是**改动半径**：增量动几微米，优化动几十微米（插一个 buffer 要连三根线），全量动整个芯片。改动半径越大，收益上限越高，副作用也越不可控。

:::pitfall 一上来就跑 `route_opt`
现象：DRC 还有 6000 条，想着"优化一下说不定一起修了"，直接 `route_opt`。
结果：它在很脏的版图上换单元、插 buffer，**DRC 没降多少，时序还被搅乱**——因为它在拥挤的区域插了更多单元，等于往堵死的路口再加车。
正确顺序：**先增量把 DRC 磨到 100 条以内 → 再跑优化修时序 → 最后再增量磨到 0**。每一步都要出报告，不要连跑三条命令再看结果。
:::

:::pitfall 全量重布当成"重置按钮"
现象：收敛不动了，`route_auto` 重跑一遍，期望回到干净状态。
结果：跑了几小时，DRC 回到 6000 附近，前面两天的局部修复全没了。
原因：全量重布不改变布局，根因（拥塞、pin access）一个都没解决，只是把同样的失败重演一遍。
处理：全量重布只在"网表或布局大改过"之后用，不作为收敛手段。
:::

## 增量布线的正确用法：一轮一记录 {#incremental}

```tcl
# 作用：ICC2 增量收敛循环，每轮存报告 + 往 csv 追加一行
# 用法：在 pnr/ 目录下、block 已打开；rpt/ 必须先建好
set csv [open rpt/optroute_rounds.csv w]                                  ;# 打开记录文件（覆盖旧文件）
puts $csv "round,drc,wns,seconds"                                         ;# 表头：轮次/DRC 数/最差 setup/本轮耗时
set t0 [clock seconds]                                                    ;# 记整个循环的起点
for {set i 1} {$i <= 10} {incr i} {
  set ts [clock seconds]                                                  ;# 本轮起点
  route_detail -incremental true                                          ;# 只重布违例附近，保留已布好的线
  redirect rpt/drc_$i.rpt { check_routes }                                ;# 每轮单独一份，绝不覆盖
  set txt [read [set f [open rpt/drc_$i.rpt r]]]                          ;# 读回报告
  close $f
  regexp {Total number of DRCs\s*:\s*(\d+)} $txt -> n                     ;# 抠出 DRC 总数
  set w [get_attribute [get_timing_paths -delay_type max -max_paths 1] slack]   ;# 最差 setup
  set dt [expr {[clock seconds] - $ts}]                                   ;# 本轮耗时（秒）
  puts $csv "$i,$n,$w,$dt"                                                ;# 追加一行，趋势一眼可见
  puts "@@@ round $i  DRC=$n  WNS=$w  ${dt}s"                             ;# 屏幕同步打印，跑的时候就能判断
  if {$n == 0} { break }                                                  ;# 归零立刻退出，不白跑
}
close $csv                                                                ;# 必须关文件，否则最后一行不落盘
puts "total [expr {[clock seconds] - $t0}] seconds"                       ;# 总耗时，写进交接记录
```

每轮要记三样东西，缺一样你就没法做判断：

| 记什么 | 为什么 | 怎么记 |
|---|---|---|
| DRC 数 | 判断收敛还是卡住 | `check_routes` 里的 `Total number of DRCs` |
| 时序（WNS / TNS） | 优化可能在偷偷恶化时序 | `report_qor` 或一条 `get_timing_paths` |
| 本轮耗时 | 判断值不值得再跑一轮 | `clock seconds` 前后相减 |

三条使用纪律：

1. **一轮只改一件事。** 这一轮就修 DRC。别顺手换单元尺寸——那会让"增量"变成事实上的全量，还查不出新违例的来源。
2. **连续两轮数字不变就停。** 不变不是"再跑跑就好"，是结构性问题（拥塞、pin access）。加轮数只是烧机器。
3. **时序一旦持续恶化就停。** 增量重布会让局部线变长，WNS 每轮掉几十 ps 属于警告信号，不是正常波动。

## 我们实测的收敛曲线（真实数据）{#real}

万门设计（ipa_top，9390 单元，纯物理流程）第一次跑出来 6000 条 DRC。逐轮记录如下：

| 轮次 | DRC | 本轮做了什么 | 备注 |
|---|---|---|---|
| 0（`route_auto` 后） | 6000 | 全局 + 详细刚结束 | 95% 是引脚访问冲突 |
| 1 | 156 | 第一次 `route_detail` | 一步清掉 97%，靠的是"真的把线画上去" |
| 2 | 119 | 增量 | 开始变慢 |
| 3 | 72 | 增量 | |
| 4 | 58 | 增量 | |
| 5 | 47 | 增量 | |
| 6 | 25 | 增量 | |
| 7 | 17 | 增量 | |
| 8 | 12 | 增量 | 每轮降个位数，接近卡住 |
| 9 | **0** | 增量，归零 | |

耗时是量级概念，不是精确日志：首轮一小时上下，后面每轮几分钟（本轮具体值以 csv 里记的为准，换机器会差一倍以上）。**看趋势，不看绝对值。**

这张表有两种读法，都要会：

- **前段**（6000 → 156）：这是"布线"的功劳。全局布线只是草图，第一次详细布线才把线落到轨道上，所以一步降 97%。任何项目都会看到这个陡降。
- **后段**（156 → 0）：这是"磨"的功劳，每轮只降几到几十条。这一段如果**完全不动**（连续两轮一样），说明剩下的是结构性违例，磨不动了。

:::note 关键发现：6000→156 是布线的功劳，156→0 是布局的功劳
只加布线轮数，会卡在 156 下不去。真正的解法是回布局端改三个开关：

```tcl
# 作用：让布局阶段就为多引脚单元留出线通道
# 用法：回到 place 阶段重跑；这三个开关改变的是"单元怎么摆"，不是"线怎么走"
set_app_options -name place.coarse.pin_density_aware -value true   ;# 多引脚单元周围留出线通道
create_placement -effort high                                      ;# 重新做一次高质量布局
legalize_placement                                                 ;# 合法化：把单元对齐到行和轨道
refine_placement                                                   ;# 局部再挪一次，改善线长和拥塞
```

改完重跑，后续每轮都在稳定下降。**这就是"DRC 的根因在布局，不在布线"的具体含义**：布线只能"在给定空间里找解"，空间不够它不是万能的。
:::

## 什么时候必须停下来回退 {#rollback}

收敛循环最难的判断不是"再跑一轮"，是"现在该停"。三个信号，出现任何一个就停手：

| 信号 | 判据 | 说明 |
|---|---|---|
| DRC 越修越多 | 连续两轮总数上升，或出现全新的违例类型 | 你的修补在制造新冲突，局部已经饱和 |
| 时序恶化超阈值 | WNS 比基线差 100ps 以上，或 TNS 翻倍 | 修 DRC 的代价已经超过收益 |
| 耗时失控 | 单轮超过 30 分钟且降幅 < 5% | 投入产出比崩了，继续跑只是等运气 |

停下之后，回退到哪一层，看违例的分布：

| 违例特征 | 回退到 | 改什么 |
|---|---|---|
| 零散、集中在几个被改过的单元附近 | 上一轮存盘（撤销本轮） | 换一种修法，或让这几条 waiver |
| 成簇、围绕多引脚单元 | place | pin density aware、refine placement |
| 成条状、沿宏单元边界 | floorplan | 加宽通道、加 halo、调宏朝向 |
| 全芯片均匀、利用率 > 0.85 | floorplan / place | 降局部密度（最贵，要评审） |

回退也要留证据：把"哪一轮、什么信号、退到哪一层、改了什么"写进同一份 csv 的备注列。否则一周后你只会记得"当时好像退过一次"。

:::pitfall 明知在恶化还继续跑，因为"再跑一轮说不定就好了"
现象：DRC 从 12 → 15 → 19，你继续跑，跑到 40 才承认不行。
原因：每轮只多几条，感觉"快好了"；但趋势是单调上升，说明修补一直在制造新冲突。
处理：把"连续两轮上升"设成硬停止条件，写进脚本（不只是记在心里）。**判断力靠人，停止条件靠代码。**
:::

## 拥塞：布线做不下去的真正原因 {#congestion}

DRC 是"已经画错了"，拥塞是"根本画不下"。看两个数：

| 指标 | 含义 | 红线 |
|---|---|---|
| overflow | 某区域需要的 track 数 − 实际可用 track 数 | > 0 就是拥塞 |
| congestion % | 该区域 track 占用率 | > 90% 高危，> 100% 一定布不通 |

在 OptRoute 阶段，拥塞有个特殊性质：**优化会在拥塞区插 buffer，让拥塞更严重**。所以"用优化修拥塞"是反的——等于往堵死的路口再加车。

诊断顺序（照这个顺序查，别乱试）：

1. **看热点**：`reportCongestion -hotSpot` 列出 overflow 最大的区域，先看形状和位置；
2. **判断归属**：条状沿宏单元 → floorplan 通道不够；大片均匀 → placement 利用率高；小簇在多引脚单元 → pin access；
3. **试便宜的**：挪宏单元、加通道、打散多引脚单元、放开高层（第 20 课算过，层选错容量差一倍）；
4. **最后才降利用率**：从 0.7 降到 0.55，面积涨 27%、功耗跟着涨。这是最贵的修法，要写进评审记录。

:::pitfall 拥塞了就降利用率
降利用率确实能让 DRC 变好，但芯片面积变大、线变长、成本上升。

先试便宜的：挪宏单元、加通道、开 pin density aware、放开高层。四样都不行，再降利用率，并且明确记录"为什么必须付这个代价"。
:::

## 天线效应：一个容易被忽略的硬违例 {#antenna}

制造时用等离子体刻蚀金属，长金属线像天线一样收集电荷。如果这根线只连到晶体管的栅极，电荷没有泄放通路，会越积越多，最后击穿栅氧化层——永久损坏。

规则：**接在栅上的金属面积 ÷ 栅氧化层面积** 不能超过工艺给的比值（典型 300:1 到 500:1，具体看工艺手册）。

OptRoute 阶段要特别记住一点：**优化会改变栅的连接**。换单元尺寸、插 buffer、重布，都可能让原本达标的天线比变差。所以天线不是"布线时查一次"就完了，优化之后必须复查。

```tcl
# 作用：优化之后复查天线，并对违例 net 做局部修复
# 用法：每次 route_opt / optDesign -postRoute 之后都要跑一遍
verifyProcessAntenna                       ;# 按工艺规则算 antenna ratio，列出违例
setNanoRouteMode -drouteFixAntenna true    ;# 允许局部重布时用跳层方式修
ecoRoute                                   ;# 只动违例 net，不做全芯片重布
```

三种修法（跳层、改布线、插二极管）的原理和代价在第 20 课讲过，这里只说 OptRoute 阶段的特殊之处：**这一阶段你是在别人的成果上动手**。第 20 课修天线是在布线过程中顺手做，跳层空间当时还够；到了 OptRoute，版图已经布满，跳层要挤过已经占用的轨道，很容易撞出新的 spacing 或 via 违例。

所以顺序要更保守：先试改布线（在违例 net 附近局部重布，不动其他线），再试跳层（要确认目标层还有空轨道），插二极管放最后（它要改网表，意味着 LVS 要重跑）。每修一批就复查一次 DRC，别攒着一起看。

算一次天线比，就知道为什么跳层有效。假设某根 net 接在栅上，栅面积 0.4µm²，它在中层走了 200µm、线宽 1µm，同层金属面积 200µm²：

`antenna ratio = 200 ÷ 0.4 = 500:1`

如果工艺阈值是 300:1，这条就违例。跳层后把 200µm 拆成两段各 100µm、分别走两层，每层对栅的贡献变成 100µm²，比值降到 250:1，达标。

**注意拆法**：必须从靠近栅的那一段开始"垫高"，也就是说，从栅往上数的第一段要短。拆反了（长段留在下层），比值一点没降——这是新手最常犯的错。

:::term Crosstalk | 串扰
相邻两根线之间的耦合电容把信号"灌"到邻居身上。受害者线的延迟可能变快（信号被推着走）也可能变慢（被拖住），前者伤 hold，后者伤 setup。

布线越密、并行走线越长，串扰越严重。签核时要用带串扰的时序分析（SI 分析），不能只看无串扰的结果。
:::

:::term Antenna Effect | 天线效应
制造过程中，接在晶体管栅极上的长金属线像天线一样收集等离子体电荷，电荷无处泄放就把栅氧化层击穿。

判断依据是"接在栅上的金属面积 ÷ 栅面积"，超过工艺给的比值就违例。修法有三种：跳层、改布线、插二极管。
:::

## 布线后必须回签的两个数 {#signoff}

布完、优化完，不是结束，要重新出报告，而且要和**布线前的基线**对比：

```tcl
# 作用：布线后的回签报告，三份一起出
# 用法：每次优化动作之后执行；重定向到 rpt/ 存证，别只看屏幕
report_timing -delay_type max -max_paths 10 > rpt/postroute_setup.rpt   ;# setup：线延迟有没有拖崩
report_timing -delay_type min -max_paths 10 > rpt/postroute_hold.rpt    ;# hold：有没有变差
check_routes > rpt/postroute_drc.rpt                                    ;# DRC 是否为 0
```

| 报告 | 看什么 | 通过标准 |
|---|---|---|
| setup | WNS / TNS | 与布线前基线比，恶化不超过 10%；WNS ≥ 0 |
| hold | 最差 slack、违例条数 | 全部 ≥ 0，或每条都有书面 waiver |
| DRC | 总数 + 分类 | 0（或只剩已批准的 waiver） |

有一条纪律容易被忽略：**报告不能复用**。每次优化动作之后都要重新出一份，文件名带上时间和步骤（`postroute_setup_r3.rpt`），因为优化一插 buffer，上一份报告里的每一条路径都不再存在。拿着旧报告做判断，等于看别人的体检单给自己开药。

:::note 课程环境的两组对照数据
同一个万门设计，两种做法差得很远：

- 时序驱动流程（12026 单元）：`route_auto` 首轮 DRC 就是 **0**，`route_opt` 之后保持 0，10 轮增量全为 0，setup WNS +1.00ns；
- 纯物理流程（9390 单元）：首轮 6000，磨 9 轮才归零。

**差别不在布线参数，在于前面有没有做时序驱动的布局和引脚密度感知。** 这也是本课反复强调"回退到 place"的原因：花在布局上的两小时，能省掉布线阶段的两天。
:::

## 工作中怎么用：OptRoute 在项目里的位置 {#in-work}

**谁做**：PR 工程师。大设计里通常由"布线负责人"统一跑收敛循环，因为每一轮要几十分钟，多人同时改同一个数据库会互相覆盖。

**输入是什么**：布线后的数据库、第 20 课出的三份报告（DRC/时序/天线）、布局阶段的拥塞热图。

**输出交给谁**：DRC 归零且时序过线之后，交给 ChipFinish（第 23 课）。同时把 `optroute_rounds.csv` 一起交出去——它证明"这 0 条 DRC 是怎么来的"，也是下次遇到同类问题时最快的参考。

**评审看什么**：DRC 的收敛曲线（不是终值）、WNS/TNS 与布线基线的差、有没有 waiver 以及理由。只报终值不报曲线的评审会被打回，因为终值可能是靠 waiver 凑出来的。

**做错会怎样**：最常见的错误是在一个已经拥塞的版图上硬磨两天，每天跑十几轮，DRC 从 6000 磨到 300 就再也不动。这两天本来是布局端两小时能省掉的。**判断"该回退"比"再跑一轮"值钱得多。**

:::lab 动手：从三份连续报告判断该不该再加一轮
**任务**：给定两组连续报告的数字，判断下一步动作，并说出依据。

**情形 A**：

```text
iteration  DRC   opens   short

```

**情形 B**：

```text

8          25    0       3
9          25    0       3
```

**步骤**：
1. 判断 A 是否还在收敛、B 是否卡住，各自给出理由。
2. 对 B 给出你的下一步：继续加轮数、回 place、还是回 floorplan？依据是什么？
3. 在课程环境里读自己的报告，把这两个情形对应到真实数字上：

```bash
# 作用：读自己的 DRC 报告，看轮次趋势和有没有短路
```

:::quiz
为什么 `route_auto` 完成后还有几千条 DRC？|它的成功标准是"每条 net 都有路径"，不是"每条 net 都合法"。大量违例来自引脚访问冲突等局部资源竞争，要另外数、另外修。
五类 DRC 分别是什么？|short（短路）、open（开路）、spacing（间距）、width/notch（线宽/缺口）、via（通孔包边与 cut 数）。
怎么判断一批 DRC 是布线留下的还是优化引入的？|做差集：每个优化动作前后各存一份报告，新增的那些零散分布在被改过的单元附近，就是优化引入的；从第一份报告就在、成簇分布的，是布线/布局留下的。
DRC 还在几千条时能跑 `route_opt` 吗？|不建议。脏版图上做优化会同时搅乱时序和布线，还会在拥塞区插更多单元。正确顺序是先增量磨到 100 以内，再优化，最后再磨到 0。
连续三轮 DRC 数字完全一样说明什么？|不是随机收敛问题，而是结构性资源不足（拥塞或 pin access）。继续加轮数无效，要回 floorplan/place 改空间。
出现哪三个信号就必须停下来回退？|DRC 连续两轮上升或出现新类型；WNS 比基线差 100ps 以上或 TNS 翻倍；单轮超 30 分钟且降幅小于 5%。
天线违例的三种修法，优先哪个？|跳层、改布线、插二极管。优先跳层，因为它不动网表、不加器件；插二极管要改网表、加漏电，放最后。
为什么优化之后还要复查天线？|优化会换单元、插 buffer、重布线，改变了"接在栅上的金属面积"，原本达标的比值可能变差。天线不是查一次就完事。
:::
