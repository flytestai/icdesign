## 开工前：让同事能复跑你的 Run {#prepare}

:::fig innovus-practice-b.svg | 原创教学示意图 · 后端项目的三个交接点
:::

:::note 资料来源
本讲参考钉钉目录第 05 项的主题安排，正文和练习为原创教学内容，不是钉钉原文、截图或项目案例的转载。
:::

先冻结顶层网表、技术与单元物理库、时序库、时序约束，以及预定的模式与工艺角。运行清单还要记录 Innovus 版本、入口脚本版本、运行目录、日志位置和输入校验值。输入目录不要一边跑一边覆盖，否则重跑时即使脚本没变，也未必使用同一套库。详见 [项目环境](/lesson/03-04-project-env/)、[工具启动](/lesson/03-02-innovus-start/)和[初始化检查](/lesson/03-03-innovus-init/)。

工具启动成功不等于导入正确。用日志核对顶层名、未解析引用、被忽略的约束，并在数据库中确认预期模式和工艺角确实启用。没有约束的路径不能当成时序通过。初始交接不以 GUI 截图为准，应让接手人能恢复数据库、查看摘要，并找到产生它的原始输入。

## Floorplan 到 Place：检查能否摆得下、接得通 {#floorplan-to-place}

**Floorplan** 交付含 Die、Core、宏、端口及布局约束的版本。除了看重叠和朝向，还要看剩余未分配的端口、宏外禁放区与摆放行，以及总线从哪一边进入通道。环境相同的两次布局，即使宏总面积不变，窄通道和零散摆放行也可能让局部资源不足。见 [Floorplan](/lesson/03-05-floorplan/)。

**PowerPlan** 交付有电源网络和供电结构的检查点，以及连接和几何检查记录。电源线看起来完整，不代表每个电源域、宏电源脚都接到了对应网络；例如相邻的两块 Memory 可能属于不同域，不能因几何相近而推断应接同一电源。见 [PowerPlan](/lesson/03-06-powerplan/)。

**Place** 交付标准单元布局数据库和合法性、时序及拥塞报告。报告中先分清「没摆上」「摆得不合法」和「能摆但可能走不通」三类问题，再决定回退。只给平均利用率，无法说明需要穿过宏通道的网络能否绕出。见 [Place](/lesson/03-07-place/)。

## CTS 到 ECO：记录每轮到底改了什么 {#cts-to-eco}

**CTS** 保存建树后的数据库并核对时钟覆盖、偏斜、插入延迟和相关时序。复核时钟覆盖时，要拿约束定义的端点集合与实际建树记录对照；有意不纳入的对象要有解释。**Route** 保存已布线版本并检查开路、短路和布线规则。**OptRoute** 基于布线后寄生信息重新评估时序与电气约束，比较优化前后变化。预布线和布线后的数值可用于了解阶段差异，不能视为一组同口径 A/B 对照。

**ECO** 交付修复后的实现、变更记录和回归报告；若改动涉及功能逻辑，还应按项目要求核对等价性或验证结果。时钟、供电或宏位置若因修复而改变，应重新执行受影响的检查，不能借用旧报告。阶段工具报告不替代最终签核。见 [CTS](/lesson/03-08-cts/)、[Route](/lesson/03-09-route/)、[OptRoute](/lesson/03-10-optroute/)和 [ECO](/lesson/03-11-eco/)。

## 给检查点配上可追溯的验收记录 {#practice-step-04}

每次交接都写清「父版本、变更、检查、结论」，让接手人知道报告是否与数据库配套。同一阶段的不同试跑各用独立目录；不要让后一次生成的报告覆盖原基线。检查状态至少区分通过、失败、未跑和获准例外；例外要写明受影响对象、判断依据及负责人，不要把未跑当成通过。

下面是教学记录格式，不是 Innovus 原生命令、文件格式或实际输出。这里的功能模式、慢角和路径组仅为说明如何对齐报告口径。

```text
case           D0            P0            R0
parent         INIT_0        D0            CTS_0
stage          floorplan     power         route
scenario       --            --            FUNC/SS, REG2REG
required       macro/pin     PG conn/geom  open/short/DRC/setup
result         pass          pass          fail: 3 opens
evidence       floor.chk     power.chk     route.rpt, setup.rpt
```

从日志找到验收记录还不够：查看报告标题中的阶段、数据库版本或生成时间，再核对场景与筛选条件。只有确认报告来自正确版本，才值得分析问题本身。比如把基线的早期拥塞图拼接到修改后的布线报告上，看似能解释开路，实际可能指出已经不存在的热点。

第一次接手时，先恢复一个检查点做只读抽验：看固定宏坐标、报告所列的关键场景，以及输出目录里的对象名能否在数据库查到。若连恢复都需要原运行者机器上的临时环境，就先修交接清单。阶段之间可以保留轻量的索引，详细报告仍放在生成它的分支中；复制一份改名容易弄丢生成来源。

## 实训起点：把三条开路按原因分组 {#practice-step-05}

练习使用纸面合成案例，基础设置是同一网表、分析视图和布线配置。路线图上，两组跨宏侧的总线位经过同一个窄通道，第三条网络的开路点在远离通道的顶边。R0 的 Route 正常结束，但连接性检查报三条开路。先根据网络名找断点坐标、所在层和相邻可达金属，不要只看一条汇总数字。

```text
教学位置示意（不按比例）
+-- 顶边 VIN[0]：端口接入开路 ------------------+
|                                                  |
|  [ MEM_A ] | 12 um | [ MEM_B ]                  |
|             DATA[2]、DATA[3]：通道内开路         |
+--------------------------------------------------+
```

先按断点位置对照宏禁布区、供电占轨和引脚附近可接入区。练习已知这两条 DATA 网络的断点在同一层同一侧，局部报告还显示该方向可用轨道不足。这支持通道假设，但并不能解释 VIN。对 VIN 单独核对端口坐标和接入标记；若标记落在非接入区，应修正端口定义并独立回归，不能把它算成扩通道的功劳。

## 实训执行：先验证一项改动，再处理另一类问题 {#practice-step-06}

从 D0 分支只调整 MEM_B 的横向位置，把通道从 12 µm 扩到 20 µm，不改约束、宏朝向和端口配置。按父子关系重新跑 PowerPlan、Place、CTS 和 Route：电源连接与几何先通过，才值得看后续结果。对比来自相同布线阶段、场景和统计范围的报告。如果只恢复 R0 直接移动宏，原供电、布局和时钟结果已不再对应当前几何，无法用来验收。

```text
合成回归                     R0 基线     R1 扩通道   R2 修端口后重跑
宏间距 (um)                     12           20             20
DATA[2] / DATA[3] 开路            2            0              0
VIN[0] 开路                       1            1              0
相邻窗口布线溢出 (轨道数)         7            0              0
短路 / DRC                         0 / 0       0 / 0          0 / 0
FUNC/SS 路径组 WNS (ns)         -0.08        -0.07          -0.07
```

R1 的两条开路和相邻窗口溢出同时消失，通道假设得到支持；第三条仍需按端口问题回退，得到 R2。即使 R2 连接检查通过，功能慢角最差裕量仍为负，本例不能宣称时序签核完成。保留该违例的路径和场景，交给下一轮有明确目标的优化。

## 失败与回滚：重新接起证据链 {#practice-step-07}

- 如果扩通道后供电连接失败，停止后续阶段，回到该分支 Floorplan 核对宏供电脚和电源接入；保留失败日志。
- 如果开路数下降但邻区新增短路或规则违例，不合入 R1；恢复基线，从同一父版本改一个变量重试。
- 如果改动没有改善局部指标，复核轨道统计范围及阻挡来源；不要连续挪宏后再用最后一张图倒推原因。
- 回归包至少留输入清单、变更前后数据库、同设置的开路与拥塞报告、受影响阶段结果和仍未通过的事项。

## 练习：验收失败后回到哪一站？ {#exercise}

Route 有三条开路，其中两条经过 Floorplan 留下的窄通道。不能仅凭数量直接跳到 ECO；先核对断点、网络和附近的布局及电源资源。若需要调整宏或扩通道，就回到 Floorplan，重新验证供电、布局、时钟和布线。把第三条当成独立假设处理，才知道每次改动究竟修了什么。

:::quiz
工具导入结束后为什么仍要核对分析视图？| 导入可完成但预期场景未启用或约束被忽略，后续时序结果会缺少应检查的路径。
R1 消除了 DATA 开路但 VIN 仍开路，下一步是什么？| 保留 R1 及对照报告，对 VIN 单独核对端口接入并回到受影响阶段，不把它当成同一根因。
R2 开路、短路和 DRC 都为零，能否宣布最终通过？| 不能，本例 WNS 仍为负，且最终签核还须使用项目规定的流程和规则。
:::
