## 为什么没有 CTS 芯片就跑不起来 {#why}

:::goal 学完这一课，你能判断一棵时钟树建得好不好：读出 skew、insertion delay、transition 三个数，指出下一步该先修什么。
:::

时钟源只有一个，触发器有几万个。最省事的做法是从源直接拉一根线，串到每个触发器上。

这么做会出两个问题：

**第一，到达时间差得离谱。** 靠近源的触发器可能 50ps 就收到时钟，最远那个要 800ps。这个差值叫 **skew（偏斜）**。skew 一大，两个触发器之间那条路径的可用时间就被吃掉一大块——时序直接崩。

**第二，一根线驱动不了几万个负载。** 时钟波形会被"拖垮"：上升沿从陡直的台阶变成慢慢爬的斜坡，这叫 **transition（转换时间）** 变差。波形一烂，触发器可能在中间电平上采样，芯片出现亚稳态——就是那种"跑一天偶尔错一次"的偶发故障。

所以必须有一步专门干这件事：**插缓冲器（buffer / inverter），把一根线变成一棵树，让每个触发器收到的时钟尽量一样**。这一步就是 CTS（Clock Tree Synthesis，时钟树综合）。

:::term Clock Tree Synthesis (CTS) | 时钟树综合
在时钟网络上按层级插入缓冲器或反相器，形成树状结构，使时钟到达每个触发器的延迟尽量一致、波形质量达标。它是布局（placement）之后、布线（route）之前的一步。
:::

:::term Skew | 偏斜
同一个时钟到达不同触发器的**时间差**。全局 skew 指整棵树的最大差值；局部 skew 指相邻两个触发器之间的差值。skew 是 CTS 的第一考核指标。
:::

:::term Insertion Delay | 插入延迟
从时钟源（clock root）到某个触发器时钟端的**总延迟**。延迟本身不可怕，可怕的是不同叶子之间差太多；另外延迟太大意味着时钟要在片内绕一大圈，功耗和 OCV 影响都会变差。
:::

:::scene 周一早上，CTS 报告全是红的
你接手一个 40nm 项目，placement 刚做完，leader 说"这周把 CTS 收掉"。你在 `pnr/` 下跑完 `ccopt_design`，打开 `report_clock_timing -type skew`，看到全局 skew 380ps、最长 insertion delay 2.1ns、还有 1200 个时钟引脚 transition 超标。周五要交 CTS review，你得先搞清楚：这 380ps 是哪一段树贡献的、2.1ns 是深还是浅、1200 个 transition 违例该从哪下手。
:::

## 时钟树的三个指标，先记住再看命令 {#metrics}

| 指标 | 含义 | 典型目标（40nm 量级） | 变差的后果 |
|---|---|---|---|
| Skew | 叶子之间到达时间差 | 全局 < 100~150ps，局部 < 30~50ps | setup/hold 预算被吃掉 |
| Insertion delay | 源到叶子的总延迟 | 越短越好，通常 0.8~1.5ns | 功耗高、OCV 悲观度变大 |
| Transition（slew） | 波形陡不陡 | 时钟网络 < 100~150ps | 亚稳态、漏电增加、EM 变差 |

这三个指标是**互相拉扯**的：想 skew 小，就多插几级 buffer 把树做平衡，但级数一多 insertion delay 就变长、功耗上去；想 delay 短，树就做得浅，skew 又压不住。

transition 差到极端是什么后果，看这张图：

:::fig wave-pulse | 最小脉宽检查：时钟经过太多缓冲器后，高电平会被"削窄"；窄到触发器锁不住时，芯片会随机出错。重点看脉宽被一级一级削短的过程——这就是上表里 transition 一行的后果写着"亚稳态"的原因，这类问题仿真几乎看不出来，只能靠 STA 的脉宽检查拦住。
:::

从这张图里要看出什么：transition 不是"慢一点"，是"波形还完不完整"的问题——所以 target_max_trans 是硬指标，不是可以拿来交换的优化目标。

:::note 一个常被搞混的点
skew 小 ≠ 时序好。CTS 的目标不是"skew = 0"，而是"在满足 transition 和功耗的前提下，把时序做到能收敛"。有些路径故意留一点 skew 反而更好——这就是后面 OptCts 课里的 useful skew。
:::

## 树长什么样 {#structure}

```
                    clk 源（root）
                         │
              ┌──────────┴──────────┐
            buf                   buf          ← 第 1 级（驱动主干）
          ┌──┴──┐               ┌──┴──┐
        buf   buf             buf   buf        ← 第 2 级
        ┌┴┐   ┌┴┐             ┌┴┐   ┌┴┐
       FF FF FF FF           FF FF FF FF       ← 叶子（触发器时钟端）
```

几个必须知道的细节：

1. **每一级 buffer 的扇出有限**（一般 8~16），所以树是"一层层扇出去"的，叶子数量决定树的深度。几万个叶子通常是 5~7 级。
2. **叶子不一定是触发器**。clock gating cell（门控时钟单元）、macro 的时钟引脚、ICG 的 CK 端，都在树上，都要平衡。
3. **树不是唯一形态**。H-tree、mesh（网格）用于高性能芯片的全局时钟，代价是占用大量布线资源；普通项目用常规树就够了。
4. **时钟分主次**。主时钟（root）到各个子时钟（generated clock）要分别建树，跨时钟域的两棵树之间不做平衡。

建好的树在版图上长这个样子：

:::fig innovus-cts | 时钟树综合后的版图：绿色线条是从时钟源（树根）一路分叉到每个触发器的时钟网络，绿点是工具自动插入的缓冲器。重点看分叉是否均匀、有没有某条分支明显更长——那条分支就是 skew 和绕线问题的来源。
:::

从这张图里要看出什么：时钟树不是示意图，是版图上真实的一张网——判断树好不好，先看这张网的分叉形状，再去核对报告里的数字。

:::term NDR (Non-Default Rule) | 非默认规则
给时钟网络单独指定的线宽和间距规则，比如"双倍线宽 + 双倍间距"。线宽加倍降低电阻（延迟和 EM 都变好），间距加倍降低耦合电容（串扰变小）。
:::

:::term Clock Gating | 门控时钟
用一个使能信号把某块逻辑的时钟关掉，省掉这部分动态功耗的单元。它的输出也是时钟，必须一起进 CTS，而且使能端有时序检查（clock gating check）。
:::

## CTS 到底做哪五步 {#five-steps}

### 第一步：确认时钟定义是对的

CTS 只处理"它看得见的时钟"。如果 SDC 里时钟没定义、名字写错、或者信号传不进来，那部分触发器就变成 **unconstrained（未约束）**——它们不在树上，等 CTS 做完你会在报告里看到一大片"no clock"。

开工前先查：

```tcl
# 作用：确认工具认到的时钟有哪些、各自定义在哪个端口上
# 用法：Innovus 里 source 完 SDC 之后执行；输出应为项目里的全部时钟
report_clocks                        # 列出所有时钟：名字、周期、源端口
check_timing -include unconstrained  # 找出"没有时钟驱动"的时序单元
```

`check_timing` 输出里的 `unconstrained_endpoints` 应该是 0。不是 0 就先修约束，别急着建树——树一旦按错的时钟建完，后面全要重来。

### 第二步：设 CTS 约束

CTS 需要三类约束：**目标（skew / latency）、规则（NDR / transition）、例外（哪些不管）**。

```tcl
# 作用：Innovus 里设置 CTS 目标和规则
# 用法：在 ccopt_design 之前执行，通常单独写成 cts.tcl
set_ccopt_property target_skew        0.08   ;# 全局 skew 目标 80ps，约周期的 3%
set_ccopt_property target_max_trans   0.12   ;# 时钟网络最大 transition 120ps
set_ccopt_property buffer_cells  {BUFX2 BUFX4 BUFX8}   ;# 允许用的缓冲器清单
set_ccopt_property inverter_cells {INVX2 INVX4}        ;# 允许用的反相器清单
set_ccopt_property use_inverters  true    ;# 允许成对反相器，比 buffer 省面积

# 给时钟网络加 NDR：双倍线宽 + 双倍间距
add_ndr -name cts_2w2s -width_multiplier 2 -spacing_multiplier 2
set_ccopt_property -net_type trunk ndr cts_2w2s   ;# 主干用 2w2s
set_ccopt_property -net_type leaf  ndr cts_2w2s   ;# 叶子也用
```

每行都在说什么：

- `target_skew` 不是越小越好。设 0（追求完美平衡）会让工具插一堆 buffer，功耗和面积暴涨，收益却很小。按周期的 5%~10% 给，比较现实。
- `buffer_cells` 要**限定清单**。不限定，工具会挑一堆奇形怪状的单元，后面 DRC 和 EM 都难收。
- `use_inverters true` 很实用：两级反相器 = 一个 buffer，但面积更小、驱动更强，时钟树上大量使用。
- NDR 加在 **trunk（主干）和 leaf（叶子）** 上。主干电流大、易受串扰，必须加；叶子线短，加了也没什么坏处。

### 第三步：建树

```tcl
# 作用：真正执行时钟树综合
# 用法：CTS 阶段单独跑，不要和 placement 揉成一步
ccopt_design -cts          ;# Innovus：一次建完
clock_opt -only_cts        ;# ICC2：只做 CTS（对照用）
```

跑完工具会打印树的规模，比如：

```
Clock tree summary: 1 root, 6421 sinks, 1834 buffers, 6 levels, max latency 1.42ns
```

这句话要会读：**1 个根、6421 个叶子、插了 1834 个缓冲器、6 级、最长延迟 1.42ns**。缓冲器数 / 叶子数 ≈ 0.28，这个比例正常；如果接近 1，说明工具在乱插，多半是约束写得太紧，或者库里驱动很弱的单元被反复用了。

### 第四步：看报告

CTS 之后不看报告就往下走，是最常见的翻车方式。

```tcl
# 作用：CTS 后的四份必看报告
# 用法：跑完 ccopt_design 立刻执行，全部重定向到 rpt/ 存证
report_clock_tree -summary > rpt/cts_tree.rpt      ;# ① 树的结构：级数、buffer 数、latency
report_clock_timing -type skew > rpt/cts_skew.rpt  ;# ② skew：全局/局部最差，以及是哪两个叶子
report_timing -max_paths 20 > rpt/cts_setup.rpt    ;# ③ setup：建树后变成什么样
report_timing -delay_type min -max_paths 20 > rpt/cts_hold.rpt  ;# ④ hold 提前看，CTS 后必变
```

| 报告 | 看什么 | 看到什么算过关 |
|---|---|---|
| `cts_tree.rpt` | 级数、buffer 数、max/min latency | 级数 5~7；buffer/leaf < 0.4 |
| `cts_skew.rpt` | 全局 skew、局部 skew、最差的那对叶子 | 全局不超过目标值 1.5 倍 |
| `cts_setup.rpt` | WNS、违例条数 | 与 place 后相比恶化不超过 20% |
| `cts_hold.rpt` | hold 最差 slack | 有负值正常，但要记基线，交给 OptCts 修 |

### 第五步：修 transition 和 DRV，再交给 OptCts

建树只看结构，**电气质量**要单独修。CTS 之后通常有一批 transition 超标、max cap 超标、max fanout 超标的引脚。

```tcl
# 作用：修时钟网络的电气违例（先不碰时序）
# 用法：CTS 之后、optDesign -postCTS 之前
setOptMode -fixFanoutLoad true   ;# 允许为了修 fanout 而插 buffer
optDesign -drv                   ;# 只修 DRV：transition / cap / fanout
```

这里有个顺序纪律：**DRV 先修，时序后修**。原因很直接——transition 不达标时，工具算出来的延迟本身就是错的，你按错的延迟去修时序，等于在错的地基上盖楼。

:::pitfall CTS 之后 hold 全崩了，是不是树建坏了
不一定。多数情况是正常的：CTS 之前时钟是"理想时钟"（ideal，零延迟），工具不知道真实 skew；CTS 之后换成传播时钟（propagated），时钟路径有了真实延迟，原来藏着的 hold 违例全暴露出来了。

判断方法：看 `report_timing -delay_type min` 里违例的**起点和终点是不是同一个时钟树分支**。如果是相邻叶子之间的短路径违例，属于正常"暴露"，交给 OptCts 修；如果是跨越大半个芯片的路径 hold 违例，那才是树或约束的问题。
:::

## 手算一次：skew 目标该给多少 {#hand-calc}

假设时钟周期 2.5ns（400MHz），一条普通路径逻辑延迟 1.6ns，触发器 setup 时间 0.15ns，时钟不确定性（uncertainty）0.1ns。

`slack = 周期 − 逻辑延迟 − setup − uncertainty − skew`

- skew = 0.05ns：`2.5 − 1.6 − 0.15 − 0.1 − 0.05 = 0.6ns` → 有余量
- skew = 0.40ns：`2.5 − 1.6 − 0.15 − 0.1 − 0.40 = 0.25ns` → 勉强
- skew = 0.60ns：`2.5 − 1.6 − 0.15 − 0.1 − 0.60 = 0.05ns` → 一点 OCV 波动就违例

结论：这条设计里 skew 目标给 100~150ps 合理，超过 300ps 就开始吃时序余量。反过来说——**skew 目标不是拍脑袋的数字，而是从时序预算里分出来的**。

这笔账背后的物理图像，就是 skew 在波形上的样子：

:::fig wave-skew | skew 的形成：同一个时钟源，因为走线长短不同，到达两个触发器的时间不一样。重点看 B 比 A 晚的那一段——CTS 的全部工作，就是把这段差压进目标值；压不动的那部分，就是时序预算里要为它预留的账。
:::

从这张图里要看出什么：skew 是"到达时间差"，不是"延迟大"——只能靠把两条路径做得一样长来压，这也解释了为什么绕开宏单元的分支最难平衡。

## 常见翻车：CTS 阶段的七个坑 {#pitfalls}

:::pitfall 时钟没传到某些触发器
现象：`report_clock_tree` 的 sink 数比触发器总数少，`check_timing` 报 `unconstrained_endpoints` 不为 0。
原因：时钟经过了一个"工具不认为是时钟"的单元（比如某个自定义 buffer 没在库里标成 clock cell），传播断了。
处理：把这类单元加入 CTS 可用的时钟单元清单，或者用工具属性明确告诉它"这也是时钟网络"。
:::

:::pitfall generated clock 忘记定义
现象：分频出来的时钟那一片，skew 报告为空或异常大。
原因：SDC 里只有主时钟，分频器输出没有写 `create_generated_clock`。
处理：补 generated clock，并确认它的 source 指向分频器的输入引脚，不是输出。
:::

:::pitfall clock gating check 报一堆违例
现象：`report_timing` 里 ICG 的 enable 端大量 setup 违例。
原因：门控单元的使能必须比时钟早到，否则会切掉半个时钟脉冲。这个检查叫 clock gating check；CTS 后时钟有了真实延迟，检查才生效。
处理：先确认 enable 来自哪个触发器；如果是组合逻辑直接驱动，通常要加一级触发器或用 skew 调。
:::

:::pitfall 为了压 skew 把 buffer 插爆
现象：buffer/leaf 比例 > 0.8，功耗涨 15%，skew 只改善 10ps。
原因：`target_skew` 设得太小（比如 20ps），工具开始疯狂插 buffer 追求平衡。
处理：把目标放宽到周期 5%~10%，或者改用 useful skew 思路（见 OptCts 课）。
:::

:::pitfall leaf 用了驱动太弱的单元
现象：leaf 网络 transition 大量超标，怎么修都不干净。
原因：叶子 buffer 清单里混进了 X1 这类小驱动单元，带不动后面十几个触发器。
处理：leaf 只允许 X4 以上，用 `leaf_cells` 明确限定。
:::

:::pitfall 屏蔽（skip）写错，把要平衡的单元排除了
现象：某个 macro 的时钟引脚 skew 特别大，其他都正常。
原因：早期为了省事把 macro 的 CK 排除在平衡之外。
处理：`report_clock_tree -skipped` 查被排除的引脚清单，只保留真正不需要平衡的（比如测试逻辑）。
:::

:::pitfall CTS 完直接跑 route
现象：布线后 DRC 里一堆时钟网络的 spacing 违例，或者 EM 违例。
原因：NDR 没加，或者加了但没作用到 clock net 上（属性写在了错的 net type 上）。
处理：确认 NDR 生效范围，布线前再做一次时钟网络的 DRC 检查。
:::

## 工作中怎么用：CTS 在项目里的位置 {#in-work}

**谁做**：数字后端工程师（PR 工程师）本人。CTS 是 PR 流程里技术含量最高的一步，通常由工作两年以上的人做，或者由资深工程师 review。

**输入是什么**：placement 之后的数据库、SDC（含时钟定义）、库文件（含 CTS 可用的 buffer / inverter 清单）、时钟网络的 NDR 规则。

**输出交给谁**：交给 OptCts 继续优化，再进 route。同时要给 STA 工程师一份 CTS 报告，让他知道时钟的真实延迟和 skew——签核时 STA 用的就是这个数。

**评审会看三个数**：skew 是否达标、insertion delay 是否合理、buffer 数量与功耗增量是否可接受。任一超预期，都要回去改约束。

**做错了会怎样**：CTS 是"上游错误放大"最厉害的一步。这里 skew 多 100ps，route 阶段要花两三天插 buffer 去补；这里 buffer 多插 30%，芯片功耗直接超标。所以 CTS 阶段宁可在报告上多花两小时，也不要急着往下走。

:::lab 动手：把一棵树的三个指标读出来
**任务**：用课程环境里的 CTS 报告（`~/backend_lab/soc/pnr/reports/` 下有 `cts_tree.rpt`、`cts_skew.rpt`、`cts_hold.rpt`），回答四个问题。

**步骤**：
1. `head -20 cts_tree.rpt` 看树摘要，记下 sink 数、buffer 数、级数、max latency。
2. `grep -c "slack" cts_hold.rpt` 数 hold 违例条数。
3. `sort -k3 -n cts_skew.rpt | head -3` 找出 skew 最差的三对叶子。
4. `awk '{print $NF}' cts_tree.rpt | sort | uniq -c` 看 leaf 上用了哪些单元。

**过关标准**：能说出"这棵树深不深（级数/叶子数）、skew 最差在哪一级、hold 违例是不是集中在同一分支"，并指出下一步先修什么。
:::

skew 和 insertion delay 的区别是什么？|skew 是不同叶子之间的时间差（相对量），insertion delay 是源到某个叶子的总延迟（绝对量）。
为什么 NDR 要加在时钟网络上？|线宽加倍降电阻（延迟和 EM 改善），间距加倍降耦合电容（串扰改善），时钟是翻转最频繁的网络，收益最大。
CTS 之后 hold 违例突然变多，最先要确认什么？|确认是不是从 ideal clock 切到 propagated clock 导致违例"暴露"，再看违例是否集中在相邻叶子之间。
target_skew 是不是设得越小越好？|不是。过小会让工具疯狂插 buffer，功耗面积上涨、收益递减；一般按周期的 5%~10% 给。
CTS 之后先修 DRV 还是先修时序？|先修 DRV（transition/cap/fanout）。transition 不准时延迟计算本身就是错的，修时序没有意义。
怎么判断一部分触发器没进时钟树？|比较 report_clock_tree 的 sink 数与触发器总数，并用 check_timing 看 unconstrained_endpoints 是否为 0。
:::
