## 为什么要用 PT 再算一遍 {#why}

:::goal 学完这一课，你能独立跑完一次 PrimeTime 签核：读进网表、库、SPEF、SDC，把 `check_timing` 清干净，读懂最差路径的每一列，说清 WNS 为什么是负的，并把违例整理成 PR 能执行的 ECO 清单。
:::

先说一个类比。

装修队自己验收自己的活，你信吗？他们当然会说"平整度没问题"——因为他们量的时候用的是自己的靠尺，而且量完还要接着干活，不会主动给自己找麻烦。所以大工程都有第三方监理：监理不砌墙、不刷漆，只拿仪器量，量完签字。

PrimeTime 就是时序上的"第三方监理"。它不优化设计、不改网表、不插缓冲器，只做一件事：**拿一版冻结的输入，算出所有路径的 slack，然后出报告**。

:::term Signoff | 签核
项目流片（tapeout）前必须完成的一系列"签字确认"动作。时序签核指用独立工具、固定输入、固定悲观度设置，证明设计在所有指定工况下都满足时序。签核报告是要归档的，出问题要能追溯。
:::

### PR 工具里的时序引擎在干什么

布局布线工具（Innovus、ICC2）内部确实有时序引擎，而且算得不差。但它算出来的数，性质完全不同：

| 维度 | PR 工具内建 STA | PrimeTime 签核 |
|---|---|---|
| 目的 | 为优化服务：告诉优化器"往哪改" | 为判断服务：告诉项目"能不能流片" |
| 输入 | 数据库里的当前状态（可能还在变） | 冻结的 netlist + SPEF + SDC + 库 |
| 寄生参数 | 早期是估算 RC 或 trial route | 必须读真实 SPEF（每个 corner 各一份） |
| 时钟 | 常常先用 ideal clock 跑，快但乐观 | propagated clock，走真实时钟树 |
| OCV | 默认可能只开一部分 | 按签核约定全套打开（derate / AOCV / POCV） |
| 约束 | 为了好优化，可能加 margin 或临时放宽 | 冻结版 SDC，改动要留记录 |
| 可复现性 | 依赖数据库状态，别人重跑未必一样 | 同样四件输入，任何人跑出同一个数 |

一句话总结：**PR 里的时序是"施工过程中的估算"，PT 里的时序是"竣工验收的测量"**。施工队自己量出来的 3 毫米误差，监理用塞尺量可能是 5 毫米——不是谁撒谎，是量法不一样。

### 三个必须换工具的理由

**第一，立场冲突。** PR 引擎的 KPI 是把设计优化到收敛。它一边算一边改，算出来的数会随优化动作漂移。你没法用一个"正在被修改的对象"的报告去证明这个对象合格。

**第二，模型精度不同。** PR 为了跑得快，会在很多地方简化：串扰用简化模型、时钟路径的 OCV 只算一部分、rc corner 只算当前场景。PT 的延迟计算是签核级实现，尤其在串扰（SI）和 OCV 上更严格。

**第三，责任要可追溯。** 签核报告要归档、要能被第三方复核。复核的人不会去打开你的 PR 数据库（版本、license、环境都对不上），他只会拿 netlist + SPEF + SDC + 库，在自己机器上跑一遍 PT，看 WNS 是否一致。

:::pitfall "PR 里 WNS 是正的，PT 一跑变负的 0.3ns"
这是后端最常见的"惊喜"，原因通常只有四类，按出现频率排：

1. **PR 用的是估算 RC，PT 读的是真 SPEF。** 布线后真实线延迟比估算差 10%~20%，长线更多。
2. **PR 里时钟是 ideal，PT 里是 propagated。** ideal clock 假设所有触发器同时收到时钟，skew 被当成 0；真实时钟树有几十到几百 ps 的偏差，还要叠加 OCV。
3. **PR 没开 OCV 或只开了一半。** 签核的 derate 一加，路径两端的延迟差被放大。
4. **约束版本不一致。** PR 用的是两周前的 SDC，PT 用的是最新冻结版，时钟周期或 input delay 改了。

排查顺序就按这四条走：先比 SPEF 是不是同一版，再比时钟模式，再比 derate 设置，最后 diff 两份 SDC。**不要一上来就怀疑工具算错了。**
:::

### 工作中怎么用

**谁做**：大公司里分工明确——PR 工程师负责"跑出干净的数据库并自检"，STA 工程师（或签核组）负责"用 PT 独立复算并签字"。小公司常常是同一个人做两遍，但**必须换工具、换时间点、换心态**，否则等于自己给自己改卷子。

**输入从哪来**：PR 导出 netlist（门级 verilog）、每个 corner 的 SPEF、冻结版 SDC、对应 corner 的库。四样东西要带版本号，缺一样报告就作废。

**输出交给谁**：签核报告进项目的 signoff checklist，是 tapeout review 的必过项。同时把违例清单交回 PR 做 ECO。

**做错了会怎样**：签核放过一条真违例，流片回来就是"某些芯片在高温低压下偶尔算错"。这种问题没法靠软件补丁修，只能改版——一次全掩膜（mask set）的钱，按工艺从几十万到上千万人民币。

## 签核到底签的是什么 {#signoff}

很多人以为签核是"看报告上有没有红字"。不是。签核签的是**一组条件**：在这些条件下，这版设计满足时序。

所以一份合格的签核记录必须能回答六个问题：

| 问题 | 记录在哪 |
|---|---|
| 哪一版网表？ | netlist 的文件名 + git commit / 版本号 |
| 哪一版约束？ | SDC 文件名 + 修改记录 |
| 用了哪些库、什么 corner？ | `link_path` 里的 `.db` 清单，逐场景列出 |
| 寄生参数从哪来？ | SPEF 文件名 + 提取工具 + 对应 rc corner |
| 悲观度怎么设的？ | derate 值 / AOCV 表 / POCV 的 sigma 设置 |
| 哪些违例被豁免了，谁批的？ | waiver 清单，每条要有理由和批准人 |

:::term Corner | 工艺角
芯片制造出来的参数会落在一定范围内。Corner 就是取范围的边界组合：工艺（process）快/慢、电压（voltage）高/低、温度（temperature）高/低。签核必须在最有代表性的几个角上都过。

常见的三档：**SS**（slow-slow，慢管）、**TT**（typical，典型）、**FF**（fast-fast，快管）。名字里的两个字母分别指 NMOS 和 PMOS 的快慢。
:::

:::term PVT | 工艺-电压-温度
Process、Voltage、Temperature 三个字母。器件延迟对这三者都敏感：慢工艺 + 低电压 + 高温通常最慢（但先进工艺里温度反转，高温反而变快，见后文 corner 一节）。
:::

先建立"多场景"的心智模型：签核不是跑一次，是跑一张表。表里每一行是一个场景（scenario），每行都要有自己的库、SPEF、约束和悲观度设置。这也是为什么 14 学时的课要花一整节讲 corner——**跑错场景，报告再漂亮也没意义**。

:::note 一个反直觉的点
签核报告"全绿"不等于芯片一定能工作。它只证明：在列出的场景下，按当前的模型和约束，时序满足。模型不准（库错了）、约束漏了（少写一个时钟）、功能有 bug（CDC 没做），签核都发现不了。

所以签核是**必要条件，不是充分条件**。这句话在面试里说出来，比背十条命令更加分。
:::

## 读入三件套：网表、库、SPEF {#read}

:::scene 周一早上，PT 一开就三行红字
你拿到上周五 PR 导出的数据，在 `signoff/pt/` 下起了一个 `pt_shell`。按同事给的脚本改了路径，`source run.tcl`，屏幕立刻刷出：

```
Error: Cannot find the link library 'sram_2048x64_ss.db'. (LINK-5)
Warning: Unable to resolve reference 'SRAM_2048X64' in 'u_mem/u_sram0'. (LINK-5)
Warning: Linking design with 1 unresolved reference.
```

设计"link 成功"了，`report_timing` 也能出结果，WNS 还特别漂亮：+1.8ns。你隐约觉得不对——上周 PR 里 WNS 是 +0.05ns。

问题就在这三行字里：**存储器宏没解析出来，PT 把它当黑盒，延迟按 0 算**。一条穿过 SRAM 的路径，凭空省掉了 1.5ns。这份报告如果交上去，等于给项目签了一张假条。

（PT 的报错码在不同版本里略有差异，`LINK-5` 这类编号可能变，但关键字 `Cannot find the link library` / `unresolved reference` 是稳定的，排查时抓关键字。）
:::

做菜要有三样东西：菜谱（做什么）、食材规格表（每样食材多大火力多久）、厨房到餐桌的路况（菜端过去会不会凉）。PT 也一样：

| 三件套 | 类比 | 文件 | 读入命令 |
|---|---|---|---|
| 网表 netlist | 菜谱：谁连谁 | `final.v`（门级 verilog） | `read_verilog` + `link_design` |
| 库 library | 食材规格：每个单元多快、多耗电 | `.db`（二进制）/ `.lib`（文本） | `set link_path` 或 `read_db` |
| 寄生参数 SPEF | 路况：每根线多长、多少电阻电容 | `final.spef` | `read_parasitics` |

### 网表：只有连接关系，没有物理信息

门级网表长这样（示意）：

```verilog
// 作用：门级网表的最小样子，让读者看清"网表里只有实例和连线"
// 用法：PT 里用 read_verilog 读入，不需要综合库以外的东西
module top (clk, rst_n, din, dout);
  input clk, rst_n;          // 端口声明
  input  [7:0] din;
  output [7:0] dout;
  wire   [7:0] n1;           // 内部连线，名字是综合工具起的
  DFFX1  u_reg0 (.CK(clk), .D(din[0]), .Q(n1[0]));   // 一个触发器实例
  BUFX2  u_b0   (.A(n1[0]),  .Y(dout[0]));           // 一个缓冲器实例
  // ……其余位省略
endmodule
```

要看出三件事：

1. 网表里全是**实例（instance）和连线（net）**，没有"这条线多长"的信息。线长要靠 SPEF 补。
2. 每个实例的类型（`DFFX1`、`BUFX2`）必须能在库里找到。找不到就是黑盒。
3. 网表**不含时钟周期、不含输入延迟**。这些全靠 SDC。

### 库：`.lib` 和 `.db` 的区别

:::term Liberty (.lib) |  liberty 时序库
描述标准单元/宏的文本格式文件：每个单元有哪些引脚、每条时序弧（timing arc）的延迟表、setup/hold 约束、输入电容、内部功耗。人可读，但文件很大（几十到几百 MB）。
:::

:::term .db | 编译后的二进制库
把 `.lib` 用 `lc_shell`（Library Compiler）编译成的二进制格式，PT 和 DC 读得快。**内容等价，只是格式不同**。签核时用 `.db`，改库参数时要回到 `.lib` 再重新编译。
:::

库里最关键的三个概念，先用大白话说清：

- **时序弧（timing arc）**：信号从 A 引脚走到 Y 引脚要多久。这个"多久"不是常数，是一张二维表——输入 transition 和输出负载各一维。
- **约束（constraint）**：触发器要求数据在时钟沿前多久稳定（setup）、沿后多久不能变（hold）。
- **条件（when）**：同一条弧在不同条件下延迟不同，比如"当 A=1 时走这条，A=0 时走那条"。

所以库里一个触发器可能有几十条弧。**库选错 corner，所有弧的数值全错**——这不是精度问题，是系统性错误。

### SPEF：每根线的电阻和电容

:::term SPEF | 标准寄生参数交换格式
Standard Parasitic Exchange Format，IEEE 1481 标准。内容是一张表：每个 net 被切成若干段，每段给电阻、对地电容、对相邻线的耦合电容。提取工具（StarRC、QRC）从版图算出来，PT 读进去算真实线延迟。
:::

SPEF 开头有一段单位声明，必须看：

```text
*SPEF "IEEE 1481-1998"
*DESIGN "top"
*DATE "Fri Nov 20 09:12:31 2026"
*VENDOR "StarRC"
*PROGRAM "StarRC"
*VERSION "<提取工具版本>"   # 版本号随工具而变，这里不写死
*DESIGN_FLOW "PIN_CAP NONE"
*DIVIDER /
*DELIMITER :
*BUS_DELIMITER [ ]
*T_UNIT 1 PS          # 时间单位：皮秒
*C_UNIT 1 FF          # 电容单位：飞秒
*R_UNIT 1 OHM         # 电阻单位：欧姆
*L_UNIT 1 HENRY
```

`*T_UNIT 1 PS` 这一行如果被改成 `1 NS`，同一份数字会被解读成慢 1000 倍——整份报告全废，而且工具不会报错。所以**每次读 SPEF 都要扫一眼单位段**，这也是 signoff checklist 里的一行。

线延迟到底多大？手算一次：

一根 M4 线长 1mm，单位电阻 0.2 Ω/µm，单位电容 0.2 fF/µm，驱动器输出电阻忽略。

- 总电阻 `R = 0.2 × 1000 = 200 Ω`
- 总电容 `C = 0.2 × 1000 = 200 fF`
- 分布式 RC 线的 Elmore 延迟约 `0.5 × R × C = 0.5 × 200 × 200f = 20 ps`

20ps 看起来很小。但一条路径上如果有 30 段这样的线，加起来 600ps；而 28nm 下一个周期才 2ns。**这就是为什么"没读 SPEF"的时序一定是假的乐观。**

### 标准读入流程与顺序纪律

```tcl
# ============================================================
# 作用：PT 读入三件套的最小可用流程
# 用法：pt_shell -f read_design.tcl，在 signoff/pt/ 目录下跑
# 前提：netlist.v / final.spef / constraints.sdc 都在当前目录
# ============================================================

# ---- 1. 设库搜索路径。三部分：当前目录、工艺库、宏库 ----
set link_path "* \
  /pdk/28nm/lib/ss_0p81v_125c/std_cell_ss.db \
  /pdk/28nm/lib/ss_0p81v_125c/sram_2048x64_ss.db \
  /pdk/28nm/lib/ss_0p81v_125c/io_ss.db"
# 说明："*" 表示"当前 design 里已有的库优先"，必须有
# 说明：每个 .db 都要写绝对路径，别依赖未知的 search_path

# ---- 2. 读网表并解析 ----
read_verilog ./netlist/final.v          ;# 只建立层次和连接，还没解析单元
link_design -keep_sub_designs           ;# 解析每个实例对应的库单元
# 说明：link 之后立刻看有没有 unresolved reference 的 warning

# ---- 3. 读 SDC。必须在 link 之后！----
source ./constraints/final.sdc          ;# 时钟、IO 延迟、例外全在这
# 说明：link 之前读，get_ports 会返回空，约束静默失效（见下面的坑）

# ---- 4. 读寄生参数 ----
read_parasitics -format SPEF ./spef/final_ss_cmax.spef
# 说明：一个 corner 一份 SPEF，别混用

# ---- 5. 确认三件事都生效了 ----
report_design -library                  ;# 列出实际用到的库，逐个对
report_clocks                           ;# 时钟有没有、周期对不对
check_timing                            ;# 未约束/无时钟/无输入延迟
```

把上面这套读入跑起来，屏幕上大致是这个样子：

:::fig pt-shell | PrimeTime 的签核会话：上半部分命令窗依次完成读库、读网表、读 SPEF、读约束、check_timing，下半部分是 report_timing 的输出。重点看命令窗的顺序——库在最前、SDC 在 link 之后，顺序错一步，下面整份报告都作废。
:::

从图里要看出什么：**签核是一次"顺序敏感"的会话，不是逐条敲命令**。下面两个 pitfall 讲的"静默失效"，全都发生在顺序错的那一步。

:::pitfall SDC 读在 link 之前，约束"静默失效"
现象：`report_clocks` 是空的，`report_timing` 报 `No paths`，或者所有路径都不受约束。PT 只给一句 `Warning: No clocks found`，不报错。

原因：SDC 里写的是 `[get_ports clk]`。`link_design` 之前，设计还没有端口对象，`get_ports clk` 返回空列表。于是 `create_clock -period 2.0 []` 什么都没创建。后面的 `set_input_delay` 同理，全部作用在空集合上。

为什么危险：PT 对"空集合"只给 warning，脚本不会中断。你可能跑完一整套报告、写进 PPT，才发现报告里一条路径都没有。

怎么查：读 SDC 后立刻跑 `report_clocks` 和 `llength [all_clocks]`。数量对不上就是没生效。**固定顺序：read_verilog → link_design → source SDC → read_parasitics。**
:::

:::pitfall link 只报 warning，不报 error
`link_design` 遇到解析不了的单元，默认只给 warning 并继续，把该实例当黑盒。后果是穿过它的路径延迟被算成接近 0，WNS 假性变好。

三个必查动作：
1. `link_design` 之后 `grep -i unresol` 日志，条数必须是 0。
2. `report_design -library` 对比网表里出现的单元类型清单，看有没有整类缺失。
3. 抽样 `report_timing -through [get_pins u_mem/u_sram0/*]`，看宏内部的延迟是不是 0。

如果宏确实要当黑盒（比如只有 lef 没有 lib），那必须**显式**用 `set_disable_timing` 并记录在案，而不是让工具默默当 0 算。
:::

### link_design 报错排查表

| 报错/现象 | 常见原因 | 处理 |
|---|---|---|
| `Cannot find the link library 'xxx.db'` | 路径写错、文件名大小写不符、库没编译 | `ls` 确认文件存在；`.lib` 用 `lc_shell` 编译成 `.db` |
| `Unable to resolve reference 'SRAM_2048X64'` | 宏库没加进 `link_path`；网表里的名字和库里不一致 | 补宏库；`report_lib` 查库里真实单元名 |
| `Linking design with N unresolved references` | 同上的批量表现 | 按单元名去重统计，一次性补齐 |
| `Cannot find port 'xxx' in design` | SDC 里的名字和网表不匹配（综合改名了） | `get_ports *xxx*` 模糊找，或回综合确认命名规则 |
| 时序好得离谱（WNS +1.8ns） | 有黑盒被当 0 延迟 | 按上面三条必查动作排查 |
| 多个库同名单元冲突 | 同时读了两个 corner 的库 | 一个场景只读一个 corner 的库，多 corner 分进程跑 |

:::note 为什么一个场景只读一个 corner 的库
两个 corner 的 `.db` 里有同名单元（比如都叫 `DFFX1`），PT 的 `link_path` 从左到右匹配，谁在前用谁。混着读的结果是"一部分单元用慢库、一部分用快库"，算出来的东西没有物理意义。

多 corner 的正确做法是**一个 corner 一个 PT session**（或用 MCMM 的多场景机制），而不是一个 session 里读多套库。
:::

## 约束怎么写：SDC 核心五条 {#sdc}

:::term SDC | 设计约束
Synopsys Design Constraints，基于 Tcl 的一套约束语言。它描述"设计要在什么条件下工作"：时钟多快、外部信号什么时候来、哪些路径不用查、信号边沿最慢允许多少。

SDC 不是"给工具的设置"，它是**设计规格的一部分**。同一个网表配两份不同的 SDC，就是两个不同的设计。
:::

SDC 有几十条命令，但**真正决定签核结论的只有五条**。剩下的是例外（false path、multicycle、clock group），放在 `06-01` 课讲。

这五条的共同点：每一条都要填一个数，而那个数**不是工具能猜的，必须有人负责**。下面逐条讲"这个数从哪来"和"写错会怎样"。

### 第一条：`create_clock` —— 时钟有多快

```tcl
# 作用：定义芯片的主时钟。这是所有时序计算的基准，写错则全盘皆错
# 用法：SDC 最前面几行，必须在任何 set_input_delay 之前
create_clock -name clk_core -period 2.000 -waveform {0 1.000} [get_ports clk]
# -name      给时钟起名。后面所有约束都引用这个名字，改名等于改全部约束
# -period    周期，单位 ns。2.000 = 500MHz
# -waveform  上升沿/下降沿时刻。{0 1.0} = 50% 占空比
```

**为什么是这个数**：周期只有两个来源——要么是芯片规格书写的目标频率（`T = 1/f`），要么是 PLL/IP 输出手册给的范围。500MHz → 2.0ns；800MHz → 1.25ns；1GHz → 1.0ns。

**写小了会怎样**：过度约束。工具拼命优化，面积和功耗白涨，最后还是能过——只是浪费了两周。**写大了会怎样**：这是真事故。周期写成 2.5ns 而芯片实际跑 2.0ns，PT 全绿，流片回来跑不到标称频率，整个项目降频卖。

三个容易漏的点：

- **占空比不是永远 50%**。DDR 接口、某些 IP 要求 40/60，`-waveform` 必须按手册写。
- **时钟名要统一**。`create_clock -name clk_core` 之后，`set_clock_uncertainty [get_clocks clk_core]` 才有效。名字打错，`get_clocks` 返回空，约束静默失效（和前面 SDC 读太早是同一类坑）。
- **虚拟时钟**。芯片外面那颗驱动 IO 的时钟不在你的网表里，用 `create_clock -name vclk -period 2.0`（**不带端口**）建一个虚拟时钟，专门给 `set_input_delay` 用。

### 第二条：`set_input_delay` —— 外面送进来的数据什么时候到

:::term Input Delay | 输入延迟
数据到达芯片输入端口时，相对于**参考时钟沿**已经过去了多久。它描述的是芯片外部（上游器件 + 板级走线）的延迟，不是你芯片内部的延迟。
:::

类比：你约人 9:00 开会，对方从家到公司要 40 分钟。你不能假设他 9:00 整出现在会议室——你要按"他 8:20 出发"来安排。`set_input_delay` 就是那个"路上要花的时间"。

```tcl
# 作用：告诉 PT 外部数据最早/最晚什么时候到达输入端口
# 用法：create_clock 之后。max 用于 setup 检查，min 用于 hold 检查
set_input_delay -clock clk_core -max 1.60 [get_ports din*]
# -max：最晚到达。setup 检查用这个数（数据来得晚，最危险）
set_input_delay -clock clk_core -min 1.10 [get_ports din*]
# -min：最早到达。hold 检查用这个数（数据来得太早，会把上一拍冲掉）
```

**为什么是这两个数**：它们来自上游器件的时序手册 + 板级走线，算两遍：

```
input_delay_max = Tco_ext_max + Tpcb_max
input_delay_min = Tco_ext_min + Tpcb_min
```

手算：上游触发器 `Tco` 手册给 0.9~1.3ns，PCB 走线仿真给 0.25ns ±0.05ns。

- `max = 1.3 + 0.30 = 1.60ns`
- `min = 0.9 + 0.20 = 1.10ns`

**写小了会怎样**：`max` 写小 → 工具以为数据来得早，内部留的时间不够，实际芯片上数据到得太晚，setup 违例，功能错。`min` 写小（或干脆不写）→ hold 检查过于乐观，芯片上数据太早冲掉上一拍，同样是功能错，而且这种错在实验室常温下可能测不出来，只在低压高温出现。

**最常见的错误是只写 `-max` 不写 `-min`**。PT 会把 min 当 0，hold 分析失真。规矩：**IO 延迟必须成对写**。

### 第三条：`set_output_delay` —— 送出去的数据要留多少时间给别人

```tcl
# 作用：告诉 PT 外部接收器件对数据的要求（建立/保持 + 板级延迟）
# 用法：对每个输出端口写一组，max 管 setup，min 管 hold
set_output_delay -clock clk_core -max 0.50 [get_ports dout*]
# -max = 外部 setup 要求 + 板级最大延迟
set_output_delay -clock clk_core -min 0.10 [get_ports dout*]
# -min = 板级最小延迟 − 外部 hold 要求（可以是负数）
```

**为什么和 input delay 不一样**：输入延迟是"别人多久送到我门口"，输出延迟是"我必须多久之内送到别人门口"。方向相反，所以 `-min` 的符号要反过来减外部 hold。

手算：外部接收触发器 setup 0.20ns、hold 0.10ns，PCB 走线 0.20~0.30ns。

- `max = 0.20 + 0.30 = 0.50ns`（我必须在时钟沿前 0.5ns 把数据送到）
- `min = 0.20 − 0.10 = 0.10ns`（我不能早于沿前 0.1ns 送到，否则冲掉别人的 hold）

**写错会怎样**：`max` 写小 → 输出路径被过度优化（浪费），或者反过来写太大 → 输出路径修不动，WNS 卡在 IO 上。更隐蔽的是 `-min` 漏写：输出 hold 不检查，芯片间通信在快速 corner 下偶发误码。

### 第四条：`set_clock_uncertainty` —— 给时钟留多少余量

:::term Clock Uncertainty | 时钟不确定性
在理想时钟之上额外加的一段"悲观量"，用来覆盖：时钟源抖动（jitter）、时钟树偏斜（skew）的残余、以及建模误差。setup 和 hold 要分别设，因为两者的最坏组合方向相反。
:::

```tcl
# 作用：给 setup/hold 分别加时钟余量
# 用法：CTS 之前用大值（覆盖未知 skew），CTS 之后可以适当收紧
set_clock_uncertainty -setup 0.150 [get_clocks clk_core]
# setup：假设捕获时钟早到 0.15ns，逼工具多留 150ps
set_clock_uncertainty -hold  0.080 [get_clocks clk_core]
# hold：假设时钟关系更差，留 80ps（hold 的余量通常比 setup 小）
```

**这个数是怎么拼出来的**（典型拆法，具体值看项目）：

| 来源 | setup 贡献 | hold 贡献 | 说明 |
|---|---|---|---|
| PLL 周期抖动 | 30ps | 10ps | 手册给，取峰峰值的一半更保守 |
| PLL 相位误差 | 20ps | 10ps | 同上 |
| CTS 后残余 skew | 40ps | 40ps | 用 `report_clock_timing` 的实测值，别拍脑袋 |
| 建模/提取误差 | 20ps | 20ps | 经验值，先进工艺要加大 |
| 合计 | 110ps | 80ps | 签核取整到 150 / 80 |

**为什么 setup 比 hold 大**：setup 检查跨一个时钟周期，两个沿的抖动不相关，最坏情况是"发射沿晚 + 捕获沿早"，抖动要算两遍；hold 检查在同一个沿附近，抖动大部分共模抵消。

**写错会怎样**：写 0 → 报告变好看，实际芯片在抖动大的时候出错，这是典型的"签核放水"。写太大（比如 0.5ns）→ 过度悲观，明明能跑的设计被修了两周还收不掉，最后被迫降频——**悲观也是一种成本**。

:::pitfall CTS 之后 uncertainty 忘了收紧
现象：CTS 前为了覆盖未知 skew 把 uncertainty 设成 0.2ns，CTS 做完 skew 实测只有 60ps，但脚本没改，签核一直按 0.2ns 算，WNS 卡在 −0.15ns 怎么都修不掉。

原因：uncertainty 里的 skew 部分和真实时钟树是**重复计算**的。CTS 之后时钟走 propagated，skew 已经在路径里体现了，uncertainty 里那份就该缩到"残余 + 抖动"。

处理：CTS 后按 `report_clock_timing -type skew` 的实测值重算 uncertainty，并在签核记录里写明"uncertainty 从 0.20 收到 0.12，依据是实测 skew 60ps"。**改动要有依据，不能为了让报告变绿而改。**
:::

### 第五条：`set_max_transition` —— 边沿最慢允许多少

:::term Max Transition | 最大转换时间
信号从低到高（或高到低）跨越阈值区间所需的时间上限。超过这个值，单元延迟表要外插（不准）、短路功耗上升、串扰和电迁移都会恶化。
:::

```tcl
# 作用：给所有输入端口和内部网络设边沿上限（DRV 检查的依据）
# 用法：可以和库里的默认值一致，也可以按设计需要收紧
set_max_transition 0.120 [current_design]
# 全设计 120ps 上限（典型值，实际看库和工艺）
set_max_transition 0.080 [get_ports din*]
# 关键输入端口更严：边界信号质量差会一路传进去
set_max_capacitance 0.050 [current_design]
# 顺带把最大负载也设上，两者是一对
```

**为什么是这个数**：库里每个单元都有 `max_transition` 属性，那是"保证延迟表有效"的边界。设计值一般取库值的 80%~100%。工艺越先进，这个数越小（16nm 常在 60~80ps）。

**写错会怎样**：不设 → 工具只用库默认值，某些路径的边沿烂到 300ps 也不报，签核"通过"但 SI 和 EM 全挂。设太松（比如 0.5ns）→ 等于没设。设太紧（0.03ns）→ 工具疯狂插 buffer，面积爆炸还收不掉。

**这条最容易被当成"次要检查"跳过**。实际上先进工艺里 DRV 违例经常是 WNS 修不掉的真因：边沿太慢 → 延迟表外插 → 延迟算不准 → 你按错的延迟修时序。

:::note 五条之外还有什么
`set_clock_groups`（异步时钟分组）、`set_false_path`、`set_multicycle_path`、`set_max_delay` 这四条决定"哪些路径该查、按几拍查"，写错的后果比数值写错更严重——它们能让一整类违例凭空消失。详见 `06-01 STA 深水区`。

本课只强调一条纪律：**每一条例外约束都要写注释说明理由，并在评审时逐条过。**没有理由的 false path，等于在签核报告上造假。
:::

### 五条约束的检查清单

写完 SDC 不要直接跑报告，先过这张表：

| 检查 | 命令 | 期望 |
|---|---|---|
| 时钟数量对不对 | `llength [all_clocks]` | 等于设计里的时钟数（含虚拟时钟） |
| 周期对不对 | `report_clocks` | 逐个对规格书 |
| 每个输入都有 max 和 min | `check_timing -include no_input_delay` | 0 条 |
| 每个输出都有 max 和 min | `report_port -delay` | 逐端口核对 |
| uncertainty 是不是双份 | 对比 CTS 前后设置 | CTS 后必须收紧并记录依据 |
| transition 有没有生效 | `report_constraint -all_violators -max_transition` | 违例数合理，不是 0 也不是几万 |

## report_timing：把一条路径逐列读出来 {#report}

:::term Path Report | 路径报告
`report_timing` 打印的一条路径的完整账本：起点、终点、经过的每个引脚、每段的增量延迟、累计延迟，最后是 required、arrival 和 slack。读报告的能力，就是 STA 工程师的核心技能。
:::

很多人看报告只看最后那个 `slack`。这就像看体检报告只看"合格"两个字——真出了问题，你不知道是哪项指标、哪个器官。

下面是一条完整的 setup 路径报告（数字是教学用的构造值，格式按 PT 的 `full_clock_expanded`）：

```text
Startpoint: u_core/u_reg[3]/CK          (rising edge-triggered flip-flop clocked by clk_core)
Endpoint:   u_core/u_alu/out_reg[7]/D   (rising edge-triggered flip-flop clocked by clk_core)
Path Group: clk_core
Path Type:  max
Corner:     ss_0p81v_125c
Scenario:   func_ss

  Point                                    Incr       Path
  ---------------------------------------------------------------
  clock clk_core (rise edge)               0.0000     0.0000
  clock source latency                     0.0000     0.0000
  clock network delay (propagated)         0.6200     0.6200
  u_core/u_reg[3]/CK                       0.0000     0.6200
  u_core/u_reg[3]/CK->Q                    0.1200     0.7400
  u_core/u_alu/U1204/Z                     0.3100     1.0500
  u_core/u_alu/U1188/Z                     0.5400     1.5900
  u_core/u_alu/out_reg[7]/D                0.0000     1.5900
  data arrival time                                   1.5900

  clock clk_core (rise edge)               2.0000     2.0000
  clock network delay (propagated)         0.5800     2.5800
  clock uncertainty                       -0.1500     2.4300
  u_core/u_alu/out_reg[7]/CK               0.0000     2.4300
  library setup time                      -0.0800     2.3500
  data required time                                  2.3500
  ---------------------------------------------------------------
  data required time                                  2.3500
  data arrival time                                  -1.5900
  ---------------------------------------------------------------
  slack (MET)                                         0.7600
```

这份报告每一行在说什么，对照着看更清楚：

:::fig report-timing-annotated | report_timing 的输出逐行注解：左边是真实格式的报告（起点终点、Incr、Path、required、slack），右边把每一段的含义写清。重点看 Incr 与 Path 两列的差别，以及捕获侧 required 是怎么被 uncertainty 和 setup 一层层扣出来的。
:::

从图里要看出什么：**瓶颈看 Incr 最大的那一行，skew 看发射与捕获两侧时钟延迟的差**。下面几节就是把这张图里的每一段拆开讲。

### 头部四行是什么意思

| 行 | 含义 | 读它干什么 |
|---|---|---|
| `Startpoint` | 发射触发器（launch FF）的**时钟引脚** | 确认是哪个寄存器发的数据；带 `CK` 说明起点取的是时钟端 |
| `Endpoint` | 捕获触发器（capture FF）的**数据引脚** | 带 `D` 说明终点取的是数据端；如果这里是 `CK`，多半是 recovery/removal 检查 |
| `Path Group` | 这条路径属于哪个时钟组 | 统计 WNS 时按组分别看，别把两个组的数混在一起 |
| `Path Type: max` | max = setup 检查（最长路径）；min = hold 检查（最短路径） | 看 hold 报告要确认这里真的是 `min` |

`Corner` 和 `Scenario` 两行是 MCMM 模式下才有的。它们非常重要——**同一路径在不同 corner 下 slack 可能差 0.3ns**，报告不带 corner 就没法讨论。

### 中间三列：`Point` / `Incr` / `Path`

这是最容易读错的地方。

- **`Point`**：路径上的节点。单元、引脚、连线都算。
- **`Incr`（increment）**：**进入这个节点所花的延迟**。单元延迟、线延迟、时钟网络延迟都记在这里。
- **`Path`**：从起点到这里的**累计时间**。注意它是累计，不是"这一段自己的延迟"。

所以 `0.74 → 1.05 → 1.59` 的意思是：CK→Q 花了 0.12，第一级组合逻辑 0.31，第二级 0.54，累计到 D 端 1.59ns。**找瓶颈就看 `Incr` 列最大的那一行**——这里 0.54 的 `U1188` 是主因。

### 发射侧：时钟不是"0 时刻到"

报告里这两行最容易被忽略：

```text
clock network delay (propagated)         0.6200     0.6200
```

它的意思是：时钟从源走到 `u_reg[3]/CK` 花了 0.62ns。**数据不是从 0 时刻出发的，是从 0.62ns 出发的。**

如果这里显示的是 `clock network delay (ideal)  0.0000`，说明你还在用理想时钟——所有时序都是乐观的，不能签核。

### 捕获侧：required 是怎么拼出来的

```text
clock clk_core (rise edge)               2.0000     ← 下一个时钟沿
clock network delay (propagated)         0.5800     ← 捕获时钟也走了 0.58ns
clock uncertainty                       -0.1500     ← 减掉余量
library setup time                      -0.0800     ← 减掉触发器 setup
data required time                                  2.3500
```

`required = 周期 + 捕获时钟延迟 − uncertainty − setup = 2.00 + 0.58 − 0.15 − 0.08 = 2.35`

注意捕获时钟延迟（0.58）比发射时钟延迟（0.62）**小** 0.04ns。这 0.04 就是这条路径上的实际 skew，它让 required 变小，等于**吃掉了 40ps 的时序余量**。skew 不是抽象概念，它就明明白白写在报告里。

### slack 与"差 0.12 到底差在哪"

`slack = required − arrival = 2.35 − 1.59 = 0.76ns`（MET）。

如果路径更长，`Incr` 那两级变成 0.31 + 1.42，arrival 变成 `0.62 + 0.12 + 0.31 + 1.42 = 2.47`，那么：

`slack = 2.35 − 2.47 = −0.12ns`（VIOLATED）

这时候回答"为什么差 0.12"的正确格式是三段：

1. **差多少**：−0.12ns，在 `u_alu` 到 `out_reg[7]` 这条路径上。
2. **差在哪**：`Incr` 列里 `U1188` 占 1.42ns，是唯一的大头；时钟侧 skew 只贡献 0.04。
3. **怎么修**：拆进位链（逻辑重构）、或把这段逻辑打一拍（加流水）、或换驱动更强的单元（`size_cell`）。

只说"工具优化不够，我再跑一遍"的人，在评审会上会被问穿。

:::scene 组长在群里问："WNS 为什么是负的？"
晚上八点，签核群弹出这句话。你手上只有一份 `viol_setup.rpt`，要在五分钟内回复。

错误回答："PR 那边优化不够，我让他们再跑一轮。"——这等于把问题推回去，什么信息都没给。

正确回答分三句：

1. "WNS −0.12ns，最差路径 `u_alu/U1188` 到 `out_reg[7]/D`，属 `clk_core` 组。"
2. "arrival 2.47 = 发射时钟 0.62 + 数据路径 1.85，其中 `U1188` 一级就占 1.42；required 2.35，被 uncertainty 0.15 和 setup 0.08 压过。skew 只贡献 0.04，不是主因。"
3. "所以不是时钟问题，是组合逻辑太深。建议两条路：拆进位链，或在 `U1188` 前打一拍。我倾向后者，因为拆链会动 RTL。"

**能定位到具体单元、给出两条可选方案并说明取舍，才叫会看报告。**
:::

### 常用参数，一次记全

```tcl
# 作用：按不同目的捞路径。每个参数解决一个具体问题
# 用法：在 pt_shell 里按需组合，输出重定向到 rpt/ 存档
report_timing -max_paths 50 -nworst 5 \
              -slack_lesser_than 0 \
              -path_type full_clock_expanded \
              -significant_digits 4 > rpt/viol_setup.rpt
# -max_paths 50           最多列 50 条路径（按 slack 从差到好）
# -nworst 5               每个 endpoint 最多列 5 条（防止一个 endpoint 刷屏）
# -slack_lesser_than 0    只报负 slack（不加就会报一堆 MET 的，看不到问题）
# -path_type full_clock_expanded  把时钟路径展开（不加则折叠，看不到 skew）
# -significant_digits 4   保留 4 位小数（−0.0712 不会被显示成 −0.1）

report_timing -delay_type min -max_paths 20 > rpt/viol_hold.rpt
# -delay_type min         看 hold（最短路径）

report_timing -from [get_pins u_ctrl/state_reg[2]/CK] -to [get_pins u_ctrl/*/D]
# -from/-to/-through      定位单条路径，改完 ECO 后复查用
```

:::pitfall 看 `Path` 列当成"这一段花了多久"
现象：有人指着 `Path` 列的 1.59 说"这一级花了 1.59ns"，然后去优化那个单元，越优化越差。

原因：`Path` 是**累计**，`Incr` 才是这一段。1.59 是整条路径到现在为止的总和。

记法：`Incr` = 这一步花了多少；`Path` = 到现在一共花了多少。看瓶颈永远看 `Incr`。
:::

:::pitfall 用默认 `path_type` 看报告，找不到 skew 来源
`report_timing` 默认把时钟路径折叠成一行 `clock network delay`，只给总数。当你需要回答"这 0.62ns 里哪几级 buffer 贡献最大"时，必须加 `-path_type full_clock_expanded`。

这份展开报告也是 CTS 工程师和 STA 工程师吵架时唯一的事实依据：**时钟树到底公不公平，看展开报告，不看直觉。**
:::

## OCV / AOCV / POCV：签核为什么比 PR 更悲观 {#ocv}

:::term OCV | 片上偏差
On-Chip Variation。同一颗芯片上，不同位置的同型号单元，因为光刻、掺杂、氧化层厚度的随机差异，实际延迟不完全一样。OCV 就是在时序计算里给这种差异留的余量。
:::

买一盒 100Ω 电阻，标称精度 ±5%，实际可能是 96~104Ω。如果一条电路上串了 20 个，最坏情况是不是 20 × 4Ω？不是——误差有正有负，全部同向的概率很低。但**签核必须按最坏情况算**，因为芯片是要量产几百万颗的，极小概率也会发生。

OCV 的做法最粗暴：所有单元统一乘一个系数。

```tcl
# 作用：设置全局 derate。setup 检查时"数据路径变慢、时钟路径变快"
# 用法：read_parasitics 之后、report_timing 之前设置
set_timing_derate -late  1.05 -cell_delay
# -late 1.05：晚路径（数据）延迟按 105% 算
set_timing_derate -early 0.95 -cell_delay
# -early 0.95：早路径（捕获时钟）延迟按 95% 算
set_timing_derate -late  1.05 -net_delay
set_timing_derate -early 0.95 -net_delay
# 线和单元分别设，互不覆盖（只写 -cell_delay 时，线延迟不加 derate）
```

### 手算：5% derate 到底吃掉多少

用上面那条路径的数：周期 2.0ns，发射时钟路径 1.0ns，数据路径（CK→Q + 组合 + 线）0.9ns，捕获时钟路径 1.1ns，setup 0.08ns，uncertainty 0。

**不开 OCV：**

- `arrival = 1.0 + 0.9 = 1.90`
- `required = 2.0 + 1.1 − 0.08 = 3.02`
- `slack = 3.02 − 1.90 = 1.12ns`

**开 5% derate（late 打数据侧和发射时钟，early 打捕获时钟）：**

- `arrival = 1.0×1.05 + 0.9×1.05 = 1.05 + 0.945 = 1.995`
- `required = 2.0 + 1.1×0.95 − 0.08 = 2.0 + 1.045 − 0.08 = 2.965`
- `slack = 2.965 − 1.995 = 0.97ns`

**一个 5% 的系数，吃掉了 0.15ns（约 7.5% 的周期）。** 本来 1.12ns 的余量变成 0.97ns。如果设计本来就紧张（余量 0.1ns），这一下直接变负。

这就是"PR 里是正的，PT 里是负的"最典型的来源之一。

:::term CPPR | 公共路径悲观度消除
Common Path Pessimism Removal。发射和捕获时钟从同一个源出发，在分叉之前走过同一段路径。这段公共路径被同时按 late（发射侧）和 early（捕获侧）算了两遍，产生了虚假的悲观量。CPPR 把这部分加回来。
:::

继续上面的手算：假设发射和捕获时钟有 0.8ns 是公共路径（从时钟根到分叉点）。

- 这段公共路径在发射侧按 `0.8×1.05 = 0.84` 算，在捕获侧按 `0.8×0.95 = 0.76` 算，差 `0.08ns`。
- 物理上它就是同一段线，不可能同时快 5% 又慢 5%。所以这 0.08ns 是假的。
- CPPR 加回 0.08：`slack = 0.97 + 0.08 = 1.05ns`。

**"OCV 吃掉 0.15，CPPR 还回 0.08，净损失 0.07"** ——这个账要会算。PT 默认开 CPPR（`timing_report_ppr` 相关变量），但你要知道报告里有一行 `clock reconvergence pessimism` 就是它。

### AOCV：路径越长，derate 越小

:::term AOCV | 先进片上偏差
Advanced OCV。核心洞察：偏差是随机变量，**路径上串联的级数越多，相对偏差越小**（统计平均）。所以 derate 不该是常数，应该按逻辑深度（depth）和物理距离（distance）查表。
:::

AOCV 的表长这样（数值为示意，真实表由 foundry 给）：

| 级数 depth | cell derate (late) | net derate (late) |
|---|---|---|
| 1 | 1.08 | 1.10 |
| 5 | 1.04 | 1.06 |
| 10 | 1.02 | 1.04 |
| 20 | 1.01 | 1.02 |

同一条 10 级的路径，统一 OCV 按 1.05 算，AOCV 按 1.02 算——**少了 3 个百分点**。对一条 2ns 的路径，就是 60ps 的差别。

所以 AOCV 比 OCV **更准，而且通常没那么悲观**（浅路径反而更悲观，深路径更宽松）。28nm~16nm 项目普遍用 AOCV。

```tcl
# 作用：读入 AOCV 表，替代统一 derate
# 用法：read_parasitics 之后，report_timing 之前
read_aocvm ./aocv/tsmc28_ss.aocvm
# 表里有 cell/net、late/early、按 depth 和 distance 的多张子表
set_timing_derate -early 0.97 -late 1.03
# AOCV 模式下这个全局值作为"兜底"，实际按表查
report_timing -path_type full_ocvm
# 加 full_ocvm 可以看到每一级实际用了多少 derate
```

### POCV / LVF：按分布算，不按边界算

:::term POCV / LVF | 参数化片上偏差 / Liberty 变异格式
POCV 把每个单元的延迟当成正态分布（均值 + sigma），路径的 sigma 按方差相加（`σ_total = √(σ1² + σ2² + …)`）。LVF 是这种数据的标准文件格式，先进工艺（16nm 以下）签核必须用。
:::

手算一次"方差相加"和"直接相加"的区别：两级单元各 σ = 10ps。

- 直接相加（最悲观）：`10 + 10 = 20ps`
- 方差相加（统计）：`√(10² + 10²) = √200 ≈ 14.1ps`

差 6ps。级数越多差得越大：10 级各 10ps，直接相加 100ps，统计相加只有 31.6ps。**这就是为什么统一 derate 在深路径上过度悲观。**

代价是：POCV 需要 foundry 提供 LVF 文件（每个单元每个弧一条分布），文件巨大，跑得慢。所以成熟工艺用 AOCV，先进工艺用 POCV，是成本和精度的折中。

| 模式 | 依据 | 典型节点 | 悲观度 |
|---|---|---|---|
| 无 OCV | 标称值 | 学习/早期探索 | 最乐观，不能签核 |
| OCV | 统一系数 | 40nm 以上、快速评估 | 偏悲观 |
| AOCV | 深度/距离查表 | 28~16nm | 中等 |
| POCV / LVF | 统计分布 | 16nm 以下 | 最准 |

:::pitfall derate 只加了 cell 没加 net
`set_timing_derate -late 1.05 -cell_delay` 只影响单元延迟，**线延迟不受影响**。有人以为设了一次就全覆盖，结果长线路径的悲观度不足。

判断方法：`report_timing -path_type full_ocvm` 看每一行的 derate 标注，单元行和线行都要有值。

规矩：cell 和 net 各设一次，四个组合（late/early × cell/net）写完才叫"OCV 开了"。
:::

## 多 corner 签核：一张场景表 {#corner}

慢 corner 查 setup，快 corner 查 hold，这是常识。但"慢"和"快"不是只看工艺一个维度。

:::term RC Corner | 寄生参数角
线延迟的边界。**Cmax**（电容最大）线最慢，用于 setup；**Cmin**（电容最小）线最快，用于 hold；**Ctypical** 用于一般分析。提取工具会为每个 RC corner 各出一份 SPEF。
:::

### 三个维度怎么组合

| 维度 | setup 取 | hold 取 | 原因 |
|---|---|---|---|
| 工艺 Process | SS（慢管） | FF（快管） | 慢管单元延迟大 |
| 电压 Voltage | 低（如 0.81V） | 高（如 0.99V） | 电压低延迟大 |
| 温度 Temperature | 高（125℃）* | 低（−40℃） | 见下方温度反转说明 |
| RC corner | Cmax | Cmin | 电容大线慢 / 电容小线快 |

\* 先进工艺（大致 28nm 以下）存在**温度反转（temperature inversion）**：高温下迁移率下降但阈值电压也下降，后者占优，导致高温反而更快。这种情况下 setup 要同时看高温和低温两个点，不能想当然。

所以 setup 的最坏场景常常写成 `ss_0p81v_m40c` 和 `ss_0p81v_125c` 两个都要跑——**"最慢"到底是高温还是低温，要看库的特性表，不能猜。**

### MCMM 场景表

:::term MCMM | 多角多模式
Multi-Corner Multi-Mode。一颗芯片有多个工作模式（功能模式、测试模式、低功耗模式）× 多个 corner，每个组合是一个 scenario（场景）。MCMM 让一个 session 里并行处理多个场景，共享网表，只切换库/SPEF/约束。
:::

一个典型项目的场景表（示意，实际按项目定）：

| 场景名 | 模式 | Corner | RC | 查什么 | 必须跑? |
|---|---|---|---|---|---|
| func_ss_cmax | 功能 | ss_0p81v_125c | Cmax | setup | 是 |
| func_ss_cmax_lt | 功能 | ss_0p81v_m40c | Cmax | setup（温度反转） | 是 |
| func_ff_cmin | 功能 | ff_0p99v_m40c | Cmin | hold | 是 |
| func_ff_cmax | 功能 | ff_0p99v_125c | Cmax | hold + EM | 是 |
| scan_ss_cmax | 扫描测试 | ss_0p81v_125c | Cmax | setup（测试模式时钟慢） | 是 |
| func_tt | 功能 | tt_0p9v_25c | Ctypical | 功耗/面积评估 | 否 |

把上面这张场景表画成矩阵，读法是固定的：

:::fig corner-matrix | 多 corner 签核表：每一行是一个工艺+电压+温度的组合，各查各的项目。重点看"SS 行查 setup、FF 行查 hold"这条主线，再看温度反转让 ss 的高温、低温两行都要跑——这正是本课强调"最差 corner 必须实算"的原因。
:::

从图里要看出什么：**签核是跑一张表，不是跑一次**。上面场景表的每一行都对应这张矩阵里的一格，裁掉任何一格，就有一个条件永远没人证明过。

**场景数量会爆炸**：3 corner × 2 模式 × 2 RC × 2 温度 = 24 个。实际项目靠"裁剪"控制：只保留能产生最坏值的组合，其余用工程判断排除，并**在签核记录里写明裁剪理由**。

:::note 场景裁剪的红线
探索阶段可以裁剪（先跑 4 个主场景看看大概）；**签核阶段不能裁**——一旦某个场景被裁掉，就没有任何报告能证明它在那个条件下能工作。

被裁掉的场景要写进 waiver 清单，注明"由谁判断、依据是什么"。这句话在 tapeout review 上会被问到。
:::

### 为什么 hold 用 Cmin 而不是 Cmax

直觉上"线越慢越危险"，但 hold 的危险方向相反：hold 要求数据**不要来太早**。线短（Cmin）→ 数据到得早 → 更容易冲掉上一拍 → hold 更危险。

所以：**setup 怕慢（SS + Cmax），hold 怕快（FF + Cmin）。** 两个方向的 derate 也是反的：setup 让数据慢、时钟快；hold 让数据快、时钟慢。

## check_timing 与 report_constraint：先找"没查的" {#checks}

时序报告只回答"查过的路径过不过"。它不回答"有没有路径根本没查"。后者更危险——**没查的路径，slack 是无穷大。**

`check_timing` 就是干这个的：

```tcl
# 作用：列出所有"约束不完整"的地方，是签核前的第一道关
# 用法：读完全部输入后立刻跑，输出必须逐条清空或记录豁免理由
check_timing -verbose > rpt/check_timing.rpt
# -verbose 会把每个受影响的引脚/端口都列出来，便于定位
```

常见条目和含义：

| 条目 | 含义 | 危险度 | 怎么处理 |
|---|---|---|---|
| `no_clock` | 有时序单元没有时钟到达 | 高 | 查时钟定义、时钟是否穿过不可传播的单元 |
| `unconstrained_endpoints` | 有终点没有任何约束覆盖 | 高 | 补时钟/补 IO 延迟/确认是否真空逻辑 |
| `no_input_delay` | 输入端口没设延迟 | 高 | 补 `set_input_delay`（max 和 min） |
| `no_output_delay` | 输出端口没设延迟 | 高 | 补 `set_output_delay` |
| `no_driving_cell` | 输入端口没建模驱动能力 | 中 | `set_driving_cell`，否则输入 transition 按理想算 |
| `loop` | 组合逻辑成环 | 高 | 多半是 latch 环或测试逻辑，需 `set_disable_timing` 断开 |
| `latch` | 有 latch 被当触发器分析 | 中 | 确认是设计意图，否则让前端改 |
| `generated_clock_no_source` | 生成时钟的源找不到 | 高 | 检查 `-source` 指向的是不是上游引脚 |

一条纪律：**`check_timing` 里有 `no_clock` 或 `unconstrained_endpoints` 时，后面所有 WNS 数字都要打问号。** 因为分母不全，通过率没有意义。

`report_constraint` 则是"查过的都过不过"的汇总：

```tcl
# 作用：一次性列出所有类型的违例（不只 setup/hold）
# 用法：签核报告必带，按类型分别统计条数
report_constraint -all_violators -verbose > rpt/all_viol.rpt
# -all_violators  只列违例（默认只列最差的）
# -verbose        带每个违例的具体对象名

report_constraint -all_violators -max_transition > rpt/drv_trans.rpt
report_constraint -all_violators -max_capacitance > rpt/drv_cap.rpt
# 单独捞某一类，便于分工：DRV 给 PR，时序给自己
```

`report_qor` 给的是数字汇总，签核 PPT 上那一页就靠它：

```tcl
# 作用：输出 WNS / TNS / 违例路径数 / 面积 / 单元数 / 功耗
# 用法：每个场景各跑一份，横向对比
report_qor > rpt/qor_ss.rpt
```

| 指标 | 全称 | 含义 | 为什么重要 |
|---|---|---|---|
| WNS | Worst Negative Slack | 最差那条路径的 slack（没有负值时为 0） | 一条路径决定整个芯片能不能跑这个频率 |
| TNS | Total Negative Slack | 所有负 slack 之和 | 衡量"烂得有多广"，WNS 只反映一个点 |
| NVP | Number of Violating Paths | 负 slack 路径条数 | 决定 ECO 工作量 |
| Area | 单元面积总和 | — | 成本 |
| Utilization | 利用率 | 单元面积 / 核心面积 | 太高布不通 |

:::note WNS 和 TNS 要一起看
- WNS −0.05、TNS −2：只有几十条路径差一点点，一轮 ECO 能收。
- WNS −0.05、TNS −800：几千条路径都差一点点，说明是**系统性问题**（约束太紧、库不对、频率定高了），ECO 修不完。

看到第二种，先别写 ECO，先去查约束和库。
:::

拿到 WNS / TNS / NVP 这三个数之后怎么用，这张图给出固定的分流顺序：

:::fig timing-summary | 时序汇总表的读法：WNS、TNS、违例条数三个数是"体检报告的第一页"，先靠它们决定往单点修还是系统性查，再按现象分流到具体路径。重点看下半部分的分流顺序——和上面 note 里"先查约束和库再动手"是同一个逻辑。
:::

从图里要看出什么：**三个数决定方向，具体路径决定动作**。跳过第一页直接修路径，就是本课反复警告的"用 ECO 修系统性问题"。

## 违例怎么反馈回 PR {#eco}

PT 不能改版图。它只能出一份"改动建议"，交给 PR 执行。这份建议就是 ECO 清单。

```tcl
# 作用：让 PT 生成修复建议（只出方案，不动网表）
# 用法：确认时序报告可信之后再跑，否则是在错的数据上生成错的方案
fix_eco_timing -type setup \
               -methods {size_cell} \
               -slack_lesser_than 0 \
               -slack_greater_than -0.20
# -type setup            只修 setup（一次只修一类，见 05-04 的四条纪律）
# -methods {size_cell}   只允许换单元尺寸，改动最小
# -slack_lesser_than 0   只修负 slack
# -slack_greater_than    只修 -0.20 以内的（太差的换单元也救不回来，别浪费）

write_changes -format icctcl -output eco/eco_setup_round1.tcl
# icctcl = ICC2 可直接 source 的格式；Innovus 用 -format innovus
# 输出是纯文本 Tcl，必须人工过一遍再交给 PR
```

一份给人看的 ECO 清单（PT 输出 + 人工补的列）：

| 列 | 例子 | 含义 |
|---|---|---|
| 动作 | `size_cell` | 换单元 / 插缓冲 / 删单元 |
| 目标 | `u_core/u_alu/U1188` | 实例全路径名（必须能唯一定位） |
| 参数 | `BUF_X8` | 换成什么单元 |
| 原始 slack | `-0.0712` | 改之前多差（4 位小数） |
| 预期收益 | `+0.09` | 预计能修回多少 |
| 原因分类 | `驱动不足/负载 12` | 为什么改（评审要看） |

完整链路是：**PT 出清单 → 人工筛（物理可行性）→ PR 应用 → 局部布线 → 重新导出 netlist+SPEF → PT 复算**。一轮修掉大部分，通常 2~3 轮收敛。具体脚本和纪律见 `05-04 ECO 实战`。

:::pitfall 用 ECO 去修本该改约束的问题
现象：WNS −0.4ns，跑了两轮 ECO，每轮修好 0.1，第三轮又冒出新违例，永远收不掉。

原因：根因不是优化不足，而是约束错了——比如某个时钟的 uncertainty 忘了在 CTS 后收紧、或者一条跨异步域的路径漏了 clock group（假违例）。

判断方法：看违例的**分布**。如果违例散落在几十个不相关的模块、每条都差 0.3~0.5ns，且 `Incr` 列没有明显大头，那基本是系统性问题，不是局部优化能解决的。

处理：停下来，回到 `check_timing` 和 SDC 逐条对。**ECO 是修局部小病的，不是治系统性疾病的。**
:::

## 签核标准：通过线怎么定 {#criteria}

"通过"不是一个数，是一组数。下面这张表是典型项目的通过线（具体数值按项目规格调整，不是行业统一标准）：

| 指标 | 通过线 | 为什么这么定 |
|---|---|---|
| setup WNS | ≥ 0，建议 ≥ +50ps | 留 50ps 覆盖模型误差和后期改动 |
| setup TNS | 0（或 ≤ −1ns 且有 waiver） | TNS 不为 0 说明面广，风险高 |
| hold WNS | ≥ 0，建议 ≥ +30ps | hold 违例无法靠降频规避，必须留余量 |
| hold TNS | 0 | hold 没有"降频可救"这一说 |
| max_transition 违例 | 0 | 边沿超标意味着延迟计算不可信 |
| max_capacitance 违例 | 0 | 负载超标意味着单元可能不工作 |
| 单元利用率 | ≤ 85%（布线后） | 再高布通率急剧下降 |
| 总功耗 | ≤ 规格 × 1.0 | 超了要重新评估封装/散热 |

**为什么 hold 比 setup 更严格**：setup 违例可以降频救（芯片还能卖低端），hold 违例是"数据冲掉了"，降频也没用——频率越低，hold 越差。所以 hold 必须真正清零。

:::term Waiver | 豁免
明知有违例但决定接受，并记录理由和批准人。合法的 waiver 场景：测试逻辑的伪路径、已知不会同时工作的模式组合、被上游 IP 保证过的接口。

**waiver 不是"改报告让它变绿"，它是"带着证据接受风险"。** 每条 waiver 都要有：违例对象、slack、理由、影响评估、批准人、复审日期。
:::

签核会上会被追问的三个问题，提前准备：

1. **这条违例为什么可以 waive？** —— 要有物理/逻辑依据，不能是"来不及修"。
2. **如果模型偏乐观 10%，还过吗？** —— 所以 WNS 要留 margin。
3. **worst case 真的是这个 corner 吗？** —— 温度反转、电压跌落（IR drop）都要考虑。

## 假违例：四种"看着要修，其实不该修" {#false-viol}

签核最耗时间的不是修违例，是**判断哪些违例是真的**。下面四类占了假违例的绝大多数。

### 第一类：false path 漏写，跨时钟域路径被当真

现象：最差路径永远跨在两个异步时钟之间，slack −3.5ns，怎么优化都不动，因为路径两端根本没有共同的时序关系。

识别：看 `Startpoint` 和 `Endpoint` 的时钟是不是同一个。不同且确实异步 → 应该设 `set_clock_groups -asynchronous`。

风险：**反过来更危险**——为了让报告变绿，把一条真实的同步路径设成 false path。这样报告全绿，芯片功能错。

纪律：每条 false path 都要写注释，注明"为什么这两组时钟异步"的依据（设计规格第几节 / 前端确认邮件）。

### 第二类：multicycle 只设了 setup，没设 hold

现象：设了 `set_multicycle_path 2 -setup` 之后，那条路径的 hold 违例突然变得很怪（要么一堆，要么一个都没有）。

原因：setup 检查点后移一个周期，hold 检查点也跟着错位。必须成对写：

```tcl
# 作用：多周期路径的正确写法——setup 和 hold 必须成对
# 用法：只对确实需要 N 拍完成的路径使用，且要写注释说明依据
set_multicycle_path 2 -setup -from [get_cells u_slow/*] -to [get_cells u_slow/*]
# setup 按 2 个周期检查
set_multicycle_path 1 -hold  -from [get_cells u_slow/*] -to [get_cells u_slow/*]
# hold 退回 1 个周期（N−1），否则 hold 检查点错位
```

识别：`report_timing -delay_type min` 里那条路径的 required 明显不对（比如应该是 0.2 却算成 2.2）。

### 第三类：generated clock 定义错，同源时钟被当成异步

现象：分频时钟那一片全是违例，或者反过来，本该检查的路径一条都不报。

原因：`create_generated_clock` 的 `-source` 指错了（指到输出而不是输入），或者 `-divide_by` 写错。工具认为这是两个无关时钟，于是要么不检查，要么按最坏相位检查。

识别：`report_clocks` 看每个 generated clock 的 source 和 divide 值，和 RTL 里的分频逻辑对一遍。

### 第四类：ideal / propagated 混用，或者 SPEF corner 用错

现象：同一版设计，两次跑出来的 WNS 差 0.3ns，代码没改。

原因只有两种：一次用了 ideal clock（skew=0），一次用了 propagated；或者一次读了 Cmax 的 SPEF，一次读了 Cmin 的。

识别：报告头部看 `clock network delay (propagated)` 还是 `(ideal)`；`report_parasitics` 看当前加载的是哪份 SPEF。

**这两种混用是"报告不可复现"的头号原因**，也是签核记录必须写清 corner 和时钟模式的原因。

## 一个完整的 PT 签核 run 脚本 {#script}

下面这份脚本按"读库 → 读网表 → 读 SPEF → 读 SDC → 检查 → 报告 → 导出"分节。可以直接改成项目用。

```tcl
# ============================================================
# 作用：单个 corner 的 PT 签核完整流程（ss / setup 场景）
# 用法：pt_shell -f signoff_ss.tcl 2>&1 | tee log/signoff_ss.log
# 前提：netlist、SPEF、SDC、库都在下面的路径里；先改路径再跑
# ============================================================

set DESIGN   "top"
set CORNER   "ss_0p81v_125c"
set RPT      "./rpt/${CORNER}"
file mkdir $RPT                                  ;# 报告目录，不存在会报错

# ---- 1. 读库：一个场景只读一套 corner 的库 ----
set link_path "* \
  /pdk/28nm/lib/${CORNER}/std_cell.db \
  /pdk/28nm/lib/${CORNER}/sram_2048x64.db \
  /pdk/28nm/lib/${CORNER}/io.db"
# "*" 让当前 design 已有的库优先；每个 .db 都要绝对路径

# ---- 2. 读网表并解析 ----
read_verilog ./netlist/${DESIGN}_final.v
link_design -keep_sub_designs
# 立刻检查：解析失败的单元会被当黑盒，延迟按 0 算
set unresolved [sizeof_collection [get_cells -hier -filter "is_black_box==true"]]
puts "@@@ 黑盒数量：$unresolved"                  ;# 必须为 0，否则停下来查库

# ---- 3. 读 SPEF（寄生参数）----
read_parasitics -format SPEF ./spef/${DESIGN}_${CORNER}_cmax.spef
# 一个 corner 一份 SPEF：setup 用 cmax，hold 用 cmin，别混

# ---- 4. 读 SDC（必须在 link 之后）----
source ./constraints/${DESIGN}_func.sdc
# 读完立刻验证：时钟数、周期、IO 延迟是否都生效
puts "@@@ 时钟数：[sizeof_collection [all_clocks]]"
report_clocks > $RPT/clocks.rpt

# ---- 5. 设悲观度（OCV / AOCV）----
set_timing_derate -late  1.05 -cell_delay
set_timing_derate -early 0.95 -cell_delay
set_timing_derate -late  1.05 -net_delay
set_timing_derate -early 0.95 -net_delay
# 四个组合都写全；只写 cell 会让线延迟没有 derate

# ---- 6. 前置检查：约束有没有漏 ----
check_timing -verbose > $RPT/check_timing.rpt
# 打开这个文件，no_clock / unconstrained_endpoints 必须为 0

# ---- 7. 出报告 ----
report_qor > $RPT/qor.rpt
report_timing -max_paths 100 -nworst 5 -slack_lesser_than 0 \
              -path_type full_clock_expanded \
              -significant_digits 4 > $RPT/viol_setup.rpt
# setup 违例全量清单，4 位小数，时钟路径展开
report_constraint -all_violators -verbose > $RPT/all_viol.rpt
# 所有类型违例（含 DRV），用于分工
report_constraint -all_violators -max_transition > $RPT/drv_trans.rpt

# ---- 8. 生成 ECO 建议（可选，只在需要修的时候跑）----
if {[sizeof_collection [get_timing_paths -slack_lesser_than 0 -max_paths 1]] > 0} {
  fix_eco_timing -type setup -methods {size_cell} -slack_lesser_than 0
  write_changes -format icctcl -output ./eco/eco_setup_${CORNER}.tcl
  puts "@@@ 已生成 ECO 建议，需人工审核后再交 PR"
}

# ---- 9. 收尾 ----
puts "@@@ 签核跑完，报告在 $RPT/"
exit
```

每个"为什么这么排"：

1. **库在最前**：`link_design` 依赖它，晚设等于白设。
2. **网表第二**：没有 design 就没有对象，SDC 无从作用。
3. **SPEF 第三**：它挂在 net 上，必须在 design 存在之后。
4. **SDC 第四**：必须在 link 之后（前面踩过这个坑）；放在 SPEF 之后也没问题，因为它只依赖对象名。
5. **derate 第五**：它是计算参数，必须在出报告之前。
6. **检查第六**：先确认分母完整，再看分子。
7. **报告第七**：全部重定向到文件，屏幕只留 `@@@` 打点，便于 `grep @@@ log` 快速判断跑到哪一步。

:::pitfall 脚本里用相对路径，换个目录跑就全错
现象：同事照你的脚本跑，报 `Cannot find the link library`，或者读到了一版旧的 SPEF，报告和你差 0.3ns。

原因：脚本里写的是 `./spef/final.spef`，他在别的目录执行，`./` 指向了别处；更坏的情况是那个目录里恰好有一份旧文件，读进去了但不报错。

处理：签核脚本里**所有输入路径用变量 + 绝对路径**，并在开头 `puts` 一遍所有实际路径（`puts "@@@ SPEF: [file normalize $spef]"`），日志里留证据。
:::

## 工作中怎么用：签核在项目里的位置 {#in-work}

**谁做**：STA 签核工程师。PR 工程师负责提供干净数据并做第一轮自检，签核工程师负责独立复算和签字。小团队里是同一人做两遍，但必须换 session、换目录、换脚本。

**时间线**（典型项目，示意）：

| 阶段 | 签核做什么 | 输出 |
|---|---|---|
| 综合后 | 快速评估（ideal clock、估算线负载） | 频率能不能达到的初判 |
| 布局后 | 用估算 RC 跑，找系统性问题 | 架构/约束问题清单 |
| CTS 后 | 用真实时钟树跑，hold 首次全量暴露 | hold 违例清单给 PR |
| 布线后 | 用真 SPEF 跑，这是第一次"接近签核" | WNS/TNS 趋势 |
| 流片前 | 全 corner 全模式 + OCV + SI，冻结版 | 签核报告 + waiver 清单 |

**交付物**：每个场景一份报告目录（`rpt/`），一份汇总表（WNS/TNS/NVP 逐场景），一份 waiver 清单，一份"输入版本记录"（netlist/SDC/SPEF/库的版本号）。

**做错了会怎样**：签核是最后一道关。这里放过一条真违例，前面所有工作都白做。反过来，过度悲观导致不必要的降频或重复 ECO，也是实打实的损失——**签核工程师的价值在于"准"，不是"严"**。

:::lab 动手：跑一次最小签核并写一份结论
**任务**：用课程环境里 05-02 的练习数据（`~/backend_lab/signoff/` 下有 `final.v`、`final_ss_cmax.spef`、`func.sdc`、`lib/` 目录），跑完一次 PT 签核，输出一份 200 字结论。

**步骤**：
1. 按上面脚本改成绝对路径，`pt_shell -f signoff_ss.tcl`。
2. 看 log 里的 `@@@ 黑盒数量`，必须为 0；不为 0 就先去补库。
3. `grep -E "no_clock|unconstrained" rpt/ss/check_timing.rpt`，必须无输出。
4. 打开 `rpt/ss/viol_setup.rpt`，抄下最差一条的：起点、终点、arrival、required、slack、`Incr` 最大的那一级。
5. 打开 `rpt/ss/qor.rpt`，抄 WNS / TNS / NVP。

**过关标准**：结论里必须包含这五句——最差路径在哪、差多少、差在哪一级、属于 setup 还是 hold、下一步建议（修逻辑 / 换单元 / 查约束）。写不出"差在哪一级"，说明还没会读报告。

**如果课程环境跑不了 PT**：用现成的报告文件做第 4、5 步，一样能练"逐列读报告"。真实项目里你会看到的就是这种格式，只是路径名和数值不同。
:::

:::quiz
为什么 PR 工具里 WNS 是正的，PT 一跑变负？|常见四因：PR 用估算 RC 而 PT 读真 SPEF；PR 用 ideal clock 而 PT 用 propagated；PR 没开全 OCV；两边 SDC 版本不一致。
`read_parasitics` 之前必须先做什么？|先 `read_verilog` + `link_design`。SPEF 挂在 net 上，没有 design 就没有对象可挂。
SDC 读在 `link_design` 之前会怎样？|`get_ports` 返回空，`create_clock` 等约束静默失效，PT 只给 warning 不报错，报告里没有时钟也没有路径。
`set_input_delay -max 1.6` 这个 1.6 是怎么来的？|上游器件 Tco 最大值 + 板级走线最大延迟；`-min` 则用两者的最小值。
报告里 `Incr` 和 `Path` 两列的区别？|`Incr` 是进入该节点所花的延迟（这一步），`Path` 是从起点到该点的累计时间。找瓶颈看 `Incr`。
required time 由哪几项拼成？|周期 + 捕获时钟网络延迟 − clock uncertainty − library setup time（hold 检查则是 + hold time，且用同沿）。
OCV 的 derate 1.05/0.95 对 setup 检查具体作用在哪？|发射侧（数据路径 + 发射时钟）按 1.05 变慢，捕获时钟按 0.95 变快，两者共同压缩可用时间。
CPPR 在修什么？|发射和捕获时钟的公共路径被同时按 late 和 early 算了两次，产生虚假悲观量，CPPR 把它加回来。
AOCV 相比 OCV 的核心改进？|按逻辑深度/物理距离查表：路径越长相对偏差越小，derate 更小，比统一系数更准也没那么悲观。
check_timing 报 `unconstrained_endpoints` 不为 0，还能看 WNS 吗？|不能。分母不全，WNS 只覆盖了受约束的那部分路径，通过率没有意义。
签核里 hold 为什么要求比 setup 更严？|setup 违例可以降频规避，hold 违例降频反而更差，无法用频率换，必须真正清零并留余量。
什么样的违例不该用 ECO 修？|系统性问题：违例散落在大量不相关模块、每条都差得多、`Incr` 无大头；根因通常是约束错误、库不对或频率定太高。
:::
