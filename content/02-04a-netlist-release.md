## 网表不是一份，是一串 {#why}

:::goal 能说出网表的命名规则与常见后缀；能画出 Release 路径结构（项目/ME|DE/模块/文件）；能说清 S1 与 S2 网表各用来干什么；能解释 instance 数量波动与模块形状变更对 PR 的影响；能说出"最后一版网表定责"这条规矩为什么重要。
:::

课上讲"网表是前段综合之后给到后端的文件"，听起来像一次性交付。实际项目里它是**连续迭代的一串版本**：V1.0、V1.1、V2.0……一直迭代到 V9.0 甚至更多。

**你拿错版本、或者拿的是别人改过的旧版本，后面几周的活全白干**——所以这一课的内容虽然不"技术"，却直接决定你会不会白加班。

## 命名规则：模块名 + 后缀 {#naming}

网表文件的后缀常见三种：

| 后缀 | 含义 |
|---|---|
| `.v` | 明文 Verilog 网表 |
| `.v.gz` | gzip 压缩的 Verilog（**最常见**，体积小） |
| `.gz` | 压缩包（有的流程把多个文件打一起） |

命名规则只有一条：**文件名主体 = 模块名，小写**。

```
模块叫 ALU   →   alu.v.gz
模块叫 IOU   →   iou.v.gz
```

:::tip 为什么必须小写、必须用模块名
因为脚本里会拿模块名拼路径与变量（`set top alu`、`read_netlist ./data/${top}.v.gz`）。名字大小写混用或改名，脚本就找不到文件——**而这类报错往往发生在半夜跑批的时候**。
:::

## Release：一个动作，也是一个路径 {#release}

:::term Release | 交付/上传
在项目语境里是个**动作**：把本地综合好的网表**上传到服务器上约定的共享路径**，让下游（后端）能取到。

注意它不是"发个邮件"，而是"放到那个大家都能访问的目录里"。
:::

路径结构（Linux 服务器上的典型形态）：

```
/proj/<项目名>/                      ← 项目根目录
├── ME/                              ← 中端（后端/综合相关）的 release 目录
│   ├── alu/
│   │   └── alu.v.gz                 ← ALU 模块的综合后网表
│   └── iou/
│       └── iou.v.gz
└── DE/                              ← 前端（Design Engineer）的 release 目录
    └── alu/
        └── alu_rtl_v2.v               ← 前端交付的 RTL 等
```

记住两条：

- **ME 放综合后的东西**（网表为主），**DE 放前端的东西**（RTL、仿真模型等）；
- **ME 下面是按模块名分的子目录**，你的网表就躺在自己模块的目录里。

:::tip 交接时最该问的一句话
"**这个模块的 release 路径在哪？**"

接手别人的模块、或者前端 owner 找不到人时，第一件事不是要代码，而是要**路径**。有了路径，版本、时间戳、谁传的，一眼就能看出来。
:::

## S1 与 S2：两版网表，两种用途 {#s1s2}

项目里你会拿到两次"正式"网表：

| 版本 | 内容 | 用来干什么 |
|---|---|---|
| **S1** | **纯功能（func）网表**，没插扫描链 | 检查 RTL 从 v1.0 到 v2.0 时**内部逻辑增长了多少**（instance 数变化），先把面积与可行性摸清 |
| **S2** | 插入 **scan chain** 之后的最终版 | **后续所有分析、签核都基于 S2** |

:::term Scan Chain | 扫描链
DFT 部门在网表里插入的测试结构：把大量触发器串成一条（或多条）移位链，让测试机能用少量引脚把内部状态扫进扫出。**它会让网表变大、路径变长**，所以 PR 必须专门为它做优化。
:::

所以流程是：**S1 到手先估算面积 → S2 到手才是真正要做的版本**。很多新人拿到 S1 就开始认真做 floorplan，做完发现 S2 涨了 20% 逻辑，全部推翻。

## 数量波动：200 万 → 400 万 → 300 万 {#instance}

:::term instance | 实例
网表里每一个"被用到的单元"就是一个 instance。**instance 数直接对应面积**，是判断"这块能不能做下"的第一指标。
:::

文档给的真实情形，值得完整走一遍：

1. S1 网表 200 万 instance，按面积算能放下；
2. 插了 scan chain 的 S2 变成 **400 万**——面积做不下了；
3. 后端反馈给顶层/前端：**逻辑增长过多，面积装不下**；
4. 前端回去优化代码，出 V3.0，instance 回落到 **300 万**；
5. 若 scan 插入导致门数异常激增（比如预估 250 万实际 300 万），要找 **DFT 同事**确认原因——**DFT 有时能优化 scan 文件**（文档提到 100 万优化到 50 万这种量级）。

:::pitfall 闷头做，不反馈
**现象**：拿到 400 万的网表，硬着头皮把面积压到极限，密度打到 95%，最后 route 绕不通、时序全崩。

**正确做法**：instance 数一超预算就**立刻反馈**，让前端/DFT 处理。**面积是上游给的，不是你硬扛出来的**——硬扛的结果是后期加班到凌晨还收不了敛。
:::

## 形状变更：为什么两个月的工作会重做 {#shape}

文档里那段关于 L 型的描述，是后端最真实的痛：

```
   矩形              长条形            L 型             两个 L
 ┌───────┐        ┌───────────┐     ┌─────┐          ┌───┬───┐
 │       │        │           │     │     │          │   │   │
 └───────┘        └───────────┘     │     └────┐     │   └───┤
                                    └──────────┘     └───────┘
```

为什么会变形？因为**顶层受面积和其他模块的限制**，把你这一块的形状切成了 L 型、LU 型，或者干脆拆成两个：

- 端口位置全变了（原来在左边，现在可能在上边）；
- Memory 的摆法必须重排——**不同形状下"memory 摆哪"的答案不一样**，要看数据流怎么走；
- 形状不一样就**没法复用**上一版的布局，同一个 block 你可能要做**多版 plan**。

:::tip 一句必须记住的话
**"代码是一样的，手工活是不一样的。"**

网表版本没变、RTL 一个字没改，但只要形状变了，你的 floorplan 就得重做。这是前期 PR 阶段（前七个月）的主要工作量来源。
:::

## Delay 的两层意思 {#delay}

课上专门提过：`Delay` 这个词在项目里有两层含义。

| 含义 | 例子 |
|---|---|
| **技术延迟** | 信号从 A 到 B 花了多少 ns（时序分析里的 delay） |
| **协作延迟** | 周三反馈问题，前端说周五改完，你下周一才拿到网表——中间这几天就是 delay |

:::pitfall 项目后期还容许"协作 delay"
**现象**：临近版图冻结，你还在等前端的新网表，等到最后一周才拿到。

**后果**：所有问题堆到最后一周，加班到凌晨一两点也救不回来。

**做法**：**后期必须把交付时间精确到天，问清楚"最晚什么时候给我"，并把不确定的 delay 提前暴露给 leader**。技术 delay 可以优化，协作 delay 只能靠沟通提前锁死。
:::

## 定责：最后一版网表之前，把问题全抛出去 {#responsibility}

这是文档里最重要的一条职场经验，原文很直白：**前端会提供最后一版网表，此后所有逻辑/约束问题都要在此前反馈，否则后端自己背锅。**

拆分一下：

1. **最后一版网表之前**：任何"逻辑太长、面积不够、时钟定义不清、约束不合理"的问题，**立刻提**，最好留邮件/群记录；
2. **最后一版之后**：网表冻结，只能靠 PR 手段（换单元、加 pipeline 不行了、调约束）去凑；
3. **凑不出来**：责任会落到"你当时没说"。

:::tip 怎么"抛"才有效
不是抱怨，而是**带数据提问**：
- "ALU 这条路径组合逻辑 32 级，周期 2ns 下最坏路径差 0.6ns，是否可以在 RTL 里打一拍？"
- "S2 网表 instance 400 万，按当前面积密度 85% 需要 1.2 倍面积，能否优化 scan 或放宽面积？"

**有数字、有选项、有建议**——这种反馈别人才会处理。空口说"做不下"没人理。
:::

## 工作节奏：前期松、后期紧 {#rhythm}

文档讲得很实：

- **前期（PR 阶段前几个月）**：模块做得顺、没有新网表时，确实比较轻松，有的项目不严格打卡；
- **后期（ECO 两个月）**：加班频繁，到晚上九点、十点甚至凌晨一两点都常见；
- **决定因素是前期质量**：前期问题清干净，后期 ECO 相对轻松；前期问题堆到最后一周，后期就是地狱。

**结论很朴素**：这一行的"累不累"不取决于后期多拼，而取决于**前期有没有把问题及时抛出去、把布局留够余量**。

:::lab 在服务器上认一遍路径与版本
在练习终端（或真机）里跑下面几条，练"看路径、看时间、看版本"：

```bash
# 1. 看项目根目录下有哪些 release 目录（ME 是后端，DE 是前端）
ls -l /proj/demo/ 2>/dev/null || ls -l .

# 2. 找自己模块的网表，注意后缀与大小写
find . -name "alu*.v.gz" -o -name "alu*.v" 2>/dev/null | head

# 3. 看时间戳：哪一版最新，谁传的（时间戳比文件名更可信）
ls -lt --time-style=long-iso *.v.gz 2>/dev/null | head -5

# 4. 不解压也能粗看网表里有多少个实例（统计以单元名开头的行）
gzip -dc alu.v.gz 2>/dev/null | grep -c "^[A-Z]" | head -1

# 5. 看网表里 module 名与顶层名是否与约定一致
gzip -dc alu.v.gz 2>/dev/null | grep -m3 "^module"
```

验收标准：能说出这个项目里网表放在哪、最新一版的时间戳是什么、顶层 module 叫什么。
:::
