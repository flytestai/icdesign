## 为什么 floorplan 值这么多学时 {#why}

:::goal 拿到一个设计，能独立算出 die 尺寸和宏单元通道宽度、定出宏单元与 pin 的位置，写出可执行的 `floorPlan` 命令，并用利用率、通道、长宽比、pin 四个数判断这一版能不能往下走。
:::

课表在 floorplan 上安排了 10 学时（本课 4 学时 + 宏单元实战 3 学时 + 相关练习），占整个 Innovus 项目的四分之一。原因不是它难，是它**不可逆**。

装修房子有个常识：先定墙在哪，再买家具。墙砌好了，沙发再贵也只能塞进去。Floorplan 就是砌墙那一步——后面的布局、CTS、布线，全都是"在既定格局里做优化"。

**格局错了，优化救不回来。** 这句话不是口号，可以用数字说明：

- 一个真实教训：六个 SRAM 贴边排成一列，间距按工具默认值给了 6µm。布线跑到 60% 卡死，热图红色区域正好在缝里。回头挪 SRAM，前面 8 小时布局 + 3 小时 CTS + 6 小时布线全部作废，工期损失两天。
- 另一个方向的代价：die 边长多给 7%（280µm → 300µm），面积多 14.8%，一片晶圆能切的 die 少约 13%，单颗成本涨 14.8%。芯片卖一千万颗，这就是一笔真金白银。

所以 floorplan 的每一版都必须回答三个问题：**多大、放哪、留多宽**。答不出来就往下跑，等于把两天的返工预支出去。

:::term Core / Die | 核心区 / 晶粒
**Die** 是整颗芯片的边界，工厂按这个尺寸切；**Core** 是可放标准单元和宏单元的区域，等于 die 减去四周边距（放 IO ring、电源环、密封环）。

`die area = core area + 四周边距`。你算的利用率，分母永远是 core，不是 die。
:::

:::scene 组长的四个问题
周一 floorplan review，组长只问四句，答不上来就得回去改：

1. "利用率多少？"——你答 0.65。他追问："是 std 除以 core，还是除以去掉 macro 的可用区？"你愣了一下。
2. "宏单元通道留了多宽？"——你答 20µm。他问："算过吗，还是工具默认值？"
3. "IO 和封装对过没有？"——你答"def 里带的"。他问："那版 def 是哪天的？"
4. "如果现在改 die 尺寸，重跑要多久？"——你答"大概两天"。他点点头："所以这一版必须一次对。"

这四个问题对应这一课的四个部分：利用率口径、通道估算、pin 来源、返工代价。答得出来，说明你真的想过；答不出来，说明你只是点了一下按钮。
:::

## 三个决定 {#three}

### 决定一：芯片多大

由两个数决定：**标准单元总面积** 和 **目标利用率（utilization）**。

```
core 面积 = 标准单元总面积 ÷ 目标利用率
长宽比 R = 1 时：core 边长 = √core 面积
长宽比 R ≠ 1 时：短边 = √(core 面积 ÷ R)，长边 = 短边 × R
die 边长 = core 边长 + 2 × 边距
```

举例：标准单元总面积 48000µm²，目标利用率 0.62，四边边距各 20µm：

```
core 面积 = 48000 ÷ 0.62 ≈ 77419 µm²
core 边长 = √77419 ≈ 278.2 µm
die 边长  = 278.2 + 20×2 = 318.2 µm
```

边距 20µm 不是随便给的，它要装下：IO ring（焊盘）、电源环（power ring）、密封环（seal ring）、以及 core 到边界的走线通道。**边距给少了，电源环压到 IO 上；给多了，白扔面积。** 40nm 项目常见 15~30µm（典型值）。

| 利用率 | 后果 |
|---|---|
| 0.40 以下 | 芯片白白做大，一片晶圆切得少，成本上升 |
| 0.60~0.75 | 常规区间，好布也好收敛 |
| 0.80 以上 | 走线空间不足，拥塞、DRC 爆炸，甚至布不通 |

不过，"面积 ÷ 利用率"只是算术，真正的 die 尺寸还要同时过三道关。这三道关缺一道，算出来的数就得改：

**约束一：封装。** die 不能比封装基板能容纳的大，也不能小到焊盘排不下。倒装封装（flip chip）还要按 bump 阵列的 pitch 反算——bump 间距 150µm 时，die 边上每一圈能放多少个 bump 是定死的，pin 多了就只能加 die 或加层。**封装是硬边界，通常一票否决。**

**约束二：成本。** die 面积直接乘到晶圆成本上。前面算过：20mm 涨到 22mm，单颗成本涨约 25%。所以"多给 10% 面积保平安"这句话，在 100 万颗的量产上是几百万人民币的差别。面积不是免费的余量，是要签字的东西。

**约束三：布线资源。** 面积太小，轨道不够，拥塞爆炸；面积太大，线变长、延迟变大、功耗上升。所以 die 尺寸不是"越大越安全"——**它有一个两头都难受的窗口**，窗口的下沿是"布得通"，上沿是"成本可接受"。

| 约束 | 给的是什么 | 违反了会怎样 | 谁能改 |
|---|---|---|---|
| 封装 | 最大尺寸、bump/pin 排布 | 封装做不出来，或焊盘对不上 | 封装团队 |
| 成本 | 面积上限 | 单颗成本超标，产品卖不动 | 产品/架构 |
| 布线资源 | 面积下限 | 拥塞、DRC、收敛不了 | 后端自己 |

所以 review 上被问"die 为什么是 318µm"，正确答法不是"算出来的"，而是"**封装允许到 350、成本线在 330、布线下限是 300，我取了 318 留 4% 余量**"。三个数都报出来，才说明你真的定过尺寸，而不是让工具算了一个。

### 决定二：IO 引脚放哪

引脚（pin）位置通常由**封装**决定，不能随便改。但你要检查四件事：

1. **同一组总线连续排布**。32 位数据线如果打散在四边，走线必然交叉，交叉就要换层，换层就多 via、多延迟。
2. **时钟、复位靠近它驱动的区域**。时钟从焊盘到 root 的延迟也算在时序预算里。
3. **电源和地引脚均匀分布**。全挤在一侧，另一侧供电不足，IR drop 难看。
4. **pin 数量和周长匹配**。这是可以算的：

```
每边能放的 pin 数 ≈ 边长 ÷ (pin 宽度 + pin 间距)
总 pin 数 ≈ 4 × 每边 pin 数（四边都放的情况下）
```

手算：die 318µm，周长约 1273µm。pin 宽 8µm、间距 12µm（即 pitch 20µm），每边能放 `318 ÷ 20 ≈ 15` 个，四边约 60 个。

如果设计需要 200 个信号 pin，60 个显然不够，只有三条路：缩小 pitch（12µm → 工艺允许的话）、把 pin 放到多层（flip chip）、或者**加大 die**。这就是"pin 数量会反过来决定 die 尺寸"的场景——先算 pin，再定 die，顺序不能反。

数量算完之后，接下来是"放哪条边"。这一步最容易凭感觉，但判据其实只有一条：信号从哪来。

:::fig fp-io | 黄色是输入、绿色是输出、红色是电源地。三条边的信号各自对应芯片内部不同方向的模块。重点看"每组总线连续排布"这件事，以及电源为什么分散在四边。
:::

从图里要看出什么：**pin 不是按名字排的，是按"它要去哪"排的**。同一组总线打散在四边，走线必然交叉；交叉就要换层，换层就多 via、多延迟、多 DRC。电源分散在四边，是为了让每个方向的单元都能就近取电——这条直接决定后面电源环的宽度算得够不够。

### 决定三：宏单元放哪

先看一眼做完的 floorplan 是什么样，再讲规则——图比文字直观。

:::fig innovus-floorplan | 四角上的蓝色块是 SRAM，中间大片是标准单元区，外侧一圈黄色小方块是 IO 引脚。重点看 SRAM 为什么贴边、以及它们和中间区域之间那条通道的宽度。
:::

从图里要看出什么：**宏单元贴边不是为了好看，是为了让中间留出一整块连续区域**。只有连续区域才能形成完整的长 row、放得下大单元；宏单元一旦散在中间，标准单元区就被切成几块碎片，碎片区放不下大单元，利用率立刻掉几个点。

SRAM、PLL、模拟 IP 这些大家伙，位置一旦定了就基本不动。放的原则：

1. **靠边、对齐**：贴边放，把中间完整区域留给标准单元。
2. **留通道**：宏单元之间的空隙要够走线（下一节给算法）。
3. **朝向正确**：宏单元的引脚要朝向标准单元区域，否则线要绕一大圈。
4. **按连接关系就近**：跟某个模块交互多的 SRAM，放在那个模块旁边。

```
✅ 好：靠边、对齐、通道均匀
┌──────────────────────────┐
│ ┌────┐  ┌────┐           │
│ │RAM │  │RAM │           │
│ └────┘  └────┘           │
│       标准单元区          │
│ ┌────┐                   │
│ │RAM │                   │
│ └────┘                   │
└──────────────────────────┘

❌ 差：散在中间、朝向乱、贴死
┌──────────────────────────┐
│      ┌────┐              │
│      │RAM │┌────┐        │
│      └────┘│RAM │        │
│  ┌────┐    └────┘        │
│  │RAM │  标准单元区       │
└──────────────────────────┘
```

朝向用四个代码控制，必须记：

| 代码 | 含义 | 什么时候用 |
|---|---|---|
| `R0` | 不翻转 | 默认 |
| `MY` | 沿 Y 轴镜像（左右翻） | pin 在左侧、需要朝右时 |
| `MX` | 沿 X 轴镜像（上下翻） | pin 在下侧、需要朝上时 |
| `R180` | 旋转 180° | 少用，容易把 pin 转到背面 |

:::term Utilization | 利用率
标准单元总面积 ÷ 可放置标准单元的面积。

**分母的口径必须说清**，这是 review 时最容易被问倒的地方：

- 口径 A（粗）：`std 面积 ÷ core 面积`
- 口径 B（工具常用）：`std 面积 ÷ (core 面积 − macro 面积 − placement blockage)`

两个数能差 20 个百分点。报数时先说口径，再报数字。
:::

:::term Macro | 宏单元
预先设计好的大块功能单元：SRAM、ROM、PLL、ADC、模拟 IP。特点是面积大（可能占芯片 5%~20%）、形状固定、引脚位置固定、只能 90° 翻转。

后端对宏单元只能"摆"，不能"改"。**它摆错位置的代价，比一万个标准单元摆错还大。**
:::

## 利用率到底怎么算 {#util}

先给严格定义，再给手算，最后说口径陷阱。

```
std_util = std_cell_area / (core_area - macro_area - blockage_area)
```

分子只算标准单元的总面积（buffer/inverter 算在内，macro 不算），分母是"真正能摆标准单元的地板面积"。工具 `report_area` 报的 utilization 通常就是这个口径，所以你自己估的时候也要这么算，否则和工具对不上。

手算一次，把口径差异看清：core 面积 100000µm²，macro 占 30000µm²，std 面积 45000µm²。

- 口径 A：`45000 ÷ 100000 = 45%` —— 看起来还很松
- 口径 B：`45000 ÷ (100000 − 30000) = 64.3%` —— 实际已经很紧了

同样一个设计，两种说法差 19 个百分点。**如果你按 45% 报"还能加逻辑"，下一版就布不通。**

这五个数字都不是拍出来的，每个都能追到源头。报数时能被追问"这个数哪来的"，才算真的算过：

| 数字 | 例子里的值 | 从哪来 | 怎么核 |
|---|---|---|---|
| std_cell_area | 45000 µm² | 综合报告的 cell area | 用单元数 × 平均面积交叉验，差 >5% 查网表版本 |
| macro_area | 30000 µm² | 每个 SRAM 的 LEF `SIZE` 宽×高，累加 | `dbGet` 逐个取 `box` 算面积，别用目录里抄的旧数 |
| core_area | 100000 µm² | floorplan 定完的 core 边界 | `dbGet top.fPlan.coreBox` 直接读，别用 die 面积 |
| blockage_area | 未计入上例 | halo + 硬禁放区，逐块累加 | 加完 halo 必须重算分母，否则利用率是假的 |
| 目标利用率 | 0.62 | 经验区间 0.60~0.75 | 看上一版拥塞报告再定，不是固定值 |

**分母每减一块，利用率就涨一截。** 加了 halo、加了电源走廊禁放区、加了 tap cell 占位，分母都会变小——所以"加完 halo 之后利用率从 62% 跳到 78%"不是工具算错，是你没重算分母。

:::fig util-overview | 四个方格是同一个设计在四种利用率下的密度，右边是各自的风险。下面那行手算把"12000 个单元需要多大芯片"算成了具体数字。重点对比 0.75 和 0.85 两格的颜色深浅。
:::

从图里要看出什么：**利用率不是"越高越省"，而是"过了一个点就开始还债"**。0.60~0.75 之间是缓冲带，超过之后每省 1% 面积，都要在布线阶段用几个小时调试换回来。图上手算那行也说明了分母是什么——是"可用 row 面积"，不是 die 面积。

再看利用率怎么反过来决定 die 尺寸。同一个 48000µm² 的设计：

| 目标利用率 | core 面积 | core 边长 | die 边长（含 20µm 边距） | 相对 0.62 的面积变化 |
|---|---|---|---|---|
| 0.55 | 87273 | 295.4 | 335.4 | +11.1% |
| 0.62 | 77419 | 278.2 | 318.2 | 基准 |
| 0.72 | 66667 | 258.2 | 298.2 | −12.2% |

利用率从 0.62 提到 0.72，die 面积小 12%，看起来省了钱；但走线空间也少了 12%，很可能在布线阶段用两天的调试换回来。**这就是"省钱"和"能收敛"的取舍**，成熟做法是先按 0.60~0.65 起步，看拥塞报告再决定要不要收紧。

:::pitfall 利用率报错口径，review 时被问穿
现象：你报"利用率 48%"，组长打开工具一看是 68%，当场质疑你的数据。

原因：你算的是 `std ÷ core`（严格说还得再减掉 macro），工具算的是 `std ÷ 可用 row 面积`（core 去掉 macro 和 blockage）。分母小了一圈，比例自然大。

怎么避免：统一用工具的口径，并且报数时加一句"std/可用区"。自己手算时也要先减掉 macro 面积。
:::

## 宽高比：为什么拉长就难布 {#aspect}

**长宽比（aspect ratio）** 是 core 的长边 ÷ 短边。通常取 1（正方形）。

理由可以从周长算出来。同样面积下，正方形周长最短：

| 长宽比 | 尺寸（面积 77419µm²） | 周长 | 相对正方形 |
|---|---|---|---|
| 1.0 | 278 × 278 | 1113 | 基准 |
| 2.0 | 394 × 197 | 1181 | +6.1% |
| 3.0 | 482 × 161 | 1285 | +15.5% |
| 4.0 | 557 × 139 | 1391 | +25.0% |

周长变长意味着什么？**所有从边界进出的信号（IO、电源）平均要绕更远的路**。更麻烦的是布线资源：

- 横向走线通道数 ∝ core 高度
- 纵向走线通道数 ∝ core 宽度

拉成 4:1 的长条之后，短边方向的通道数只剩正方形的 1/2，而长边方向的连线却变长了。结果是**一个方向资源过剩、另一个方向严重不足**，工具只能疯狂换层绕线，via 数和 DRC 一起涨。

把四个长宽比放在一起，三个数字会同时恶化——最长路径、短边通道数、平均线长：

| 长宽比 | 尺寸（面积 77419µm²） | 对角线（最长线下限） | 短边通道数（2µm pitch） | 平均线长（估算） |
|---|---|---|---|---|
| 1.0 | 278 × 278 | 393 µm | 139 条 | 基准 100% |
| 2.0 | 394 × 197 | 441 µm | 99 条 | 约 112% |
| 3.0 | 482 × 161 | 508 µm | 80 条 | 约 125% |
| 4.0 | 557 × 139 | 574 µm | 70 条 | 约 140% |

三个数一起读：

- **对角线涨 46%**（393 → 574）。这是"再远也远不过这个数"的下限，跨片长路径的延迟按这个量级往上走。
- **短边通道数掉一半**（139 → 70）。这条方向的信号没有足够轨道，只能换到别的层，via 数和 DRC 跟着涨。
- **平均线长涨四成**（估算值，不同设计差异很大）。原因是原本可以在两个方向均匀铺开的连接，被压成了"只能横向走"，纵向的绕行距离被拉长。

平均线长这一项最容易被低估：**它不只影响延迟，还直接乘到功耗上**。线长涨 40%，线电容涨 40%，动态功耗里连线那一份就涨 40%——在高频设计里，连线功耗往往占一半以上。

所以经验值是：**长宽比 1.0~1.2 最好，超过 1.5 要有人签字同意，超过 2.0 基本等于自找麻烦。**

什么情况下会故意拉长？

- 封装尺寸限制（比如必须和某个模组的外形匹配）。
- 芯片要放进特定的产品外壳（窄条形）。
- 宏单元数量太多，正方形排不下，只能拉长换空间。

这三种都是"外部约束"，不是"优化选择"。**能自由选的时候一律选正方形。**

review 时这个数会被直接问："长宽比多少？为什么？"答 1.0 就行；如果不是 1.0，要能说清是被封装、外壳还是宏单元数量逼的，而不是"面积算出来刚好这样"。

:::term Aspect Ratio | 长宽比
core 的长边 ÷ 短边。取 1 时周长最短、两个方向的布线资源最均衡。

超过 1.5 后，短边方向的通道数明显不足，长线被迫换层，via 和 DRC 一起增加。
:::

## 命令怎么写 {#cmd}

Innovus 用 `floorPlan`，ICC2 用 `initialize_floorplan`。参数含义几乎一一对应。

```tcl
# 作用：按尺寸直接定 die（已知芯片多大时用这种方式）
# 用法：init_design 之后、placeInstance 之前执行；site 名要和 LEF 里的一致
floorPlan -site coreSite \
          -d 318 318 20 20 20 20
# -d 后面六个数字：die 宽、die 高、左边距、下边距、右边距、上边距（单位 µm）
```

```tcl
# 作用：按"长宽比 + 利用率"让工具自己算 die 尺寸（最常用）
# 用法：面积还不确定时用；-dieH 用来锁定高度，让工具只算宽度
floorPlan -site coreSite \
          -r 1.0 0.62 20 20 20 20 \
          -dieH 320
# -r 后两个数：长宽比 1.0、目标利用率 0.62；再跟四边边距
# -dieH：把 die 高度钉死在 320µm，工具按长宽比反推宽度
```

参数逐个解释：

| 参数 | 含义 | 给错的后果 |
|---|---|---|
| `-site coreSite` | 用哪种行（row）的站点定义 | 名字写错直接报错；写错种类会导致行高不对、单元放不下 |
| `-d W H l b r t` | 直接给 die 尺寸和四边 core 边距 | 边距太小，电源环压 IO；太大，白扔面积 |
| `-r ratio util` | 长宽比 + 目标利用率，工具反算尺寸 | 利用率给太高，后面布不通 |
| `-dieH H` | 锁定 die 高度 | 只在 `-r` 模式下有意义，用来对齐封装或旧版本 |
| `-f file` | 从文件读 floorplan 定义 | 文件里的坐标和当前 LEF 版本不匹配时会错位 |

`-r` 和 `-d` 的区别要记牢：`-d` 是"我知道多大，照着做"；`-r` 是"我知道多密，你算多大"。**第一版一般用 `-r`**，因为面积估算本来就有误差，让工具按利用率算更稳。

实际项目里这些命令不会手敲，都写在 `02_floorplan.tcl` 里，前面用 `set` 定义 `UTIL`、`MARGIN`、`SITE` 这些变量，提交给批处理跑。这样换一版参数只改一行，报告和数据库也能对应上版本号。

摆宏单元和加保护环：

```tcl
# 作用：摆两个 SRAM，靠左边缘对齐、pin 朝右，并给它们留出禁放区
# 用法：floorPlan 之后执行；坐标单位 µm，原点在 die 左下角
placeInstance u_sram0 40 60 MY       # MY = 沿 Y 轴镜像，让左侧的 pin 翻到右侧
placeInstance u_sram1 40 200 MY      # 与上一个 x 对齐，形成整齐的竖直通道

# 让宏单元四周各留 8µm 不放标准单元，防止标准单元把引脚出口堵死
setPlaceMode -place_global_module_padding {u_sram0 8 u_sram1 8}

# 另一种写法：手动画禁放区，坐标要自己按宏单元 bbox 加 margin 算
# createPlaceBlockage -type halo -box {32 52 148 268} -name halo_sram0

checkFPlan -reportUtil               # 检查重叠、越界，并打印利用率
saveDesign db/02_floorplan.enc       # 存盘；floorPlan 会清掉已有布局，跑之前也先存一版
```

:::term Site / Row | 站点 / 行
标准单元只能摆在"行"（row）上，行由一个个"站点"（site）组成，站点宽度是最小单元的宽度（比如 0.19µm）。

所以单元坐标必须落在站点网格上，否则叫"非法位置"（illegal）。`-site coreSite` 就是告诉工具用哪种行高/站宽。
:::

### 加 pin：`editPin` / `create_io_pin`

网表里的端口只是逻辑名字，**物理位置要另外给**。两种做法：

1. **从 DEF 导入**（真实项目主流）：封装工程师给一份带 pin 坐标的 `.def`，`read_def` 灌进来。
2. **在工具里摆**：用 `editPin`（Innovus 常用）或 `create_io_pin`（部分流程/版本里的叫法），指定边、层、顺序、间距。

```tcl
# 作用：把一组总线 pin 均匀摆到 die 的上边，指定层和间距
# 用法：floorplan 之后执行；pin 名要和网表端口名完全一致
editPin -pin {data[0] data[1] data[2] data[3]} \
        -side Top \
        -layer M5 \
        -spreadType center \
        -spacing 20
# -side：放哪条边（Top/Bottom/Left/Right）
# -layer：pin 所在金属层，通常和封装打线/凸点匹配
# -spreadType：分布方式，center 表示在这一段居中均匀铺开
# -spacing：相邻 pin 的中心距（µm），要和封装的最小 pitch 对过
```

命令名在不同版本/流程里会变（有的写 `create_io_pin`），但四件事不变：**哪条边、哪一层、什么顺序、多大间距**。记这四件事，换工具也能查出来。

:::pitfall pin 位置晚到，floorplan 全推翻
现象：floorplan 做完、布局跑了一半，封装团队发来正式 pin 文件，和你现在摆的位置差了大半圈。

原因：项目启动时用了"临时 pin 假设"，没人跟封装确认最终版本。

怎么避免：floorplan 开始前，把"pin 文件版本 + 日期"写进脚本注释；如果拿不到正式版，就按最坏情况留余量（每条边多留 20% 空间），并在 review 上明确写"pin 待定，风险：可能重做 floorplan"。
:::

## 通道留白怎么估 {#channel}

宏单元之间的缝，是拥塞最高发的地方。留多宽不该靠感觉，可以算。

思路：**数清楚这条通道要过多少根线，再看每根线占多少横向宽度。**

```
通道宽度 = (出线总数 ÷ 可用金属层数) × 每线间距 × 余量
出线总数 = 靠这条通道的引脚数 × 平均每引脚扇出
```

手算一次：两个 SRAM 面对面，各朝通道出 64 个引脚，平均每个引脚 3 根连线（数据 + 控制 + 测试），可用 M2~M5 四层横向走线，40nm 金属 pitch 约 0.28µm，余量 30%。

```
出线总数 = 64 × 3 = 192 根（单侧）
单层需要 = 192 ÷ 4 = 48 根
信号宽度 = 48 × 0.28 = 13.4 µm
加 30% 余量 = 17.5 µm
```

别忘了电源。通道里通常还要穿一条电源条：stripe 宽 8µm，两侧各留 2µm 间距：

```
电源占宽 = 8 + 2×2 = 12 µm
通道总宽 = 17.5 + 12 ≈ 30 µm
```

所以"两个 SRAM 之间留 30µm"是有依据的，不是拍脑袋。工具默认给的 10µm 在这种密度下必然爆。

| 场景 | 建议通道宽度（40nm 量级） |
|---|---|
| 单个小 macro，出线 < 50 | 10~15µm |
| 中等 SRAM，出线 100~200 | 20~30µm |
| 大 SRAM 密集区、多排 macro | 35~50µm |
| 通道里还要走电源 stripe | 在上面基础上 +12~15µm |

:::term Channel | 通道
两个宏单元之间（或宏单元与 core 边界之间）留给走线的空间。

太窄 → 拥塞、DRC 爆；太宽 → 白扔面积、标准单元区被切碎。**它是 floorplan 里少数能算出来的量**，所以 review 时最该被追问。
:::

:::term Power Corridor | 电源走廊
为电源条（stripe）预留的通道，通常在宏单元之间或宏单元与边界之间，宽度要覆盖 stripe 本身加上两侧的间距和通孔阵列。

电源走廊和信号通道经常抢同一块地。**先定电源走廊，再算信号通道还剩多少**，顺序反了会反复改。
:::

:::note 另一种算法：按连线数估
上面是按"引脚数 × 扇出"估，适合早期还没有布线信息的时候。等布局跑完，可以用"实际穿过该区域的连线数 ÷ 层数 × pitch"来复核，方法在第 14 课（宏单元实战）。两种算法互相验证，差得太多说明有一边假设错了。
:::

## floorplan 完成后的自检 {#selfcheck}

跑完 `floorPlan` 不要直接往下做电源，先花十分钟自检。六个检查项，每一项都有明确的通过与不通过：

```tcl
# 作用：floorplan 之后的六项自检，全部通过才允许进电源规划
# 用法：在 Innovus 里 source 这段，或逐条敲；输出贴进交接记录
checkFPlan -reportUtil          # ① 重叠/越界：必须报 no overlap，利用率与目标差 <3%
report_area                     # ② 面积：单元总面积是否与综合报告一致（差 <2%）
dbGet top.fPlan.coreBox         # ③ core 坐标框：确认四周边距真的按预期留出来了
dbGet top.terms.name            # ④ pin 清单：数量和名字能否与封装文件一一对上
checkDesign -all                # ⑤ 一致性：有没有实例落在 core 外面
saveDesign db/02_floorplan.enc  # ⑥ 存盘，并把这一版的六个数字写进交接记录
```

| 检查项 | 通过标准 | 不通过先怀疑什么 |
|---|---|---|
| 利用率 | 与目标差 <3 个百分点 | 面积估算错、口径不对 |
| 宏单元通道 | 每条 ≥ 估算值，无 <10µm 的窄缝 | 没算通道、halo 给太小 |
| 电源走廊 | stripe 不压 macro pin，宽度够 | 先摆了 macro 再想电源 |
| 长宽比 | ≤1.5（最好 ≤1.2） | 为了凑面积硬拉长 |
| pin 与封装 | 数量、边、层、顺序全对 | 用了临时假设版 pin 文件 |
| 重叠/越界 | 0 个 | 坐标算错、朝向搞反 |

前四项是"数"，后两项是"对文件"。**数不对可以调，文件不对要重做**——所以 pin 文件版本一定要在开工前确认。

## 评审只看六个数字 {#review}

floorplan review 不是看图好不好看。有经验的评审只问六个数字，每个数字对应一个决策，答不出就等于这一版没做。

| # | 数字 | 怎么得到的 | 答不出的后果 | 谁最关心 |
|---|---|---|---|---|
| 1 | 利用率（带口径） | std 面积 ÷ 可用 row 面积 | 报错口径，被当场质疑数据 | 组长 |
| 2 | die / core 边长 + 长宽比 | 面积 ÷ 利用率，再定 R | 说不出为什么是这个尺寸 | 架构/成本 |
| 3 | 最窄的那条宏通道宽度 | 按引脚数 × 扇出算，取最小值 | 通道不够，布线 60% 卡死 | 布线 |
| 4 | pin 总数 + 封装文件版本号 | 封装给的 pin 文件，逐条对 | 用了临时假设，可能重做 | 封装 |
| 5 | 电源占用轨道比例 | (ring + stripe 占宽) ÷ pitch | 电源铺完没地方走信号 | 电源/PI |
| 6 | 这一版重跑要多久 | floorplan→place→CTS→route 累加 | 说不出改尺寸的代价，就没法决策 | 项目经理 |

第 6 个数最容易被漏，但它是**唯一决定"要不要现在改"的数**。评审上有人说"这个通道再宽 5µm 更好"，你要能立刻回答"改这一下要重跑 15 小时，值不值"——没有这个数，讨论就变成拍脑袋。

六个数字的正确用法是排成一页纸，每行一个数、一句依据、一个来源：

| 项 | 这一版的值（示例） | 来源 |
|---|---|---|
| 利用率 | 62.0%（std 48000 ÷ 可用 77419） | `report_area` |
| die / core / 长宽比 | 318.2 / 278.2 / R=1.00 | `checkFPlan` |
| 最窄宏通道 | 29.5µm（64 pin × 3 ÷ 4 层 × 0.28 × 1.3 + 12） | 手算表 |
| pin 数与封装版本 | 200 个，封装 rev 1.3（2026-11-10） | `pkg_pin.def` |
| 电源占用 | 17.8%（ring 4µm + stripe 3µm @ 40µm pitch） | power plan 脚本 |
| 重跑代价 | 约 15 小时（fp 2 + place 4 + CTS 3 + route 6） | 上一版实测 |

这一页纸比十张版图截图有用：**图能让人"感觉"对不对，数字才能让人"决定"改不改。**

## 常见返工原因 {#rework}

floorplan 返工，八成是下面五种之一：

| 原因 | 现象 | 根因 | 返工代价 |
|---|---|---|---|
| 利用率拍太高 | 布线 60% 卡住，热图大片红 | 想省面积，按 0.75 起步 | 高：布局起全部重跑，约两天 |
| 宏单元贴死 | 局部 DRC 清不干净 | 没算通道，用默认间距 | 高：同上 |
| pin 位置晚到 | floorplan 做完才发现方向反了 | 没确认封装版本 | 高：可能连 die 尺寸都要改 |
| die 尺寸抄旧项目 | 逻辑放不下，或白扔 15% 面积 | 没按本项目面积重算 | 中高：改尺寸等于坐标全废 |
| 电源条压 macro pin | 宏单元引脚接不出来 | 先摆 macro 后铺电源，没检查 | 中：改 stripe 位置，电源要重铺 |

判断"这一版要不要返工"，有个简单标准：**看问题能不能靠"挪标准单元"解决**。

- 能（拥塞在局部、时序差一点）→ 不用返工，交给布局优化。
- 不能（通道不够、die 放不下、pin 方向错）→ 必须返工，越早越好。

:::pitfall floorPlan 之后再改尺寸，代价很大
`floorPlan` 一旦执行，后面的布局坐标都是相对它的。改尺寸等于重来。

而且 `floorPlan` 会清掉已有布局，**没有确认提示**。跑之前先 `saveDesign`，跑完之后立刻再存一版。

所以第一版宁可留 10% 余量：利用率先给 0.60，跑完看拥塞报告，紧的话下一版再提到 0.68。反过来（先做紧再放松）要重做。
:::

:::pitfall 宏单元贴边但忘了 halo
现象：`checkFPlan` 通过，布局也正常，布线时 macro 周围一圈全是 DRC。

原因：标准单元贴着 macro 摆进去了，把 macro 的引脚出口堵死。工具不会拦你，因为它认为那里"合法"。

怎么处理：给每个 macro 加 halo（`createPlaceBlockage -type halo`），或者在 `setPlaceMode` 里给模块加 padding。halo 宽度按通道估算的一半给，至少 5µm。
:::

:::lab 动手：算一遍你自己的 floorplan
**任务**：给定条件算 die 尺寸和通道宽度，写出 `floorPlan` 命令，并用 `checkFPlan` 验证。

给定：标准单元总面积 48000µm²，目标利用率 0.62，四边边距 20µm，长宽比 1.0；两个 SRAM 各朝通道出 64 个引脚，平均扇出 3，4 层可用，pitch 0.28µm，余量 30%，通道里还要走一条 8µm 的电源条。

```bash
# 作用：把 floorplan 的两个关键数算出来——die 边长、宏单元通道宽度
# 用法：任意目录 python3 直接跑；改 util 或 pins 可以看结果怎么变
python3 - <<'EOF'
area, util, margin = 48000.0, 0.62, 20.0        # 单元总面积、目标利用率、单边边距
core = area / util                               # core 面积
side = core ** 0.5                               # 长宽比 1.0 时的 core 边长
die = side + 2 * margin                          # die 边长 = core + 两侧边距
print("core = %.1f um2, side = %.1f um, die = %.1f um" % (core, side, die))

pins, fanout, layers, pitch, guard = 64, 3, 4, 0.28, 1.3   # 引脚数、扇出、层数、线距、余量
nets = pins * fanout                             # 这条通道要过的线数
sig = nets / layers * pitch * guard              # 信号需要的宽度
pwr = 8 + 2 * 2                                  # 电源条 + 两侧间距
print("signal = %.1f um, power = %.1f um, channel = %.1f um" % (sig, pwr, sig + pwr))
EOF
```

**预期**：`core = 77419.4, side = 278.2, die = 318.2`；`signal = 17.5, power = 12.0, channel = 29.5`。

**再走一步**：把这两个数写成命令并验证。

```tcl
# 作用：用上面算出的数建 floorplan，并检查是否合法
# 用法：Innovus 里 init_design 之后执行；site 名按你的库改
floorPlan -site coreSite -d 318 318 20 20 20 20   # 直接给 die 尺寸和四边 core 边距
checkFPlan -reportUtil                             # 看利用率是否接近 0.62、有无 overlap
```

**过关标准**：能说出三件事——die 边长为什么是 318 而不是 278（差的是两侧边距）；把利用率改成 0.78 后 die 变小多少、为什么更危险；通道 29.5µm 里信号和电源各占多少。
:::

:::quiz
利用率的定义是什么？两种口径差在哪？|标准单元总面积 ÷ 可放置标准单元的面积。粗口径分母是 core 面积，工具口径分母是 core 减去 macro 和 blockage，两者能差 20 个百分点。
利用率 0.85 会有什么问题？|走线空间不足，容易严重拥塞、DRC 大量违例，甚至布不通；省下的面积往往要用几天调试换回来。
宏单元的 pin 朝向为什么重要？|pin 朝向标准单元区，连线可以直接拉出；朝错方向线要绕一大圈，增加延迟和拥塞。
`floorPlan -r 1.0 0.62 20 20 20 20` 里各参数是什么意思？|长宽比 1.0、目标利用率 0.62、四边 core 边距各 20µm；工具按这些反算 die 尺寸。
`-d` 和 `-r` 两种方式怎么选？|`-d` 是已知 die 尺寸照着做；`-r` 是已知目标密度让工具算尺寸。第一版面积估算有误差，通常用 `-r`。
为什么第一版 floorplan 宁可留余量？|因为改尺寸会导致后面所有坐标失效，等于重做；先松后紧比先紧后松代价小。
为什么长宽比越大越难布？|同样面积下周长变长，IO 平均绕远；更关键的是短边方向通道数 ∝ 宽度，拉长后一个方向资源严重不足，长线被迫换层。
通道 30µm 是怎么算出来的？|出线数 = 引脚 64 × 扇出 3 = 192，单层 48 根 × 0.28µm = 13.4µm，乘 1.3 余量得 17.5µm；再加电源条 8µm 和两侧间距 4µm，共约 30µm。
floorplan 做完要检查哪几项？|利用率（口径一致、与目标差 <3%）、宏通道宽度、电源走廊不压 pin、长宽比 ≤1.5、pin 与封装一致、无重叠越界。
:::

- 会用"面积 ÷ 利用率"估 core 尺寸，并加边距得到 die 尺寸
- 能说清利用率的两种口径，报数时主动说明分母
- 知道利用率的安全区间和过高/过低的后果
- 能说出宏单元摆放的四条原则，并会选 `R0/MX/MY/R180`
- 能手算一次通道宽度（引脚数 × 扇出 ÷ 层数 × pitch × 余量 + 电源）
- 能解释长宽比为什么影响布线资源，并给出 1.5 这个阈值
- 知道 `-site`、`-d`、`-r`、`-dieH` 四个参数的含义与风险
- 能按顺序跑完六项自检，并说出每项的通过标准
:::
