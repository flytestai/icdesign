## 为什么 floorplan 值这么多学时 {#why}

课表在 floorplan 上安排了 10 学时，占整个 Innovus 项目的四分之一。原因很简单：

**floorplan 定了，后面的布局、CTS、布线都只是在既定格局里优化。格局错了，优化救不回来。**

一个真实的教训：宏单元（SRAM）贴得太近，中间没留通道，布线阶段这块区域永远布不通。回头把 SRAM 挪开，前面 8 小时的布局和 CTS 全废。

## 三个决定 {#three}

### 决定一：芯片多大

由两个数决定：**总面积** 和 **利用率（utilization）**。

```
核心面积 = 标准单元总面积 ÷ 利用率
芯片面积 = 核心面积 + IO 环宽度 + 边距
```

举例：标准单元总面积 50000 µm²，目标利用率 0.65：

```
核心面积 = 50000 / 0.65 ≈ 76923 µm²
若做成正方形：边长 ≈ 277 µm
```

| 利用率 | 后果 |
|---|---|
| 0.40 以下 | 芯片白白做大，一片晶圆切得少，成本上升 |
| 0.60~0.75 | 常规区间，好布也好收敛 |
| 0.80 以上 | 走线空间不足，拥塞、DRC 爆炸，甚至布不通 |

:::term Aspect Ratio | 长宽比
芯片的长 ÷ 宽。通常取 1（正方形），因为正方形周长最短、走线最均衡。

特殊情况下会拉长（比如要和封装尺寸匹配），但长宽比超过 1.5 就会明显难布。
:::

### 决定二：IO 引脚放哪

引脚位置通常由**封装**决定，不能随便改。但你要检查：

- 同一组总线（比如 32 位数据）的引脚最好连续排布，否则走线会交叉。
- 时钟、复位这类关键信号，离它要驱动的区域越近越好。
- 电源和地引脚要均匀分布，否则局部供电不足。

### 决定三：宏单元放哪

SRAM、PLL、模拟 IP 这些大家伙，位置一旦定了就基本不动。放的原则：

1. **靠边、对齐**：贴边放，把中间完整区域留给标准单元。
2. **留通道**：宏单元之间的空隙要够走线（后面 03-03 专门算）。
3. **朝向正确**：宏单元的引脚（pin）要朝向标准单元区域，否则线要绕一大圈。
4. **按连接关系就近**：跟某个模块交互多的 SRAM，放在那个模块旁边。

```
✅ 好：靠边、对齐、通道均匀
┌──────────────────────────┐
│ ┌────┐  ┌────┐           │
│ │RAM │  │RAM │           │
│ └────┘  └────┘           │
│       标准单元区          │
│ ┌────┐                   │
│ │RAM │                   │
│ └────┘                   │
└──────────────────────────┘

❌ 差：散在中间、朝向乱、贴死
┌──────────────────────────┐
│      ┌────┐              │
│      │RAM │┌────┐        │
│      └────┘│RAM │        │
│  ┌────┐    └────┘        │
│  │RAM │  标准单元区       │
└──────────────────────────┘
```

## 命令怎么写 {#cmd}

```tcl
# 方式一：按尺寸直接定（已知芯片多大）
floorPlan -site coreSite \
          -d 280 280 20 20 20 20
# -d 后面四个数字：宽 高 左 下 右 上 边距

# 方式二：按利用率自动算（更常用）
floorPlan -site coreSite \
          -r 1.0 0.65 20 20 20 20 -dieH 280
# -r 长宽比 利用率，工具自己算 die 尺寸

# 摆宏单元（举例：两个 SRAM，靠左边缘对齐）
placeInstance u_sram0 40 60 MY      # MY = 镜像朝向，让 pin 朝右
placeInstance u_sram1 40 200 MY

# 加 IO 引脚（如果网表里没有）
# 实际项目多用 def 文件导入引脚位置，比手写可靠

# 加边界的特殊处理（可选）：endcap / tap cell
addEndCap
addWellTap -cell FILLTAP -cellInterval 40

# 检查
checkFPlan
saveDesign db/02_floorplan.enc
```

:::term Site / Row | 站点 / 行
标准单元只能摆在"行"（row）上，行由一个个"站点"（site）组成，站点宽度是最小单元的宽度（比如 0.19µm）。所以单元坐标必须落在站点网格上，否则叫"非法位置"（illegal）。

`-site coreSite` 就是告诉工具用哪种行高/站宽。
:::

:::pitfall floorPlan 之后再改尺寸，代价很大
`floorPlan` 一旦执行，后面的布局坐标都是相对它的。改尺寸等于重来。

所以**第一版宁可留 10% 余量**：利用率先给 0.60，跑完看拥塞报告，紧的话下一版再提到 0.68。反过来（先做紧再放松）要重做。

另外：`floorPlan` 会清掉已有布局，但没有确认提示。跑之前先 `saveDesign`。
:::

:::scene 组长的三个问题
review 的时候，组长通常只问三句：

1. "利用率多少？"（0.65）
2. "宏单元通道留了多宽？"（按 03-03 的方法算出来的数）
3. "IO 有没有和封装对过？"（引脚文件哪来的）

答得出来，说明你真的想过；答不出来，说明你只是点了一下按钮。
:::

:::lab 动手：算一遍你自己的 floorplan
给定条件：

- 标准单元总面积：48000 µm²
- 目标利用率：0.62
- 边距每边 20µm
- IO 环宽忽略

```bash
python3 - <<'EOF'
area = 48000
util = 0.62
core = area / util
side = core ** 0.5
die = side + 20 * 2
print("core area  = %.1f um2" % core)
print("core side  = %.1f um" % side)
print("die side   = %.1f um" % die)
print("实际利用率 = %.3f" % (area / (side * side)))
EOF
```

预期：

```
core area  = 77419.4 um2
core side  = 278.2 um
die side   = 318.2 um
实际利用率 = 0.620
```

过关标准：把利用率改成 0.78 再算一次，说出"边长变小了多少、为什么这个版本更危险"。
:::

:::check
- 会用"面积 ÷ 利用率"估核心尺寸
- 知道利用率的安全区间和过高/过低的后果
- 能说出宏单元摆放的四条原则
- 知道 `-site`、`-r`、`-d` 三个参数的含义
- 记得 floorplan 前后都要 `saveDesign`
:::

:::quiz
利用率的定义是什么？|标准单元总面积 ÷ 核心可用面积。
利用率 0.85 会有什么问题？|走线空间不足，容易严重拥塞、DRC 大量违例，甚至布不通。
宏单元的 pin 朝向为什么重要？|pin 朝向标准单元区，连线可以直接拉出；朝错方向线要绕一大圈，增加延迟和拥塞。
`floorPlan -r 1.0 0.65 20 20 20 20` 里各参数是什么意思？|长宽比 1.0、利用率 0.65、四边边距各 20µm。
为什么第一版 floorplan 宁可留余量？|因为改尺寸会导致后面所有坐标失效，等于重做；先松后紧比先紧后松代价小。
:::
