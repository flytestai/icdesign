## 版图画完，为什么还是不知道它有多慢 {#why}

:::goal 学完这一课，你能说清一条长线为什么会慢、能读懂一份 SPEF 的四个主要段，并在拿到提取结果时先查三件事：名字对不对、层映射对不对、网络全不全。
:::

布线器把线连上了，只证明"电气上通了"，不证明"速度够快"。

一条路径的延迟由两部分组成：单元内部延迟（门延迟）和线延迟。40nm 以前的工艺，门延迟占大头，线可以当理想导线；40nm 以后，线宽变细、线间距变小，线延迟占一条路径的比例轻松超过 40%，长线甚至到 60% 以上。也就是说，**同样一条逻辑路径，线画得长一点还是短一点，结果可能差一倍**。

线的延迟从哪来？金属有电阻，相邻金属之间有电容。这两个参数合起来写成 **RC（电阻-电容）**，它们不是设计者手填的数字，而是要从版图的真实几何里"提取"出来。

:::term RC Extraction | 寄生参数提取
根据布线后的版图几何（每层金属的长度、宽度、厚度、与邻居的距离）和工艺的电阻电容模型，计算出每一段网络的电阻和电容，输出成工具能读的寄生参数文件。它发生在布线之后、时序签核之前。
:::

:::term Parasitics | 寄生参数
不是设计者故意加的元件，而是版图结构"顺带"产生的电阻、电容（有时还有电感）。它们客观存在，不能删除，只能通过改版图或改约束去控制。
:::

:::scene 周三下午，PT 比 PR 慢了 0.4ns
你刚跑完 route，Innovus 里 `report_timing` 显示 WNS +0.08ns，勉强算过。leader 让你用 PrimeTime 复算，你读进 SPEF 后 WNS 变成 −0.32ns。leader 只问了三个问题："SPEF 是 route 之后那一版吗？rcworst 读的是哪个文件？十二个 corner 都齐吗？"

你打开 `spef/` 目录，看到 `soc_top_cworst.spef`、`soc_top_rcworst.spef`、`soc_top_cbest.spef` 等文件，时间戳有先有后，还有一个文件名写着 `_old`。这一刻你才意识到：**提取不是"跑一下"就完了，它有自己的输入、版本和 corner。**
:::

### 估算和提取，差在哪

布局布线工具在各个阶段都会算 RC，但"算"的方式完全不同：

| 阶段 | RC 从哪来 | 典型误差 | 用途 |
|---|---|---|---|
| placement 前 | 按扇出、线长统计模型估 | 30%~50% | 只看大致趋势 |
| trial route | 按虚拟布线路径估 | 15%~30% | 指导布局优化 |
| route 后工具内提取 | 按真实几何查表算 | 5%~15% | 边做边修 |
| signoff 提取（StarRC/QRC） | 真实几何 + 完整工艺模型 + 耦合 | 基准 | 签核、ECO 依据 |

"估算"的本质是**用统计规律猜**：工具看到这个引脚扇出是 4、平均线长 30µm，就套一个经验公式。它不知道这条线实际绕了两个弯、旁边正好有一条同时翻转的时钟线。提取则是**按真实几何算**：这条线有多长、多宽、上下左右各是什么、邻居会不会动，全都进模型。

所以差距不是"工具准不准"，而是"有没有看图纸"。短线两者差不多；长线、宽线、密集并行线，差距能到 2 倍。

:::fig inputs-map | 这张图列的是后端开工要凑齐的七类输入。RC 提取这一格的关键不是"有没有文件"，而是"工艺模型和层映射是不是与这一版 PDK 匹配"——拿错版本的 ITF，后面所有 corner 都会算错。
:::

## 金属线为什么有电阻和电容 {#rc}

把金属线想成水管：管子越细越长，水流越难通过，这是电阻；管壁有弹性，水压变化时管壁会先"存"一点水，这是电容。芯片里的金属线同时具备这两种性质，而且信号频率越高，电容充放电占的时间越多。

### 电阻：用"方块"来数

工艺厂给出的不是"每微米多少欧"，而是 **方块电阻（sheet resistance）**，单位 Ω/□。意思是：把这段金属看成若干个正方形拼起来，每个正方形贡献一个固定电阻，与正方形的大小无关。

`R = Rs × (L / W)`

- `Rs`：方块电阻，40nm 铜互连典型值 0.02~0.1 Ω/□，层越底层越薄、Rs 越大。
- `L / W`：长宽比，也就是"几个方块"。线宽减半，方块数翻倍，电阻翻倍。

### 电容：对地电容 + 耦合电容

单位长度电容 `Ca` 典型 0.2 fF/µm（对地），旁边有邻居时还要加 **coupling capacitance（耦合电容）**，量级 0.1~0.3 fF/µm，取决于间距。

`C_total = Ca × L + C_coupling`

耦合电容的特殊之处：它连接的是两条信号线，不是地。邻居翻转时，会通过它往你的线上"灌"电荷，这就是后面串扰（crosstalk）的根源。提取时如果不算耦合，电容会少一大块，延迟算得偏乐观。

:::term Coupling Capacitance | 耦合电容
两条相邻金属线之间的电容。它的大小与间距成反比，与并行长度成正比。邻居翻转时通过它影响本网络的波形，是串扰和延迟变化的来源。
:::

:::fig chip-stack | 这张图画的是金属层剖面：越往上线越厚、越宽，方块电阻越小。看两个地方——下层细线（M1/M2）电阻大，适合短距离；上层厚金属（M7/M8）用来做电源和长距离主干。提取时同一段长度在不同层上的 RC 可以差好几倍。
:::

### 手算：一条 200µm 的 M3 线有多慢

取 40nm 典型值：M3 宽 0.1µm，方块电阻 0.05 Ω/□，单位长度电容 0.2 fF/µm，忽略耦合。

1. 方块数：`200 / 0.1 = 2000` 个。
2. 电阻：`R = 2000 × 0.05 = 100Ω`。
3. 电容：`C = 200 × 0.2 = 40 fF`。
4. 用 **Elmore 延迟** 估：`0.69 × R × C = 0.69 × 100 × 40f = 2.76ns`。

2.76ns 是什么概念？一个 40nm 的普通反相器延迟约 30~50ps。也就是说，**光这一根线，就相当于 60 个门串起来**。如果时钟周期是 2.5ns，这条线自己就把周期吃光了。

:::term Elmore Delay | 埃尔莫尔延迟
用一阶 RC 网络近似计算"信号从 0 爬到 50%"的时间，公式 `t = 0.69 × R × C`（0.69 = ln2）。它把分布式 RC 线简化成一个集中 RC，精度约 10%~20%，用于快速判断"这根线要不要插 buffer"，不能替代真实提取。
:::

### 为什么长线必须插 buffer

把 200µm 切成 4 段，每段 50µm，段间插一个 buffer（每个 buffer 延迟按 40ps 算）：

- 每段：`R = 500 × 0.05 = 25Ω`，`C = 50 × 0.2 = 10fF`
- 每段 Elmore：`0.69 × 25 × 10f = 0.17ns`
- 四段线延迟：`0.17 × 4 = 0.69ns`
- 四个 buffer：`4 × 0.04 = 0.16ns`
- 合计约 **0.85ns**

对比不插 buffer 的 2.76ns，快了 3 倍多。原因不是"buffer 让线变短了"，而是 **RC 延迟与长度的平方成正比**：长度减半，`R` 和 `C` 各减半，乘积变成四分之一。这就是"长线必须打断"的数学依据。

真实项目里不会手算这个，工具会自动插 buffer；但你要知道**它为什么插**，否则看到工具在一条线上插了 6 个 buffer，你会以为是浪费面积。

## SPEF 里到底存了什么 {#spef}

提取工具的输出叫 **SPEF（Standard Parasitic Exchange Format，标准寄生参数交换格式）**，IEEE 1481 标准，本质是一个纯文本文件。它不存版图，只存"每个网络上有哪些电阻、哪些电容、分别连到哪个引脚"。

一个 SPEF 分两大部分：**头部**（单位、设计名、分隔符）和**网络记录**（每个网络一段）。下面是一个两引脚网络的节选，数字是示意值，但格式与真实文件一致：

```text
// 节选：一个两引脚网络的完整记录，单位 ps / fF / ohm
*SPEF "IEEE 1481-1998"
*DESIGN "soc_top"
*DATE "Mon Nov 16 10:22:31 2026"
*VENDOR "StarRC"
*DIVIDER /
*DELIMITER :
*T_UNIT 1 PS
*C_UNIT 1 FF
*R_UNIT 1 OHM
*D_NET *1024 4.1200
*CONN
*I *88:A I *C 120.500 340.200
*I *91:Z O *C 121.000 344.800
*CAP
1 *1024:1 1.1800
2 *1024:2 *1024:1 0.3200
3 *1024:3 2.6200
*RES
1 *1024:1 *88:A 32.0
2 *1024:2 *1024:1 126.0
3 *1024:3 *1024:2 41.0
4 *91:Z *1024:3 28.0
*END
```

逐段读：

| 段 | 含义 | 怎么核对 |
|---|---|---|
| `*SPEF` / `*DESIGN` | 格式版本与设计名 | 设计名必须和 PT 里 `link_design` 的名字一致 |
| `*T_UNIT` / `*C_UNIT` / `*R_UNIT` | 时间 ps、电容 fF、电阻 Ω | 单位错了，数值会差 1000 倍，且工具不一定报错 |
| `*DIVIDER` / `*DELIMITER` | 层次分隔符 `/`、引脚分隔符 `:` | 与网表命名风格不匹配时，连接会全部失败 |
| `*D_NET *1024 4.1200` | 一个网络，总电容 4.12 fF | 末尾数字应等于下面 `*CAP` 各项之和 |
| `*CONN` | 这个网络连到哪些引脚、方向、坐标 | `*I` 是实例引脚，`*P` 是顶层端口 |
| `*CAP` | 每个节点的对地电容，或两节点间的耦合电容 | 三行相加 `1.18+0.32+2.62=4.12`，对得上说明没被截断 |
| `*RES` | 节点之间的电阻，构成一棵 RC 树 | 每个节点最终要能连到某个引脚，孤立节点是异常 |

几个读文件时的实用判断：

1. **`*D_NET` 的数量**应该和网表里的信号网络数同量级。少一个数量级，说明只提了一部分。
2. **耦合电容**的行有两个节点名（如 `*1024:2 *1024:1`），对地电容只有一个节点名。如果全是单节点，说明提取时没开耦合。
3. **坐标**（`120.500 340.200`）可以用来抓"两个引脚坐标完全重合"的异常，通常是 LEF 引脚位置错了。

:::term SPEF | 标准寄生参数交换格式
Standard Parasitic Exchange Format 的缩写，IEEE 1481 定义。把提取得到的每段 RC 以文本形式交给时序工具。一个设计每个 corner 一份，签核时 corner 与文件必须一一对应。
:::

:::note SPEF、DSPF、SDF 不要混
SPEF 存的是**寄生 RC**（物理量）；SDF 存的是**延迟值**（已经算好的门延迟、线延迟），用于门级仿真；DSPF 是另一种细节更多的寄生格式。签核流程读 SPEF，仿真流程读 SDF。
:::

## 四个 corner：同一版图，四种算法 {#corner}

工艺有波动：金属厚度可能偏薄（电阻变大），介质厚度可能偏薄（电容变大）。签核不能只算"典型值"，要算最坏组合。

| corner | 电阻 | 电容 | 主要用来查 |
|---|---|---|---|
| `cworst` | 典型 | 最大 | setup：负载/耦合最重 |
| `cbest` | 典型 | 最小 | hold：线最快 |
| `rcworst` | 最大 | 最小 | setup：长线电阻主导时最坏 |
| `rcbest` | 最小 | 最大 | hold：线最快且驱动最强 |

注意 `rcworst` 不是"R 和 C 都最大"，而是 **R 最大、C 最小**。听起来反直觉，但对一条长线，延迟近似 `0.69RC`，R 和 C 同时最大确实更慢；可工艺上 R 变大通常伴随线变薄、对地电容变小，两者是相关的，foundry 给的是**相关 corner**，不能自己随便组合。真正哪个最差，必须四个都跑。

:::term Corner | 工艺角
工艺、电压、温度（PVT）的一组极端组合，代表芯片可能遇到的最坏工作条件。寄生提取 corner 只描述 RC 的极端，和晶体管 corner（SS/FF）是两套坐标，签核时要配对使用。
:::

:::pitfall 只跑了 cworst，hold 在 ff 角全崩
现象：setup 在 `ss_125c` 下勉强收敛，换到 `ff_m40c` 跑 hold，违例数从 30 条涨到 900 条。

原因：hold 查的是"数据来得太早"，对应的是**最快**的路径：FF 工艺 + 低温柔快 + `cbest/rcbest` 寄生。只跑 cworst 等于只看了慢的一侧。

处理：签核矩阵至少覆盖 `ss/cworst`（setup）、`ff/cbest`（hold）、`ss/rcworst`（长线 setup）、`ff/rcbest`（长线 hold）。跑完把四张表的 WNS 并排放，缺哪个角都要在报告里写明理由。
:::

## 提取工具的输入输出 {#tools}

工业界主流是 Synopsys 的 **StarRC** 和 Cadence 的 **Quantus QRC**。它们不参与优化，只做一件事：读几何、算 RC、写 SPEF。

| 输入 | 长什么样 | 缺了会怎样 |
|---|---|---|
| 布线后几何 | DEF（含每层走线与 via）或 GDS | 没有几何，只能按估算，等于没提取 |
| 工艺 RC 模型 | ITF / nxtgrd（StarRC）、QRC tech file | 缺模型直接报错退出 |
| 层映射表 | layer map：GDS 层号 ↔ 提取层名 | 某些层被跳过，长线偏快 |
| 网表/引脚 | Verilog 或 DEF 内的连接关系 | 名字对不上，SPEF 无法与设计关联 |
| corner 定义 | 每个 corner 的 R/C 缩放系数 | 十二个 corner 只出了一份 |

输出只有两样是关键：**每 corner 一份 SPEF**，以及一份**提取日志**。日志比 SPEF 更值得先看，因为层没映射、网络被跳过，都只在日志里留一行 warning。

课程环境跑不了 StarRC/QRC（没有 license，也没有完整 PDK）。真实项目里你会看到项目组封装好的脚本，形如 `run_extract.csh -design soc_top -corner rcworst`，你不需要手写提取命令，但必须会验收入口和出口。

拿到 SPEF 后，先做三项体检（这些命令课程环境可跑）：

```bash
# 作用：拿到 SPEF 先验三件事——设计名、单位、网络数
# 用法：在 spef/ 目录下执行，文件名换成你手上的 corner
head -12 soc_top_rcworst.spef                  # 看 *DESIGN 与三个单位
grep -c "^\*D_NET" soc_top_rcworst.spef        # 网络数，和网表信号数比量级
grep -c "^\*CAP" soc_top_rcworst.spef          # 电容段数，为 0 说明文件不完整
ls -lh soc_top_*.spef                          # 看十二个 corner 是否同批生成
```

`grep -c "^\*D_NET"` 的结果如果是 3 位数而设计有几万个网络，不是"设计小"，是文件被截断或只提了部分层次。`ls -lh` 看时间戳：十二份文件时间跨度超过一小时，中间很可能有人改过网表。

## 三种典型错误 {#errors}

### 名字对不上

最常见，也最容易被误判成"工具坏了"。SPEF 里的实例名、引脚名必须和 PT 读进来的网表**逐字符一致**。差异来源：

- 层次分隔符：网表用 `/`，SPEF 用 `|` 或 `.`。
- 总线写法：`data[3]` vs `data\[3\]`（转义）。
- 综合后改名：网表是 `u_add_0`，SPEF 是 `u_add`。
- 展平 vs 层次：一方 `flatten` 过，另一方没有。

:::pitfall SPEF 读进去，一半网络没连上
现象：PT 里 `report_annotated_parasitics` 显示大量网络 `0.0000` 皮法，时序突然变得极度乐观。

典型首行（PT，版本不同措辞略有差异）：`Error: Cannot find port 'u_core/u_alu/u_add/A[3]' in design 'soc_top'.`

原因：网表里这个引脚叫 `A[3]`，SPEF 里写成 `A\[3\]`，或者层次分隔符不一致，工具按名字找不到，就把这段寄生丢了，**不一定是报错退出，可能只是警告后继续跑**。

怎么查：先用 `grep` 在 SPEF 里搜一个确定存在的实例名，确认它长什么样；再在 PT 里 `get_pins` 同名对象，两边字符串直接对比。不要靠肉眼"看起来一样"。
:::

### 层映射错

提取工具靠 layer map 把版图的 GDS 层号翻译成工艺模型里的层名（M1、M2…）。映射错一层，那一层的线就按错误模型算：可能把 M5 当 M4（厚度不同，电阻差 30%），也可能整层没映射被跳过。

症状很隐蔽：DRC 全过，时序也不报错，只是某几条跨宏单元的长线"莫名很快"。查法：

- 看提取日志里有没有 `layer ... not mapped` 或 `skipped`。
- 在 SPEF 里找那条长线的 `*RES`，如果总电阻明显小于手算值（按 `Rs × L/W`），就是层用错了。
- 对比两个 corner 的同一网络：如果 RC 比例不符合工艺系数，也说明模型不对。

### 只提取了部分网络

常见于三种情况：脚本里加了 `-exclude` 把某些层次排除了；网表与 DEF 版本不一致，部分实例在 DEF 里找不到；分层提取只跑了某个 block。

判断标准只有一个：**`*D_NET` 数量与设计中需要时序检查的网络数对齐**。电源地网络本来就不提，可以排除；信号网络少 10% 以上就要停下来查。

## 工作中怎么用：提取在项目里的位置 {#in-work}

**谁做**：大项目有专门的 RC extraction 工程师，小项目由 PR 工程师兼。timing signoff 工程师（STA）负责验收 SPEF，不负责生成。

**什么时候做**：第一次在 route 之后；之后每次 ECO 改了布线，都要**重提对应区域**，不能拿旧 SPEF 直接跑签核。最终签核用的是"最后一次改动之后"的提取结果。

**输入从哪来**：PDK 里的 ITF/QRC tech 与 layer map（foundry 给）、route 后的 DEF（PR 给）、corner 列表（项目签核规范给）。三者版本必须来自同一套 PDK，混用是最隐蔽的错误。

**输出交给谁**：每个 corner 一份 SPEF 交给 STA；同时给一份提取日志和一张"corner 清单"，写清每份文件对应的工艺/电压/温度与提取时间。

**评审会看什么**：`*D_NET` 数是否与上一版同量级（波动 < 2%）、总电容与上一版偏差是否 < 5%、日志有没有 warning、十二个 corner 是否齐全。任一项异常，先别跑时序——**在错的寄生上修时序，等于白修**。

**做错了会怎样**：SPEF 少一层，PT 会给出一个"漂亮"的 WNS，流片后 silicon 上时序失效；SPEF 与网表错版，ECO 会改错单元。前者是量产事故，后者是两周的返工。

:::lab 动手：验一份 SPEF，并用手算校验它
**任务**：课程环境 `~/backend_lab/soc/spef/` 下有一份 `soc_top_rcworst.spef`（节选，约 2000 个网络）。完成三件事。

**步骤**：
1. `head -12` 记下 `*DESIGN`、`*T_UNIT`、`*C_UNIT`、`*R_UNIT`，判断单位是否自洽。
2. `grep -c "^\*D_NET"` 数网络；再 `grep -c "^\*CAP"` 数电容段。两者比例若小于 1，说明有网络没有电容记录。
3. 随便挑一个 `*D_NET`，把它下面 `*CAP` 的数字相加，与 `*D_NET` 行末的总电容对比，误差应小于 0.5%。
4. 找到该网络 `*RES` 的总电阻，用 `Rs × L/W` 手算一遍（层和宽度从 DEF 或报告里查），偏差超过 50% 就说明层映射可疑。

**过关标准**：能说出这份 SPEF 覆盖了多少网络、单位是什么、随手挑的一个网络 RC 与手算是否吻合，并给出"可用/需重提"的结论。
:::

:::quiz
RC 提取在流程里的哪一步之后、哪一步之前？|布线（route）之后、时序签核（STA signoff）之前；ECO 改动布线后要局部重提。
"估算 RC"和"提取 RC"的本质区别是什么？|估算按扇出/线长套统计模型猜，提取按版图真实几何与工艺模型算；长线和耦合多的网络差距可达 2 倍。
一条 200µm、宽 0.1µm 的 M3 线，Rs=0.05Ω/□，C=0.2fF/µm，Elmore 延迟约多少？|方块数 2000，R=100Ω，C=40fF，0.69×100×40f=2.76ns。
为什么长线插 buffer 能大幅降延迟？|RC 延迟与长度平方成正比；切成 n 段后每段 RC 降为 1/n²，总延迟约降为 1/n，代价是 n 个 buffer 的延迟。
SPEF 里 `*D_NET` 行末的数字是什么？怎么核对？|该网络的总电容；把它下面 `*CAP` 各项相加，应基本相等，不等说明文件被截断或解析异常。
cworst 和 rcworst 的区别是什么？|cworst 是电容最大、电阻典型；rcworst 是电阻最大、电容最小（相关 corner），前者查负载/耦合，后者查长线电阻主导的路径。
SPEF 与网表名字对不上时，PT 一定会报错退出吗？|不一定。常见是警告后把该网络寄生当 0 继续跑，结果是时序假乐观，必须用 `report_annotated_parasitics` 主动查。
:::
