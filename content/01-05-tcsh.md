## 为什么是 tcsh {#why}

:::goal 学完这一课，你能读懂公司里任何一个 `.csh` 流程脚本，改对里面的变量和循环，并说出脚本第一行 `#!/bin/tcsh -f` 里每个字符的作用。
:::

Linux 默认是 bash，为什么芯片公司还在用 tcsh？

因为时间。EDA 工具在 1990 年代定型，那会儿商用 Unix（SunOS、Solaris、HP-UX）上主流是 csh/tcsh。公司的环境脚本、流程脚本、回归脚本在那时候写成 tcsh，之后二十年一直在上面加东西——没人敢重写，因为重写就意味着几万个已经跑通的任务要重新验证。

类比：一栋老楼的电线还是铝线，你知道铜线更好，但换线要停整栋楼的电。所以大家继续用铝线，只是不去动它。

现实一点说：**你可以用 bash 干活，但读不懂 tcsh，就看不懂公司的流程。** 新人最容易卡住的地方不是工具，而是组长丢过来一个 `run_all.csh`，说"把 top 名字改一下跑另一版"，你不知道该改哪一行。

这一课的目标很明确，不是让你用 tcsh 写大型程序，而是三件事：

1. **读懂**：看到 `setenv PDK_ROOT /home/pdk` 知道它在干什么。
2. **改对**：加一个参数、改一个循环范围、把一个写死的路径换成变量。
3. **不被坑**：知道 `set` 和 `setenv` 哪个能传给子进程——这一条错，脚本必挂。

:::term Tcsh | 增强版 C Shell
csh（C Shell）的改进版，语法接近 C 语言。提示符常见 `%` 或 `>`。与 bash 最大的结构差异是：变量分成 shell 变量和环境变量两类，分别用 `set` 和 `setenv` 设置。

查当前 shell：`echo $SHELL`；临时切进 tcsh 敲 `tcsh`，退出用 `exit`；只看某个脚本用什么解释器，看它第一行。
:::

## 变量分两种：set 和 setenv {#vars}

这是 tcsh 与 bash 最大的差异，也是新人第一个跟头。bash 只有一套变量（`A=1` 加 `export` 才进环境），tcsh 从语法上就分成两套。

| 对比项 | shell 变量（本地） | 环境变量 |
|---|---|---|
| 定义 | `set n = 10` | `setenv N 10` |
| 读取 | `$n` | `$N` |
| 等号 | **要写**，两边可以有空格 | **不写**，用空格分隔 |
| 传给子进程 | ❌ 不能 | ✅ 能 |
| 能被 `env` 列出 | ❌ 不能 | ✅ 能 |
| tcl 里怎么读 | 读不到 | `$::env(N)` |
| 支持数组 | ✅ `set path = ( ... )` | ❌ 只能是字符串 |
| 查看全部 | `set`（不带参数） | `setenv`（不带参数） |
| 删除 | `unset n` | `unsetenv N` |
| 值里有空格 | 必须加引号 | 后面的整串就是值，不用引号 |
| 写错的典型结果 | `set N = 1 2` 直接语法错 | `setenv N = 1` 值变成 `= 1`，不报错 |
| 典型用途 | 循环计数、临时路径、开关 | PATH、license、项目根目录 |

判断标准只有一句话：**这个变量要不要被脚本里启动的工具看到？** 要，就用 `setenv`；只在当前 shell 里算一算，用 `set`。

两种变量在屏幕上的区别是这样的：

:::fig term-tcsh | `set` 与 `setenv` 的差别。重点看 `env` 的输出：只有 `setenv` 设的那个能被列出来，`set` 设的只活在当前 shell 里。
:::

要看出的是：**`env | grep 名字` 是唯一可信的证据。** 你 `echo $TOP` 明明有值，不代表工具拿得到——它只证明当前 shell 里有。判断依据永远是"`env` 里有没有"。

工具是脚本的**子进程**，子进程只能继承环境变量。所以 `set TOP = ipa_top` 之后，`dc_shell` 里读 `$TOP` 是空的；必须 `setenv TOP ipa_top`。

```csh
# 作用：两种变量各建一个，并用子进程验证谁能传下去
# 用法：在 tcsh 里逐行敲；env 会打印所有环境变量
set    LOCAL_VAR = "only here"     # shell 变量：只在当前 shell 里存在
setenv ENV_VAR   "goes to child"   # 环境变量：会传给子进程

echo $LOCAL_VAR                    # 输出 only here
echo $ENV_VAR                      # 输出 goes to child

env | grep ENV_VAR                 # 能查到 → 它真的在环境里
env | grep LOCAL_VAR               # 查不到（退出码 1）→ 它只是本地变量
```

`env` 这条命令是判据：**环境变量能被 `env` 列出来，shell 变量不能。** 以后怀疑"变量没传进去"，先 `env | grep 名字`，比猜快得多。

还有两个必须知道的细节：

**第一，同名时 shell 变量遮住环境变量。** 如果你既 `setenv TOP a` 又 `set TOP = b`，那么 `$TOP` 读出来是 `b`（shell 变量优先），但子进程看到的是 `a`。这种"我自己 echo 是对的、工具里却是错的"的怪事，九成是这里。

**第二，PATH 在 tcsh 里对应一个小写数组 `path`。** 加目录的标准写法是 `set path = ( /new/dir $path )`，用空格分隔、用圆括号包住。写 `set path = /a:/b` 是错的（那是一个字符串，不是数组），写 `setenv PATH /a:/b` 虽然通常也能用，但和公司的 `set path` 风格混在一起，同一份路径就要维护两处。

```csh
# 作用：给 PATH 加目录的两种写法（第二种只作对照），以及两种查看方式
# 用法：在 ~/.cshrc 里用第一种；后一种看懂即可，别在脚本里混用
set path = ( $HOME/bin /usr/local/bin /usr/bin /bin $path )   # 正统：数组，新目录在前
setenv PATH /opt/eda/bin:$PATH        # 能用，但和上面的写法混着容易漏改
echo $path                            # 打印数组，空格分隔；echo $PATH 是冒号分隔
```

手算一次"为什么 PATH 越短越好"：PATH 里有 12 个目录，每个目录平均 300 个可执行文件。你敲一个不存在的命令，shell 要在最坏情况下查 `12 × 300 = 3600` 个文件名才报 `command not found`；按 Tab 补全时，每敲一个字符都要重扫一遍。这就是为什么有些人终端里 Tab 补全明显卡顿——PATH 里塞了二十几个目录，其中一半是早就删掉的。

:::term Shell Variable | shell 变量（本地变量）
tcsh 里用 `set` 定义的变量，只在当前 shell 进程内有效，不会传给子进程。值为一个词或一个数组（`set path = ( ... )`）。

`set` 不带参数会列出当前所有 shell 变量，用来排查"这个变量到底有没有设"。
:::

:::scene 周五下午，脚本跑完了，产出的是错的
组长让你把 `run_pnr.csh` 里的 top 从 `ipa_top` 换成 `soc_top`。你打开脚本，看到一行 `set TOP = ipa_top`，顺手改成 `set TOP = soc_top`，晚上十点挂上去跑，第二天早上看报告。

报告里所有模块名还是 `ipa`。日志里没有一行红字。你 `echo $TOP`，明明打印的是 `soc_top`。

问题就在那个 `set`：它设的是 shell 本地变量，工具作为子进程根本看不到，tcl 里的 `$::env(TOP)` 读到空，工具用了默认值——**不报错，跑完，结果是错的**。改法是把 `set` 换成 `setenv`，或者更稳：脚本用 `sed` 把 top 名字替换进 tcl 模板，不依赖环境变量传递（01-06 会写这个版本）。

这个场景之所以值得记住，是因为它不报错。tcsh 里"变量没传下去"几乎从不报错，只会在几小时后给你一份错的结果。
:::

:::pitfall set msg = hello world 报错
现象：`set msg = hello world` 执行后直接报语法错误（不同 tcsh 版本措辞略有差别，都以 `set:` 开头），脚本停在这一行。

原因：`set` 按 `set 名 = 值` 的格式解析，一个值只能是一个词。`world` 是多出来的词，tcsh 把它当成"第二个要设置的变量名"，整句语法就崩了。

怎么改：值里有空格就加双引号：`set msg = "hello world"`。另外注意 `set` 的等号两边**可以**有空格（`set n = 10` 是对的），但 `setenv` 不能写等号：`setenv A 1` 对，`setenv A=1` 会把变量名当成 `A=1`，等于白设。
:::

:::pitfall set 的变量在脚本里读不到
现象：`set TOP = ipa_top` 之后跑 `dc_shell -f syn.tcl`，tcl 里 `getenv TOP` 返回空。

原因：`set` 是 shell 变量，不进环境，工具作为子进程看不到。

怎么查：`env | grep TOP` 没输出就是这个问题。改成 `setenv TOP ipa_top`。
:::

## 别名：把长命令变短 {#alias}

别名（alias）是"给一条命令起个短名字"。它的价值不在省几个字符，而在**把容易写错的长命令固定下来**。

```csh
# 作用：常用别名的定义、查看、删除
# 用法：在终端里即敲即用；想常驻就写进 ~/.cshrc
alias ll 'ls -lht'                 # ll = 按时间倒序列出，带大小
alias la 'ls -la'                  # la = 含隐藏文件
alias .. 'cd ..'                   # .. 当命令用（bash 里这是目录名，行为不同）
alias grep 'grep --color=auto'     # 让命中词高亮

alias                              # 列出所有别名（tcsh 里 which 也能看出别名）
which ll                           # 输出 ll: aliased to ls -lht
unalias ll                         # 删掉一个
unalias '*'                        # 删掉全部（小心，可能删掉公司配好的）
```

带参数的别名要写 `\!*`，这是 tcsh 的历史替换机制：

```csh
# 作用：让别名接受参数
# 用法：定义之后 tailf syn.log 等价于 tail -f syn.log
alias tailf 'tail -f \!*'          # \!* 表示"把用户给的参数原样接在这里"
alias grepv 'grep -v \!* '         # 同理

tailf syn.log                      # 实际执行 tail -f syn.log
```

`\!*` 里的反斜杠不能省。不写反斜杠，tcsh 在**定义别名的这一刻**就把 `!*` 替换掉了（替换成空），别名变成 `tail -f`，用起来永远少一个参数。

关于别名，有一条纪律要记住：**别名是给人打字用的，不是给脚本用的。** 别名定义在谁的 `.cshrc` 里、脚本启动时读没读那份 `.cshrc`，都会影响它生不生效——同一句 `rm`，在你终端里可能带 `-i`，在别人跑的脚本里可能不带。所以脚本里一律写完整命令，不依赖任何别名。

:::term Alias | 别名
给一条命令（或一串命令）起的短名字。敲 `ll` 等于敲 `ls -lht`。别名只存在于当前 shell，写在 `~/.cshrc` 里才会每次登录都有。

查看某个名字是不是别名：`which 名字`；bash 里对应的命令是 `type 名字`。
:::

## 通配符与命令历史 {#glob}

通配符（wildcard）是 shell 在把参数交给命令之前先做的一次"文件名展开"。

```csh
# 作用：通配符的四种写法和花括号展开
# 用法：在你要匹配的目录下执行；先 echo 看展开成什么，再交给真命令
ls *.tcl                 # * 匹配任意多个字符（含 0 个）
ls run?.log              # ? 匹配恰好一个字符：run1.log 匹配，run10.log 不匹配
ls run[1-9].log          # [] 匹配范围内一个字符
ls {a,b,c}.tcl           # 花括号展开成 a.tcl b.tcl c.tcl，不存在的也会被列出来报错
cp pnr.tcl{,.bak}        # 展开成 cp pnr.tcl pnr.tcl.bak —— 备份的极简写法
echo *                   # 先看展开结果，避免 rm * 时才发现范围不对
```

`{}` 是 csh 家族特有的，bash 也有，但 tcsh 里用得更多。`cp file{,.bak}` 这种写法在备份配置文件时非常顺手。

历史（history）是另一个每天用几十次的功能。tcsh 的历史扩展在**回车之前**就把 `!` 开头的片段替换成之前的命令。

```csh
# 作用：历史扩展的六个常用形式
# 用法：在交互式 shell 里用；script 里不要用（见下面的坑）
!!                    # 重复上一条命令（最常用：sudo !!）
!$                    # 上一条命令的最后一个参数
!*                    # 上一条命令的所有参数
!120                  # 执行历史编号 120 的那条
!-3                   # 倒数第三条
!gre                   # 最近一条以 gre 开头的命令
^old^new^             # 把上一条命令里的 old 换成 new 再执行
history               # 列出历史；history 20 只看最近 20 条
```

`!$` 值得单独讲，因为它解决的是后端最烦的事——长路径。

```csh
# 作用：长路径只敲一次
# 用法：先 ls 一个长路径，再用 !$ 复用最后一个参数
ls /home/proj/28nm/backend/pnr/run/20261122_2015/reports
# 输出一堆报告
cd !$                 # 等价于 cd 上面那个 reports 目录
cd !$:h               # :h 去掉最后一级，进入它的上一级（pnr/）
```

历史默认只存在内存里，关掉终端就没了。想留着，在 `.cshrc` 里加两行：`set history = 2000`（内存里存多少条）、`set savehist = 2000`（退出时写进 `~/.history`，下次登录读回来）。

:::term History Expansion | 历史扩展
用 `!` 引用之前执行过的命令片段。`!!` 是整条，`!$` 是最后一个参数，`!*` 是全部参数，`^a^b^` 是替换。

扩展发生在命令执行**之前**，所以你看到回显的命令已经是替换后的完整形式——这也意味着写错一个 `!` 会执行一条你完全没预料的命令。
:::

:::pitfall echo "hello!" 报 Event not found
现象：在 tcsh 里敲 `echo "build done!"`，输出不是那句话，而是

```
done!: Event not found.
```

原因：`!` 在双引号里**仍然**会触发历史扩展，tcsh 去找一条以 `done!` 开头（或以 `done` 结尾）的历史命令，找不到就报错。这是 csh 家族独有的行为，bash 里双引号中的 `!` 不会展开。

怎么改：三条路——用单引号 `echo 'build done!'`（单引号内不展开）、加反斜杠 `echo "build done\!"`、或者干脆关掉：`set histchars` 改成别的字符。写脚本时更简单：**别在双引号里写 `!`**，用单引号就永远不会碰到这个坑。
:::

:::pitfall 通配符没匹配到，脚本直接中断
现象：`rm run/*.log` 在空目录里执行，报 `rm: No match.` 然后什么都没做；更糟的是 `set FILES = ( run/*.log )` 报 `No match.` 后 `FILES` 根本没被设置，下一行 `$FILES[1]` 报 `Subscript out of range`。

原因：bash 里匹配不到时会把 `*.log` 原样传下去；csh/tcsh 默认相反——**匹配不到就报 `No match.` 并放弃这条命令**。

怎么查：看报错是不是 `No match.`；先 `echo run/*.log` 试一次，看它展开成什么。

怎么改：两条路。① 先用 `ls 模式 >& /dev/null` 判断 `$status`，有文件再进循环（这一课的 lab 就这么写）；② 在脚本开头 `set nonomatch`，让未匹配的模式按字面量传下去。
:::

## 控制流：if、foreach，以及 tcsh 的算术 {#flow}

tcsh 的控制流关键字和 bash 完全不同，且**对空格极度敏感**：`if` 和左括号之间必须有空格，`then` 必须独立成词，结尾必须是 `endif`。

```csh
# 作用：if 的完整结构（注意空格和 then/endif）
# 用法：存成 .csh 文件或直接粘进终端
if ( -f run.tcl ) then            # ( 前面有空格，) 后面有空格，then 单独写
    echo "found run.tcl"
else if ( -d run ) then           # else if 要写成一行，不能拆成两行
    echo "run is a directory"
else
    echo "nothing here"
endif                             # 必须有 endif，不能只写 fi
```

判定条件常用写法：

| 写法 | 含义 |
|---|---|
| `-f file` | 是普通文件 |
| `-d dir` | 是目录 |
| `-e path` | 存在（不管类型） |
| `-r / -w / -x file` | 可读 / 可写 / 可执行 |
| `-z "$str"` | 字符串为空 |
| `$a == $b` | 相等（数字或字符串都按字面比） |
| `"$a" != "$b"` | 不等（加引号，防止空值导致语法错误） |

`-z` 是脚本里最有用的一个：`if ( -z "$TOP" ) then ... exit 1`，等价于"参数没给就退出"。注意引号——`$TOP` 为空时，不加引号会变成 `if ( -z ) then`，语法直接崩。

循环用 `foreach ... end`，没有 `for ... do ... done`：

```csh
# 作用：foreach 遍历文件、遍历列表、遍历数字
# 用法：在含 .tcl 的目录下执行
foreach f ( *.tcl )               # 括号里是一组词，*.tcl 会先被通配符展开
    echo "processing $f"
end                               # 循环体以 end 结束（不是 done）

foreach mode ( fast normal slow )  # 遍历手写列表
    echo "mode = $mode"
end

foreach i ( `seq 1 5` )           # csh 没有 range，用 seq 生成 1..5
    echo "round $i"
end

foreach i ( `seq 1 8` )
    if ( $i == 3 ) continue        # 跳过第 3 轮
    if ( $i == 7 ) break           # 第 7 轮直接跳出整个循环
    echo "run $i"
end
```

数字运算要用 `@`，不能写 `i = $i + 1`：

```csh
# 作用：tcsh 的算术（@ 是"求值赋值"）
# 用法：计数、累加
@ n = 1                 # 定义并赋值
@ n = $n + 1            # 加一，等价于 @ n++
@ total = $n * 8        # 乘
@ n--                   # 减一
echo $n                 # 输出数字
```

`@` 后面不能有 `$` 在左边（`@ $n = 1` 是错的），右边可以用 `$n`。

需要按值分支时用 `switch`，比一串 `if` 清楚：

```csh
# 作用：switch 分支（每个 case 用 breaksw 结束）
# 用法：按阶段名分派
switch ( $stage )
case "place":
    echo "do placement"
    breaksw
case "cts":
    echo "do CTS"
    breaksw
default:
    echo "unknown stage: $stage"
    breaksw
endsw
```

### 一个完整的可跑脚本：if + foreach + @ 拼起来

零散语法看过就忘，拼成一个能跑的东西才记得住。下面这个脚本做一件真事：**给三个利用率各建一个运行目录，已存在就跳过，最后报告建了几个。**

```csh
#!/bin/tcsh -f
# 作用：按三个利用率建运行目录，演示 if / foreach / @ / 退出码的完整写法
# 用法：./make_runs.csh <工作目录>；目录必须存在且可写
# 返回码：0 成功 / 1 参数错 / 2 目录不可写 / 3 建目录失败

# ---- 1. 参数校验：没给参数就退出，别让 $1 为空往下跑 ----
if ( $#argv < 1 ) then
    echo "usage: $0 <workdir>"
    exit 1
endif
set WORK = $1

# ---- 2. 环境校验：目录存在且可写（-d 存在，-w 可写）----
if ( ! -d "$WORK" || ! -w "$WORK" ) then
    echo "[ERROR] not a writable dir: $WORK"
    exit 2
endif

# ---- 3. 主循环：三个利用率，已存在就跳过 ----
set n = 0
foreach u ( 0.30 0.35 0.40 )
    set RUN = $WORK/util_$u
    if ( -d "$RUN" ) then
        echo "[SKIP] $RUN already exists"
    else
        mkdir -p $RUN
        if ( $status != 0 ) then        # mkdir 失败要立刻停，不能假装成功
            echo "[FAIL] mkdir $RUN"
            exit 3
        endif
        @ n++                           # 计数用 @，不能用 n = $n + 1
        echo "[OK] created $RUN"
    endif
end

echo "[DONE] created $n dir(s) under $WORK"
exit 0
```

跑一遍，预期输出（第一次和第二次结果不同，这正好说明脚本有状态判断）：

```
$ ./make_runs.csh /tmp/demo
[OK] created /tmp/demo/util_0.30
[OK] created /tmp/demo/util_0.35
[OK] created /tmp/demo/util_0.40
[DONE] created 3 dir(s) under /tmp/demo

$ ./make_runs.csh /tmp/demo
[SKIP] /tmp/demo/util_0.30 already exists
[SKIP] /tmp/demo/util_0.35 already exists
[SKIP] /tmp/demo/util_0.40 already exists
[DONE] created 0 dir(s) under /tmp/demo
```

三个值得注意的写法，都是新人常错的地方：

1. **`! -d "$WORK" || ! -w "$WORK"`** —— `||` 是"或"，`!` 是"非"。`$WORK` 必须加引号：如果它是空的，不加引号会变成 `if ( ! -d || ... )`，语法直接崩。
2. **`set RUN = $WORK/util_$u`** —— 变量拼接不需要 `${}`，`$u` 从 `$` 开始解析，前面的 `util_` 是字面量。
3. **`exit 1/2/3` 分段** —— 调用者看返回码就知道该改用法（1）、换目录（2）、还是查磁盘（3）。这是 01-06 那个跑批脚本的地基。

:::pitfall if 少一个空格就报错
现象：`if(-f run.tcl) then` 直接报错，错误以 `if:` 开头（常见是表达式语法或数字格式问题），脚本停住。

原因：`if` 和左括号之间必须有空格。`if(` 被当成一个整体去解析，tcsh 在里面找不到合法表达式。`)` 和 `then` 之间缺空格同样出问题。

怎么改：严格按 `if ( 条件 ) then` 写，三处空格都不能省：`if` 后、`(` 后、`)` 前后。`else if` 必须写在一行里，写成 `else` 换行 `if` 会报 `else: Then/else was not terminated`。
:::

## source 与 .cshrc 的加载顺序 {#shellrc}

`source` 和"执行脚本"是两件不同的事，这一点在 tcsh 里格外重要，因为环境配置全靠它。

| 动作 | 在哪个进程里执行 | 变量会留下吗 |
|---|---|---|
| `source setup.csh` | **当前** shell | 会，立刻生效 |
| `./setup.csh` | 新开一个子进程 | 不会，子进程退出就没了 |
| `tcsh setup.csh` | 新开一个 tcsh 子进程 | 不会 |

所以环境脚本必须 `source`。`./setup.csh` 跑完不报错、变量却没了，是新人最常见的困惑之一。

把四种常见动作放在一起对比，边界就清楚了：

| 你做的事 | 变量留在当前 shell 吗 | 会读 `~/.cshrc` 吗 | 典型用途 |
|---|---|---|---|
| `source setup.csh` | ✅ 会，立刻生效 | ❌ 不会（没起新 shell） | 加载项目环境，最常用 |
| `./setup.csh` | ❌ 不会，子进程退出就没了 | ✅ 会（除非脚本带 `-f`） | 不推荐，容易误判"设置没生效" |
| `tcsh` | ❌ 不会，进了新 shell | ✅ 会 | 临时切一个干净/脏的 shell |
| `tcsh -f setup.csh` | ❌ 不会 | ❌ 不会 | 跑脚本，结果可复现 |

`source` 和 `.cshrc` 的关系还有一层：**`.cshrc` 本身就是一个"每次启动都被 source 的脚本"**，所以你写在里面的东西等价于"每次开终端自动敲一遍"。区别只在触发时机：`.cshrc` 由 shell 启动触发，`source` 由你手动触发。

加载顺序里有一个经典事故：`.cshrc` 里 `source $PROJ/setup.csh`，而 `setup.csh` 里写的是

```csh
# 反例：没有带 $path，把前面所有 PATH 冲掉了
set path = ( /opt/eda/bin )       # 错：系统的 /usr/bin 全没了
set path = ( /opt/eda/bin $path ) # 对：新目录在前，原有目录保留
```

结果是你打开终端后，`ls`、`grep`、`vim` 全部 `command not found`——因为 `setup.csh` 把 PATH 覆盖成了只剩工具目录。**判断依据：连最基础的命令都找不到，就是 PATH 被整体覆盖了，不是"命令没装"。** 救法：`set path = ( /usr/local/bin /usr/bin /bin /sbin $path )`，或直接开一个新终端、把那一行改对。

`.cshrc` 的加载时机，一句话：**每个 tcsh 启动时都会读一次 `~/.cshrc`（交互式、跑脚本都一样），只有登录 shell 额外读一次 `~/.login`。**

| 场景 | 读 `~/.cshrc` | 读 `~/.login` |
|---|---|---|
| ssh 登录（登录 shell） | ✅ | ✅ |
| 在终端里敲 `tcsh`（子 shell） | ✅ | ❌ |
| 跑脚本 `./run.csh` | ✅（除非加 `-f`） | ❌ |
| `tcsh -f` | ❌ | ❌ |

注意第三行：**普通脚本也会读你的 `.cshrc`**。这就是为什么同一个脚本，你跑没事、同事跑挂掉——他 `.cshrc` 里的别名或变量把你的脚本搞乱了。下一节的 `-f` 就是来解决这个的。

`.cshrc` 里最常出现的其实不是 `setenv`，而是 `module load`。它本质是执行一段 modulefile 脚本，往环境里写 PATH：

:::fig term-module | `module load` 改的是环境变量，相当于把 PATH 指向另一套工具。重点看 load 前后 PATH 里多了哪一段。
:::

要看出的是：**`module load` 不是"安装"，是"改指针"。** 所以它随 shell 生灭——你在这个终端 load 了，隔壁终端没有；脚本里也一样，必须自己 load 一次（01-06 会写这一行）。

加完新目录或新命令后，tcsh 可能还在用旧的命令路径缓存，`rehash` 刷一下（bash 里是 `hash -r`）。现象是：文件明明刚装好、`ls` 能看到，敲命令还是 `command not found`。

:::term Source | 加载（在当前 shell 里执行）
读一个脚本并**在当前 shell 进程里**执行它，所以脚本里设的变量会影响你当前这个终端。

tcsh 里只有 `source` 一种写法（bash 里还能用 `.`）。`~/.cshrc` 本质就是一个每次开终端都会被 source 的脚本。
:::

## 第一行的 -f：为什么公司脚本都这么写 {#shebang}

打开公司任何一个 `.csh`，第一行几乎都是：

```csh
#!/bin/tcsh -f
```

这一行叫 shebang（读作"释伴"）。内核执行 `./run.csh` 时，读第一行开头两个字符 `#!`，把后面的路径当成解释器，把 `-f` 当成传给解释器的第一个参数。所以等价于手工执行 `/bin/tcsh -f run.csh`。

`-f` 的意思是 **fast start：不读 `~/.cshrc` 和 `~/.login`**。它带来三个好处，每一个都对应一类真实事故：

1. **快。** 一个大 `.cshrc` 里可能有几十行 `set path`、几个 `module load`，每次跑脚本都要执行一遍。批量跑 200 个任务，光读配置就浪费时间。
2. **可复现。** 你的 `.cshrc` 里有 `alias rm 'rm -i'`、`set noclobber`，这些会改变脚本行为；同事的没有。加 `-f` 之后，两个人跑出来的结果一样。
3. **输出干净。** 不加 `-f`，`tcsh -x script.csh` 的跟踪输出里会混进 `.cshrc` 的几十行，你得先翻过它们才看得到脚本自己在干什么。加了 `-f`，第一行就是脚本的第一行。

把 `.cshrc` 里常见的东西逐条对上，就知道 `-f` 到底省了什么、不加会出什么事：

| `.cshrc` 里的内容 | 加 `-f` 后 | 不加时可能出的事 |
|---|---|---|
| `alias rm 'rm -i'` | 不生效 | 脚本里的 `rm` 变成交互式，**批量任务卡在等你按 y** |
| `set path = ( ... )` | 不执行 | 脚本里工具找不到（所以脚本要自己 `set path` 或 `module load`） |
| `module load icc2/2019` | 不执行 | 脚本用了你终端里的版本，跑出和别人不一样的结果 |
| `setenv PROJ_ROOT ...` | 不执行 | 脚本报 `PROJ_ROOT: Undefined variable` |
| `set noclobber` | 不生效 | 不加时脚本里 `> 已存在的文件` 会报 `File exists`，脚本当场停 |
| `set history = 2000` | 不生效 | 脚本不需要历史，无影响 |
| 提示符 / `stty` 设置 | 不执行 | 纯交互用，脚本无影响 |

最狠的是第二、五行：**一个让脚本找不到工具，一个让脚本莫名其妙停在一句 `>` 上**，而报错都不指向 `.cshrc`。所以公司脚本一律 `#!/bin/tcsh -f`，把"环境"这件事从"某人的配置"变成"脚本自己负责"。

不加 `-f` 的典型事故：同事的 `.cshrc` 里有一行 `source ~/proj/setup.csh`，那个目录半年前归档了。他自己每次开终端都看到一行红字，早就习惯了；你把他的脚本拿来跑，第一行输出就是 `No such file or directory`，你以为是脚本坏了，查了半小时。**脚本不该继承任何人的个人配置。**

调试时还有两个开关：

```bash
# 作用：脚本调试的两个 tcsh 开关
# 用法：不改脚本，命令行上加参数
tcsh -x run.csh ipa_top     # 逐行回显"展开后"的命令，看变量到底变成了什么
tcsh -v run.csh ipa_top     # 逐行回显"原文"，看脚本读到了哪一行
tcsh -n run.csh             # 只做语法检查，不执行（改完脚本先跑这个）
```

`-x` 是查"为什么 if 没进去"的唯一可靠手段：它会把 `if ( -f run.tcl ) then` 展开成实际比较的值，你一眼就能看出 `$TOP` 是空的还是拼错了。

:::term Shebang | 释伴（脚本首行）
脚本第一行的 `#!解释器路径`。内核靠它知道"这个文件该用哪个程序执行"。`#!/bin/tcsh -f` 就是"用 tcsh，并且别读我的个人配置"。

没有 shebang 的脚本，`./run.csh` 会由当前 shell 尝试执行，行为随人而异；`sh run.csh` 则完全绕开 shebang，用 sh 去解释 tcsh 语法，必挂。
:::

:::pitfall 别人跑得通，我跑就挂
现象：同事给你的 `run.csh`，他跑没问题，你 `./run.csh` 直接报 `TOP: Undefined variable.`。

原因：脚本没加 `-f`，读的是**你的** `.cshrc`；而脚本依赖的 `setenv TOP` 写在他 `.cshrc` 的项目段里，你这里没有。

怎么查：`tcsh -x run.csh` 看第一处 `Undefined variable` 出现在哪一行；`env | grep TOP` 确认变量是否存在；`head -1 run.csh` 看有没有 `-f`。

怎么改：短期在你的 `.cshrc` 里补上 `source 项目/setup.csh`；长期让脚本自己在开头 `source` 项目环境，并加 `-f`——**脚本不该依赖任何人的个人配置。**
:::

## bash 与 tcsh 对照表 {#diff}

从 bash 转过来的人，报错大多集中在这张表里。贴一份在显示器边上，一周就不用看了。

| 场景 | bash | tcsh |
|---|---|---|
| 设环境变量 | `export A=1` | `setenv A 1` |
| 设本地变量 | `A=1` | `set A = 1` |
| 读变量 | `$A` / `${A}` | `$A` |
| if | `if [ ... ]; then ... fi` | `if ( ... ) then ... endif` |
| 循环 | `for x in ...; do ... done` | `foreach x ( ... ) ... end` |
| while | `while [ ... ]; do ... done` | `while ( ... ) ... end` |
| 算术 | `((i++))` 或 `$((i+1))` | `@ i++` |
| 函数 | `f() { ... }` | `alias` 或独立脚本 |
| 输出+错误重定向 | `cmd > log 2>&1` | `cmd >& log` |
| 丢弃输出 | `> /dev/null 2>&1` | `>& /dev/null` |
| 命令替换 | `$(cmd)` 或 `` `cmd` `` | 只有 `` `cmd` `` |
| 上一命令退出码 | `$?` | `$status` |
| 参数个数 | `$#` | `$#argv` |
| 脚本首行 | `#!/bin/bash` | `#!/bin/tcsh -f` |
| 查看命令来源 | `type cmd` | `which cmd` |

从 bash 抄脚本到 tcsh，按这个清单逐条过一遍，能避掉九成的错：

1. 所有 `export` 改成 `setenv`（且去掉等号）。
2. 所有 `[ ... ]` 改成 `( ... )`，`fi` 改成 `endif`，`done` 改成 `end`。
3. 所有 `2>&1` 改成 `>&`，否则报 `Ambiguous output redirect`。
4. 所有 `$?` 改成 `$status`，且**紧接着读**（中间插一条 `echo` 就把它覆盖了）。
5. 首行加 `-f`。

第 3 条要特别记：tcsh 里 `>` 后面跟 `&` 表示"输出和错误一起"，语法是 `cmd >& file`，没有 `2>&1` 这种文件描述符写法。硬写会得到：

```
Ambiguous output redirect.
```

:::pitfall $status 被自己覆盖了
现象：脚本里 `dc_shell -f syn.tcl` 失败，但 `if ( $status != 0 )` 永远进不去。

原因：`$status` 只保存**上一条命令**的退出码。你在中间插了一句 `echo "done"`，`$status` 就变成了 echo 的 0。

怎么查：`tcsh -x` 看执行顺序，或者临时把判断改成 `echo RC=$status` 放在紧邻的下一行。

怎么改：命令执行完**立刻**存下来：`set rc = $status`，后面都判断 `$rc`。这是 tcsh 脚本里最容易写错、最难发现的一类 bug。
:::

:::lab 动手：写一个 tcsh 脚本，把目录里的 .tcl 全跑一遍
**任务**：写 `run_all.csh`，接受一个目录作为参数，遍历里面所有 `.tcl`，打印每个文件名；没有 `.tcl` 时打印提示并返回非 0。

```csh
#!/bin/tcsh -f
# 作用：遍历目录下所有 .tcl 并逐个处理（公司批量脚本的最小骨架）
# 用法：./run_all.csh <目录>；目录不存在或没有 .tcl 时返回非 0
# 注意：shebang 必须在第 1 行，任何注释都不能写它前面

if ( $#argv < 1 ) then                 # 参数检查：没给目录就直接退出
    echo "usage: $0 <dir>"
    exit 1
endif

set DIR = $1                           # 取第一个参数（本地变量就够，不用 setenv）
if ( ! -d "$DIR" ) then                # 目录不存在也退出，别带着错路径往下跑
    echo "[ERROR] not a directory: $DIR"
    exit 2
endif

# tcsh 的通配符匹配不到会直接报 "No match."，所以先用 ls 探一次
ls $DIR/*.tcl >& /dev/null
if ( $status != 0 ) then
    echo "[WARN] no .tcl under $DIR"
    exit 3
endif

set n = 0
foreach f ( $DIR/*.tcl )               # 这里才展开成真实文件列表
    @ n++                              # 计数用 @，不是 ((n++))
    echo "[$n] $f"
end

echo "[DONE] $n files"
exit 0
```

**过关标准**：

1. `./run_all.csh` 不带参数 → 打印 usage，`echo $status` 为 1。
2. `./run_all.csh /tmp` → 打印 `no .tcl`，退出码 3。
3. 在含 3 个 `.tcl` 的目录下跑 → 打印 `[1] .. [2] .. [3] ..`，最后一行 `[DONE] 3 files`。
4. 验证 `-f` 到底跳过了什么：在 `~/.cshrc` 里加一行 `setenv DEMO_FROM_RC yes`，在脚本里加一行 `echo "DEMO_FROM_RC=$DEMO_FROM_RC"`。带 `-f` 跑输出为空；去掉 `-f` 再跑输出 `yes`——这就证明 `.cshrc` 确实被 script 读到了。
:::

## 工作中怎么用：tcsh 在你手里的三种场合 {#in-work}

**谁写这些脚本**：流程脚本一般是项目里的资深工程师或 CAD 团队写，写完全组共用；新人负责"改参数、加一轮实验、把报错贴回去"。所以你不需要从零写，但必须能读懂每一行。

**典型任务一：改 top 名字跑另一版。** 组长说"这个脚本跑的是 `ipa_top`，你改成 `soc_top` 跑一遍"。你要能定位到 `setenv DESIGN ipa_top` 这一行，知道为什么它是 `setenv`（工具要读），改完 `tcsh -n` 检查语法，再跑。

**典型任务二：加一组实验。** 原本只跑 `util=0.30`，你要跑 `0.30/0.35/0.40` 三组。把写死的一行改成 `foreach u ( 0.30 0.35 0.40 )`，循环体里 `setenv UTIL $u`。

**典型任务三：判断脚本为什么挂。** 报 `Undefined variable` 就去查变量名和 `set`/`setenv`；报 `Ambiguous output redirect` 就是从 bash 抄来的 `2>&1`；报以 `if:` 开头的语法错误，就是 `if` 少空格或漏了 `then`；跑得慢先看有没有 `-f`。

**做错了会怎样**：把 `setenv` 写成 `set`，脚本前半段一切正常，工具读不到 top 名字，用默认值跑完 6 小时，产出的是一个错设计的报告，而且日志里没有任何红字。这是 tcsh 最典型的"静默失败"——不报错，但结果是错的。**所以变量设完要 `env | grep` 验证一次。**

:::quiz
`set` 和 `setenv` 的本质区别是什么？|`set` 定义 shell 变量，只在当前 shell 有效，不传给子进程；`setenv` 定义环境变量，会传给子进程（工具能读到）。判断标准是"要不要被脚本里启动的工具看到"。
`#!/bin/tcsh -f` 里的 `-f` 做什么？|让 tcsh 启动时不读 `~/.cshrc` 和 `~/.login`。好处是启动快、结果可复现、不受个人别名和配置干扰。
tcsh 里给 PATH 加目录的正确写法？|`set path = ( /new/dir $path )`，小写 `path`，空格分隔的数组，用圆括号包住。
`set msg = hello world` 为什么报错，怎么改？|值里有空格被当成多个参数，语法崩掉。改成 `set msg = "hello world"`。另外 `setenv` 不能写等号。
`!$` 和 `!*` 分别是什么？|`!$` 是上一条命令的最后一个参数；`!*` 是上一条命令的所有参数。常用来复用长路径。
为什么 `echo "build done!"` 在 tcsh 里会报 Event not found？|tcsh 的历史扩展在双引号里也会触发，`!` 被当成历史引用。改用单引号、加反斜杠，或者 `set histchars` 换成别的触发字符。
`source setup.csh` 和 `./setup.csh` 有什么区别？|`source` 在当前 shell 里执行，变量留下并立刻生效；`./setup.csh` 在新子进程里执行，进程结束变量就没了。
tcsh 里 `$status` 为什么经常"读不到失败"？|它只保存上一条命令的退出码，中间插一条 `echo` 就被覆盖。要立刻 `set rc = $status` 存下来再判断。
从 bash 抄脚本到 tcsh，`2>&1` 要改成什么？|改成 `>&`，写成 `cmd >& log`。tcsh 没有 `2>&1` 这种写法，硬写会报 `Ambiguous output redirect`。
`.cshrc` 和 `.login` 分别在什么时候被读？|`.cshrc` 每个 tcsh 启动都读（交互和跑脚本都一样）；`.login` 只在登录 shell 读一次。加 `-f` 两个都不读。
