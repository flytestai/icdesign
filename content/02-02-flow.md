## 一条线看懂全流程 {#map}

:::goal 能按顺序画出八个阶段，对每个阶段说出"输入是什么文件、产出什么文件、交给谁"，并判断出问题该往回退到哪一步。
:::

后端不是"一个软件跑一遍"，而是**八个阶段串起来的流水线**。每个阶段的输出就是下一个阶段的输入，中间任何一个环节偷工，后面都要加倍偿还。

```
RTL 代码
   │  ① 综合 Synthesis            → 网表 .v + 约束 .sdc + 时序库 .db
   ▼
门级网表
   │  ② 布局规划 Floorplan        → 芯片尺寸、引脚、宏单元位置  (.def)
   │  ③ 电源规划 Power Plan       → 电源网格、电源环、通孔
   │  ④ 布局 Placement            → 每个标准单元的坐标
   │  ⑤ 时钟树 CTS                → 时钟缓冲器 + 平衡后的时钟网络
   │  ⑥ 布线 Route                → 所有信号的金属连线
   │  ⑦ 收尾 Chip Finish          → filler、DRC 修复、导出 GDSII
   ▼
   │  ⑧ 签核 Signoff              → STA 时序 + PV 物理验证 + IR/EM
   ▼
GDSII → 工厂
```

:::term Gate-level Netlist | 门级网表
综合的输出。里面不再是 `always @(posedge clk)`，而是一堆标准单元实例和它们之间的连线。

把它想成"配料表"：用了哪些门、各多少个、谁连谁。**网表只描述连接关系，不描述位置**——位置是后面布局阶段才决定的。
:::

:::term Handoff | 阶段交接
一个阶段把成果交给下一个阶段。规范的做法是交"一个能复现的包"：数据库存档 + 脚本 + 报告 + 一行说明"这一版改了什么、已知问题是什么"。

交接不清是项目里最常见的扯皮来源：接手的人不知道上一版动过什么，只能重跑一遍对比。
:::

八个阶段，一张总览表：

| 阶段 | 一句话 | 最大风险 | 详细课号 |
|---|---|---|---|
| ① 综合 | RTL 变成门 | 约束写错，后面全白做 | 本课 ①、阶段四 |
| ② 布局规划 | 定芯片多大、东西放哪 | 格局错了优化救不回来 | 03-02、03-03 |
| ③ 电源规划 | 铺电网 | 线太细 IR drop，线太粗没地方走信号 | 03-04 |
| ④ 布局 | 摆标准单元 | 拥塞、时序同时恶化 | 03-05 |
| ⑤ 时钟树 | 让时钟同时到 | skew/功耗/buffer 数量失控 | 03-08 |
| ⑥ 布线 | 连线 | DRC 清不干净 | 03-09 |
| ⑦ 收尾 | 补齐、导出 | 密度、天线、DRC 残留 | 03-12 |
| ⑧ 签核 | 签字放行 | corner 不全、waiver 无依据 | 05-02、05-03 |

:::scene 周一接手一个"都做完了"的工程
同事离职，交接给你一个项目。他留下的话是："布局布线都跑完了，就差收尾，脚本在 `pnr/` 下。"

你打开目录，看到 40 多个 `.tcl` 文件、一堆 `db/` 存档、几十份报告，文件名是 `run_new.tcl`、`run_new2.tcl`、`run_final.tcl`、`run_final_bak.tcl`。

现在有三个问题必须先答出来，否则你今天什么都不敢跑：

1. 最后一个能用的存档是哪个？——`db/06_route.enc` 还是 `db/06_route_v2.enc`？
2. 这一版的网表和 `.sdc` 是不是配对？——`netlist/` 里有三个 `.v`，没有说明。
3. 上一版布线 DRC 剩多少条、都修在哪？——`rpt/route_drc.rpt` 有三份，时间戳差两天。

这就是"交接"这件事的具体形状：**不是把文件丢过去，而是让对方能回答"这一版是什么、从哪来、下一步该干什么"。** 八阶段四栏表，就是给这件事准备的模板。
:::

## ① 综合：从"逻辑"到"门" {#syn}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| RTL（`.v`/`.sv`）、SDC、`.db` | 把行为级逻辑映射成标准单元，按时序/面积/功耗做权衡 | 门级网表 `.v`、时序报告、面积报告 | 布局布线（PR）工程师 |

综合工具要做的决策很具体：一个 32 位加法器，用行波进位（面积小、慢）还是超前进位（面积大、快）？某个信号扇出 40，是插两级 buffer 还是用一个大驱动单元？这些选择没有标准答案，取决于 SDC 里的周期和 `set_max_transition` 这类规则。

综合的核心矛盾是**面积、时序、功耗三角**：想快就加大驱动、多插 buffer，面积和功耗跟着涨；想省电就降电压、用小单元，时序又不够。综合工程师的工作就是在这三者之间找一个能过签核的点。

```tcl
# 作用：DC 综合的最小骨架，绑库 → 读设计 → 读约束 → 映射到门 → 出报告
# 用法：在 syn/ 目录下 dc_shell -f syn.tcl；依赖 rtl/ 和 lib/ 下的 .db
set target_library lib/tsmc40_tt.db          # 目标库：真正用来映射的单元库，必须最先设
set link_library "* $target_library"         # 链接库：解引用找不到单元时查的库，别漏了引号里的 *
read_verilog rtl/ipa_top.v                   # 读 RTL，此时还是行为描述
link                                         # 把模块端口和库里的单元对应起来
source constraints/ipa.sdc                   # 读时序约束，决定优化目标
compile_ultra                                # 真正做优化并映射成标准单元
report_timing -max_paths 20 > rpt/syn.rpt    # 出时序报告，看 WNS 和违例条数
report_area > rpt/area.rpt                   # 出面积报告，看单元总面积
write -hierarchy -format verilog -output netlist/ipa_top.v   # 写门级网表
```

综合没做好的后果会一路放大。见过最常见的一种：综合为了压时序插了一堆大驱动单元，面积超 20%，后端拿到网表发现 die 怎么排都放不下，只能回去重综合。**所以后端拿到网表第一件事不是布图，是看单元数、总面积、WNS。**

:::pitfall 用错 corner 综合，后面全对不上
现象：综合报告 WNS 是 +0.2ns，PR 阶段同一个设计变成 −0.5ns。

原因：综合用了 `tt`（typical）库，PR 用了 `ss`（slow）库。慢角下延迟更大，原来的余量直接变成违例。

怎么查：看综合日志第一行的库路径，和 PR 日志第一行比对。两个名字不一样，就是这个坑。
:::

## ② 布局规划：决定这颗芯片的生死 {#fp}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| 网表、`.lef`、面积报告、封装引脚文件 | 定 die 尺寸与利用率、摆宏单元、定 IO 与 pin 位置 | 带尺寸和宏位置的 `.def`、利用率报告 | 电源规划 |

Floorplan 要做三个决定，后面所有工作都受它约束：

1. **芯片多大（die size）**。太大浪费钱（一片晶圆切的 die 少），太小布不通。
2. **IO 引脚放哪**。引脚位置通常由封装决定，放错了信号要绕远路。
3. **宏单元（SRAM 等）放哪**。这是最关键的——放错了会造成局部拥塞，怎么布都布不通。

这个阶段的产出物只有几个数字和一堆坐标，看起来最"轻"，实际上最"重"。因为后面的布局、CTS、布线都只是在既定格局里做优化，**格局错了，优化救不回来**。详细方法在第 13 课，这里只记住一句话：floorplan 花的时间应该占整个 PR 的 30%。

判断这一版能不能往下走，看三个数：利用率是否落在 60%~75%、宏单元通道是否按出线算过、pin 位置是否和封装确认过版本。三个数里任何一个说不清，就不要急着做电源——电源一铺，改尺寸就要连电源一起重做。

## ③ 电源规划：芯片的血脉 {#power}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| floorplan 后的 `.def`、功耗估算、电流密度 | 铺电源环（ring）、电源条（stripe）、连到每行的电源轨（follow pin）、打通孔 | 带完整电源网络的 `.def`、IR 预估报告 | 布局 |

每个单元都要吃电，电源规划就是铺一张"电网"。

```
┌════════════════════════════┐   ← power ring（外圈）
║  │    │    │    │    │    ║   ← stripe（纵向/横向电源条）
║  │    │    │    │    │    ║
║ ─┼────┼────┼────┼────┼─   ║   ← follow pin（每行标准单元的电源轨）
└════════════════════════════┘
```

为什么重要：**线太细 → 电阻大 → 电压掉（IR drop）→ 单元工作变慢甚至失效；线太粗 → 占地方 → 没地方走信号线。**

这一阶段最容易被低估，因为它"看起来只是画几条粗线"。真实项目里电源规划要考虑三件事：电流从焊盘进来要经过几层金属、每条 stripe 能扛多少电流（EM 限制）、以及电源线压在宏单元引脚上会不会挡路。

做错的后果要等到签核才看得见：IR drop 超标意味着芯片跑到最高频时局部电压塌陷，表现是"大部分片子能跑、少数片子随机死机"——这类问题最难定位，也最难和客户解释。所以电源规划宁可多铺一层、宽一点，也不要赌。

## ④ 布局：把单元摆进去 {#place}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| 带电源的 `.def`、网表、SDC | 决定每个标准单元的坐标和朝向，同时做初步时序优化 | 带坐标的 `.def`、拥塞报告、时序报告 | 时钟树（CTS） |

把网表里几万个标准单元，按行摆进标准单元区。目标很矛盾：

- 放在一起 → 连线短、时序好，但局部太挤、布不通。
- 摊开 → 好布线，但连线长、时序差。

工具的做法是先算一个"最优位置"（可能重叠），再逐步摊开（legalize）到合法位置。这个"先理想后合法"的过程会产生一类典型现象：**legalize 之后时序变差**，因为单元被推离了理想位置，连线变长。这时候要靠 `place_opt_design` 之类的优化步骤补回来。

拥塞（congestion）是布局质量的直接反馈：某块区域的走线需求超过可用轨道数，工具会报 `routing congestion` 或者绕远路。看到拥塞，先怀疑两件事——宏单元通道留窄了、或者利用率太高。

布局质量直接决定后面两步能不能收敛：单元摆得太散，CTS 的缓冲器要跑更远、insertion delay 变大；摆得太挤，布线无路可走，只能靠拆线重布硬扛。所以布局报告不能只看时序，一定要同时看拥塞热图和单元密度图。

## ⑤ 时钟树：让时钟同时到达 {#cts}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| 布局后的 `.def`、SDC（含时钟定义）、CTS 可用缓冲器清单 | 插缓冲器建树，把 skew、latency、transition 做到目标内 | 带时钟树的 `.def`、skew/树结构报告 | 布线（中间会先过 OptCts） |

时钟要送到每一个触发器。几万个触发器，如果直接从时钟源拉线，延迟差异巨大，时序根本没法收敛。

CTS（Clock Tree Synthesis，时钟树综合）的做法是**建一棵树**，一层层插缓冲器，让到每个触发器的延迟尽可能相等。核心指标是 skew（不同叶子之间的到达时间差）和 insertion delay（源到叶子的总延迟），两个指标互相拉扯，第 19 课整课都在讲。

这一步的特殊性在于：**它是全流程里唯一"专门为时钟服务"的阶段**。CTS 之前时钟是理想时钟（零延迟），CTS 之后换成真实传播时钟，原来藏着的 hold 违例会一次性暴露出来——这是正常现象，不是树建坏了。

正因为时钟延迟变了，CTS 之后必须重跑全芯片时序，而不是拿布局阶段的报告改几个数凑结论。这一步的输出还要给 STA 团队一份：签核时用的时钟延迟和 skew，就是这里定下来的值。

## ⑥ 布线：把线连起来 {#route}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| CTS 后的 `.def`、时序约束、NDR 规则 | 全局布线定通道、详细布线定轨道和通孔，修 DRC 和时序 | 布线后 `.def`、DRC 报告、寄生文件 `.spef` | 收尾 + 签核（STA） |

给每个连接找一条物理上可走的路径，分两步：

1. **全局布线（global route）**：规划大致走哪条通道，像导航规划走哪条高速。
2. **详细布线（detail route）**：精确到具体轨道、具体层、具体过孔。

布线要同时满足：连通、不短路、满足 DRC、时序不太差。这四件事经常冲突——绕开一个障碍可能多打四个 via，多出来的电阻就把时序吃掉了。

布线阶段最典型的"慢性病"是 DRC 清不干净：跑 8 小时，剩 300 条 spacing 违例，改一个参数重跑又是另外 300 条。根因往往不在布线，而在 floorplan 或布局阶段留下的拥塞。

布线完成后的 `.spef` 是后续 STA 的唯一依据：签核报告上每一个线延迟数字，都是从这里算出来的。所以布线结束时必须确认"提取用的 corner 和签核的 corner 一致"，否则前面所有时序结论都要重算。

:::term Via | 过孔
连接不同金属层的"楼梯"。M1 到 M2 要打一个 via，M2 到 M3 再打一个。

via 太多会占面积、增加电阻；via 太少或打错位置会 DRC 违例。布线工具会在"换层省距离"和"多打 via 增电阻"之间做权衡。
:::

## ⑦ 收尾：让它能交给工厂 {#finish}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| 布线后 `.def`、DRC 报告 | 插 filler 和边界单元、修 DRC、检查天线和密度、导出 GDSII | `.gds`、最终网表、寄生文件、DRC 报告 | 签核（PV）与工厂 |

- **插 filler**：标准单元行里会有空隙，填上不功能的填充单元，保证每层密度均匀（否则工厂抛光不平）。
- **修 DRC**：把剩下的违例逐条修掉，或者写 waiver 说明理由。
- **导出**：DEF（布局布线信息）、GDSII（完整版图）、带寄生的网表。

收尾阶段的工作看起来是"打扫卫生"，但它决定了工厂收不收。密度不达标、天线效应没修、边界单元漏插，任何一条都会让这批片子良率难看。

这一步由 PR 工程师自己做，做完把 `.gds` 和 `.def` 交给物理验证（PV）团队跑 DRC/LVS，同时把 `.spef` 和最终网表交给 STA 团队做签核。**交接前必须自己先跑一遍 DRC**——把 3000 条违例丢给下游，等于让别人的第一周都在替你擦屁股。

:::term Filler Cell | 填充单元
没有逻辑功能、只占面积的单元，用来填满标准单元行的空隙。

两个作用：一是保证每一层金属和poly的密度均匀（工厂 CMP 需要）；二是把电源轨连成连续的一条，不然行中间断开就没法供电。
:::

:::term Antenna | 天线效应
布线时一段长金属连到晶体管栅极上，在等离子刻蚀过程中会像天线一样收集电荷，电荷积累多了会把栅氧化层击穿。

检查办法是算"金属面积 ÷ 栅面积"的比值，超了就断开这段线、跳到更高一层再连回来（跳层）。这是课表外补充，但收尾阶段必查。
:::

## ⑧ 签核：最后一道门 {#signoff}

| 输入 | 做什么 | 输出 | 交给谁 |
|---|---|---|---|
| 最终 GDSII、最终网表、`.spef`、SDC | 用独立工具做 STA、DRC/LVS、IR/EM，逐条确认或写 waiver | 签核报告包、签字记录 | 流片（Tapeout） |

| 项目 | 工具（课程里） | 通过标准 |
|---|---|---|
| 时序 STA | PrimeTime | setup/hold 违例 = 0（或每条都有 waiver） |
| 物理验证 PV | Calibre / KLayout | DRC = 0，LVS 一致 |
| 功耗完整性 | RedHawk | IR drop 在阈值内，EM 不超限 |

签核不是"跑一遍工具"，而是"每个数都有人负责"。同一条路径要在多个 corner（tt/ss/ff、不同电压温度）下都过；剩下的违例要逐条写清为什么不影响功能。第 28 课会专门讲签核流程。

这一步的负责人**不是 PR 工程师**，而是独立的 STA 和 PV 团队，时间点通常在流片前 2~4 周。这么安排是有意的：做设计的人不能自己判自己及格。签核不过的处理只有三种——改设计、降频、延后流片，没有"打个补丁"这个选项，因为掩模版一旦开工就改不了。

:::term Waiver | 豁免
对某条已知违例的"书面放行"：写清违例位置、数值、判断依据（为什么不影响功能）、谁批准的。

waiver 不是"忽略"，是"知情接受"。没有依据的 waiver 等于埋雷——签核会议上被问到答不出来，这条就得回去修。
:::

## 全流程交付物清单 {#deliverables}

这张表建议打印出来贴在工位上。**文件名级**，因为交接时说不清文件名的人，通常也没想清自己做了什么。

| 阶段 | 交付物（典型文件名） | 下一环谁用 |
|---|---|---|

几点说明：

- `.def` 是布局布线信息的标准交换格式，**同一种格式从头传到尾，每阶段存一版**，所以文件名要带序号。
- `.spef` 是寄生参数文件（每根线的电阻电容），STA 靠它算真实线延迟。没有它，时序报告只能按"估算线延迟"算，不准。
- 报告不要只留最后一版。签核出问题时，需要回看"哪一版开始变差的"，历史报告就是证据。

为什么强调"文件名级"？因为交接时最常发生的对话是："你说的那份报告是哪个？"——目录里有五份 `timing.rpt`，谁也不知道哪份对应哪一版数据库。文件名里带阶段序号和日期，这个问题就不存在了。**能说清文件名，才说明你真的知道自己交付了什么。**

这张表还有一个用法：当成 review 的检查表。逐项问"这一步的文件在哪"，指不出来的那一行，就是这一步没做完。

## 哪个阶段最容易返工 {#rework}

答案是：**布局规划**。其次是综合（网表质量），再其次是 CTS。

| 返工点 | 什么时候发现 | 返工代价 | 为什么要重来 |
|---|---|---|---|
| 宏单元位置 / die 尺寸 | 布线拥塞、放不下 | 最高：布局 8h + CTS 3h + 布线 6h，约 2 天 | 所有坐标相对 floorplan，改了等于坐标全废 |
| 网表质量（面积/结构） | floorplan 排不下、时序差太远 | 高：重综合数小时 + 全流程重跑 | 单元数和连接关系变了，后面全要重做 |
| 时钟约束 / CTS 设置 | CTS 报告 skew 超标 | 中高：CTS 到布线要重跑 | 树结构变了，布线资源分配跟着变 |
| 利用率 / 布局密度 | 布线 DRC 爆炸 | 中：布局到布线重跑，约 1 天 | 单元位置要重摆 |
| 布线参数 | 布线 DRC 残留 | 低：重跑布线几小时 | 只影响布线本身 |
| filler / 密度 | 收尾检查 | 低：几十分钟 | 只加单元，不动逻辑 |
| 签核 corner 缺失 | 签核前一周 | 表面低、实际致命：可能要改设计 | 前面所有"通过"都不作数 |

判断该退回哪一步，有个简单方法：**问"这个错误的根源在哪一阶段的输入里"**。

- 布线拥塞 → 看是不是宏单元通道窄（退回 floorplan）
- 时序全线差 → 看是不是网表本身太慢（退回综合）
- hold 大面积崩 → 先看是不是 CTS 后正常暴露（不用退，交给 OptCts）

:::pitfall 一出问题就从头上重跑
现象：布线 DRC 多，工程师直接 `restoreDesign` 回综合后，从头跑一遍，跑了两天还是同样的 DRC。

原因：问题根源在 floorplan 的宏单元位置，从头跑只是重复同一个错误。

正确做法：先定位。看拥塞热图落在哪、是不是正好在两个宏单元之间；看违例类型是不是全是同一种 spacing。定位到阶段再回退，比盲目重跑快十倍。
:::

:::lab 动手：给一个"卡住的工程"定位返工点
**任务**：读下面三条现象，各自判断该退回哪个阶段，并说明依据。

1. 布线跑到 60% 卡住，日志报 `Routing congestion detected in region (1200,800)-(1800,1400)`，热图上红色区域正好在两个 SRAM 之间 6µm 的缝里。
2. 布局刚做完，`report_timing` 显示 WNS −1.2ns，而综合报告 WNS 是 +0.1ns，违例路径全是跨模块长线。
3. CTS 后 `report_timing -delay_type min` 出现 4000 条 hold 违例，最差的 −0.09ns，起点终点都在同一片触发器阵列里。

**步骤**：

```bash
# 作用：把每个阶段的报告按时间排序，找出"从哪一版开始变差"
# 用法：在 pnr/rpt/ 下执行；文件按阶段前缀命名，前缀数字决定顺序
ls -1 *.rpt | sort                    # 按文件名排序，看清有哪些阶段的报告
grep -H "worst slack" *.rpt | sort    # 每份报告的 WNS 一行对齐，找突变点
```

**过关标准**：三条分别答出"退回 floorplan（宏通道 6µm 太窄）/ 退回检查网表或布局约束（综合与布局差 1.3ns，先查 corner 和 SDC）/ 不用退，交给 OptCts（同簇短路径 hold 属正常暴露）"，并说出各自的判断依据。
:::

:::quiz
综合的输出三件套是什么？|门级网表 `.v`、时序报告、面积报告；约束 `.sdc` 和库 `.db` 是输入，不是输出。
为什么 floorplan 阶段的宏单元位置这么关键？|宏单元面积大、位置固定，放错会造成局部拥塞和长连线，后面布线怎么优化都救不回来，只能回头重做，而重做会让布局和 CTS 全部作废。
电源规划里"线太粗"和"线太细"各有什么问题？|太细电阻大、IR drop 严重，单元吃不饱电；太粗占走线资源，信号没地方走。
CTS 解决的是什么问题？|时钟到各触发器延迟不一致（skew 大），hold 无法收敛；CTS 插缓冲器建树把 skew 压小、把波形做陡。
布局阶段"legalize 之后时序变差"是为什么？|理想位置允许重叠，legalize 把单元推到合法位置后连线变长，延迟增加；需要后续优化步骤补回来。
收尾阶段插 filler 的两个作用是什么？|保证每层密度均匀（工厂 CMP 需要），以及把每行的电源轨连成连续一条。
返工代价最高的是哪个阶段，为什么？|布局规划。所有后续坐标都相对它，改尺寸或挪宏单元等于让布局、CTS、布线全部重来。
怎样判断一个问题该退回哪一阶段？|问"这个错误的根源在哪一阶段的输入里"：拥塞查宏通道（floorplan），全线时序差查网表（综合），同簇 hold 属 CTS 正常暴露（不用退）。
:::
