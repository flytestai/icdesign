ICC2：换一套工具，把同一件事再做一遍

ICC2 Fundamentals

IC Compiler II 的第一课：同一批后端动作在 Innovus 和 ICC2 里有两套名词，标准单元库还要先"建"成 NDM 才能用。这一课给出 20 组命令对照、OPT-041 的逐词读法，以及建库时最先撞上的版本坑。

约 35 分钟 课表学时 2 ICC2NDM建库
01

为什么换工具会卡住

本章目标学完这一课，你能把一条 Innovus 命令翻译成 ICC2 的对应命令，能独立判断"库建得对不对"，并在看到 OPT-041 时先往上翻日志而不是乱改脚本。

会开一辆车，不等于会开另一辆。方向盘、油门、刹车都在，但雨刷在左边还是右边、挡位是旋钮还是拨杆，全变了。你越想凭肌肉记忆操作，越容易在第一个路口熄火。

Innovus 换到 ICC2 就是这样。动作是同一批：读网表、摆单元、建时钟树、布线、导出。名词全换了，而且底层的数据组织方式也换了。

先认一下 ICC2 的脸：以后所有 review、所有排错，最后都要回到它的主窗口上看。

从图里要看出什么："长得像"不等于"用得对"。三个区域的位置可以照搬 Innovus 的习惯，但每一条命令都要重新学——这正是下面两章要给对照表的理由。

卡住通常发生在两个层面：

  • 名词层：你想查一个实例的坐标，手上只有 dbGet 的记忆；ICC2 只认 get_cells + get_attribute。
  • 数据层：Innovus 直接读 .lef 和 .lib 就能开工；ICC2 必须先把它们"合成"成一个 NDM 库。库没建好，后面每条命令都跑不动。

这一课先把这两层拆开讲清楚，再给对照表。命令可以查，"为什么这条命令在这个工具里不存在"必须想明白，否则每次换工具都要从零开始。

工作场景 · 周一早上，一个跑不通的 ICC2 会话

leader 把一个在 Innovus 里已经跑通的设计交给你："9390 个单元，QoR 报告在 pnr/rpt/，你用 ICC2 再跑一遍，对比一下。"

你打开 icc2_shell，read_verilog 成功，敲 link_block 之后 report_design_mismatch 里列了三百多个单元。你想查其中一个 SRAM 的坐标，习惯性敲 dbGet [dbGet top.insts.name u_sram0]，工具回了一句 invalid command name "dbGet"。

下午两点，你还没开始 floorplan。leader 问进度，你只能说"在调库"。

NDM (New Data Model)新数据模型库点击看解释

Synopsys 为 ICC2 设计的库容器。一个 NDM 目录里同时装三类东西：物理视图（来自 LEF）、时序视图（来自 .db）、工艺与寄生信息（来自 .tf / TLU+）。它不是一个文件，是一个目录，不要手改里面的内容。

Milkyway银河库（上一代库格式）点击看解释

ICC（现在常被叫 ICC1）时代使用的库格式。ICC2 换成了 NDM，两者不能直接互读。项目里如果还有 Milkyway 库，正规做法是从 LEF 和 .db 重建 NDM，而不是指望格式转换工具保住全部信息。

Scenario场景点击看解释

ICC2 里"一套可计算的时序条件"：一个 mode（功能模式、测试模式）+ 一个 corner（工艺/电压/温度）+ 一份寄生参数。Innovus 的对应概念是 analysis view。一个设计通常有 4~12 个 scenario，跑优化时要指定用哪个。

Link链接点击看解释

把网表里写的单元名（比如 BUFX4）和库里真实的单元定义对上号。链接不上的单元叫 unresolved（未解析），它没有时序模型、没有版图，后面所有优化都会算错或者直接停。

02

同一件事，两套名词

先看一张最小的对照。左边是"你要干的活"，中间和右边是两个工具的说法：

你要干的活InnovusICC2
查某个单元dbGet top.insts.nameget_cells
取单元属性dbGet $inst.ptget_attribute $inst origin
设全局模式setOptMode -fixFanoutLoad trueset_app_options -name <开关名> -value true
打开设计restoreDesign x.encopen_lib + open_block
读网表read_netlist x.vread_verilog x.v + link_block
多模式多端角create_analysis_viewcreate_scenario
建时钟树ccopt_designclock_opt

dbGet 和 get_* 最大的区别不在拼写，在返回值：

  • dbGet 返回的是对象列表，可以直接 foreach，也可以直接取属性。
  • ICC2 的 get_cells 返回的是 collection（集合），不能当普通 Tcl 列表用；遍历要 foreach_in_collection，取属性要 get_attribute。

同一件事写两遍，你就能看出差别：

tcl
# 作用：在 Innovus 里按名字找 SRAM，并打印坐标# 用法：Innovus 命令行直接执行；当前设计已经 open 且有实例 u_sram0set insts [dbGet -p top.insts.name u_sram*]      ;# 按通配符筛出名字以 u_sram 开头的实例foreach i $insts {                                ;# dbGet 返回的是列表，可以直接 foreach    puts "[dbGet $i.name] [dbGet $i.pt]"          ;# 取实例名和坐标（pt 是 point 的缩写）}
tcl
# 作用：同一件事在 ICC2 里的写法# 用法：icc2_shell 里执行；先 open_block，否则 get_cells 返回空set insts [get_cells u_sram*]                                   ;# 返回 collection，不是列表foreach_in_collection i $insts {                                ;# 遍历 collection 必须用这个命令    puts "[get_attribute $i full_name] [get_attribute $i origin]" ;# 取属性要用 get_attribute}

记住一句话：Innovus 把数据库当 Tcl 列表用，ICC2 把数据库当对象集合用。 这一条能解释一半的"命令不认识"。

Innovus 那一边的 dbGet 会话长什么样，下面这张图是一段真实摘录。

从图里要看出什么：dbGet 返回的是对象不是值，想要值必须再点一层属性。这是"命令不认识"的另一半来源——返回值形态变了，旧写法整套作废，不是只换个命令名。

再补一个高频差异：设全局开关。Innovus 用 setOptMode -fixFanoutLoad true，一个命令管一类行为；ICC2 用 set_app_options -name place.coarse.continue_on_missing_scandef -value true 这种"点分路径"，每个开关一个完整名字。ICC2 的写法更长，但好处是能按前缀列出相关开关（get_app_options），排查时不用翻整本手册。开关名随版本增删，照抄教程前先 man set_app_options 确认。

命名风格也有规律

ICC2 的命令更像"动词 + 名词"的英文：create_lib、open_block、report_qor。Innovus 里 camelCase（驼峰）更多：restoreDesign、place_opt_design、report_area。

看到一条陌生命令，先判断它是"读/写/建/报"哪一类，再去对照表里找同一类，比死记快。

03

两套工具的数据库不一样

把库想成收纳箱：三家厂商各有各的箱子，盖子形状都不一样。

数据谁产生Innovus 怎么用ICC2 怎么用
LEF库厂商直接 read_lef建 NDM 时读进去
.lib / .db库厂商 / Library Compiler直接读 .lib建 NDM 时读 .db
TLU+库厂商read_parasitic_tech（或等效命令）同样要单独读
设计数据库工具自己.enc 目录library 里的 block
库容器—无（散着读）NDM 目录

三件事值得单独说清：

第一，NDM 是"合起来"的产物。 Innovus 可以今天读一版 LEF、明天换一版 .lib，工具不拦你。ICC2 把两者在建库那一刻焊死在一起：LEF 里有的单元、.db 里没有，check_workspace 就会报出来。好处是后面不会出现"物理和时序不是同一版"的鬼故事，坏处是建库多了一道必须过的关。

第二，Milkyway 是上一代，不要混着用。 Milkyway 是 ICC1 的库格式，NDM 是 ICC2 的。两者不是"新旧文件名"的关系，是两套完全不同的存储结构。看到教程里写 create_mw_lib，那讲的是 ICC1，不是 ICC2。

第三，Innovus 的 .enc 是目录，不是单文件。 saveDesign 会写一整个目录，restoreDesign 读它。它同样跟工具版本强相关——大版本升级后老 .enc 常常打不开。所以项目里存盘文件名一定要带工具版本，比如 04_place_icc2_2023.03.enc，别只写 04_place.enc。

常见坑 · 用错版本的库，跑六小时才发现

现象：create_lib 能过，place_opt 跑到一半报时序计算异常，或者 report_qor 里所有单元的延迟都是 0。

原因：NDM 是用另一个 ICC2 版本建的。NDM 内部记录了生成它的版本号，跨大版本经常不兼容；.db 更是纯二进制，跨版本直接读不了。

怎么查：进 icc2_lm_shell 用 report_workspace（具体子选项以 -help 为准）看库的生成信息；再和 icc2_shell -version 对一下。对不上就重建，不要试图"修"。

怎么避免：把库的版本号写进 run 脚本的头部注释，和网表、约束一起存档。建库是 CAD 或库管理员的责任，但用库的人必须会看版本。

04

建库：ICC2 的第一道关

建库要在 icc2_lm_shell（Library Manager，库管理器）里做，不是在 icc2_shell 里。两个 shell 的命令集是互补的：read_lef、read_db、commit_workspace 只在 lm_shell 里有；place_opt、clock_opt 只在 icc2_shell 里有。

把它想成"先把零件和说明书装进标准工具箱，再拿工具箱去干活"。

tcl
# 作用：把 LEF（物理）、.db（时序）、.tf（工艺）合成一个 NDM# 用法：终端先执行 icc2_lm_shell 进入库管理器，再逐条执行；路径换成你环境里的 PDKcreate_workspace -technology /pdk/tsmc32/tsmc32.tf tsmc32_ws  ;# 建一个空工作区，先挂上工艺文件（层定义、单位）read_lef /pdk/tsmc32/lef/tsmc32_stdcell.lef                    ;# 读物理视图：每个单元的外框、引脚位置、阻挡层read_db  /pdk/tsmc32/db/tsmc32_tt_1v0_25c.db                   ;# 读时序视图：延迟表、功耗表、setup/hold 约束check_workspace                                                 ;# 交叉检查两份数据：单元名、引脚名、面积是否一致commit_workspace -output /pdk/ndm/tsmc32_tt.ndm                 ;# 检查通过后落盘，生成 NDM 目录

逐行说清三件容易忽略的事：

  • -technology 指向的 .tf 决定"这个库有哪些层、单位是微米还是纳米"。同一个 LEF 配错 .tf，读进去不报错，但所有坐标会差 1000 倍。
  • read_db 读的是编译过的 .db，不是文本 .lib。手里只有 .lib 时，要先编译：Library Compiler（lc_shell）里 read_lib + write_lib -format db。有些公司把这一步包成一个叫 librate 的脚本，名字各家不同，看到它就理解成"把 .lib 编成 .db"。
  • check_workspace 是唯一一道"物理和时序对不上"的拦截。它过了，才允许 commit_workspace。
常见坑 · check_workspace 不过，别硬 commit

现象：check_workspace 打印一批 mismatched cells，commit_workspace 直接失败。

常见原因有三类：

  1. 单元只在一侧存在：.db 里有 LOGIC0/LOGIC1，LEF 里没有；或者 LEF 里有 TAPCELL，.db 里没有（tap cell 本来就没有时序）。
  2. 引脚名不一致：LEF 里叫 A，.db 里叫 A1。
  3. 面积对不上：LEF 的外框面积和 .db 里的 area 差太多，通常是版本不匹配。

处理：先 report_workspace 看清单，再用 remove_lib_cell 把冲突单元剔掉，或者补一份匹配的 LEF。我们实测时剔掉过 3 个单元（LOGIC0、LOGIC1、TAPCELL），因为综合阶段会用反相器做 tie、tap 由后端单独插，剔掉不影响流程。

注意：剔单元要有记录。 在库的 build 记录里写清"剔了哪三个、为什么"，否则半年后没人知道这个库里少了东西。

05

版本不匹配：最先撞上的一堵墙

.db 是二进制，不是文本。文本 .lib 你能用眼睛看出周期、面积；.db 打开是乱码，只能由同版本的 Library Compiler 或 ICC2 读。

所以版本关系是一条链：

text
.lib 文本  --(lc_shell, 某个版本)-->  .db  --(icc2_lm_shell, 同代版本)-->  NDM  --(icc2_shell, 同代版本)--> 可以跑

链上任何一环换了大版本，都要从头重建。判断方法：

bash
# 作用：一次性打印工具版本，确认库和工具是不是同一代# 用法：在项目 run 目录下执行，把输出贴进 run.log 头部icc2_shell -version        # 打印 ICC2 版本，例如 2023.03-SP2（以你环境为准）icc2_lm_shell -version     # 库管理器版本，正常应与 icc2_shell 同代lc_shell -version          # 如果自己编译 .db，Library Compiler 也要对得上

真实项目里你会看到两种典型报错：一种是读库时直接说 cannot read library / 含 version、format 字样；另一种更阴——库能读进来，但 report_lib 里 timing view 是空的。第二种最难查，因为工具不报错。

所以"能用"不等于"版本对"。判断一个库能不能进项目，除了能打开，还要看三处：report_lib 有 timing view、report_parasitic_tech 有 corner、report_qor 里单元延迟不是 0。三处都过，才算这个 NDM 和当前 ICC2 是配套的。至于 NDM 内部具体子目录叫什么，各版本都在变，以你手上版本的 man 和 report_workspace 输出为准，不要按网上截图去核对目录名。

常见坑 · read_db 成功了，但时序是空的

现象：report_lib 能看到单元，get_cells 也能取到，但 report_timing 一条路径都没有，place_opt 报 OPT-041。

原因：建库时只读了 LEF，没读 .db，或者 .db 读失败但被脚本里的 catch 吞掉了。

怎么查：在 lm_shell 里用 report_workspace 看每个库挂了多少视图（选项名以 -help 为准）；在 icc2_shell 里 report_lib 看 Timing Data 那一栏是不是空的。

怎么避免：建库脚本里 read_db 后面立刻加一条断言式检查，读不到就直接退出，不要让它带着半个库往下走。

不要背名字，背七类动作：读入、设模式、布局、时钟、布线、优化、导出。每类记住"输入是什么、输出是什么"，名字忘了就 man 一下。

07

一个真实的坑：OPT-041

第一次跑 place_opt，报错只有一行：

text
Error: OPT-041 Scenario Manager creation failed

很多人看到这句就去查 NDM 有没有 timing view。方向对了一半——但如果你查了，发现 timing view 明明在，就会彻底卡住。

正确做法是把这句话拆开逐词读：

片段含义
Error错误级别（还有 Warning、Information）
OPT消息来自优化器模块（optimizer）
041该模块的第 41 号消息，查手册时用这个号
Scenario Manager场景管理器，负责把 mode + corner + 寄生组合成可计算的时序条件
creation failed它没能建出场景

这句话告诉你的是结果：场景没建起来。它没告诉你原因。原因通常在上一行或上几行——工具是"先出错，再报一个更笼统的错"。

往上翻，我们看到了真正的原因：

text
NEX-018: no valid parasitic for default corner (LATE)

再拆一次：

  • no valid parasitic：没有可用的寄生参数模型。
  • default corner：工具在用默认端角，说明你没有显式指定。
  • LATE：晚端角，也就是算 max delay / setup 用的那一套。与之对应的是 EARLY（算 hold）。

结论：缺的是 TLU+（寄生参数模型），不是时序视图。

修复要在 link_block 之后、place_opt 之前：

tcl
# 作用：读入 TLU+ 寄生模型，并指定 early/late 各用哪一套# 用法：open_block + link_block 之后执行；否则工具还不知道当前设计，参数挂不上去read_parasitic_tech -tlup /pdk/tsmc32/tlup/tsmc32.tlup \        ;# 读 TLU+ 文件（每个金属层的 R/C 表）    -layermap /pdk/tsmc32/tlup/layer.map \                        ;# 层号映射：TLU+ 里的层名对到设计里的层号    -name tt                                                       ;# 给这套参数起名 tt，后面引用这个名字set_parasitic_parameters -early_spec tt -late_spec tt              ;# early（算 hold）和 late（算 setup）都用 tt
常见坑 · 只看最后一条错误

现象：日志最后一行是 OPT-041，你按 OPT-041 查了半天文档，改了 scenario 设置，还是同样的错。

原因：OPT-041 是下游症状。上游可能已经报了 NEX-018、LIB-xxx、read_db failed，只是被刷屏刷过去了。

规矩：从最后一条错误往上翻 5 行，找第一条 Error。 第一条才是根因，后面都是连锁反应。日志里搜 ^Error 比看最后 20 行有用得多。

命令：grep -n "^Error" run.log | head -5。

08

工作中怎么用：建库这一步归谁

谁做：大公司由 CAD 组或库管理员建库，PR 工程师只负责用；小公司或实验室里，PR 自己建。无论谁建，用库的人必须会看版本。

输入：PDK 里的 LEF、.db、.tf、TLU+；以及一份"这次建库剔了哪些单元"的记录。

输出：一个 NDM 目录 + 一份 build 记录（工具版本、日期、剔除清单、check_workspace 结果）。这份记录要跟网表、约束一起进项目归档。

评审看什么：库里 timing view 数量对不对（多少种 corner）、面积和 LEF 是否一致、有没有为了"能过"而剔掉关键单元。剔 LOGIC0/LOGIC1 可以，剔一个真实的 buffer 就是事故。

做错了会怎样：库版本不对，最短的代价是重跑一天；最长的代价是 signoff 时发现 PR 和 STA 用的不是同一版库，两边时序对不上，整轮返工。所以 run 脚本第一行就该写清库路径和版本。

自测：先自己想，再点开答案
ICC2 里为什么不能直接用 dbGet？
dbGet 是 Innovus 的命令；ICC2 用 get_cells/get_nets 等返回 collection，遍历要用 foreach_in_collection，取属性要用 get_attribute。
NDM 里必须同时有什么？
物理视图（LEF）和时序视图（.db）。只有物理视图时能打开设计，但优化器算不了时序。
建库为什么在 icc2_lm_shell 而不是 icc2_shell？
read_lef、read_db、create_workspace、commit_workspace 这些库管理命令只在 Library Manager 里提供；icc2_shell 负责用库做实现。
check_workspace 报单元不匹配，通常有哪三类原因？
单元只在一侧存在（如 LOGIC0、TAPCELL）、引脚名不一致、面积对不上（版本不匹配）。
OPT-041 Scenario Manager creation failed 应该怎么查？
这是结果不是原因。往上翻找第一条 Error；常见根因是 NEX-018: no valid parasitic，即缺 TLU+，不是缺 timing view。
Milkyway 和 NDM 是什么关系？
Milkyway 是 ICC1 的库格式，NDM 是 ICC2 的库格式；两者不通用，需要从 LEF/.db 重建。
Innovus 的 .enc 和 ICC2 的 block 有什么区别？
.enc 是独立目录，saveDesign 写、restoreDesign 读；ICC2 的 block 存在 library 里，要先 open_lib 再 open_block。
为什么 .db 必须和 ICC2 版本匹配？
.db 是二进制格式，跨大版本通常读不了；库、NDM、工具三者要同代，否则轻则时序为空，重则直接报错。
