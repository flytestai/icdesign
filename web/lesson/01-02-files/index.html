01

文件不止一种

本章目标学完这一课，你能用 ls -l 第一列判断文件类型和权限，独立算出任意 chmod 数字，并在脚本报 "Permission denied" 或 "bad interpreter" 时三分钟内定位原因。

ls -l 输出的第一列看着像乱码，其实第一位就告诉你这是什么：

text
drwxr-xr-x   2 weizhen pdteam  4096 Nov 22 10:12 scripts-rw-r--r--   1 weizhen pdteam  1820 Nov 22 10:12 run.tcllrwxrwxrwx   1 weizhen pdteam    18 Nov 22 10:12 latest -> runs/20261122
第一位类型说明工程里的例子
-普通文件文本、网表、报告、压缩包timing.rpt、soc.v、.db
d目录directory，能进去的"文件夹"pnr/、scripts/
l符号链接快捷方式，指向别处latest -> runs/20261122

Linux 里"一切皆文件"，所以还会见到 c（字符设备，如 /dev/tty）、b（块设备，如硬盘）、s（socket）、p（管道）。这四个你不用记，只要认得前三个就够干活了。

一个实用技巧：ls -F 会在目录名后加 /、可执行文件后加 *、符号链接后加 @，一眼分清：

bash
# 作用：用后缀区分类型；在任意目录下执行ls -F                    # pnr/  scripts/  run.sh*  latest@ls -lF                   # 长格式 + 类型后缀，两个信息一起看
Symlink（Symbolic Link）符号链接点击看解释

一个"指向另一个文件的文件"，类似 Windows 的快捷方式。删掉链接不会删掉原文件；原文件被删，链接会变成"断链"（红色闪烁或 ls -l 显示目标不存在）。
工程里常用来做"最新版本"指针：latest -> runs/20261122，脚本永远读 latest/，就不用每次改路径。

02

复制、移动、重命名、删除

bash
# 作用：文件的复制、移动、删除；在工程目录下执行，动手前先 ls 看一眼cp run.tcl run_backup.tcl       # copy：复制一份，命名 run_backup.tclcp -r scripts/ scripts_bak/     # -r = recursive，目录必须加 -r，否则报 "omitting directory"cp -p run.tcl /tmp/             # -p = preserve，保留原文件的修改时间和权限（备份时有用）cp -a scripts/ scripts_bak2/    # -a = archive，等于 -rp 再加保留链接，整目录备份用这个cp run.tcl{,.bak}               # 花括号展开：等价于 cp run.tcl run.tcl.bak，改配置前必备份 mv run.tcl scripts/             # move：把文件移到 scripts 目录下mv run.tcl run_v2.tcl           # mv 同时承担"重命名"（同一目录内移动就是改名）mv old_dir/ old_dir.bak/        # 比 rm -r 安全得多的"删除"：先改名，确认没用了再删 rm run_backup.tcl               # remove：删除文件rm -r old_runs/                 # 删目录必须 -rrm -f *.log                     # -f = force，不询问直接删rm -i *.log                     # -i = interactive，逐个问你要不要删（批量删时先这么跑一遍） mkdir scripts2                  # 建目录mkdir -p a/b/c                  # -p：父目录不存在就一起建rmdir empty_dir                 # 只能删空目录，有文件会报 "Directory not empty"touch new.tcl                   # 建一个空文件；文件已存在则只更新修改时间

cp 和 mv 有一个很多人不知道的语义差别：mv 是同文件系统内的"改名"，不复制数据，瞬间完成；跨文件系统时它才真的复制再删除。 所以把 6GB 的数据库 mv 到另一个挂载点时，会等很久——这不是卡住了。

常见坑 · rm -rf 是这门课里最危险的命令

rm -rf /path/to/dir 会不问、不回收、不提示地删掉整个目录。Linux 没有回收站。

三个保命习惯：

  1. 删之前先 ls 看一眼。ls old_runs/ 确认内容，再 rm -r old_runs/。
  2. 变量要加引号。rm -rf $DIR/ 如果 $DIR 是空的，就变成了 rm -rf /。
  3. 路径别用通配符。rm -rf run/* 手滑打成 rm -rf run /*，中间多一个空格，删的就是整个根目录。

再加一条工程习惯：能改名就别删。mv old old.bak 之后，你还有一次反悔的机会；rm -r old 之后没有。

工作场景 · 周五 18:40，一条 rm 让整个组加班

你入职两个月，在 route 阶段负责清理磁盘。师傅说过"run/ 下超过三天的都可以删"，于是你敲了：

text
rm -rf run/2026111*

本来想删 20261110、20261111 这几天的旧目录，结果把当天的 20261119_0930 也匹配进去了——那个目录里是刚跑完、还没保存到 pnr/db/ 的布线结果。

Linux 没有回收站，也没有"撤销"。唯一的补救是重跑，7 小时。

老工程师删文件前总要先 ls 一眼，不是谨慎，是被这么坑过。所以行业里有个默认规矩：先看后删，能改后缀就别删（mv old old.bak 比 rm -r old 安全得多）。你会在很多老脚本里看到 mv 到 trash/ 目录而不是 rm，那不是啰嗦，是工程成本算出来的。

04

权限：rwx 到底是什么

ls -l 的那串 -rw-r--r-- 拆成四段看：

text
-      rw-        r--        r--类型   属主权限    属组权限    其他人权限

真实屏幕上是这样（每一列都对得上）：

要看出的是：9 位权限永远是"属主 3 位 + 属组 3 位 + 其他人 3 位"，顺序不会变。所以脚本跑不了时，先数到第 3 位看有没有 x——那就是"你自己能不能执行"。

三个字母对应三种动作：

字母含义对文件对目录
rread 读能看内容（cat）能列出里面有什么（ls）
wwrite 写能修改内容能在里面新建/删除文件
xexecute 执行能当程序运行能进去（cd）、能穿过它访问子路径

所以 -rw-r--r-- 的意思是：属主能读写，同组和其他人只能读。

注意目录那一列容易反直觉：目录的 w 不是"能改目录名"，而是"能在里面增删文件"。所以一个只有 r 没有 w 的目录，你能看列表但删不掉里面的东西；只有 x 没有 r 的目录，你能 cd 进去、能访问已知文件名，但 ls 会报 Permission denied。

Permission权限点击看解释

谁能对某个文件做什么。Linux 用三组 rwx 表示，分别对应"文件的主人 / 同组的同事 / 其他所有人"。
权限不对，工具就读不到库、脚本就跑不起来——这是新手最常遇到的"环境问题"，其实 90% 是权限问题。

数字表示法：755 和 644 是怎么加出来的

r=4，w=2，x=1，每一组内部把字母对应的数字加起来，就是一个 0~7 的数：

权限加法数字
rwx4+2+17
rw-4+26
r-x4+15
r--44
-wx2+13
-w-22
--x11
---00

三组数字连起来就是 chmod 的参数。手算三个例子：

  • 755 = rwx + r-x + r-x = 7/5/5：我能读写执行，同组和其他人能读能执行。目录和脚本的标准权限。
  • 644 = rw- + r-- + r-- = 6/4/4：我能读写，别人只能读。普通文件的标准权限。
  • 640 = rw- + r-- + --- = 6/4/0：同组能读，其他人完全看不到。放敏感配置（含密钥、工艺参数）时用。

反过来算：750 是什么？7=rwx，5=r-x，0=---，即 rwxr-x---——属主全权限，同组能读能进，外人无权限。这是团队共享目录的常见配置。

bash
# 作用：改权限；在文件所在目录执行，改完用 ls -l 验证chmod 755 run.sh                # 数字法：整体重设成 rwxr-xr-xchmod 644 config.tcl            # 普通配置文件chmod 640 soc.sdc               # 只让同组看，外人看不到chmod +x run.sh                 # 符号法：只给三组都加执行位，其他权限不动chmod u+x,go-w run.sh           # 符号法精确控制：属主加 x，同组和其他人去掉 wchmod -R 755 scripts/           # -R = 递归，把整个目录下所有东西都改掉（慎用）chmod -R u+rwX scripts/         # 大写 X 只给目录加 x，不给普通文件加（比 -R 755 安全）

+x 和 755 的区别：+x 是"在现有基础上加"，会保留原来的 6 或 4；755 是"整体覆盖"。所以 chmod 755 一个原本 600 的私钥文件，等于把它变成了所有人可读——这是安全事故。改权限前先 ls -l 看现状。

三步换算：任意一行权限都能和数字互转

不管是"给我一个数字"还是"这一行是什么意思"，都走同样三步：

  1. 切段：跳过第 1 位类型，剩下 9 位每 3 位一组（属主 / 属组 / 其他人）。
  2. 组内加：r=4、w=2、x=1，有哪个加哪个。
  3. 拼起来：三组各得一个 0~7 的数，从左到右连写。

练四个，都是工程里真会遇到的：

看到切段加法数字读作
-rwxr-x---rwx / r-x / ---7 / 5 / 0750我能读写执行，同组能读能进，外人无权
-rw-rw-r--rw- / rw- / r--6 / 6 / 4664同组也能改（团队共享文件）
-rwsr-xr-xrws / r-x / r-x7 / 5 / 5 + 特殊位4755任何人执行时都以属主身份运行
drwxrwxrwtrwx / rwx / rwt7 / 7 / 7 + 特殊位1777谁都能写，但只能删自己的文件

后两个里的 s 和 t 是特殊位，占的是 x 的位置：有执行权时显示小写 s/t，没有执行权时显示大写 S/T。三个特殊位只要记住用途：

数字位名字加在哪作用典型
4setuid属主段的 x 位执行时借用文件属主的身份/usr/bin/passwd（4755）
2setgid属组段的 x 位目录上：新建文件自动继承该属组团队共享目录（2775）
1sticky其他人段的 x 位目录里只能删自己建的文件/tmp（1777）

反向也要会。给你数字，能说出"谁能干什么"：

  • 700 的目录：只有我能进，同组和外人在 cd 这一步就被拒。
  • 640 的文件：我读写，同组只读，外人连打开都不行（适合放 license 和工艺参数）。
  • 777 的脚本：谁都能改——等于把执行权交给全公司，这是隐患，不是方便。
常见坑 · Permission denied：脚本明明在，为什么跑不了

现象：

text
$ ./run.sh-bash: ./run.sh: Permission denied

原因：文件没有 x（执行）权限。ls -l run.sh 会看到 -rw-r--r--，第三位是 - 不是 x。

查法：ls -l run.sh 看第一列。注意报错说的是 -bash: 开头，说明 shell 读到了这个文件、只是不让执行——这和"文件不存在"是两回事，别去查路径。

解法：chmod +x run.sh，再 ls -l 确认变成 -rwxr-xr-x。

工作场景 · EDA 工具报 "cannot open library"

你跑综合，报错：

text
Error: Cannot open library file 'slow.db'. (LCSH-3)

文件明明在啊？看权限：

bash
# 作用：排查"文件存在但读不到"；在库文件所在目录执行ls -l lib/slow.db               # 输出 ---------- 1 weizhen weizhen ... slow.db

权限是 ----------（000），谁都读不了。chmod 644 lib/slow.db 之后正常。

这类问题在跨团队拷库、从压缩包解压时特别常见——解压工具的 umask 设置不同，出来的文件权限就不一样（umask 在最后一章讲）。判断依据：报错里出现 "Cannot open" 而不是 "Cannot find"，八成是权限，不是路径。

05

小组：属主和属组

ls -l 中间两列是属主（owner）和属组（group）：

text
-rw-r--r-- 1 weizhen pdteam 1820 Nov 22 10:12 run.tcl             │        │            属主      属组

权限的三段就是按这两个身份划分的：你是属主，看你那段；你不是属主但在属组里，看中间那段；都不是，看最后一段。

多人协作时，同一组的同事需要能改你的文件，就会把文件属组设成 pdteam 并给组写权限（664 或 775）。

bash
# 作用：查看和修改归属；改属主通常需要 sudoid                              # 看自己的 uid、gid、以及属于哪些组groups                          # 只看组名列表ls -ln                          # -n = numeric，把用户名显示成 uid，排查"同名不同号"时用chgrp pdteam run.tcl            # 只改属组（你要先是该组成员）chown weizhen:pdteam run.tcl    # 同时改属主和属组（一般要 sudo）chown -R weizhen:pdteam pnr/    # 递归改整个目录（跨团队交接时用）

为什么会有"文件明明可读，工具却说读不到"？一个常见原因：你的账号不在这个文件的属组里，而其他人权限是 ---。id 一看就知道。这在跨部门拿库、或者从别人目录里直接拷文件时特别常见。

三个工作中真实的归属问题，每个都有对应的解法：

第一，"我拷过来的文件，属主还是他"。 用 cp 复制别人目录里的文件，新文件的属主是你（因为是你创建的），但如果你用 cp -p 保留了原属性，属主会试图保持原样——普通用户做不到，只有 root 能改属主。所以交接库文件时，正确做法是让对方把文件放进共享目录、由管理员统一 chown，而不是各自拷来拷去。

第二，"同组同事改不了我的文件"。 这是 umask 和属组共同决定的。共享目录的标准配置是：

bash
# 作用：搭一个团队共享目录；目录属主执行，成员需先加入 pdteam 组mkdir -p /proj/sharechgrp pdteam /proj/share          # 属组设成团队chmod 2775 /proj/share            # 2 = setgid：新建的子文件自动继承 pdteam 属组umask 002                         # 配合 775，同组才能写

2775 里最前面那个 2 是 setgid（设置组 ID）：目录带上它以后，在里面新建的任何文件都自动属于 pdteam 组，而不是创建者自己的主组。没有它，每个人建的文件属组都不一样，权限规则就永远对不齐——这是团队共享目录必须加的一个位。

第三，"离职同事的文件谁都动不了"。 属主账号被删后，文件属主显示成 uid 数字（ls -ln 能看到），这时只能由 root chown 给接手的人。所以项目交接清单里，一定要有"目录属主改成接手人"这一条。

属主不对：为什么你改不了

交接过来的目录，ls -l 显示的是别人的名字；你连里面的脚本都存不进去。第一反应是 chown 一下——然后得到：

text
chown: changing ownership of 'run.sh': Operation not permitted

这不是命令写错，是权限模型不让你做。 chown 的语义是"把文件送给另一个用户"，只有 root 能做，原因有两条：

  1. 配额：如果谁都能把文件送给别人，就能把 50GB 的垃圾塞进同事的家目录，占满他的配额。
  2. setuid 安全：如果谁都能把文件的属主改成 root，就能造一个"属主是 root 的 setuid 程序"，等于拿到 root 权限。

所以普通用户能做的只有三件事，按代价从低到高排：

做法命令前提适合什么场景
改属组chgrp pdteam run.sh + chmod 664你是 pdteam 组成员同组协作，最常见
让属主本人给你他自己 chown 你 run.sh他还愿意配合、账号还在同事之间临时交接
找 root / IT提工单有管理员离职交接、跨部门、账号已删
bash
# 作用：属主/属组排查，以及普通用户真正能做的修改# 用法：在目标文件所在目录执行；最后一行需要 root 权限ls -ln run.sh                  # 第 3、4 列显示数字 uid/gid：账号删了也能看出"没有属主"id                             # 我在哪些组里，决定 chgrp 能不能成功stat -c '%U %G %a %n' run.sh   # 一次拿到 属主 / 属组 / 权限 / 文件名chgrp pdteam run.sh            # 我能做的：改到自己所在的组（不需要 root）chmod 664 run.sh               # 配合上一条：组内可写chown weizhen:pdteam run.sh    # 需要 root：把文件"送"给别人

还有一个容易误解的点：cp -a 并不能把属主一起搬过来。 它保留了权限位和时间戳，但"属主"这一项普通用户改不了，所以拷完的文件属主是你自己。这就是为什么跨组拿库时，"拷一份到自己目录"往往比"申请改别人的目录"更快——前提是拷完之后 ls -l 确认权限位还是 644，而不是 000。

判断依据：报错里出现 Operation not permitted（不是 Permission denied），就是这一层——文件本身你可能读得了，但"改归属"这个动作被内核拒绝了。 别去试 sudo，先想清楚这文件该归谁、该由谁改。

06

一个文件在磁盘上是什么：inode、硬链接、软链接

这一节解释一个困扰很多人的现象：为什么删了大文件，磁盘空间没释放？为什么"文件还在"却打不开？

先说结论：Linux 里文件名不是文件本身。文件的内容和元数据（权限、属主、大小、时间、数据块位置）存在一个叫 inode 的结构里，目录只是"文件名 → inode 编号"的一张映射表。

inode（Index Node）索引节点点击看解释

文件系统里描述一个文件的"档案卡"：存权限、属主、大小、时间戳、数据块在哪，但不存文件名。文件名存在目录里，目录项指向 inode 编号。所以同一个 inode 可以有多个名字（硬链接），也可以有零个名字（文件被删但进程还开着）。

ls -l 第二列那个数字（-rw-r--r-- 1 ... 里的 1）就是硬链接数，即"有多少个文件名指向这个 inode"。

bash
# 作用：观察 inode 与链接；在自己的 demo 目录里执行ls -i run.tcl                   # -i 显示 inode 编号，比如 1318422 run.tclln run.tcl run_hard.tcl         # 硬链接：两个名字，同一个 inodels -li run.tcl run_hard.tcl     # 两个文件的 inode 号相同，链接数变成 2ln -s run.tcl run_soft.tcl      # 软链接：新建一个 inode，内容是"指向 run.tcl"的路径ls -li run.tcl run_soft.tcl     # inode 号不同，软链接的类型位是 lrm run.tcl                      # 删掉原名cat run_hard.tcl                # 还能读：inode 还有 1 个名字cat run_soft.tcl                # 报错：No such file or directory（断链）

一句话记牢：硬链接是同一个 inode 多了一个名字，软链接是一个新文件、内容只是一条路径。 下面所有差别都是从这句话推出来的——比如"删了原文件硬链接还能读"（inode 还有名字）、"软链接会断"（路径指向的目标没了）。

两者的差别，一张表说清：

硬链接（hard link）软链接（symlink）
能否跨文件系统不能能
能否指向目录不能（防止环）能
删掉原文件后仍可访问（链接数减一）变成断链
占用 inode不额外占占一个

"删了文件空间不释放"的真相：rm 只是把目录项去掉、链接数减一；只要还有进程开着这个文件（比如你 3 小时前启动、还在写日志的工具），inode 和数据块就不会回收。df -h 显示满了、du -sh 却算不出谁占的——就是这种情况。查法：lsof | grep deleted（真机命令），杀掉那个进程空间立刻回来。

"磁盘没满却写不进去"的真相：inode 用完了。文件系统在格式化时就把 inode 总数定死了。

手算一次：一个 500GB 的盘，inode 总数 300 万。你的流程每天产生 20 万个 1KB 的小报告文件，30 天就是

20万 × 30 = 600 万个文件 > 300 万 inode

于是第 15 天左右，df -h 还显示剩 400GB，但任何写入都报：

text
-bash: echo: write error: No space left on device

df -h 看空间、df -i 看 inode，两个都要看。这是后端服务器上真实发生过无数次的事故，根源是脚本把每一轮迭代都单独存了一个小文件。

脚本为什么"跑不了"：三个检查点

"跑不了"有三种完全不同的原因，报错也完全不同。分不清就会在错的方向上修半天。

报错首行原因修法
-bash: ./run.sh: Permission denied没有 x 权限chmod +x run.sh
-bash: ./run.sh: /bin/bash^M: bad interpreter: No such file or directory文件里有 Windows 换行符（CRLF）dos2unix run.sh
-bash: ./run.sh: /bin/tcsh: bad interpreter: No such file or directoryshebang 指向的解释器不存在（本机没装在 /bin）which tcsh 查真实路径，改 shebang
-bash: run.sh: command not found只写了 run.sh，而当前目录不在 PATH 里写成 ./run.sh

这几种报错在真实终端里的样子，先混个脸熟：

从这张图里要看出什么：看到报错先在上面的表里对号入座，确定是权限、shebang 还是 CRLF，再动手——三种原因的修法完全不同，方向猜错会白查半天。

按这个顺序查，三步就能定位：

bash
# 作用：脚本跑不了时的标准排查；在脚本所在目录执行ls -l run.sh                    # 第一步：看第一列有没有 xhead -1 run.sh                  # 第二步：看 shebang 指向哪个解释器file run.sh                     # 第三步：看是不是 "with CRLF line terminators"（真机命令）

检查点一：shebang

脚本第一行 #!/bin/bash 叫 shebang（读作"沙邦"），作用是指定"用哪个解释器来读这个文件"。#! 后面必须是解释器的绝对路径，因为内核要直接执行它。

bash
#!/bin/bash# ↑ shebang：必须是文件第一行、第一列，前面不能有空行、空格、注释# 作用：一个最小可用脚本；放在任意目录，chmod +x 后 ./脚本名 运行echo "hello from $(basename "$0")"     # $0 是脚本自己的名字，便于日志里区分是哪个脚本

三个常见错误：

  1. shebang 不在第一行。前面有空行、有注释，shebang 就失效，内核会当成 sh 脚本跑（很多 bash 语法会报错）。
  2. 解释器路径不存在。#!/usr/bin/tcsh 但机器上 tcsh 装在 /bin/tcsh，就报 bad interpreter: No such file or directory。用 which tcsh 确认真实路径。
  3. 写成相对路径。#!bash 不合法，必须 /bin/bash 这种绝对路径。

检查点二：执行位

chmod +x 只是"允许执行"，还需要 shebang 告诉系统用什么执行。两者缺一不可：

  • 有 x、没 shebang：系统会用默认 shell 尝试执行，语法不兼容时报一堆莫名其妙的错。
  • 有 shebang、没 x：Permission denied。

检查点三：CRLF

Windows 的换行是 \r\n（CRLF），Linux 是 \n（LF）。把 Windows 上编辑的脚本传上去，shebang 行实际是 #!/bin/bash\r，内核会去找一个名字叫 bash\r（显示成 bash^M）的解释器——当然找不到。

bash
# 作用：去掉 Windows 换行符；在脚本所在目录执行，先备份再改cat -A run.sh | head -3         # 看到行尾是 ^M$ 就是 CRLF，$ 是行尾标记sed -i.bak 's/\r$//' run.sh     # 去掉行尾的 \r，.bak 留一份原件（改坏了能回退）dos2unix run.sh                 # 专用工具，等价效果（装了 dos2unix 才有）

判断依据：报错里出现 ^M 或 bad interpreter，且这个脚本是从 Windows 传过来的、或者用 Windows 编辑器改过——直接按 CRLF 处理，不用怀疑别的。

Shebang释伴（脚本首行的解释器声明）点击看解释

脚本第一行的 #! 加上解释器绝对路径，例如 #!/bin/bash。内核执行脚本时先读这一行，决定用哪个程序来解释剩下的内容。写错或放错位置，脚本必然跑不起来。

动手动手：亲手制造三种"跑不了"，再逐个修好

任务：在真机（或 WSL）上把三种失败各复现一次。只有自己制造过，下次看到报错才能立刻对上。

bash
# 作用：复现权限、CRLF、解释器三种失败；在 ~/demo 下执行，不要在共享目录里跑mkdir -p ~/demo && cd ~/demo # ---- 失败一：没有执行位 ----printf '#!/bin/bash\necho hello\n' > a.sh   # 写一个最小脚本，默认权限 644./a.sh                                      # 预期：-bash: ./a.sh: Permission deniedchmod +x a.sh                               # 加执行位./a.sh                                      # 预期输出 hello # ---- 失败二：CRLF 换行 ----printf '#!/bin/bash\r\necho hello\r\n' > b.sh   # \r\n 模拟 Windows 换行chmod +x b.sh./b.sh                                      # 预期：-bash: ./b.sh: /bin/bash^M: bad interpretercat -A b.sh | head -1                       # 确认行尾是 ^M$，这就是证据sed -i.bak 's/\r$//' b.sh                   # 去掉 \r./b.sh                                      # 预期输出 hello # ---- 失败三：shebang 指向不存在的解释器 ----printf '#!/bin/tcsh\necho hello\n' > c.sh   # 假设本机 tcsh 不在 /bin 下chmod +x c.sh./c.sh                                      # 预期：bad interpreter: No such file or directorywhich tcsh || echo "本机没装 tcsh，这条正好复现了报错"

08

umask：新文件的权限从哪来

你已经知道 644 和 755 是标准值。问题是：你 touch 一个文件、mkdir 一个目录，权限为什么自动就是这两个数？ 答案是 umask。

umask（User File-creation Mask）权限掩码点击看解释

新建文件/目录时，"从默认权限里扣掉哪些位"的掩码。规则是按位清除：新文件 = 666 去掉 umask 里的位；新目录 = 777 去掉 umask 里的位。
为什么文件默认是 666 而不是 777？因为新建的文本文件不该默认可执行——这是 Unix 很早以前就定下的安全默认值。

手算三个常见 umask：

umask新文件 = 666 去掉掩码新目录 = 777 去掉掩码用在什么环境
022644755最常见：自己写，别人读
002664775团队共享：同组也能写
027640750保密：外人完全看不到

验算 022：666 里每一位减去 2（去掉 w）→ 644；777 每一位减去 2 → 755。注意是"按位清除"不是"减法借位"，6-2=4、7-2=5，不会出现负数。

"不是减法"这件事，在 umask 带 3 的时候才露出来。设 umask 为 033，如果按减法算 666 − 033 = 633，中间那个 3 是 -wx——新建的文本文件默认可执行，显然不对。正确做法是逐位清除：

  • 属主：6 去掉 0 → 6
  • 属组：6 去掉 3（即去掉 w 和 x）→ 4
  • 其他人：同样去掉 3 → 4
  • 结果 644，和预期一致。

把三个常见 umask 各走一遍，就再也不会算错了：

  • 022：文件 6/6/6 去掉 0/2/2 → 644；目录 7/7/7 去掉同样位 → 755。
  • 002：文件去掉 0/0/2 → 664（同组可写）；目录 → 775。
  • 027：文件去掉 0/2/7 → 640（外人全无）；目录 → 750。

判断依据：新建文件的权限位里不该有 x（也就是每一位不该是 3、5、7）。算出 7 或 3 就说明 umask 没盖住可执行位，那是安全隐患，不是"方便"。

bash
# 作用：查看和临时修改 umask；在任意目录执行umask                           # 输出 0022（前导 0 表示八进制）umask -S                        # 用符号显示：u=rwx,g=rx,o=rxumask 027                       # 只在当前 shell 生效，关掉窗口就恢复touch t1 && mkdir d1 && ls -ld t1 d1   # 验证：t1 是 640，d1 是 750

这个数字解释了前面那个"从压缩包解压出来的库文件权限是 000"的场景：打包时的 umask 和你在自己机器上的不一样，解压后权限就可能是任何值。所以拿到别人给的库，第一件事是 ls -l 看一眼，必要时统一 chmod -R 644。

  • 知道目录的 x 和 r 分别意味着什么，以及"能 ls 不能 cd"是哪种组合

  • 能说出脚本跑不了的三种原因，并各给一条排查命令

  • 能算出 umask 022 下新建文件和目录的权限
自测：先自己想，再点开答案
-rw-r--r-- 里属主有什么权限？
读和写（rw-），不能执行。
755 展开成 rwx 是什么？
rwxr-xr-x：属主读写执行，同组读执行，其他人读执行。手算：7=4+2+1，5=4+1。
为什么删目录必须加 -r？
-r 是递归。不加的话 rm 认为目录不是普通文件，会报 "omitting directory" 并跳过。
脚本报 bad interpreter: ^M 是什么原因？
文件里混入了 Windows 换行符（CRLF），shebang 变成 #!/bin/bash\r，内核找不到叫 bash\r 的解释器。用 dos2unix 或 sed -i 's/\r$//' 去掉。
chmod +x 和 chmod 755 有什么区别？
+x 只给三组都加上执行位，其他权限不变；755 是把权限整体重设为 rwxr-xr-x。对 600 的文件执行 chmod 755 会变成所有人可读。
一个目录权限是 --x，你能做什么、不能做什么？
能 cd 进去、能访问已知文件名（如 cat d/file），但不能 ls 列目录（需要 r）。
rm 删了大文件，为什么 df -h 显示空间没释放？
还有进程开着这个文件，inode 的链接数不为 0，数据块不会回收。用 lsof 配合 grep deleted 找到那个进程，结束它空间才回来。
umask 是 027 时，新建文件和目录分别是什么权限？
文件 640（666 去掉 027 的位）、目录 750（777 去掉 027 的位）。
硬链接和软链接最本质的区别是什么？
硬链接是同一个 inode 的另一个名字（链接数加一，删原名仍可访问）；软链接是独立 inode，内容是一个路径，原文件删了就断链。
