修时序：六种手段和它们的代价

Timing Closure

违例不是"点一下优化就没了"。这一课把六种手段的收益、代价和禁用场景摆在一张表上，讲清 useful skew 的三条纪律、先 setup 后 hold 的完整论证，以及修完必须复算的三份报告。

约 55 分钟 课表学时 6 时序优化ECOholdsizing
01

六种手段一张表

本章目标学完这一课，你能从一份时序报告的延迟构成里选出该用哪种手段，说出它的代价和禁用场景，并按 DRV → setup → hold → 复算的顺序把一轮修复做完。

修时序像给堵车的路做疏通。可以换更快的车（换大驱动单元）、让车提前出发（调时钟）、把单位挪到近一点的地方（挪位置）、在慢速路段加一条加速道（插缓冲器）、拆掉中间多余的红绿灯（改逻辑）、甚至重新规划这条路（重定时）。

每种办法都能让这一段快一点，但都要付钱：钱、面积、功耗、或者别人的时间。

先说一条判断原则，它决定你该翻到哪一节：看延迟构成。

报告的构成说明问题在优先手段
cell delay 占 70% 以上逻辑本身慢upsize、换 LVT、改逻辑
net delay 占 60% 以上距离太远挪位置、插 buffer
延迟不大但 fanout > 32一个驱动带太多负载插 buffer 树
slack 只差 30~80ps差一点点useful skew、小幅 upsize
逻辑级数 > 20 级结构问题改逻辑、重定时

这张表的使用方式不是"从上往下试"，是"先看报告再选行"。 拿一条 net delay 占 78% 的路径去 upsize，等于给堵在高速上的车换发动机——钱花了，路还是堵。

ECOEngineering Change Order，工程变更单点击看解释

在不推翻整个流程的前提下，对设计做小范围修改：换一个单元、插一个 buffer、挪一个位置、改一根线的连接。

02

手段一：upsize 与换阈值电压

这两种手段经常一起说，因为都是"换单元"，但改的维度不同。

upsize 是同一功能、更大驱动：NAND2_X1 → NAND2_X4。驱动能力大约翻倍，输出转换时间（transition）变陡。

它有两层收益，很多人只看到第一层：

  1. 自身延迟变小：驱动电流大，充放电快。
  2. 下游延迟也变小：输出波形更陡，下一级单元的输入转换时间更好，它的延迟随之下降。

所以 upsize 一个关键节点，报告上常常能看到"这一级降 30ps，下一级又降 15ps"。这也是它性价比高的原因。

但收益是递减的：X1→X2 能降 25%，X8→X16 可能只降 8%，面积却翻倍。一般不超过两级。

还有一层反作用必须知道：输入电容变大，会拖累上一级。

text
X1 的输入电容约 1 个单位，X4 约 3 个单位上一级的负载从 1C 变 3C → 它的 net delay 可能涨 15%~20%

于是就出现一种典型现象：你把第 3 级 upsize 了，第 3 级快了 30ps，第 2 级慢了 15ps，净收益只有 15ps。修好自己，拖累上游——这是 upsize 最容易被忽略的代价。

换 VT 是另一个维度：尺寸不变，把晶体管的阈值电压调低。

类型速度漏电用在哪
HVT（高阈值）慢最小非关键路径，占大多数
SVT（标准阈值）中中默认
LVT（低阈值）快 20%~40%大 3~5 倍只给真正紧张的路径

这叫多阈值（multi-Vt）优化。判断标准很硬：LVT 占比控制在 10%~20%（典型值），超过 25% 就要看漏电报告了。

tcl
# 作用：先定位最慢的那一级，再决定换尺寸还是换阈值# 用法：Innovus 里 ECO 阶段执行；实例名从报告里抄，不要手打（打错会改到别的单元） # 第一步：打出完整路径，含每一级的 cell 延迟和 net 延迟，重定向到文件report_timing -from [get_pins u_core/u_alu/reg_a/CK] -to [get_pins u_core/u_alu/reg_b/D] -path_type full_clock_expanded > rpt/path_alu.rpt # 第二步：打开 rpt/path_alu.rpt，按 cell delay 从大到小找前三名，那才是候选# 第三步：按候选的性质选手段——要大驱动还是低阈值 ecoChangeCell -inst u_core/u_alu/add_32/U12 -cell NAND2_X4      ;# 同功能换大驱动：面积↑、delay↓ecoChangeCell -inst u_core/u_alu/U15 -cell NAND2_X1_LVT         ;# 同尺寸换低阈值：面积不变、漏电↑

report_timing 那一行故意写成一条长命令，不用 \ 续行——Tcl 里 \ 后面再接 # 注释，注释会被当成参数，工具直接报错。要行尾注释就用 ;#。

ICC2 / DC 里的等价写法（命令名不同，语义一样）：

tcl
# 作用：在 ICC2 或综合阶段做同样的两种替换# 用法：ICC2 里对已布局的单元执行；DC 里要在 compile 之后、有网表的情况下size_cell [get_cells u_core/u_alu/add_32/U12] NAND2_X4    ;# 换尺寸，等价于 Innovus 的 ecoChangeCellsize_cell [get_cells u_core/u_alu/U15] NAND2_X1_LVT       ;# 换阈值，面积不变

什么时候别用：

  • 报告里 net delay 占 70% 以上——换单元救不了距离。
  • 这个单元已经是库里最大尺寸（X16 之类），再换没有下一档。
  • 单元带 dont_touch 属性（时钟树上的 buffer、扫描链里的 lockup latch 常有），工具会直接拒绝，硬改会破坏 CTS 结果。
  • 上一级 fanout 已经很大（>32），再加大输入电容会把它压垮。
Vt阈值电压点击看解释

晶体管的"开启门槛"。门槛低（LVT）→ 开得快 → 延迟小，但关不严 → 漏电大；门槛高（HVT）→ 慢但省电。
库通常提供 HVT / SVT / LVT 三档（有的还有 ULVT），后端按路径紧张程度混用，叫 multi-Vt 优化。

常见坑 · LVT 用太多，功耗爆炸

现象：时序差了 100ps，你把关键模块的单元全换成 LVT，WNS 立刻从 −0.10 变 +0.15，问题"解决"。

三个月后签核：静态功耗（leakage）比预算高 2.8 倍，芯片在高温下超规格，封装散热方案要重做。

原因：LVT 的漏电是 HVT 的 3~5 倍。全换等于把整块模块的静态功耗乘以 4——而静态功耗不随频率下降，降频也救不了。

处理：只给真正紧张的那几条路径换 LVT，其余保持 HVT/SVT；换完看 report_power 的 leakage 分项；LVT 占比控制在 10%~20%。

判断口诀：LVT 是止痛药，不是维生素。

工作中怎么用：upsize 之前先查这个单元被几条路径经过（report_timing -through）。它同时在三条紧张路径上，换大一档三条都受益；只服务一条，收益有限，不如换 LVT 省面积。

03

手段二：插 buffer

长线的延迟不是线性增长的，是平方增长的：

text
未插 buffer 的线延迟 ≈ R × C × L²      （R、C 是单位长度电阻电容，L 是长度）

长度翻倍，延迟变四倍。这就是跨越大半个芯片的那根线为什么能吃掉 0.6ns。

插 buffer 的作用是把一根长线切成 N+1 段，每段长度变成 L/(N+1)：

text
插 N 个 buffer 后：总延迟 ≈ R×C×L²/(N+1) + N × t_buf                                   └─ 线延迟 ─┘   └ 每级自身的延迟 ┘

前半段随 N 下降，后半段随 N 上升，所以存在一个最优点。手算一次：2mm 的线，不插时 480ps，每个 buffer 自身 30ps。

buffer 数 N线延迟 = 480/(N+1)buffer 自身 30N总延迟
04800480ps
124030270ps
216060220ps
312090210ps
496120216ps
760210270ps

结论：这根线插 3 个最划算。插到 7 个反而比不插还差——"多插几个总没坏处"是错的。

这也解释了为什么长线不插 buffer 时延迟会"跳变"：线长从 1mm 到 2mm，延迟不是翻倍而是四倍，报告上看起来像是突然崩了。

代价有四个：面积、功耗（buffer 一直在翻转，动态功耗不低）、拥塞（新增的单元要占地、要接电源）、以及多一级延迟。最后一项在大扇出场景下尤其要注意：插 buffer 树解决 fanout 问题，但树本身有 2~3 级延迟。

tcl
# 作用：在长线中段插一个缓冲器，把一段长 RC 切成两段# 用法：Innovus ECO 阶段；坐标要落在合法 row 上，插完立刻看拥塞和时序ecoAddRepeater -net u_core/n_1234 -cell BUF_X4 -loc {120 340}   ;# 更通用的写法：指定网络、单元、坐标# 部分版本/流程里等价命令是 insertBuffer，参数顺序不同，敲之前 man 一下

ICC2 里的写法：

tcl
# 作用：ICC2 在网络中间插 buffer（位置由工具按拥塞和时序自动选）# 用法：ICC2 ECO 阶段；插完用 check_legality 确认没落在非法位置insert_buffer [get_nets u_core/n_1234] BUF_X4      ;# 插缓冲器，工具自选坐标

修 hold 时也插"buffer"，但那是另一件事。 修 hold 插的是延迟单元（delay cell）——一种驱动很弱、延迟固定的单元，目的是故意加延迟。用的不是 BUF_X4，选错了会让 hold 修不准。

什么时候别用：

  • 线本来就短（<100µm），插 buffer 纯属加延迟，只有修 hold 时才这么干。
  • 区域已经拥塞（overflow > 500），再插单元等于往堵车里加车。
  • 时钟网络。时钟上插 buffer 要走 CTS 的规则（专用单元、NDR、平衡），在 ECO 里随手插会破坏时钟树平衡，skew 直接崩。
Delay Cell延迟单元点击看解释

一种专门用来"加延迟"的单元：驱动能力弱、输入电容小、延迟固定且可预测。修 hold 时插它，而不是插普通 buffer。
它的价值在于可控：延迟 20ps 就是 20ps，不会因为负载变化飘太多。用普通 buffer 修 hold，实际延迟经常是估算值的两倍。

工作中怎么用：插 buffer 的位置比数量重要。插在长线正中，两段等长最优；插在靠端点的位置等于没切。工具自动插时会算最优点，手工插要自己按长度估。

04

手段三：挪位置

如果报告显示 net delay 占 60% 以上，而且这根线的两个端点相距 300µm 以上，那问题不是"单元慢"，是"离得远"。

挪位置是最有效也最危险的手段。有效是因为距离和延迟近似成正比（短距离段），挪近一半距离，延迟差不多减半；危险是因为你挪的每一个单元，都同时在服务好几条路径。

tcl
# 作用：把一个单元挪到指定坐标，或让工具对一小片区域重新布局# 用法：Innovus 里 ECO 阶段执行；坐标必须落在合法 row 上，否则合法化会把它弹回去placeInstance u_core/u_alu/U20 180 260      ;# 精确挪到 (180,260)，适合已知最优位置的情况refinePlace                                  ;# 让工具对局部重新做布局，比手挪更安全

三条纪律：

  1. 一次只挪几个（≤10 个），挪完立刻看 reportCongestion 和 reportTiming。挪 50 个再一起看，出了问题定位不到是谁。
  2. 确认这个单元不在别人的关键路径上。用 report_timing -through 查它被哪些路径经过。挪对了 A 路径，可能把 B 路径搞崩。
  3. 不要用挪位置修宏单元相关的问题。宏单元动一下是全片重来，那是 floorplan 的活，不是 ECO。

什么时候别用：密度已经 >0.85（挪过去也没地方）、两端之间被宏单元挡住（挪了还是要绕）、以及"合法化会把你弹回来"的情况（目标位置在 row 之外）。

工作中怎么用：挪位置前先 report_timing -through 查这个单元服务几条路径；挪完只看两份报告——这条路径的 slack，和全片 overflow。两个都好了才算成功，只看一个是自欺欺人。

05

手段四：useful skew

这是六种手段里唯一"零面积零功耗"的，也是最容易用错的。

原理在第 17 课讲过：让捕获触发器的时钟晚到一点，等于多给它时间。但时钟晚到会同时伤害它的下游路径和它的 hold 检查。所以有三条纪律，缺一条就会把 setup 违例换成 hold 违例。

纪律一：只能借，不能抢

借的对象必须是"有余量的路径"。判断方法是查目标触发器的所有 fanout 路径，取其中最小的 slack：

text
可借上限 = min(该触发器所有下游路径的 slack) − 安全余量安全余量一般给 30~50ps（留给 OCV 和后续 ECO）

手算一次。触发器 B 有三条下游路径，slack 分别是 +150ps、+120ps、+60ps：

text
可借上限 = 60 − 30 = 30ps

而 B 的输入路径（A→B）差 80ps。借 30ps 只补了三分之一，剩下 50ps 得靠别的手段。 这就是 useful skew 的真实定位——它是"补最后一刀"的工具，不是主力。

"抢"的典型错误：看到某条路径 slack 是 +20ps，觉得"还有 20ps 可以借"，借走 20ps 之后那条路径正好 0，任何一点波动就违例。

纪律二：借了要还

时钟树是会被重新平衡的。你在 place 阶段用 set_clock_latency 给某个叶子加了 80ps，CTS 一跑，工具按 target_skew 把整棵树拉平，这 80ps 就没了——你的"修复"在 CTS 后自动失效。

正确做法是在 CTS 阶段用工具认可的机制固化：

tcl
# 作用：让 CTS 在满足时序的前提下主动制造 skew（而不是把树拉平）# 用法：CTS/PostCTS 阶段设置；数值是允许的最大 skew，不是目标值setUsefulSkewMode -maxSkew 0.08 -usefulSkewMode yes    ;# 允许最多 80ps 的有用偏斜optDesign -postCTS                                     ;# 在这个约束下同时优化 setup 和 hold

-maxSkew 0.08 是上限，不是"必须借 80ps"。工具会挑真正有收益的路径借，借完自动检查 hold。

借完还要还一笔账：重新跑 hold 检查。这是硬性步骤，不是可选项。useful skew 把 hold 的余量直接吃掉了，不吃亏的只有那些下游余量充足的路径。

纪律三：时钟树要能支持

三条硬条件，缺一条就借不动：

  1. 叶子上还有可加的延迟：那个触发器的时钟路径上还能再插一级 buffer，或者现有 buffer 还有驱动余量。如果叶子已经挂在一个驱动到极限的 buffer 上，加不了。
  2. skew 在预算内：借完之后这个叶子和邻居的差不能超过 target_skew 的 1.5 倍。超过就不是"有用偏斜"，是"树歪了"。
  3. 不跨时钟域：不同时钟、主时钟和 generated clock 之间不能借。它们的相位关系不由你控制。

什么时候别用：跨时钟域、下游没有余量、CTS 还没跑（pre-CTS 时钟是理想时钟，加了也没用）、以及 hold 已经临界（再借就是直接制造 hold 违例）。

Useful Skew有用偏斜点击看解释

故意让时钟到达不同触发器的时间不同，把时间从"有余量的路径"借给"紧张的路径"。
本质是时间搬运，不是时间创造：借来的每一 ps 都从下游扣。所以它只能解决几十 ps 量级的问题，且必须复核 hold。

常见坑 · 用全局 latency 代替 useful skew

现象：setup 差 100ps，你给整个时钟域 set_clock_latency -0.1，setup 全好了。

第二天 hold 报告：这个域 200 多条违例，最差 −0.15ns。

原因：全局加 latency 是"给所有人同时提前/推后"，skew 一点没变，只是把整棵树平移。setup 变好是因为捕获沿推后了，但 hold 的捕获沿也推后了同样多——所有 hold 一起变差 100ps。

处理：useful skew 必须按路径、按叶子做，不能按域做。全局动时钟只有一个合法场景：接口时序需要调整整体 insertion delay，那是另一件事。

工作中怎么用：useful skew 要在 CTS 阶段跟工具一起做，不要事后用 set_clock_latency 手工补。手工补的延迟会被下一次 CTS 或 ECO 抹掉，而且没人记得你补过——这是最典型的"修了但没留下痕迹"。

06

手段五：改逻辑

前四种手段都是在"既定逻辑结构"里挪时间。改逻辑是动结构本身，收益最大，代价也最大。

三种常见改法：

改法做什么典型收益谁来做
减少逻辑级数重构表达式（如把串行进位改成超前进位）2~5 级，几百 ps前端 RTL
重定时（retiming）把寄存器往前或往后搬一级，重新分配组合逻辑一级逻辑，100~300ps前端 + 综合
拆流水在长路径中间插一级寄存器直接砍一半前端（要改协议/延迟）

重定时值得单独说，因为它最反直觉：把寄存器从 A 点搬到 B 点，逻辑功能不变，但原来"两级逻辑 + 一个寄存器"变成了"一级逻辑 + 两个寄存器"，那条路径的时间预算直接多了一个周期。

text
改前：FF ──[ 逻辑 1.8ns ]── FF        周期 2.0ns，勉强改后：FF ──[ 逻辑 0.9ns ]── FF ──[ 逻辑 0.9ns ]── FF      多了一级流水，每条路径只剩 0.9ns，但输出晚了 1 个周期

代价写在这里：延迟增加一个周期。功能上等价的前提是"下游能接受晚一拍"，很多协议不接受。

什么时候别用：距 tapeout 少于两周（改 RTL 要重跑综合、DFT、验证、STA 全流程）、路径在第三方 IP 内部（你改不了）、以及没有形式验证（LEC）资源来证明改动等价。

这条手段的存在意义：它告诉你"时序收敛的上限是架构决定的"。如果一条路径用了所有后端手段还差 300ps，那不是后端不行，是 RTL 写的时候就没给够预算。越早发现越便宜——在综合前发现，改一行 RTL；在 tapeout 前发现，改的是项目计划。

Retiming重定时点击看解释

在不改变电路功能的前提下，把寄存器沿组合逻辑前后移动，重新分配各级的逻辑量。
它改变的是"哪一级承担多少延迟"，不改变总逻辑。代价是接口延迟可能变一个周期。

Dont_touch禁改属性点击看解释

加在实例或网络上，告诉优化工具"这个不许动"。时钟树上的 buffer、扫描链的 lockup latch、模拟 IP 的接口单元通常都有这个属性。
作用是保护关键结构不被 ECO 破坏。副作用是：修时序时这些单元不能 upsize、不能挪，必须换别的路径绕过去。

工作中怎么用：提改逻辑需求要给前端三样东西：路径起点终点、差多少 ps、你试过哪些后端手段。只说"这条路径不收敛"，对方没法判断改哪；给了这三样，他能直接定位到 RTL 的哪一段。

07

最容易踩的坑：先修 hold 还是先修 setup

正确顺序：先修 setup，再修 hold。

结论很多人背得出来，但能讲清理由的不多。这里给完整论证。

论证一：方向性——修 hold 必然恶化 setup

修 hold 的手段是"给数据路径加延迟"。加进去的延迟会同时抬高 Tlogic_max 和 Tlogic_min：

text
修 hold 前：setup +0.05，hold −0.04插 80ps delay cell修 hold 后：setup −0.03（差 80ps），hold +0.04

这不是"可能恶化"，是数学上必然恶化——同一个延迟项在两条公式里符号相反。

所以：先修 hold，等于先给 setup 挖坑，然后再填。

反过来，修 setup 的手段（upsize、缩短线、删 buffer）是"减延迟"，会同时压低 Tmax 和 Tmin，也会消耗 hold 余量。看起来对称，但两者有一个关键区别：修 setup 的动作作用在长路径上，而 hold 违例绝大多数出在短路径上，两个集合重叠很小。

所以实际影响是：

顺序会发生什么
先 hold 后 setuphold 修复的 100% 被 setup 修复推翻，hold 要重做一遍
先 setup 后 holdsetup 修复只影响少数短路径的 hold 余量（通常几十 ps），最后统一修一次 hold 即可

论证二：影响面——setup 修复动结构，hold 修复动点位

setup 违例往往几十上百条，分布在长路径上，要换单元、挪位置、甚至改逻辑——这是结构性修改，会改变大量 net 的负载和布线。

hold 违例往往集中在少数短路径上，每条插一两个 delay cell 就解决——这是点位式修改，影响范围几十微米。

工程上永远先做影响面大的，后做影响面小的。这是所有流程设计的通用原则，不只是时序。

论证三：可验证性——hold 必须在最终网表上修

签核报告用的是最终网表 + 最终寄生参数。hold 违例的数值对线延迟极其敏感（短路径上多 10µm 线就是几个 ps），任何一次结构性改动都会让它变。

所以 hold 必须在"网表不再变"之后修一次，修完直接签核。这也是流程上把 hold 放在最后的根本原因——不是它不重要，是它必须最后做才准。

一个例外：hold 违例其实是树的问题

如果 12 条 hold 违例全部落在同一个时钟分支上，且 Tskew 高达 150ps 以上，那不是数据路径的问题，是时钟树歪了。

这时候正确动作是回去修树（重新平衡那个分支、检查有没有漏 buffer、检查 leaf 驱动），不是插 12 个 delay cell。判断方法：看违例路径的起点终点是否在同一个时钟树分支、看 report_clock_tree 里那个分支的 skew。

插 delay cell 修树的问题，等于给歪掉的秤加砝码——这次平了，换个 corner 又歪。

常见坑 · 顺序搞反，白干两轮

现象：花两小时把 12 条 hold 修干净（每条插 60~80ps delay cell），然后去修 setup。upsize 了 30 个单元、挪了 8 个位置、删了 5 个 buffer。

重跑：hold 违例从 0 变回 31 条，最差 −0.11ns。

原因：upsize 和删 buffer 都在减延迟，Tmin 一起变小，把刚加的余量吃光了。

代价：两小时白干，还要再花两小时修 hold，而且这次修的路径和上次不完全一样（因为网表变了），等于重新分析一遍。

记住：setup → hold → 最后整体验一遍。 顺序错了不是慢一点，是白干一轮。

工作中怎么用：这条顺序要写进流程脚本，而不是靠人记。run.tcl 里 hold 修复那一步前面加判断：setup WNS < −20ps 就退出并报错。用机器保证顺序，比用培训保证顺序可靠。

08

时序修复的标准动作序列

把上面的结论固化成流程：DRV → setup → hold → 复算。

为什么 DRV 要在最前面？因为 DRV（设计规则违例：max transition、max capacitance、max fanout）会直接影响延迟计算。transition 不达标时，工具算出来的 cell delay 本身就是错的——你按错的延迟去修时序，等于在错的地基上盖楼。

tcl
# ---- 第 0 步：修 DRV（transition / cap / fanout），所有优化之前 ----setOptMode -fixFanoutLoad true          ;# 允许为了修 fanout 而插 bufferoptDesign -drv                          ;# 只修 DRV，不动时序# 门槛：DRV 违例 = 0，才允许往下走 # ---- 第 1 步：pre-CTS 修 setup ----setOptMode -effort high                 ;# 优化力度拉满，跑得慢但结果好optDesign -preCTS                       ;# 修 setup：sizing / buffering / 少量挪位置saveDesign db/05_prects.enc             ;# 存盘，出问题能回退到这里 # ---- 第 2 步：建时钟树（这一步不在修复序列里，但它是分界线）----ccopt_design -cts                       ;# 建树；之后时钟从 ideal 变 propagated，所有时序要重算saveDesign db/06_cts.enc                ;# 存盘：CTS 后的数据库是 hold 修复的起点 # ---- 第 3 步：CTS 之后修 setup（此时时钟有真实延迟）----optDesign -postCTS                      ;# 修 setup，可用 useful skew# 门槛：setup WNS ≥ −20ps（留一点给后面），再看 hold # ---- 第 4 步：修 hold（必须在 setup 之后）----setOptMode -holdTargetSlack 0.05        ;# 目标 +50ps，不要修到 0optDesign -postCTS -hold                ;# 只插 delay cell / 调 skew，不动 setup 结构saveDesign db/07_optcts.enc             ;# 存盘：布线前最后一次能便宜回退的机会 # ---- 第 5 步：布线后再来一轮（线延迟进来了，前面全要重算）----optDesign -postRoute                    ;# 修 setupoptDesign -postRoute -hold              ;# 修 holdsaveDesign db/09_postroute.enc          ;# 存盘：这一版才是签核用的网表 # ---- 第 6 步：复算（见下一节）----timeDesign -postRoute -outDir rpt/final ;# 出全套时序报告，setup/hold 都要重看

每一步之间的"门槛"要写进流程脚本，不达标就停下来看，不要一路跑到底：

阶段门槛不达标怎么办
DRV 后transition / cap / fanout 违例 = 0加 buffer、换驱动，别急着修时序
pre-CTS 后setup WNS ≥ −50ps差太多说明约束或 floorplan 有问题
post-CTS 后setup WNS ≥ −20ps，hold 记基线hold 负值是正常的，但要记下条数
post-CTS hold 后hold WNS ≥ 0，条数 = 0修不干净就别进布线，布线后会变更差
post-Route 后setup/hold 都 ≥ +30ps回到对应阶段，不要在现场硬改

为什么每一步都要 saveDesign？ 因为 ECO 是破坏性的：换了一个单元，原来的数据库就变了。没有存档，出问题只能从头跑，那是几小时。

常见坑 · 不留余量，修到 0 就收工

现象：optDesign -hold 跑完，hold WNS = 0.001ns，报告全绿，收工。

两周后签核：hold WNS = −0.03ns。因为签核用了更精确的寄生提取（SPEF 版本更新），线延迟涨了一点。

原因：0.001ns 不是"通过"，是"刚好压在线上"。任何一点提取误差、温度漂移、电压波动都会把它推过去。

处理：setOptMode -holdTargetSlack 0.05（留 50ps），setup 留 50~100ps。签核标准是"留出安全边际"，不是"压线通过"。

工作中怎么用：这套序列通常固化成一个 run.tcl，每个阶段一个函数，中间存盘。新人接手不需要理解全部，只要知道"哪一步没过就停在哪"，就不会把错误往下游放大。

ECO 改的是网表。网表一变，之前所有报告全部作废——不是"可能不准"，是"一定不准"。

报告回答什么问题谁看不通过的后果
时序全量真的收敛了吗STA + PR签核不过

三份报告对应三个不同的负责人，任何一份单独通过都不算收敛。这是"时序收敛"和"时序看起来变绿了"的区别。

工作中怎么用：三份报告要一起归档，目录名带版本号和日期（final_r3_1122/）。签核时被问"这一版和上一版差在哪"，靠的是归档，不是记忆。

回答四问：

  1. A 路径该用什么？为什么不是挪位置？
  2. B 路径该用什么？为什么 upsize 收益有限？
  3. C 路径的延迟只有 0.25ns 却违例，问题在哪？
  4. useful skew 在这三条里能用吗？

参考答案：

  1. A：cell delay 占 89%，逻辑级数 14 级 → 先 upsize 那级 NAND2_X1 到 X4，还差就换 LVT 或减级数。挪位置没用，net 只占 0.10ns，挪到哪都省不出 90ps。
  2. B：net 占 70%、距离 620µm → 挪位置（或插 2~3 个 buffer）。upsize 只影响 0.30ns 的 cell 部分，撑死省 70ps，而且会让上一级更慢。
  3. C：0.25ns 的延迟本身不是问题，48 的 fanout 才是。一个单元带 48 个负载，输出 transition 一定超标，延迟计算不可信。先插 buffer 树把 fanout 降到 8~12，再看时序。
  4. 不能用：A、B 是长路径，借 skew 会让它们的下游（同样紧张）更差；C 是 fanout 问题，和时钟无关。三条都不适合。

自测：先自己想，再点开答案
六种手段里，哪一种零面积零功耗？它的代价是什么？
useful skew。代价是下游路径少掉同样的时间，且会恶化捕获触发器的 hold。
报告显示 net delay 占 70%，应该优先用什么？为什么 upsize 效果有限？
挪位置或插 buffer 把长线切开。upsize 只作用于 cell delay 那一小部分，且会加大输入电容拖累上一级。
upsize 除了面积，还有什么容易被忽略的副作用？
输入电容变大，上一级的负载变重、net delay 上升，出现"自己快了 30ps、上一级慢了 15ps"的净收益缩水。
为什么长线不是插越多 buffer 越好？
总延迟 = 线延迟/(N+1) + N×buffer 自身延迟，前半降后半升，存在最优点；超过最优点后每多插一个都在净增延迟。
useful skew 的三条纪律是什么？
只能借不能抢（从有余量的路径借）、借了要还（CTS 会重新平衡，必须用工具机制固化并复查 hold）、时钟树要能支持（叶子有可加延迟、skew 在预算内、不跨时钟域）。
为什么 useful skew 在 CTS 之前做没用？
pre-CTS 时钟是理想时钟，没有真实延迟和 skew；CTS 会按目标 skew 把树拉平，之前加的延迟会被抹掉。
为什么必须先修 setup 再修 hold？给两条理由。
一是修 hold 插的 delay cell 会同时抬高 Tmax，数学上必然恶化 setup；二是 setup 修复是结构性修改、影响面大，hold 修复是点位式修改，必须放在网表定稿后做一次。
DRV 为什么要排在时序之前修？
transition/cap/fanout 不达标时，工具算出的 cell delay 本身就是错的；按错的延迟修时序，修出来的结果是假的。
修完为什么必须复算三份报告？
ECO 改了网表，旧报告全部作废；三份分别回答"时序真收敛了吗""还能造出来吗""代价付得起吗"，对应三个不同负责人，任何一份单独通过都不算收敛。
holdTargetSlack 0.05 为什么要留 50ps 而不是修到 0？
修到 0 是压线通过，任何提取误差、温度漂移、电压波动都会让它变负；留余量才是签核标准。
