03

实测数据（万门设计，9390 单元）

我们用这套流程跑过一个 9390 单元的设计（6 个 SRAM、IPA 图像处理加速器）：

阶段耗时结果
place_opt3.5 min单元数 9390 → 12026（插了 2636 个 buffer/时钟树单元）
clock_opt9.5 minhold 从 −10ns 级收敛到 −0.07ns
route_auto1.7 minDRC 首轮即 0
route_opt2.3 minDRC 保持 0，setup WNS +1.00ns
route_detail ×52.2 minDRC 仍 0
合计21.7 min芯片 222.5×222.2µm，利用率 49.8%
工作场景 · 这组数字为什么值得记
  • route_auto 首轮 DRC = 0 说明 floorplan 和 place_opt 做对了。如果首轮就几千个 DRC，别急着磨布线，回头查布局。
  • place_opt 插了 28% 的单元是正常的（buffer 和时钟树）。如果插得过多（>50%），说明约束太紧或库不合适。
  • clock_opt 花的时间最长（9.5 min），因为它在解 hold 这个硬骨头。
常见坑 · 静默失败：一个单元都没放

第一次跑 place_opt，跑得飞快（几秒），报告也没报错，但打开布局一看：空的。

原因：ICC2 默认要求有 scan def（扫描链定义），没有就直接跳过布局，而且不报致命错误。

解法：

tcl
set_app_options -name place.coarse.continue_on_missing_scandef -value true

这类"跑得特别快、结果为空"的情况，比报错更危险，因为容易误以为成功。

自测：先自己想，再点开答案
place_opt 之前为什么必须先读寄生参数？
否则报 NEX-018: no valid parasitic，优化器无法计算线延迟，place_opt 起不来。
place.coarse.continue_on_missing_scandef 解决什么问题？
没有 scan def 时布局器会静默跳过布局（一个单元都不放），设为 true 后可以继续。
clock_opt 主要优化什么？
建立时钟树（降 skew），同时优化 setup 和 hold。
route_auto 出来 DRC 就是 0，说明什么？
说明 floorplan、布局、时钟树都比较健康；如果 DRC 很多，应该回头查布局而不是硬磨布线。
place_opt 之后单元数涨了 28%，正常吗？
正常。插 buffer、时钟树单元、驱动增强都会增加单元数，超过 50% 才需要怀疑约束或库。
