CTS：时钟树综合，从 skew 定义到建树验收

Clock Tree Synthesis

为什么时钟必须建树；latency、skew、global/local 的准确含义与算法；NDR 为什么是 2W2S；ICG 的三种角色；约束命令的使用场景；CTS 后五项检查与延迟调整方案。附原始资料对照。

01

先想清楚：为什么时钟需要专门"建一棵树"

数据信号的路径是设计决定的——网表里写谁连谁，就怎么连。时钟不一样：时钟要到达每一个触发器，而触发器的位置是布局算出来的。

假设一个设计有 20 万个触发器，散落在 2 mm × 2 mm 的芯片上。时钟源只有一个，在某个角落。如果从时钟源直接拉一根线到每个触发器，会发生三件事：

  1. 驱动能力不够：一个源驱动 20 万个负载，边沿会被拖成斜坡，根本不像时钟；
  2. 延迟巨大：线太长，RC 延迟让时钟到得极晚；
  3. 到达时间完全不同：近的触发器早到，远的晚到，差几纳秒——时序无法收敛。

所以必须建一棵缓冲器树：时钟源先驱动几个一级缓冲，每个一级缓冲再驱动几个二级缓冲，层层展开，直到每个触发器都被一个"就在附近"的缓冲驱动。

这棵树要同时优化四个互相矛盾的指标：

指标含义为什么要控制
Latency（插入延迟）时钟从源到叶节点的时间太长会吃掉时序余量
Skew（偏斜）不同叶节点到达时间的差差太大，时序无法收敛
Transition（转换时间）边沿的陡峭程度太缓会导致短路功耗和时序偏差
Power/Area树本身的功耗和面积时钟树常常吃掉全芯片 30% 以上的动态功耗
CTSClock Tree Synthesis 时钟树综合

在已完成布局的设计上，自动插入缓冲器/反相器，把时钟从源分发到所有叶节点（触发器、宏的时钟脚），并控制插入延迟、偏斜和转换时间的过程。业内也说「建树」「做时钟树」。
同义词提醒：叶节点在资料里可能叫 sink、端点、叶节点、balance point，都是同一个东西——时钟树的终点。

02

Latency 和 Skew：两个容易混的概念

原始资料的定义是"latency: 时钟的传播延迟；skew: 时钟延迟的差值"。这个定义对，但要精确到能算。

Latency 是"一个点"的延迟

text
Latency(叶节点 i) = 时钟源出发时刻 → 叶节点 i 收到边沿的时刻

这是一个绝对量，单位是时间（ps）。

Skew 是"两个点"的差

text
Skew(i, j) = Latency(i) − Latency(j)

这是一个相对量。注意它可以是正也可以是负，取决于谁先到。

Global Skew 与 Local Skew 的区别

原始资料写：

text
分为Global Skew（工具更关注）和Local skewGs：同一时钟域，任意两个路径的最大skew。CTS阶段工具更关注的是gs，尽可能把gs做小Ls：同一时钟域，任意两个有逻辑关联关系的路径最大skew。分析timing时更多关注ls

这段话是整门课最重要的一句，但"任意两个"这个说法容易误解。展开一下：

Global Skew（GS）：在一个时钟域内，取所有叶节点，找出最晚到达的和最早到达的，两者之差。

text
GS = max(Latency) − min(Latency)   对域内所有叶节点

Local Skew（LS）：只考虑有逻辑关联的两个叶节点——也就是一条真实时序路径的发射端和接收端。

text
LS = |Latency(接收端) − Latency(发射端)|   对某一条具体路径

为什么 CTS 阶段压 GS，时序分析看 LS

这是最反直觉的一点，但道理很清晰：

GS 是"整体控制力"的度量。 CTS 阶段树还没建完，工具能做的是把整棵树的延迟分布压窄。GS 小，说明树建得均衡，后面无论哪条路径，两端的差都不会太离谱。

LS 才是真正影响时序的量。 时序检查的是具体路径：

text
Setup: 数据到达时间 < 捕获时钟到达时间 − 建立时间

这里用的是这条路径两端的时钟延迟差，不是全局最差。可能出现这种情况：GS 很大（某个远端分支特别晚），但所有关键路径的 LS 都很小，时序照样全绿。

反过来也成立：GS 很小（整体很均衡），但某条特定路径的 LS 很大（恰好这条路径的两端一个早一个晚），这条路径就违例。

常见坑 · 只看 GS 就宣布 CTS 通过

GS 达标只是"树建得均衡"，不代表时序能过。必须另外跑 STA，按路径看 LS。

正确顺序：GS 作为 CTS 的优化目标（工具内部会压），LS 作为时序验收的依据（你要自己查）。

一个常见误区

"skew 越小越好"是错的。

skew 压到极小通常要靠插入大量缓冲器，代价是 latency 变长、功耗上升、面积增大。实际项目里是在 latency、skew、power 之间找平衡点。有些设计甚至故意给某些分支加延迟（见下面的 balance points），让它们和另一条路径对齐。

03

Latency 达标怎么判断

原始资料给了一个具体例子：

text
target_latency      DCLK     850pstarget_skew如果latency低于target latency， 需要垫tree如果latency高于target latency 需要分析为什么latency变得这么长

这段话逻辑很实用，但要理解"为什么低也要修"。

Latency 偏低为什么要"垫tree"

看起来"延迟小是好事"，但在多时钟设计里不是。

假设设计有两个时钟域 A 和 B，需要它们之间有数据交互。如果 A 的 latency 是 300 ps，B 的 latency 是 850 ps，那么从 A 到 B 的路径就要多等 550 ps，时序极难收敛。

所以项目会规定一个目标延迟（target latency），让所有相关时钟都对齐到这个值。某个时钟延迟不够，就要故意加缓冲器把它垫长——这就是"垫 tree"。

tcl
# 给某个 pin 单独做长 latency（正数 = 做长）set_clock_balance_points -clock [get_clocks CLK] -delay 50 \    -balance_points [get_pins U2/CLK] # 做短 latency（负数 = 做短）set_clock_balance_points -clock [get_clocks CLK] -delay -200 \    -balance_points [get_pins U2/CLK]

注意这里 delay 的正负号含义：正数表示"这条路径要比基准晚 50 ps"，负数表示"早 200 ps"。这是相对量，不是绝对值。

Latency 偏高怎么查

原始资料给了三个排查方向，都很实用：

  1. 找最长路径并高亮：看是否有 detour（绕路）或兜圈。物理距离远的两个点之间建树，延迟必然大。
  2. 看 latency 报告：rpts/clock_latency.rpt.gz，找哪一段 delay 特别大。通常是 net delay 大（线太长）而不是 cell delay 大。
  3. 看是否插了过多缓冲器：约束太严格（比如 skew 目标定得过小）会逼工具堆缓冲器，延迟叠加。

调整方案

情况方案
物理距离太远手动 bound sink，把远端负载分配到就近的缓冲器
需要缩短set_clock_balance_points -delay -200
需要加长set_clock_balance_points -delay +200
约束过严导致堆 buffer放宽 skew 目标，重新建树
04

NDR：为什么时钟线要用"非默认规则"

原始资料的说明是：

text
什么是NDR： Not Default Routing Rule   非默认绕线规则针对cts tree的部分的走线单独设置绕线规则，  宽度和间距2W2S  2倍的宽度width  2倍的间距spacing2W1S4W2S创建ndr的方法

清楚，但没解释"为什么"。

三个理由

  1. 降低电阻：宽度加倍，电阻减半，延迟下降。时钟要送到全芯片，电阻影响巨大。
  2. 提高抗干扰能力：间距加倍，耦合电容下降，串扰风险降低。时钟是全芯片翻转最频繁的网，最怕干扰。
  3. 提高可靠性：更宽的线抗电迁移能力更强，不容易因长期电流而断线。

2W2S 是什么意思

  • 2W = 线宽是默认值的 2 倍
  • 2S = 与相邻线的间距是默认值的 2 倍

常见组合的选择依据：

规则适用场景代价
1W2S一般时钟，主要防串扰面积增加较小
2W1S长距离主干，主要降电阻抗串扰一般
2W2S时钟主干，兼顾电阻和串扰（最常用）面积和布线资源占用大
4W2S顶层超长主干、大驱动资源占用很大，只在必要时用
常见坑 · 全树都上 4W2S

NDR 越宽越占布线资源。给整棵树都设 4W2S，会导致时钟区域布线资源枯竭，数据网绕不出去，反而制造大量 DRC 和 short。

合理做法是分层设置：主干（top 几层）用宽规则，叶支（靠近触发器）用默认或 1W2S。

05

ICG：门控时钟不只是"省电开关"

原始资料说：

text
clk gating： 门控时钟， 类似于一个与门，控制时钟信号的翻转，在不需要工作的时候，可以关闭某些path的时钟翻转，达到节省功耗目的

这个理解是对的，但 ICG（Integrated Clock Gating）在 CTS 里的角色比"省电"复杂得多。

ICG 在树里的三个身份

身份一：负载（load）。ICG 本身是时钟树上的一个节点，它有自己的时钟输入脚，CTS 要把它当叶节点对待。

身份二：分叉点（branch point）。ICG 的输出驱动下游一批触发器，形成子分支。所以 ICG 的位置直接影响树的结构。

身份三：可克隆对象（clonable）。当某个 ICG 驱动的负载太多、或者位置不佳导致 DRV 问题时，可以克隆出多个副本，每个副本驱动一部分负载，改善扇出和延迟。

原始资料给的两条命令正是对应"身份三"：

tcl
# 允许 CTS 通过克隆 clock gate 来修复 DRV（扇出、转换时间超标）set_ccopt_property clone_clock_gates true # 允许通过克隆 ICG 来减少平衡冲突（多个分支抢同一个节点）set_ccopt_property clustering_clone_cells_to_reduce_balancing_conflicts true
常见坑 · 无脑打开 clone

克隆 ICG 会让时钟树的网表与原始 RTL 综合结果不一致，影响后续的 formal 检查（形式验证）和功耗分析。开启前要确认流程允许，并在交付时说明。

另外克隆会增加 ICG 数量，功耗未必下降。

06

屏蔽（Shielding）：给关键网穿件外套

原始资料：

text
特殊保护的netshielding一般使用VSS，打在需要保护的net的上下track上

做法：在受害网的上下（或左右）相邻 track 上，平行布一根接地线（VSS）。

原理：耦合电容是并联关系。加了屏蔽之后，受害网的耦合对象从"旁边那根会翻转的信号线"变成"一根不动的地线"。地线电位恒定，不会通过电容注入电荷，干扰就被"吸"到地上了。

代价：

  • 每根被屏蔽的网要占用 2 条额外 track；
  • 屏蔽线本身要接到地网，增加布线复杂度；
  • 大面积屏蔽可能造成局部资源不足。

所以只对真正关键的网做屏蔽：时钟主干、复位、敏感模拟信号。

07

Clock Transition 超标怎么修

原始资料给了两步法：

text
clock_transtion怎么修复1、根据rpt的net，找到对应net2、查看电路图，找到net前后一级的buf，在net中间插buffer

原理：转换时间（transition）本质是 RC 充电太慢。在中间插一个缓冲器，等于把一段长 RC 拆成两段短 RC，每段充电更快，边沿更陡。

但要注意两点：

  1. 插 buffer 会增加 latency：因为多了一级门延迟。所以要权衡：transition 改善了，latency 变长了，可能超出 target。
  2. 插的位置要对：应该插在"RC 负担最重"的那一段中间，不是随便插。通常看报告里 net 的负载分布。
08

CTS 之后必须检查的五项

原始资料列了检查项，但顺序和判据需要补全。

检查一：DRV（设计规则违例）

tcl
report_ccopt_clock_tree

看什么：

  • max transition：边沿是否过缓
  • max capacitance：负载是否过重
  • max fanout：单个缓冲器驱动是否过多

任一项超标，说明树的结构有问题，需要调整（加 buffer、克隆 ICG、改 NDR）。

检查二：Latency 是否达到 target

这是原始资料标为"重点检查"的一项。

tcl
report_clock_timing -type latency -clock FCLK -nosplit

判断逻辑见上文「Latency 达标怎么判断」。

检查三：Setup 和 Hold

原始资料给了一个重要提示：

text
3、检查setup和hold（可选，可以放到optcts再检查）此时clock不是idea的，是真实的，需要检查hold

这句话的关键是"clock 不是 ideal 的"。

CTS 之前做时序分析时，时钟被当作理想网络：延迟为 0（或统一值），skew 为 0。CTS 之后，时钟有了真实的延迟和偏斜，所有时序数字都要重算。

尤其是 hold：CTS 之前 hold 通常很容易过（因为时钟理想），CTS 之后 hold 违例会冒出来。原因是 hold 检查的两个时钟边沿在同一个周期，skew 直接进入计算：

text
Hold 余量 = Latency(捕获) − Latency(发射) − 数据路径延迟 − hold 时间

如果捕获端比发射端早到（负 skew），hold 余量就被吃掉。

检查四：时钟树结构合理性

看树的分支是否均衡、是否有异常长的单支、是否有扇出特别大的节点。

检查五：时钟覆盖完整性

确认所有应该在树上的叶节点都上了树。检查方法就是原始资料里的 sink 统计（见下节）。

09

Sink 统计：用脚本查时钟覆盖

原始资料给了一组查询命令：

tcl
# 得到所有 clock tree 的名字get_ccopt_clock_trees * # 得到 HCLK 的所有 sink 名字get_ccopt_clock_tree_sinks * -in_clock_tree HCLK # 获取 test_clk 的 sink 点数量llength [get_ccopt_clock_tree_sinks * -in_clock_trees test_clk]

注意第三条命令里有个细节：-in_clock_trees（复数）和 -in_clock_tree（单数）是两个不同选项。前者用于按名字集合过滤，后者指定单个树。用错会得到空结果或报错。

为什么必须统计 sink 数量

因为"时钟没上树"是最隐蔽的错误。

一个触发器如果在约束里被漏掉了，CTS 根本不会给它建时钟路径。工具不会报错——它只是"没看见"这个负载。结果就是这个触发器没有时钟，功能直接错。

所以必须做集合对比：

text
应该上树的 sink 集合（从约束和网表推出来）        vs.实际上树的 sink 集合（get_ccopt_clock_tree_sinks 查出来）

两个集合必须完全一致。差集里的每一个对象都要有解释：是被有意排除了（比如测试逻辑），还是漏了。

原始资料的脚本要求

text
实现一个脚本  count_sinks.tcl，写完之后可以 source count_sinks.tcl1.0版本：自动统计出所有的clk的sink点数量输出：my_clk is .... sinks / div_clk is ...sinks / test_clk is ... sinks2.0版本：自动根据clk数量不同，自动统计每个clk的数量

这是一个很好的练手题目。下面给一个可运行的实现思路：

tcl
# count_sinks.tcl —— 统计每个时钟树的 sink 数量# 用法： source count_sinks.tcl set trees [get_ccopt_clock_trees *] if {[llength $trees] == 0} {    puts "WARNING: 没有找到任何 clock tree，检查约束是否加载"} else {    puts "=========================================="    puts "时钟树 sink 统计"    puts "=========================================="    foreach t $trees {        set name [get_object_name $t]        set sinks [get_ccopt_clock_tree_sinks * -in_clock_tree $name]        set n [llength $sinks]        puts [format "%-20s : %6d sinks" $name $n]    }    puts "=========================================="}
小技巧

只打印实际数量，你还是不知道对不对。更实用的版本是：把预期数量写进一张对照表（或者从另一份报告读），脚本同时打印"实际 / 预期 / 差值"。差值非 0 的地方就是要查的地方。

时钟频率与周期：一个必须会算的换算

原始资料最后有一段：

text
时钟的频率和时钟的周期是倒数关系时钟频率 = 1/时钟周期已知时钟周期是1000ps，计算时钟的频率频率 = 1s/1000ps      1s=1x10的9次方ps1Ghz = 1000Mhz

这是基础但容易算错的换算。把单位关系理清楚：

text
1 s   = 10^9 ns = 10^12 ps1 GHz = 10^9 Hz1 GHz 的周期 = 1 / 10^9 s = 10^-9 s = 1000 ps

所以：

周期频率
1000 ps1 GHz
500 ps2 GHz
2000 ps500 MHz
2500 ps400 MHz
100 ps10 GHz
记住这个锚点

1 GHz = 1000 ps 周期。 其他都可以按比例推：

  • 周期减半 → 频率加倍
  • 周期 ×2 → 频率 ÷2

例：周期 400 ps → 1000/400 = 2.5 GHz。

动手从三个数字判断 CTS 是否可交付

假设你拿到一份 CTS 完成后的报告，关键数字如下（合成的教学数据）：

请回答：

  1. DCLK 的 latency 是 852 ps，target 是 850 ps，这个偏差要不要处理？
  2. SCLK 的 latency 超出 target 390 ps，优先怀疑什么？说出两个最可能的原因。
  3. SCLK 的 GS 是 95 ps、LS 是 110 ps。为什么 LS 会大于 GS？这说明了什么？

自测
Global Skew 和 Local Skew 的区别是什么？
GS 是时钟域内所有叶节点的最晚减最早；LS 只取有逻辑关联的一对发射/接收端的延迟差。
为什么 CTS 阶段压 GS，而时序验收看 LS？
GS 反映整棵树的均衡程度，是 CTS 的优化目标；真正影响某条路径时序的是这条路径两端的延迟差，即 LS。
Latency 低于 target 为什么也要修？
多时钟域需要对齐延迟，某个时钟太短会导致跨域路径时序难收敛，所以要"垫 tree"故意加长。
set_clock_balance_points 的 delay 参数正负号分别表示什么？
正数表示把该点做长（延迟增加），负数表示做短（延迟减少），是相对基准的偏移量。
NDR 的 2W2S 表示什么？为什么时钟要用宽线宽间距？
线宽 2 倍、间距 2 倍。宽降低电阻和电迁移风险，间距降低耦合电容和串扰。
为什么 1 GHz 的时钟周期是 1000 ps？
周期 = 1/频率 = 1/10^9 s = 10^-9 s，而 1 s = 10^12 ps，故为 1000 ps。
CTS 之后为什么 hold 违例会变多？
CTS 前时钟被视为理想（延迟为 0、skew 为 0），CTS 后有了真实延迟差，负 skew 会直接吃掉 hold 余量。
sink 统计为什么必须做？
漏掉约束的触发器不会被建时钟路径，工具也不报错，只能靠"应上树集合"与"实际在树集合"对比发现。

时钟树长什么样：四种基本结构

前面说了"要建一棵树"，但树有很多种形状。选错结构，后面无论怎么调参数都吃力。

① 单级星形（Single-Level Star）

一个根缓冲器直接驱动所有叶节点。

text
        ┌── FF1   BUF ─┼── FF2        ├── FF3        └── ...（几十上百个）

适用：叶节点很少（十几二十个）、面积很小。

问题：扇出太大。一个缓冲器驱动上百个负载，边沿会被拖成斜坡，transition 超标。所以现实中很少用纯星形。

② 多级树（Multi-Level Tree）

层层分叉，每级驱动少量下级。

text
              ┌── BUF ─┬── FF1        ┌─────┤        └── FF2   ROOT ─┤     └── BUF ─┬── FF3        │              └── FF4        └───── BUF ─┬── FF5                     └── FF6

适用：绝大多数设计。这是 CTS 工具的默认产出。

关键参数：每级扇出多少、分几级。扇出大则级数少、延迟短但边沿缓；扇出小则级数多、边沿好但延迟长。

③ H-Tree（H 形树）

一种几何上刻意对称的结构，形如字母 H 的递归。

text
   ┌─────────────┐   │             │───┼─────────────┼───   │             │   └─────────────┘

适用：对偏斜要求极高的场景（比如高速接口、时钟网格）。

优点：几何对称意味着到各叶节点的路径长度接近，skew 天然小。

缺点：需要预留专门的布线通道，占用大量资源；而且只适合叶节点分布规整的情况。

④ 时钟网格（Clock Mesh / Grid）

不建树，直接铺一张网格，所有叶节点从网格就近取时钟。

text
  ──┬──┬──┬──┬──┬──    │  │  │  │  │  ──┼──┼──┼──┼──┼──    │  │  │  │  │  ──┴──┴──┴──┴──┴──

优点：skew 极小（网格上任意两点电位几乎相同），抗 PVT 变化能力强。

缺点：功耗极高（整张网格每个周期都在充放电）、面积占用大、布线资源消耗巨大。

适用：高性能 CPU 的关键时钟域，普通设计用不起。

怎么选

实际项目里 95% 的情况用多级树。H-tree 和 mesh 是特殊情况：

  • 叶节点分布极规整 + skew 要求极严 → 考虑 H-tree；
  • 高性能处理器核心 + 愿意付功耗代价 → 考虑 mesh；
  • 其余 → 多级树 + 调参数。

工具默认给你多级树，你需要做的是判断这棵树建得对不对，而不是自己设计形状。

CTS 之前必须确认的五件事

CTS 是"在已有基础上建树"，如果基础有问题，树建得再好也没用。这五项必须在跑 CTS 之前确认。

① 布局合法且稳定

tcl
checkPlace

为什么：CTS 会根据单元的实际位置计算树的结构。如果布局还有大量重叠、非法位置，工具算出的位置是错的，树也会建歪。

判据：无 overlap、无 unplaced、无 VT 不匹配。

② 时钟定义完整

tcl
report_clocks

要确认：

  • 每个时钟域的源在哪（是 port 还是内部引脚）；
  • 周期、波形（占空比）对不对；
  • 生成时钟（分频、倍频）的源和关系定义了吗；
  • 有没有时钟完全没定义（会导致那部分路径"无约束"）。
常见坑 · 漏定义的时钟最危险

一个时钟如果 SDC 里根本没定义，CTS 不会给它建树——那些触发器就没有时钟路径。

工具不会报错，它只是"没看见"。结果就是这部分逻辑上电后不工作。

所以必须做集合对比：网表里所有时钟引脚 vs SDC 里定义的时钟。

③ 时钟例外（exceptions）已就位

tcl
report_exceptions

要确认：

  • false path 是不是真的不用检查（写错了会漏掉真实路径）；
  • multicycle path 的周期数对不对；
  • 有没有 set_disable_timing 把不该断的路径断了。

为什么在 CTS 前确认：CTS 会根据例外调整优化重点。例外错了，工具优化的方向就错了。

④ 时序库与 RC 技术文件对应正确

要确认：MMMC 里每个视图引用的 Liberty、RC tech 是不是同一套发布。混用会导致延迟计算错误。

⑤ 电源网络已就位

tcl
verifyConnectivity -net {VDD VSS}

为什么：CTS 要插大量缓冲器，这些缓冲器需要电源。如果电源网格还没打好，新插的单元会悬空。

过关标准（都能做到才算学完）
  • checkPlace 无 overlap、无 unplaced
  • report_clocks 覆盖所有时钟域，生成时钟关系正确
  • report_exceptions 的 false path / multicycle 都核对过
  • MMMC 各视图的库和 RC tech 来自同一发布
  • verifyConnectivity 无 floating

时钟树的三个代价：latency、skew、power 不可兼得

前面讲了三个指标，但没说它们互相冲突。这一节把冲突关系讲清楚，因为实际调参就是在三者之间取舍。

冲突一：压 skew 会让 latency 变长

为什么：压 skew 需要让所有分支的延迟接近。做法通常是给"跑得快"的分支故意加延迟（多插缓冲器、绕远路）。

结果：最慢的那条分支没变，但整体延迟被拉长了。

text
初始：分支 A 到 800ps，分支 B 到 900ps    → skew = 100ps，latency = 900ps压后：分支 A 加延迟到 890ps                → skew = 10ps，latency = 900ps

这个例子 latency 没变，但如果 A 原本只有 600ps：

text
初始：A=600ps，B=900ps  → skew=300ps，latency=900ps压后：A 加到 890ps      → skew=10ps，latency=900ps（多插了很多缓冲器）

代价：为了把 A 从 600 拉到 890，插了一堆缓冲器——功耗上升、面积增大。

冲突二：压 latency 会让 skew 变差

反过来，如果为了缩短 latency 而减少缓冲器级数，各分支的延迟差异会变大（因为少了调节手段）。

冲突三：加大驱动（压 transition）会增加功耗

驱动强的缓冲器，输入电容大，时钟树整体的动态功耗上升。

时钟树的功耗通常占全芯片动态功耗的 20%–40%，所以这个代价很实在。

怎么取舍

优先级场景做法
latency 优先多时钟域需要对齐先定 target latency，再压 skew
skew 优先单时钟域、时序紧张尽量压 skew，接受 latency 变长
power 优先低功耗设计减少缓冲器级数，接受 skew 稍大
常见坑 · 三个指标都想最优

新手常想"我要 skew 最小、latency 最短、功耗最低"。

这在物理上不可能——它们共享同一组资源（缓冲器、布线、驱动能力）。加一个必然牺牲另一个。

正确心态：先明确这个设计的首要目标是什么，然后接受其他两项的合理退化。

CTS 的五种常见失效模式

跑完 CTS，报告可能"看起来还行"但实际有问题。这五种是最常见的。

① 时钟没到（missing sink）

某些触发器完全没接上时钟。

怎么发现：sink 数量对比（应上树 vs 实际在树）。

原因：约束漏了、时钟定义不全、或者被 set_disable_timing 误断。

② 时钟到了但延迟极大（long branch）

某条分支的 latency 远大于其他分支。

怎么发现：看 latency 分布，找离群值。

原因：物理距离远（单元分布在芯片两端）、约束太严导致堆了过多缓冲器。

③ 偏斜看起来小但时序不过（hidden skew）

GS 很小，但某些路径的 LS 很大。

怎么发现：必须跑 STA，按路径看。

原因：GS 是全局统计，会掩盖局部异常。某条路径的收发两端恰好一个在最早分支、一个在最晚分支。

④ Transition 超标但被忽略

时钟边沿太缓，但没超过 max_transition 的设定值（因为约束设得太松）。

怎么发现：对比实际 transition 和工艺库推荐的典型值，不要只看是否违例。

后果：边沿缓会导致触发器采样点漂移、短路功耗上升。

⑤ 树上有非法单元

CTS 插入了被禁用的单元（dontuse list 里的），或者用了不该用的驱动强度。

怎么发现：checkDesign 或检查单元类型。

后果：签核时被判不合格，要重做。

过关标准（都能做到才算学完）
  • sink 数量与预期一致，无缺失
  • latency 分布无离群值（最长分支不超过最短的 1.5 倍）
  • GS 和 LS 都查过，不只看 GS
  • transition 实际值接近库推荐值，不只是"没违例"
  • 树上没有 dontuse 单元
