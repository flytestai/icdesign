CTS 时钟树：让时钟同时到达

Clock Tree Synthesis

时钟是芯片的心跳。几万个触发器要同时收到时钟，靠的是插入缓冲器建成一棵树。这一课讲清 skew、insertion delay、NDR，以及 CTS 之后必须看的三份报告。

约 48 分钟 课表学时 4 CTSskewclock treeNDR
01

没有 CTS 会怎样

时钟源只有一个，但触发器有几万个。如果直接从源拉线到每个触发器：

  • 有的线长 2mm，有的线短 50µm → 延迟差几百 ps → skew 巨大
  • 一个源驱动几万个负载 → 驱动能力完全不够，时钟波形直接变形

结果：hold 违例报到 −10ns 级，setup 也没法收敛，芯片根本不能工作。

Clock Tree时钟树点击看解释

从时钟源出发，一层层插入缓冲器（buffer/inverter），形成一个树状结构，把时钟分配到所有触发器。
目标：每个触发器收到时钟的时间尽可能一致，且波形质量（transition、占空比）达标。

02

树长什么样

shell
                 clk 源                   │            ┌──────┴──────┐          buf            buf          ← 第一级        ┌──┴──┐       ┌──┴──┐      buf   buf     buf   buf        ← 第二级      ┌┴┐   ┌┴┐     ┌┴┐   ┌┴┐     FF FF FF FF   FF FF FF FF       ← 触发器（叶子）

几个术语：

术语含义典型值
Levels树的层数6~12 级
Skew叶子之间到达时间的最大差<100ps（成熟工艺）
Insertion Delay从源到叶子的总延迟0.5~2ns
Transition时钟边沿的上升/下降时间<100ps
Insertion Delay插入延迟点击看解释

时钟从源出发，经过树的缓冲器，到达触发器所花的时间。
它本身不是问题，问题是它占用了时序预算：时钟晚到 1ns，数据路径就少 1ns 可用时间。

03

命令与关键参数

tcl
# Innovus 用 CCOpt（并发时钟与优化）# 1. 定义时钟树要用的单元set_ccopt_property buffer_cells {BUF_X2 BUF_X4 BUF_X8}set_ccopt_property inverter_cells {INV_X2 INV_X4 INV_X8} # 2. 设定目标set_ccopt_property target_skew 0.08        # 目标 skew 80psset_ccopt_property target_max_trans 0.10   # 最大 transition 100ps # 3. 关键：NDR（非默认布线规则），时钟线要更宽、间距更大set_ccopt_property routing_layer -type trunk M4   # 主干走 M4set_ccopt_property ndr "2w2s"                     # 双倍线宽、双倍间距 # 4. 跑ccopt_design # 5. 三份必看报告report_ccopt_clock_trees -file rpt/cts_trees.rpt    # 树结构、层数、延迟report_ccopt_skew_groups  -file rpt/cts_skew.rpt    # 每组 skewreport_timing -max_paths 20 > rpt/cts_timing.rpt    # 时序变化 saveDesign db/05_cts.enc
NDR非默认布线规则点击看解释

Non-Default Rule。给特定网络指定更宽的线、更大的间距。
时钟线必须用 NDR，原因：
1. 时钟翻转频繁，电阻要小（宽线降电阻）。
2. 时钟对噪声敏感，间距要大（减少耦合电容）。
3. 时钟要抗 EM（电流密度大）。
常见写法 2w2s = 2 倍线宽、2 倍间距。

04

CTS 之后必须看的三份报告

1. 树结构报告

shell
Clock: clk_core  Levels: 9  Total buffers: 1240  Insertion delay: 0.82ns  Max transition: 0.09ns

判断：层数 6~12 正常；层数过多（>15）说明驱动不够或负载太重；insertion delay 过大要查是不是走的层不对。

2. Skew 报告

shell
Skew Group: clk_core  Target skew: 0.080ns  Achieved skew: 0.062ns     ✅  Worst pair: FF_u_core/u_reg[3] (0.71ns) vs FF_u_ddr/u_reg[1] (0.77ns)

判断：achieved ≤ target 才算达标。worst pair 告诉你哪两个触发器差最多，可能是布局上离得太远。

3. 时序报告（对比 CTS 前后）

重点看 hold：

  • CTS 前：hold 违例可能 −5ns 到 −10ns（skew 太大）
  • CTS 后：应该收敛到 −0.1ns 以内
  • 再靠 optDesign -postCTS -hold 修到 0
常见坑 · CTS 用了太多 buffer，面积和功耗都涨

现象：CTS 跑完，单元数从 12000 涨到 15000，面积涨 8%，功耗报告也变差。

原因：skew 目标定得太紧（比如 0.02ns），工具只能疯狂插缓冲器去平衡。

对策：

  1. skew 目标按工艺给（成熟工艺 80~100ps，先进工艺 30~50ps），不要盲目求小。
  2. 允许工具用 inverter 代替 buffer（反相器更省面积，成对使用）。
  3. 检查是否有"超远距离"的触发器被塞进同一组——分组（skew group）要按物理区域划。
工作场景 · CTS review 现场

组长打开 CTS 报告，问三个问题：

  1. "skew 多少？达标没有？"（0.062ns，目标 0.08）
  2. "用了多少 buffer？面积涨了多少？"（1240 个，涨 6%）
  3. "时钟线用 NDR 了吗？走的哪层？"（2w2s，主干 M4）

答不出来，说明你只是敲了 ccopt_design，没有真的控制它。

动手动手：算一下 skew 预算

条件：时钟周期 2.0ns，触发器 setup 0.15ns、hold 0.08ns，组合逻辑最长 1.6ns、最短 0.20ns。

bash
python3 - <<'EOF'P, tsu, th = 2.0, 0.15, 0.08logic_max, logic_min = 1.6, 0.20 # setup: skew 最多能吃掉多少skew_budget_setup = P - logic_max - tsu# hold: skew 最多能吃掉多少（正 skew 对 hold 不利）skew_budget_hold = logic_min - th print("setup 允许的最大正 skew: %+.3f ns" % skew_budget_setup)print("hold  允许的最大正 skew: %+.3f ns" % skew_budget_hold)print("取交集 → 实际可用 skew 预算: %.3f ns" % min(skew_budget_setup, skew_budget_hold))EOF

预期：setup 允许 0.25ns，hold 只允许 0.12ns → 真正的瓶颈是 hold。

过关标准：能解释"为什么 CTS 的 skew 目标不能只看 setup 预算"。

过关标准（都能做到才算学完）
  • 能解释为什么必须做 CTS（不做会怎样）
  • 知道 skew / insertion delay / transition 三个指标
  • 知道时钟必须用 NDR，以及为什么
  • 会看树结构、skew、时序三份报告
  • 知道 skew 目标不是越小越好
自测：先自己想，再点开答案
CTS 的核心目标是什么？
把时钟同时、干净地送到所有触发器，即控制 skew 和 transition。
Insertion delay 为什么会影响时序？
时钟晚到会占用数据路径的时间预算，等效于可用时间变少。
时钟为什么必须用 NDR？
时钟翻转频繁、电流大、对噪声敏感，需要更宽的线（降电阻/抗 EM）和更大的间距（降耦合）。
CTS 后最先看哪份报告？为什么？
看 skew 报告和时序（重点是 hold），因为 CTS 的主要收益就是把 hold 从 −ns 级收敛到 −0.1ns 以内。
skew 目标定得过紧会有什么代价？
工具大量插缓冲器，面积、功耗上升，可能引入新的拥塞。
