时序路径调试：从 WNS 数字走到那一个单元

Debugging a Timing Path

报告上写着 WNS -0.35ns，然后呢？这一课把一条路径拆成五个时间点，给出五步定位法（WNS → 路径类型 → 逻辑级数或线长 → 单元类型 → 手段）、四类假违例的识别方法、六种过滤的组合用法，以及"该修还是该 waive"的判断标准。

01

为什么报告看不懂

本章目标学完这一章，你能把 slack = required − arrival 展开成两组可核对的分项，并在报告里逐项指出对应的行。

report_timing 的输出有几十行，新人往往从头读到尾，读完还是不知道问题在哪。

原因只有一个：不知道工具在算什么式子。

工具只算一个减法，但两边的来源要说清：

text
arrival  = 发射时钟延迟 + CK→Q + 组合逻辑 + 线延迟required = 周期 + 捕获时钟延迟 − uncertainty − setup (+ CPPR)slack    = required − arrival
  • arrival（到达时间）：数据从发射触发器的时钟沿开始，一路走到捕获触发器 D 端，花了多久。
  • required（要求时间）：数据最晚必须在什么时候到。它从"下一个时钟沿"倒推：先加捕获时钟走了多久，再减掉不确定性和 setup。
  • 两者一减，负的就是违例。

很多人以为 "required 就是周期"，这是最常见的误解。周期 2.5ns 的路径，required 可能是 2.84ns（捕获时钟走得比发射时钟久），也可能是 2.19ns（捕获时钟走得早，或者 uncertainty 很大）。required 不是周期，是"周期经过时钟树和库参数修正之后的结果"。

Slack余量点击看解释

slack = required − arrival。正数表示还有富余，负数表示来不及。
WNS（Worst Negative Slack，最差负余量）= 所有违例里最差的那个数，回答"最坏有多坏"。TNS（Total Negative Slack，负余量总和）= 所有负 slack 相加，回答"总共欠多少"。NVP（Number of Violating Paths，违例路径数）= 回答"要修多少条"。

Arrival Time到达时间点击看解释

数据真正到达终点引脚的时刻，从发射时钟沿起算。它包含发射时钟树延迟、触发器 CK→Q、每一级组合逻辑、每一段线。报告里 data arrival time 这一行就是它的总和。

一个必须建立的直觉：arrival 和 required 都会随时钟树变化。 时钟树变深，两边同时变大，slack 未必变差；但两边变的不一样多，差值就是 skew 的影响。所以看到 slack 变化，先问"是 arrival 动了还是 required 动了"。

02

一条路径的五个时间点

本章目标学完这一章，你能在报告上指出 t0 到 t4 五个时刻，并用它们手算出 arrival、required、slack。

把一条 reg→reg 路径想成一次接力跑。五个时间点就是五次交接棒：

text
t0 时钟源           t1 发射CK        t2 发射Q         t3 到达D        t4 捕获沿  |                  |                |                |               |  ├─ 发射时钟树 ─────┤                │                │               │  │                  ├── CK→Q ────────┤                │               │  │                  │                ├── 组合+线 ─────┤               │  │                  │                │                ├─ setup ──────┤  └──────────────────┴────────────────┴────────────────┴───────────────┘
时间点名字计算报告里对应的行
t0时钟源0（参考点）clock clk (rise edge) 0.0000
t1发射时钟引脚t0 + 发射时钟树延迟clock network delay (propagated)
t2发射触发器 Q 端t1 + CK→Qu_a/reg_a[3]/CK->Q
t3捕获触发器 D 端t2 + 组合逻辑 + 线最后一个单元之后的 .../D 行
t4捕获时钟沿周期 + 捕获时钟树延迟data required time 上方几行

注意 t1 和 t4 里的"时钟树延迟"是两个不同的数。它们来自同一棵树的不同分支，差值就是这条路径上的实际 skew。

如果报告里这两行显示的是 (ideal) 而不是 (propagated)，说明时钟还是理想时钟，两个延迟都被当成 0，skew 也就被当成 0——所有结果都是乐观的。看到 ideal，先别讨论修法，先回去把时钟切到传播模式。

手算一次，和报告对上

设定：周期 2.5ns，发射时钟树延迟 0.62ns，CK→Q 0.11ns，组合逻辑 1.42ns，线延迟 0.10ns，捕获时钟树延迟 0.58ns，uncertainty 0.15ns，setup 0.09ns。

  • arrival = 0.62 + 0.11 + 1.42 + 0.10 = 2.25ns
  • required = 2.5 + 0.58 − 0.15 − 0.09 = 2.84ns
  • slack = 2.84 − 2.25 = +0.59ns → MET

现在把组合逻辑换成 1.85ns（比如多了一级 32 位加法器）：

  • arrival = 0.62 + 0.11 + 1.85 + 0.10 = 2.68ns
  • slack = 2.84 − 2.68 = +0.16ns → 还是正的

再加 5% derate（数据侧 2.68×0.05 ≈ 0.13）：

  • slack ≈ 0.16 − 0.13 = +0.03ns → 擦线

这就是"报告上写着 MET，但你知道它随时会翻"的样子。看 slack 要连 derate 一起看，否则等于看税前工资。

03

五步定位法

本章目标学完这一章，你能在十分钟内从 WNS 走到"该动哪个单元、动它还是动结构"的结论。

不要一上来就改。按这五步走，顺序不能跳。

工作场景 · 周一早上九点半，群里只有一句话

组长在项目群里发："WNS 为什么是 −0.35？十分钟后开会。"

你手上只有一份昨晚跑完的 viol_setup.rpt，两百多行。十分钟不够读完，但够走完五步：看 QoR 数字、看最差那条的起终点、数级数和线占比、找最大 Incr、给出两个手段。

开会时你要说的不是"我再查查"，而是"差 0.35，差在 u_dp 的 41 级逻辑上，超预算 5 级，换 LVT 能省 0.07，剩下的要动 RTL"。 这句话的前提，就是下面五步。

第 1 步：看 WNS，先判断"点"还是"面"

tcl
# 作用：拿到全局数字，判断是单点问题还是系统性问题# 用法：每次跑完 PT 第一件事，三个数一起记report_qor > rpt/qor.rpt# 说明：WNS 最坏一条、TNS 总和、NVP 违例条数，三个数决定后面怎么走report_timing -max_paths 20 -slack_lesser_than 0 > rpt/wns20.rpt# 说明：先看最差 20 条，看它们是不是集中在同一个模块/同一对时钟

判断标准：

组合含义下一步
WNS 差、NVP 少（< 50）单点问题，几条难路径直接进第 2 步，逐条修
WNS 差、NVP 多（> 1000）系统性问题先查约束、库、频率，别急着修
WNS 小负、TNS 巨大大面积擦线多半是 uncertainty 或 margin 给多了
WNS 正、NVP 0没有 setup 问题转去看 hold 和 DRV

第 2 步：看路径类型，先排除"不该查的"

一条路径的身份由四个字段决定：Path Group、Path Type、起点的时钟、终点的时钟。

  • Path Type: max 是 setup，min 是 hold。看 hold 报告时要确认这里真的是 min，否则你在拿 setup 的数字讨论 hold。
  • 起点和终点是不是同一个时钟？不同就要问"这两个域是不是异步"，异步就该有 clock group（见 06-01）。
  • 起点是端口还是触发器？in→reg 的路径受 set_input_delay 支配，修法完全不同（要改板级或接口协议，不是改布局）。

这一步能筛掉一半的"假违例"。 很多 WNS 榜首的路径，一看起终点就知道根本不该比。

第 3 步：看是"逻辑级数多"还是"线太长"

数两样东西：

  • 逻辑级数：路径上经过的单元个数（不含时钟树）。超过预算级数 20% 就是结构问题。
  • 线延迟占比：所有 net（连线）的 Incr 之和 ÷ arrival。超过 50% 就是布局/绕线问题。
tcl
# 作用：把一条路径的单元延迟和线延迟分开统计# 用法：先导出单条路径报告，再用 awk 按行首缩进和列特征分类report_timing -from [get_pins u_a/reg[3]/CK] -to [get_pins u_b/reg[7]/D] \              -path_type full_clock_expanded -max_paths 1 > rpt/one.rpt# 说明：full_clock_expanded 才能看到线段的 Incr，默认输出会把线合并grep -c "/" rpt/one.rpt# 说明：粗略数一下路径上有多少个带层次名的节点，估逻辑级数

两类问题的修法完全不同：

现象结论手段
级数 42，预算 36结构太深前端重构、加流水、换复杂门合并逻辑
级数 20，但线占 65%摆得太远改 floorplan、加区域约束、把相连逻辑拉近
两者都正常，但某一级 Incr 0.4ns单元问题进第 4 步

第 4 步：看单元类型，找"最贵的那一级"

Incr 最大的那一行，看它是什么：

单元类型典型问题处理
BUF_X1 / INV_X1驱动不足，带十几个负载upsize 到 X4/X8，或拆负载
复杂门（AOI/OAI/MUX）本身延迟就大，还在关键路径上换低阈值（LVT）或重构逻辑
高扇出 net 的驱动一个输出带 30 个负载复制驱动（clone）、插缓冲树
时钟 buffer出现在数据路径里多半是约束或网表错，回去查

一个经验值：单级普通门在 28nm 约 40~60ps（典型值）。某一级到 300ps 以上，基本就是驱动或负载问题，不是逻辑问题。

第 5 步：定手段，一次只改一处

诊断首选手段代价
级数太深前端加流水 / 重构动 RTL，周期长，但根治
线太长改 floorplan / 加 region 约束可能引起拥塞转移
单级驱动弱upsize / 换 LVT面积、漏电上升
扇出太大clone 驱动 + 插 buffer面积上升
时钟 skew 大回 CTS 调树 / useful skew影响全局，需 CTS 工程师确认

改完只重跑这一条（用 -from/-to），确认好了再全量。一次改五个参数的人，永远不知道是哪个起了作用。

常见坑 · 拿 hold 的报告去修 setup

现象：有人把 report_timing 默认输出（max）和另一份 -delay_type min 的报告混在一起看，发现同一条路径一会儿 −0.05 一会儿 +0.30，以为工具不稳定。

原因：max 和 min 是两条不同的路径（最长和最短），required 的算法也不同——setup 用下一个沿减 setup，hold 用同一个沿加 hold。

规矩：文件名里必须带 setup / hold，报告第一眼看 Path Type。两份报告永远不放在同一个表格里比较。

04

四类"假违例"：不是设计的问题，是约束的问题

本章目标学完这一章，你能用四条命令分别确认四类假违例，并说出每类该怎么补约束。

签核时最耗时间的不是修违例，是判断哪些违例是真的。下面四类占了假违例的绝大多数。

第一类：false path 漏写，跨域路径被当真

症状：最差路径永远跨在两个时钟之间，slack −3ns 级别，怎么优化都不动。

确认：看起点和终点的时钟是不是同一个；不同且确实异步，就该有 set_clock_groups -asynchronous。补上之后重跑，WNS 应该跳变。

注意方向：漏写只是多几条假违例，写宽了会藏真违例。 前者浪费两天，后者报废一版芯片。

第二类：multicycle 写错，检查拍数不对

症状：一条路径的 required 是个奇怪的整周期倍数（比如 3.75 而不是 1.25），或者明明逻辑很深却一条违例都没有。

确认：report_timing 看 required 是几个周期；回 RTL 数使能信号的拍数；检查有没有配套的 -hold N-1。

三类典型错误：N 写多了（放过真实违例）、只写 setup 不写 hold（hold 检查错位）、对没有使能保护的路径硬设 multicycle（功能上就会采错）。

第三类：时钟定义错，整片结论都歪

症状：某个域的违例特别多或特别少；或者 report_clocks 里的周期和规格书对不上。

确认：report_clocks 逐个核对周期、波形、source。重点查三种：

  • generated clock 的 -source 指到了输出而不是输入；
  • -divide_by 写错（2 写成 3）；
  • 两个时钟同名，后一个把前一个覆盖了。

时钟错是"上游错"，它会让所有下游结论失效。 发现周期不对，先停下所有优化。

第四类：unconstrained，路径根本没被查

症状：某个模块"一条违例都没有"，看起来特别干净。对它单独跑 report_timing -to <某个端点> 却返回 No paths。

确认：

tcl
# 作用：找出没有任何约束覆盖的端点和没有时钟的单元# 用法：每次读入 SDC 之后立刻跑，两项都必须为 0check_timing -include {unconstrained_endpoints no_clock} > rpt/check.rpt# 说明：unconstrained_endpoints = 有终点但没有约束，等于"永远 MET"# 说明：no_clock = 时序单元没有时钟到达，多半是时钟穿过了不可传播的单元

没查的路径，slack 是无穷大。 它比违例危险得多——违例会报红，没查的不会。

类型一句话识别补什么
漏 false path跨域、slack 极差、修不动set_clock_groups -asynchronous
multicycle 写错required 是整周期倍数改成正确 N，补 -hold N-1

六种过滤，把范围缩小到一条路径

本章目标学完这一章，你能用六个参数的组合，从几万条路径里精确捞出"就是这一条"。
tcl
# 作用：六种过滤各自解决一个问题，组合起来可以精确到一条路径# 用法：定位阶段逐个加，每加一个看条数怎么变report_timing -max_paths 10# 说明：① -max_paths 控制条数，按 slack 从差到好取report_timing -from [get_pins u_core/reg_a_reg[3]/CK]# 说明：② -from 限定起点，写 CK 引脚最精确report_timing -to [get_pins u_core/reg_b_reg[7]/D]# 说明：③ -to 限定终点，写 D 引脚最精确report_timing -through [get_pins u_core/u_alu/U2317/Z]# 说明：④ -through 限定"必须经过"，用来抓惯犯单元report_timing -path_group clk_core# 说明：⑤ -path_group 限定时钟组，跨域问题多时先分组看report_timing -delay_type min# 说明：⑥ -delay_type 切换 setup/hold，min 是 hold

三种常见组合的用途：

目的组合看什么
找惯犯单元-through + -max_paths 200同一单元出现在多少条违例里

现象：明明在报告里看到 U1188 这个单元，加 -through [get_pins u_alu/U1188/Z] 之后返回 No paths。

原因：三种可能——引脚名写错（Z 还是 ZN）、层次名少了前缀、或者这条路径根本不是 max（是 hold）。

怎么查：先 get_pins *U1188* 看真实名字；再不加 -delay_type 跑一次；最后用 -through [get_cells u_alu/U1188] 代替引脚。

06

逻辑级数与时序预算：手算一次就懂

本章目标学完这一章，你能用 FO4 估算一个周期能放多少级逻辑，并判断实际路径超了几级、值多少钱。
FO4四扇出反相器延迟点击看解释

Fanout-of-4 Inverter delay。一个反相器驱动四个同样的反相器时的延迟。它是工艺的"时间单位"：不管具体逻辑多复杂，都可以折算成几个 FO4。
28nm 约 25ps，16nm 约 14ps（典型值，随库和电压变化）。FO4 让跨工艺、跨项目的比较成为可能。

2.5ns 周期（400MHz）下，一个触发器到下一个触发器之间能放多少级逻辑？

text
周期                    2.500 ns- CK→Q                  -0.110- setup                 -0.090- 时钟不确定性          -0.150- 时钟 skew（预算）     -0.100- 布线/OCV 余量         -0.250────────────────────────────────= 留给组合逻辑          1.800 ns

按一级 NAND2 ≈ 2 FO4 = 50ps：

  • 1.800 / 0.050 = 36 级

按一级复杂门（AOI21、MUX2）≈ 4 FO4 = 100ps：

  • 1.800 / 0.100 = 18 级

所以"这条路径 42 级"意味着什么，要看它是什么门。 42 级 NAND2 超预算 6 级 ≈ 0.30ns；42 级混合逻辑（平均 70ps）就是 2.94ns，直接崩。

再看线：一条 M4 线 1mm，单位电阻 0.2Ω/µm、单位电容 0.2fF/µm，Elmore 延迟约 0.5 × 200Ω × 200fF = 20ps。一条路径绕了 15mm，光绕线就 0.30ns——相当于 6 级 NAND2。

Logic Level逻辑级数点击看解释

一条路径上从发射触发器 Q 到捕获触发器 D 之间经过的单元个数（不含时钟树）。它是"结构深度"的度量，和"线长"是两个独立维度。
判断口径：级数 × 单级延迟 + 线延迟 ≈ arrival − CK→Q。两者对不上，说明你的单级延迟估错了。

诊断口诀：

观察结论
级数 ≤ 预算，线占比 < 30%健康，问题在别处（时钟或约束）
级数 > 预算 20%结构太深，找前端
线占比 > 50%摆得太远，找 floorplan
级数和线都正常，单级 Incr 异常大单元/扇出问题，找实现
为什么用 FO4 而不是"门的个数"

不同工艺的门延迟差三倍，用"多少个门"没法跨项目比较。FO4 是归一化单位：说"这条路径 30 个 FO4"，在任何工艺下都能立刻判断深浅。

面试里说"我们路径太深了"没有信息量，说"42 级、约 84 个 FO4，超预算 20%"才叫懂。

07

该修还是该 waive：一个判断表

本章目标学完这一章，你能为一条违例给出"修 / waive / 留到下一版"的结论，并说出合法依据。

不是所有违例都值得修。按这个顺序判断：

情况处理理由
hold 违例必须修与频率无关，降频也救不了，硅片上一定出错
setup 违例、路径真实、slack < −50ps修影响良率与最高频率
setup 违例在假路径上waive（补约束）功能上不会发生，补约束才是正解
违例 < 20ps 且在 Cmax 场景可 waive（记录）在模型误差范围内，修的成本高于收益
测试/DFT 逻辑违例通常 waive测试模式频率低，且有专门时序
spare cell 上的违例waive备用单元不参与功能

"留给下一版"的四个合法条件

"下一版再修"是工程常态，但必须同时满足四条，缺一条就是耍赖：

  1. 不影响本版功能：本版的工作模式不会踩到这条路径（有模式分析或使用场景支撑）。
  2. 有量化风险：能说出"这条路径在 125℃ 下 slack −0.03，触发概率约多少"，而不是"应该没事"。
  3. 有明确 owner 和时间点：谁在下个版本修、什么时候修、修不动怎么办。
  4. 相关方知情：系统/产品/客户知道这个限制，并接受（比如"最高频率降 5%"）。

四个非法理由，说了会被当场打断：

  • "来不及了"
  • "以前也这么放过"
  • "仿真没报错"
  • "应该不会那么巧"
常见坑 · waive 不写记录

现象：签核报告里有一条 −0.05ns 的违例，备注栏空白。三个月后新人接手，不知道该不该修，于是又花两天查了一遍。

规矩：每条 waive 都要进 waiver 表，六列——路径名、slack、场景、原因、批准人、复审日期。没有批准人的 waive 等于没 waive。

08

report_timing -format：把报告变成一张表

本章目标学完这一章，你能用 -format 一次导出几十条路径的关键列，直接贴进 Excel 做统计。

默认报告是"一条路径一段文字"，几十条就没法比较。-format 把它变成表格，一行一条路径。

tcl
# 作用：导出表格化的违例清单，便于排序和统计# 用法：签核汇总、ECO 分工、周报都用这份report_timing -max_paths 100 -slack_lesser_than 0 \              -format {startpoint endpoint path_group path_type slack arrival required} \              > rpt/viol_table.rpt# 说明：-format 后面是字段列表，顺序就是输出列顺序# 说明：字段名必须是工具认识的，写错会报 "unknown field"

每列怎么用：

列含义拿它判断什么
startpoint起点引脚全名同一模块的起点扎堆 → 模块级问题
endpoint终点引脚全名同一终点多条 → 扇入太多，该拆
path_group所属时钟组按组统计 TNS，找出最差的域
path_typemax（setup）/ min（hold）防止 setup 和 hold 混在一张表里
slack余量排序、算 TNS、定修复优先级
arrival到达时间和 required 比，看是哪边的问题
required要求时间明显是整周期倍数 → 怀疑 multicycle

拿到表之后做三件事：

  1. 按 path_group 分组求 TNS，找出"哪个域最欠"。
  2. 按 endpoint 去重计数，找出"哪个终点被最多路径抢"。
  3. 按 startpoint 的模块前缀统计，找出"哪个模块拖后腿"。

这三步做完，修哪一块就有答案了，不需要逐条读报告。

09

一个完整案例：从 −0.16 到 ECO

本章目标学完这一章，你能把前八章的方法串成一次完整的 20 分钟定位。

现象：report_qor 显示 WNS −0.16ns，TNS −1.8ns，NVP 47。

第 1 步（WNS）：NVP 47，属于单点问题，可以逐条修。

第 2 步（路径类型）：最差路径 Path Group: clk_core、Path Type: max，起点 u_dp/acc_reg[7]/CK，终点 u_dp/acc_reg[7]/D——同一个寄存器组，是真实的同步路径，不是跨域。

第 3 步（级数 vs 线）：路径上 41 个单元，net 延迟合计 0.31ns，占 arrival 的 12%。→ 线不是问题，级数是问题。预算 36 级，超 5 级 ≈ 0.25ns。

第 4 步（单元类型）：最大 Incr 是 u_dp/U8821（AOI21X1）0.19ns，扇出 1，负载正常；第二是 u_dp/U9102（MUX2X1）0.17ns。都是复杂门，本身延迟大，且都在关键路径上串联。

第 5 步（手段）：两条路——把 U8821/U9102 换 LVT（预计每级省 30~40ps，合计 0.07），或者把这段 8 位宽的 mux 树拆成两级流水（省 0.25 但动 RTL）。

决策：本版只剩两周，选 LVT + 局部重排（把 mux 树的两个输入拉近，省线 0.05）。预计 −0.16 + 0.07 + 0.05 = −0.04，仍差一点，剩下 0.04 走 waiver，理由写"模型误差范围内，下一版重构 mux 树"。

这个案例的完整回答格式：差多少 → 差在哪 → 为什么 → 怎么办 → 办完还差多少 → 剩下的怎么办。六句话，缺一句就会被追问。

动手动手：把一条路径拆到单元级

任务：用课程环境里的 ~/backend_lab/soc/pnr/reports/timing.rpt（或 05-02 练习数据里的违例报告），完成一次五步定位，产出一页结论。

步骤：

  1. 抄下 WNS / TNS / NVP，判断是点还是面。
  2. 抄下最差路径的 Path Group、Path Type、起点、终点，判断是不是真实同步路径。
  3. 数路径上的单元个数（grep -c "/"），统计 net 的 Incr 之和，算出线占比。
  4. 找出 Incr 最大的三行，记下单元类型和数值。
  5. 按第五章的表给出至少两个手段，估算各自能省多少，算出剩余 slack。

过关标准：结论里必须出现"超预算几级、折合多少 ns、最大 Incr 是哪个单元、两个手段各能省多少"。写不出具体数字，说明还在猜。

自测：先自己想，再点开答案
slack = required − arrival 里，required 由哪几项拼成？
周期 + 捕获时钟树延迟 − clock uncertainty − library setup time（hold 则是同沿 + hold time，且用发端的下一个沿）。
arrival 里最容易漏掉哪一项？
发射时钟树延迟。数据不是从 0 时刻出发的，是从"时钟走到发射触发器 CK 端"的时刻出发。
五步定位法的第三步在区分什么？
区分"逻辑级数太多"（结构问题，找前端）和"线延迟占比太高"（布局问题，找 floorplan），两者修法完全不同。
FO4 是什么，为什么用它？
四扇出反相器延迟，是归一化的时间单位；跨工艺比较路径深度时用它，比"多少个门"有意义。
-through 返回 No paths，可能是什么原因？
引脚名写错（Z/ZN）、层次前缀不全、或者路径类型不是 max（实际是 hold）。
一条路径 required 显示为 3.75ns、周期 1.25ns，先怀疑什么？
multicycle 设成了 3 拍，或者时钟周期定义错了；先看 report_clocks 和 SDC 里的 multicycle。
"留给下一版"需要哪四个条件？
不影响本版功能、有量化风险、有 owner 和时间点、相关方知情并接受。
check_timing 里 unconstrained_endpoints 不为 0，为什么比违例更危险？
这些路径根本没被检查，slack 视为无穷大，报告上完全看不到，等于签核漏了一片。
过关标准（都能做到才算学完）
  • 能在报告上指出 t0~t4 五个时刻，并手算 arrival / required / slack 与报告对上
  • 能按五步法走完一次定位，第三步能算出线延迟占比和逻辑级数
  • 能用 FO4 估算一个周期能放多少级，并判断实际路径超了几级
  • 能识别四类假违例，各自说出确认命令和补什么约束
  • 能用六个过滤参数组合出"只看这一条"，并知道 -through 失败怎么查
  • 能给出"修 / waive / 留到下一版"的结论，且"留到下一版"能说全四个条件
  • 能用 -format 导出表格并按 path_group、endpoint、模块前缀做三次统计
