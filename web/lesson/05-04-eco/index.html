ECO 实战：从 PT 的违例到版图上的一次改动

Engineering Change Order in Practice

版图都快送厂了，PT 报出 3 条 hold 违例。全流程重跑要两天，ECO 只要两小时。这一课讲清 ECO 的三种类型、五环节链路、清单格式、可执行脚本、PT 侧 fix_eco_timing 的用法、SVF 与 Formality 为什么不能省，以及一次真实的 -0.07ns hold 修复全过程。

约 50 分钟 课表学时 4 ECOPTICC2时序修复等价性
01

ECO 是什么，什么时候用它

本章目标学完这一课，你能从一份 PT 违例报告出发，写出一份人能评审、脚本能执行的 ECO 清单，在版图上应用改动、局部重布、回签，并说清每一步为什么不能省。

给一个已经上线的手机 App 修 bug，有两种做法：

  • 重装整个系统：重新编译、重新打包、重新发布。干净，但用户要重新下载 200MB。
  • 打一个热补丁：只替换出问题的那一个函数。快，但补丁必须精确——改错一行，整个 App 崩。

ECO 就是芯片版的"热补丁"。

ECOEngineering Change Order，工程变更单点击看解释

原意是设计流程里的"变更申请单"。在后端语境下，特指在已有版图上做局部修改：换单元尺寸、插缓冲器、改连线，然后局部重布、重新签核。
它的对立面是"全流程重跑"（改 RTL → 重新综合 → 重新布局布线）。

工作场景 · 送厂前三天，PT 报 3 条 hold 违例

周三下午，签核报告出来：hold WNS −0.0712ns，一共 3 条，全在 u_ctrl 那组状态寄存器上。tapeout 定在下周一，全流程重跑要两天，而且新版本还要重新收一遍所有 corner——时间不够，风险更大。

leader 的指令是："用 ECO，只动这三条，改完当天回签。"

你要在今晚做完四件事：把三条路径的终点找出来、定一个改动最小的方案、写一份别人能看懂的清单、跑完应用和回签。改错的代价是周一交不出片子；改多了的代价是引入新问题，同样交不出。

这三个新插的延迟单元，面积代价是 3 × 0.77µm² ≈ 2.3µm²，占芯片 49440µm² 的 0.005%。这就是 ECO 的价值：用最小改动换签核通过。

维度全流程重跑ECO
耗时几小时到两天十几分钟到两小时
改动范围全芯片重新优化只动必须动的几十个单元
结果可预测性低（新版本可能引入新问题）高（改动面小，影响可枚举）
前提无必须能精确定位到具体引脚
风险布局全变，时序全变，要重新收一遍局部拥塞、局部 DRC

什么时候该用 ECO

四种典型场景：

  1. tapeout 前最后修补：只剩几条 hold/setup 违例，重跑一次两天，来不及。
  2. 流片后发现功能小 bug：只改几根连线（metal-only，见下一节）。
  3. 加一个迟到的功能：前端改了 20 行 RTL，不想全流程重跑（这种通常还是要重跑综合，只是布局可以复用）。
  4. 修 DRC/天线：局部改线，不动逻辑。

什么时候不该用 ECO

这一条比上一条更重要：

  • 违例是系统性的（几千条、散落全芯片）→ ECO 修不完，根因在约束/库/架构。
  • 要改的逻辑超过几十个单元 → 手工 ECO 的出错概率超过重跑。
  • 时序余量只剩 20ps → ECO 之后再加 OCV 波动就没了，应该回架构层解决。
常见坑 · 把 ECO 当成"万能橡皮擦"

现象：WNS −0.6ns，打算用 ECO 修。写了 400 条改动，应用后 WNS 变成 −0.55ns，还多出 60 条 DRC。

原因：ECO 是在已经优化到极限的版图上做局部微调，它能修的是"差一点点"（几十 ps 量级）。差 0.6ns 说明架构或约束有问题，局部改动救不回来。

判断标准：单条违例差的量 ≤ 单个单元的一档驱动差（约 50~100ps），才适合用 ECO 修。超过这个量级，先问"为什么差这么多"。

02

三种 ECO 与 metal-only 为什么不动 base layer

芯片的掩膜（mask）不是一张，是一叠。粗略分两层：

  • base layer（基础层）：晶体管层——阱、扩散区、多晶硅栅。它决定了"这里有一个什么样的管子"。
  • metal layer（金属层）：M1~M8 的连线和通孔。它决定"这些管子怎么连起来"。
Metal-only ECO只改金属层的 ECO点击看解释

只修改金属层掩膜、不动晶体管层的 ECO。因为晶体管层掩膜不用重做，成本低一个数量级、周期短几周。前提是版图里预先埋了备用单元（spare cell），需要时只改连线把它接进电路。

Spare Cell备用单元点击看解释

在布局阶段故意撒在芯片各处的"闲置"标准单元（常见比例是总面积 1%~3%）。它们输入端接固定电平、输出悬空，不参与功能。需要 ECO 时，改几根金属线就能把它们变成反相器、与非门、触发器。

为什么 metal-only 不改 base layer？因为改 base layer 意味着：

  1. 所有掩膜重做：一套 28nm 掩膜按层数计价，全套几十万到上百万人民币（先进工艺更贵）。
  2. 所有在制批次报废：fab 里正在跑的那批 wafer 全部作废。
  3. 周期从几周变几个月：要重新流片、重新封装、重新测试。

而 metal-only 只改 1~2 层金属掩膜，成本可能是全掩膜的 1/10~1/5，周期短得多。这就是为什么芯片设计里要"预留 spare cell"——它买的是一个"后悔药"的期权。

类型改什么要不要重跑综合要不要重做 base 掩膜典型周期
RTL ECO改 RTL 代码要要最长
门级 ECO改网表（换单元、插 buffer）不要要（单元位置变了）中等
Metal-only ECO只用 spare cell 改连线不要不要最短
一个诚实的边界

本课讲的 apply_eco.tcl 属于门级 ECO：它会插入新单元、改变布局，因此需要重做全部掩膜（只是不用重跑综合和全局布局）。

真正的 metal-only ECO 是另一套流程：只能用预留的 spare cell、只允许改金属，工具链和检查项都不同（还要额外检查 spare cell 的电源/地是否已接好）。课程环境不覆盖 metal-only 的完整流程，但你要知道它的存在和代价差异——面试里经常问。

完整链路：五个环节，一个都不能省

text
① PT 出违例报告（带具体 pin 名和 4 位小数的 slack）      ↓② 生成 ECO 改动清单（哪个单元、换成什么、插在哪、为什么）      ↓③ 人工审核 + 在 PR 工具里应用（改网表 + 改布局）      ↓④ 局部合法化 + 局部布线 + 局部时序优化（不是全芯片）      ↓⑤ 回签：PT 复算时序、Formality 验证等价、DRC 复查
环节谁做工具交付物做错了会怎样
① 找违例STA 工程师PrimeTime违例清单（含坐标级的 pin 名）修错对象，白忙一轮
② 出清单STA + 脚本PT / 自写脚本eco.txt（人可读 + 机器可执行）清单歧义，脚本执行到一半失败
③ 应用PR 工程师ICC2 / Innovus改过的数据库单元重叠、连线错乱
④ 局部重布PR 工程师同上布线后的数据库 + 新网表/SPEF引入新 DRC、新违例
⑤ 回签STA 工程师PT + Formality新报告 + 等价性结论改了但没验证，等于没改

三个最容易省的环节，恰恰最不能省：

  • ③ 之前的人工审核：PT 只看时序不看物理，它的建议可能放不下。
  • ④ 的合法化：新单元坐标是浮点，不和轨道对齐，不 legalize 就是一堆 DRC。
  • ⑤ 的 Formality：改了网表不做等价性检查，你根本不知道改的是不是还是原来那个电路。
04

改动清单长什么样

一份好的 ECO 清单是纯文本，一行一个动作。人能读懂，脚本能解析，git 能 diff。

text
# eco.txt —— 列：动作  目标  参数  原因# 动作只允许三种；目标必须是层次化全名；原因必须能追溯到 PT 报告里的 slacksize_cell   u_core/u_alu/U2317              BUF_X4      # 驱动不足，扇出 12insert_buf  u_core/u_ctrl/state_reg[2]/D    DELAY_X1    # hold -0.0712ns，需 +72psremove_buf  u_core/u_mul/U882               -           # 冗余缓冲，占布线资源

逐列说清：

列含义约束写错会怎样
1 动作size_cell / insert_buf / remove_buf只能是脚本认识的关键字脚本走 default 分支，静默跳过
2 目标实例全路径名，或引脚全路径名必须唯一，不能有通配符get_cells 返回多个或空，改错对象
3 参数换成的单元名 / 插入的单元名 / -必须在库里存在报 Cannot find cell，该行失败
4 原因自由文本，# 之后必须带 slack 或问题描述评审时说不清为什么改

目标名为什么必须唯一

u_ctrl/state_reg[2]/D 这种名字包含三部分：层次路径 + 实例名 + 引脚名。三个地方都可能出错：

  • 层次写错：u_ctrl 写成 u_ctl → get_cells 返回空。
  • 实例名写错：state_reg[2] 写成 state_reg(2) → 返回空（Verilog 用方括号）。
  • 引脚名写错：/D 写成 /d → 有些工具大小写敏感，返回空。

所以清单生成之后，第一步不是应用，而是校验每一条目标是否存在：

tcl
# 作用：应用前校验清单里每个目标都能在设计中唯一定位# 用法：在 ICC2/Innovus 里 source 这份脚本，或把循环抄进 apply_eco.tclset fh [open "./eco.txt" r]                    ;# 打开清单set bad 0                                       ;# 计数器：找不到的目标数foreach line [split [read $fh] "\n"] {          ;# 逐行读  set line [string trim [lindex [split $line "#"] 0]]   ;# 去掉 # 后面的注释  if {$line eq ""} { continue }                 ;# 空行跳过  set tgt [lindex $line 1]                      ;# 第 2 列是目标  if {[sizeof_collection [get_cells -quiet $tgt]] == 0 && \      [sizeof_collection [get_pins  -quiet $tgt]] == 0} {    puts "@@@ 找不到目标：$tgt"                 ;# 打印出来人工确认    incr bad                                    ;# 累计  }}close $fhputs "@@@ 校验完成，异常 $bad 条"               ;# 必须是 0 才继续

-quiet 的作用是抑制 "no objects matched" 的报错，让你自己统计，而不是脚本中途崩掉。

05

应用脚本：可执行的骨架

下面这份脚本读取 eco.txt，在已有版图上应用改动。逐行看注释。

tcl
# ============================================================# 作用：读取 eco.txt，在已有版图上应用 ECO 改动# 用法：icc2_shell -f apply_eco.tcl 2>&1 | tee log/apply_eco.log# 前提：block 已 open；当前目录有 eco.txt；已确认目标是唯一名字# ============================================================ set ECO_FILE "./eco.txt"                  ;# 清单路径set SNAP_PRE "snap_pre_eco"               ;# ECO 前快照名（回退用） # ---- 2. 合法化：把新单元对齐到轨道，消除重叠 ----legalize_placement                         ;# 不改逻辑，只挪位置check_lvs                                  ;# 连接关系自检：有没有开路/短路 # ---- 3. 只布改动的网，不要全芯片重布 ----set eco_nets [get_nets -of_objects [get_cells -hier -filter "is_physical==true"]]# 取所有被标记为物理单元的网（即刚插进去的那些）route_auto -nets $eco_nets                 ;# 先做全局布线（给这些网分配轨道）route_detail -incremental true             ;# 再做详细布线（只改这些网周围） # ---- 4. 局部时序优化 ----set_app_options -name opt.post_route.effort -value medium   ;# 中等力度，避免大改route_opt -incremental                     ;# 只优化受影响区域 # ---- 5. 出报告 + 存盘 ----redirect eco_drc.rpt    { check_routes }    ;# 布线 DRC 自检redirect eco_timing.rpt { report_qor }      ;# 局部时序快照（最终以 PT 为准）save_block -as snap_post_eco                ;# ECO 后快照puts "@@@ 完成。报告：eco_drc.rpt / eco_timing.rpt"

几个必须理解的细节：

  1. save_block -as 放在最前面，不是最后面。ECO 的价值在于可回退，快照存晚了就没意义。
  2. catch 包住每个动作：一条失败不应该让整份清单中断（否则你修一条要重跑一遍）。但失败数必须为 0 才继续往下走。
  3. legalize_placement 必须在布线之前：insert_buffer 给的坐标是"贴着目标引脚"的浮点值，不和标准单元轨道（row/track）对齐。
  4. route_auto 只给 $eco_nets：不加 -nets 就是全芯片重布，两小时变两天，而且会把原来干净的线搅乱。
  5. route_detail -incremental true：增量模式只动违例附近的线，保留原有布线。
常见坑 · insert_buffer 之后忘了 legalize_placement

现象：ECO 应用"成功"，一跑 DRC 出来 200 条 spacing 违例，还有几条 short。

原因：新插入的单元坐标是浮点数，可能和旁边的单元重叠，也可能跨在两个 row 之间。不合法化直接布线，布线器只能在非法的位置上勉强连。

规矩：任何改变布局的 ECO，应用完第一件事就是 legalize_placement，第二件事是 check_lvs，第三件才是布线。

常见坑 · remove_buf 把下游一起删了

现象：删掉一个冗余 buffer 之后，那片逻辑的功能全错，Formality 报一堆不等价。

原因：直接 remove_cell 会把输出 net 上的所有负载变成悬空（dangling）。正确顺序是：先记下输出 net 上的所有 sink，把这些 sink 改接到输入 net，最后才删单元。

这也是为什么 remove_buf 是三种动作里最容易出错的一种——能不改就不改。删单元省的那点面积，不值得冒功能错的风险。

06

让 PT 帮你算：`fix_eco_timing` 与 `write_changes`

手写清单适合几条违例。几百条时，让 PT 生成初稿。

tcl
# 作用：让 PT 生成 ECO 修复方案（只出建议，不改网表）# 用法：在 pt_shell 里，确认时序报告可信之后执行report_timing -delay_type min -max_paths 50 -significant_digits 4 > rpt/hold.rpt# 先自己看一眼：违例集中在哪些 endpoint、差多少 fix_eco_timing -type hold \               -methods {insert_buffer size_cell} \               -buffer_list {DELAY_X1 DELAY_X2 BUF_X2} \               -slack_lesser_than 0 \               -slack_greater_than -0.15# -type hold              只修 hold（一次只修一类）# -methods                允许的手段，按顺序尝试# -buffer_list            限定可插的单元，别让工具自由发挥# -slack_lesser_than 0    只修负 slack# -slack_greater_than     差太多的不修（换单元也救不回来，浪费面积） write_changes -format icctcl -output ./eco/eco_hold_r1.tcl# icctcl  = ICC2 可直接 source 的格式# innovus = Innovus 用的格式# ptsh    = PT 自己的格式（用于在 PT 里预演）
参数作用建议值为什么
-type修 setup 还是 hold一次一种混修会互相破坏（修 hold 加的延迟会让 setup 更差）
-methods允许的手段hold 优先 insert_buffer；setup 优先 size_cellhold 要"加延迟"，插单元最直接；setup 要"减延迟"，换大驱动更有效
-buffer_list可插的单元清单明确列出 2~3 种不限定会插进奇怪单元，后面 DRC/EM 难收
-slack_lesser_than / -greater_thanslack 区间0 到 -0.15只修"差一点点"的，符合 ECO 的适用边界

为什么 PT 生成的清单必须人工过一遍

PT 只懂时序，不懂物理。它可能建议：

  • 把一个单元换大两档，但那个位置旁边就是 macro，放不下。
  • 在已经拥塞率 95% 的区域插 5 个 buffer，布线器根本布不通。
  • 在一条跨电源域的路径上插单元，忘了 level shifter 的问题。

所以流程是：PT 出方案 → 人看一遍 → 删掉物理上不合理的 → 再应用。这十分钟是 ECO 里性价比最高的十分钟。

一个好的习惯：给每条改动写"预期收益"

PT 输出的清单只有"改什么"，没有"能修回多少"。人工审核时补一列预期收益（比如 +0.09），应用后对比实际值。

差异大的条目要回头看：是模型不准，还是这条路径上还有别的问题没被发现。这个对比做几轮，你对"什么改动值多少 ps"就有了手感——这是 ECO 工程师最核心的经验。

07

功能等价性：SVF 与 Formality 为什么必须

Formality形式等价性验证工具点击看解释

Synopsys 的形式验证（formal equivalence checking）工具。它把两份网表（参考设计 vs 实现后的设计）转成数学模型，用数学方法证明"对所有可能的输入，两者输出相同"。不需要测试向量，覆盖是完备的。

SVFSynopsys Verification File，验证引导文件点击看解释

综合和优化工具在改网表时，顺手写下的一份"我做了什么"的记录：哪些寄存器被合并了、哪些常数被传播了、哪些端口被重命名了。Formality 读它，才知道"这些差异是我允许的"。

为什么需要 SVF

综合工具会把你的 RTL 改得面目全非：寄存器复制、常数传播、无用逻辑删除、状态机重编码。这些改动在形式上是"不等价"的（结构完全不同），但功能等价。

Formality 如果只看两份网表，会报几万个 mismatch。SVF 就是那份"改动说明书"：

tcl
# 作用：Formality 读入 SVF，知道哪些差异是工具优化造成的、可以接受# 用法：fm_shell 里在 verify 之前设置set_svf ./svf/top.svf                      ;# 综合阶段产生的引导文件read_verilog -container r -libname WORK ./netlist/rtl_style.v   ;# 参考设计read_verilog -container i -libname WORK ./netlist/final.v        ;# 实现后设计set_top r:/WORK/top                        ;# 指定参考侧的顶层set_top i:/WORK/top                        ;# 指定实现侧的顶层match                                      ;# 按名字配对比较点verify                                     ;# 开始形式验证

ECO 的手工改动为什么不在 SVF 里

关键点：SVF 是综合/优化工具写的，你手工改的网表它不知道。

insert_buffer 插了一个延迟单元，逻辑上完全等价（buffer 不改变逻辑值），但结构上多了一个实例。Formality 在两边找不到对应点，就报 unmatched。

三种正确处理方式：

  1. 只允许物理类改动：插 buffer/delay cell、换同功能不同驱动。这类改动理论上等价，可以在 FM 里把这几条路径排除：
tcl
# 作用：把 ECO 插入的物理单元设为"不比较"，避免 FM 误报# 用法：只在确认改动是纯物理的（buffer/delay/size_cell）时使用set_dont_verify_points [get_cells -hier -filter "is_physical==true"]# 注意：这只对"确实等价"的改动合法；用它掩盖逻辑改动是造假
  1. 导出增量 SVF：部分流程支持在 PR 侧导出 ECO 的引导文件，和综合的 SVF 一起喂给 FM。工具命令名各版本不同，课程环境不验证，真实项目里问一下你们的 flow owner。
  1. 重新跑一遍综合级的等价性：把 ECO 后的网表当成新的实现，用原始 RTL 做参考，重跑 FM。最保险，也最慢。
常见坑 · 因为 FM 报错就把违例点设成 don't care

现象：Formality 报了 12 个 unmatched point，你为了让它变绿，把这 12 个点全 set_dont_verify_points。

问题：这 12 个点里可能有一个是真的改错了（比如 size_cell 时选错了功能不同的单元，把 AND 换成了 OR）。你把验证变成了"假装验证"。

正确做法：逐个看 unmatched 点的类型。是 buffer（等价，可排除）、是 size_cell（同功能不同驱动，可排除）、还是功能不同的单元（真错误，必须改回来）。

判断依据：report_unmatched_points 会列出每个点的类型和所在的逻辑锥（logic cone）。看不懂逻辑锥，就不要 waive。

下面是课程案例（12026 个单元，ICC2 流程，数据为教学整理，非工具原始输出）。

读法：三条都在 u_ctrl 的同一组状态寄存器上，slack 都在 −0.07 附近。required − arrival 约 0.07，说明数据来得太早（hold 违例的典型形态）。

第二步：定方案

方案做法代价选不选
A. 数据路径插延迟单元在 D 端前插 DELAY_X1（约 66~72ps）3 个单元，面积 +2.3µm²✅ 选这个

C. 换更大驱动的上一级size_cell对 hold 帮助不确定，可能更快❌ 不针对 hold
D. 换更小驱动的上一级size_cell 换小可能让数据更晚到⚠️ 备选，但影响扇出

选 A 的理由：hold 违例的本质是数据太早，最直接的办法就是让数据晚一点。插延迟单元只影响这一条路径，副作用最小。

回退与版本：ECO 的另一半价值

ECO 之所以敢做，是因为能退回去。没有回退能力的 ECO 是裸奔。

回退需要三样东西同时在：

要素具体做法缺了会怎样
数据库快照save_block -as snap_pre_eco_r1改坏了只能重跑全流程
清单版本eco.txt 进 git，commit message 写清修什么不知道该退回哪一版
报告基线改动前的 PT/DRC/FM 报告存档无法证明"只变好了，没变坏"
bash
# 作用：给每一轮 ECO 打一个可追溯的标记# 用法：在项目根目录执行，eco/ 下放清单，rpt/ 下放报告git add eco/eco_hold_r1.txt rpt/hold_before.rptgit commit -m "eco r1: fix 3 hold violations at u_ctrl/state_reg (WNS -0.0712)"# commit message 必须含：轮次、修什么、改动前 WNSgit tag eco_r1_before_apply# 打 tag，方便之后 diff 或回退到这一版清单

回退的决策点：出现以下任一情况就回退，不要在坏版本上继续修。

  • 应用后 WNS 反而更差（说明改动方向错了）。
  • Formality 出现无法解释的 mismatch（说明改错了逻辑）。
  • 新增 DRC 超过 20 条（说明局部布线失败）。

回退之后不要直接重写清单，先对比日志：fail 是哪一条、Incr 变化在哪、拥塞率变成多少。搞清楚原因再改第二版，否则会一直重复同一个错误。

回退怎么做

tcl
# 作用：回到 ECO 前的快照，从一个已知干净的状态重新开始# 用法：在 ICC2/Innovus 里执行；先把坏版本另存，别覆盖掉（它是证据）save_block -as snap_bad_r2          ;# 坏版本留一份，供事后分析open_block snap_pre_eco_r1          ;# 打开 ECO 前快照（库路径写法按项目约定）# 之后重新应用修好的清单：source ./apply_eco.tcl

注意 save_block -as snap_bad_r2 这一步。很多人回退时直接覆盖，结果"为什么坏"这个问题永远查不清。坏版本和好版本一样有价值。

回退的成本要提前算清：一次全流程重跑两天，一次 ECO 回退加重做两小时。所以 ECO 的正确心态不是"一次做对"，而是"错了能在两小时内重来"——这正是快照和 git 存在的意义。

10

ECO 的四条纪律

  1. 一次只改一类问题。先 hold，回签；再 setup，回签。混在一起改，出问题不知道是谁的锅，也没法判断哪一类改动带来了副作用。
  2. 每轮都复算，不许"攒着一起验"。改 10 条复算一次，和改 100 条复算一次，出错时的排查成本差 10 倍。
  3. 记录版本。清单、报告、快照名三者要能对应上（eco_hold_r1.txt ↔ snap_pre_eco_r1 ↔ rpt/hold_r1_before.rpt）。
  4. 留回退点。每次 save_block 都用一个有意义的名字，不用 tmp1、test2。

这四条听起来像管理要求，其实是技术约束：ECO 的每一步都可能引入新问题，没有隔离和复算，你无法定位是哪一个改动引入的。

Legalization合法化点击看解释

把标准单元的坐标对齐到合法的行（row）和轨道（track），并消除重叠。ECO 插入的新单元初始位置是浮点的，必须合法化才能布线。

自测：先自己想，再点开答案
ECO 相比全流程重跑，核心优势是什么？
改动面小、时间短、风险可控：只动必须动的单元，不重跑综合与全局布局，影响范围可枚举。
三类 ECO（RTL / 门级 / metal-only）的区别？
RTL ECO 改代码要重跑综合；门级 ECO 改网表不动 RTL；metal-only 只用 spare cell 改金属层，不动 base layer，掩膜成本最低。
为什么 metal-only ECO 能省一大笔钱？
只重做 1~2 层金属掩膜，不重做晶体管层，也不用报废在制批次；代价是只能用预埋的 spare cell。
为什么 PT 生成的 ECO 建议不能直接 source？
PT 只看时序不看物理：可能建议换大单元但位置放不下，或插 buffer 但区域已拥塞，必须人工筛一遍。
insert_buffer 之后为什么必须 legalize_placement？
新插单元坐标是浮点、可能与其他单元重叠，不合法化会产生 spacing DRC 和短路。
ECO 后为什么必须重跑 Formality？
手工改动不在 SVF 引导文件里，等价性从未被验证；不重跑等于没验证，可能改错逻辑。
SVF 是什么，为什么它能消除 FM 的误报？
综合/优化工具写下的改动说明（寄存器合并、常数传播等），FM 读它才知道哪些结构差异是允许的。
FM 报 unmatched 时，什么情况可以设 dont_verify_points？
只有确认改动是纯物理等价（插 buffer、同功能换驱动）时才可以；用它掩盖逻辑改动是造假。
修完 hold 为什么必须重看 setup？
插延迟单元让数据更晚到，hold 变好但 setup 会变差；只看 hold 会漏掉新引入的 setup 违例。
ECO 出现什么情况应该回退而不是继续修？
WNS 反而变差、FM 有无法解释的 mismatch、新增 DRC 超过阈值（如 20 条）——说明方向错了，先回退再分析。
