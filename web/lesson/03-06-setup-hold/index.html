setup 与 hold：用"拍照"讲明白时序

Setup & Hold

时序只有两条不等式，却难住大多数人。这一课用照相机讲清成立条件，把 setup/hold 公式逐项推一遍，用波形图说明"同一条路径为什么怕最长又怕最短"，再手算一个 setup 违例和一个 hold 违例。

约 55 分钟 课表学时 6 时序setupholdskewOCVcorner
01

触发器就是一台照相机

本章目标学完这一课，你能不看资料写出 setup 与 hold 两条不等式，逐项说出每一项的物理含义，手算一条路径的两个 slack，并解释为什么 hold 违例不能靠降频解决。

数字电路里，绝大多数数据在触发器（flip-flop，简称 FF）之间传递。触发器的工作方式像一台定时拍照的相机：

text
        ┌─────────┐数据 D ─▶│         │        │  触发器  │──▶ 输出 Q时钟 ──▶│         │        └─────────┘           ▲      时钟上升沿 = 按下快门

快门按下的那一瞬间，D 端的数据必须已经稳定，并且之后还要保持一小会儿稳定。 否则拍出来的照片是糊的——触发器内部采到一个既不是 0 也不是 1 的中间电平，输出可能振荡，也可能停在一个随机的值上。这个状态叫亚稳态（metastability）。

为什么需要"前后都稳定"？因为触发器内部不是一瞬间完成采样的。它由主、从两级锁存器构成：时钟沿到来时，主锁存器先把 D 的值"扣住"，再过一小段时间传给从锁存器。在这段内部翻转的时间里，D 端如果还在动，扣住的值就不可靠。

于是有了三个时间参数：

参数中文含义40nm 典型值
Tcq时钟到输出延迟时钟沿到 Q 端出新值的延迟0.08~0.15ns
Tsetup建立时间时钟沿之前数据必须稳定的时长0.05~0.15ns
Thold保持时间时钟沿之后数据必须稳定的时长0.02~0.10ns

用相机打比方：Tsetup 是"按快门前要留的对焦时间"，Thold 是"快门关闭前别让人动"，Tcq 是"拍完之后出照片要等的时间"。

两个检查，管的是两件完全不同的事：

  • setup 检查"数据来得够不够早" → 决定这颗芯片最快能跑多快（频率上限）。
  • hold 检查"数据来不来得及太早" → 决定这颗芯片在任何频率下能不能正确工作（功能正确性）。

这个区别是整节课的骨架。setup 违例，降频就能救；hold 违例，降频一点用都没有。

Setup Time建立时间点击看解释

时钟有效沿到来之前，数据必须已经稳定的最短时间。不满足叫 setup violation（建立时间违例）。
它的物理来源是触发器内部主锁存器的开启时间：数据要在锁存器"关门"之前到达并稳定。
注意区分两个词：Tsetup 是触发器的一个固定参数（查库），setup slack 是这条路径还剩多少余量（算出来的）。

Hold Time保持时间点击看解释

时钟有效沿到来之后，数据必须继续保持稳定的最短时间。不满足叫 hold violation（保持时间违例）。
物理来源是从锁存器关门的时间：数据太早变化，会把还没锁稳的值冲掉。
hold 违例一旦在硅片上真的发生，就是功能错误（抓到的是新值或亚稳态），而且往往只在特定电压温度下出现，测试很难覆盖。

Clock-to-Q (Tcq)时钟到输出延迟点击看解释

时钟沿到达触发器时钟端，到 Q 端输出稳定为新值之间的延迟。
它同时出现在 setup 和 hold 两条公式里，但作用相反：setup 里它是"必须等待的成本"，hold 里它是"帮忙推后数据的延迟"。

工作场景 · 流片前三天的两个负数

Tapeout review，投影上两行：

text
Path Group   Type    WNS      TNS     Violating Pathsclk_core     setup   -0.12    -3.40   47clk_core     hold    -0.04    -0.31   12

组长问三句：

  1. "setup 这 120ps 差在哪一段？是 cell 还是 net？"
  2. "hold 这 40ps，能不能靠把频率降到 400MHz 解决？"
  3. "如果两个都要修，先动哪个？改完怎么证明没把另一个弄坏？"

第一问要会拆延迟构成；第二问考的是"hold 与周期无关"；第三问考的是修复顺序——这三问的答案，全部来自这一课的两条不等式。

工作中怎么用：setup/hold 是 STA（静态时序分析）工程师和 PR 工程师的共同语言。PR 在每个阶段结束跑一次 timeDesign，把 WNS/TNS 报给项目组；STA 在签核时用带 OCV 的多 corner 报告复核。两个人看到的 slack 不一样是正常的（corner、derate、提取精度不同），但如果差超过 50ps，就要一起查约束。

02

setup 在算什么

一条路径从"发射触发器"到"接收触发器"，中间经过组合逻辑：

text
      ┌────┐        ┌──────────┐        ┌────┐CLK ─▶│ FF │──Q────▶│ 组合逻辑  │───────▶│ FF │◀─ CLK      │ A  │        │ (延迟 T) │        │ B  │      └────┘        └──────────┘        └────┘      发射                                捕获

数据在第 0 个时钟沿从 A 出发，要在第 1 个时钟沿（一个周期之后）被 B 稳稳抓住。

把这条时间线画出来，每一项就都能对上号了（数字取下面手算的例子，先不计 skew 和 uncertainty）：

text
发射沿                                                      捕获沿  │                                                            │  ├─ Tcq 0.12 ─┤                                               │  │            ├──────── Tlogic_max 0.95 ────────┤             │  │            │                                  ├ Tsetup ┤    │  ▼            ▼                                  ▼  0.09 ▼    ▼ t=0         0.12                               1.07     1.16  1.25                                             数据到达 D 端  └ 必须已稳定

读法：数据 1.07ns 到达，加上 0.09ns 的建立时间，最晚 1.16ns 必须站稳；捕获沿在 1.25ns。中间那 90ps 就是这条路径的余量（还没扣 skew 和 uncertainty）。

推导只有一步：数据到达时间 + 建立时间 ≤ 捕获沿到来的时间。

text
T_launch + Tcq + Tlogic_max + Tsetup ≤ T_capture + Tclk

把时钟到达时间之差记为 skew：

text
Tskew = T_capture − T_launch        （捕获端晚到为正）

代进去，整理成最常见的形式：

text
Tclk ≥ Tcq + Tlogic_max + Tsetup − Tskew

再考虑两件不能忽略的事：时钟本身的抖动，和工艺偏差带来的不确定性，合并成 Tunc（uncertainty，时钟不确定性）：

text
Tclk + Tskew ≥ Tcq + Tlogic_max + Tsetup + Tunc

做时序预算时，我们并不知道 skew 会是正还是负，只能按对 setup 最不利的情况（捕获端早到，即 Tskew 为负）预留，于是把它和 uncertainty 合并成一项：

text
Tclk ≥ Tcq + Tlogic_max + Tsetup + Tskew_margin     ← 预算式Tskew_margin = |Tskew_worst| + Tunc

这就是课表上那条公式的来历。注意它是"预算式"，不是"计算式"——真算 slack 的时候，skew 的符号必须按实际方向代入，否则会算反。

slack 的定义是"实际 − 要求"，setup 里就是"留给数据的时间 − 数据实际用的时间"：

text
setup slack = Tclk + Tskew − Tcq − Tlogic_max − Tsetup − Tunc

正数有余量，负数违例。这一条式子拆开看，每一项都有明确的抓手：

项变大时 slack 怎么变工程上怎么动它
Tclk变大（变好）降频（最后手段）
Tskew捕获端晚到则变好CTS / useful skew
Tcq变小（变差）换触发器（很少动）
Tlogic_max变小（变差）upsize、换 LVT、拆逻辑、缩短线
Tsetup变小（变差）换库单元（很少动）
Tunc变小（变差）靠约束和实测校准

setup 的敌人是"最长的那条延迟"。 同一对触发器之间，如果有多条路径（不同 bit、不同逻辑分支），工具只检查最慢的那一条——因为只有它能把这个周期撑爆。

工作中怎么用：报 setup 违例时，第一句说差多少，第二句说差在 cell 还是 net。只说"时序不收敛"，别人帮不上忙；说"差 120ps，其中 85ps 在三级 NAND 上"，讨论立刻能落到具体手段。

03

hold 在算什么

hold 检查的是同一个时钟沿上的竞争。

第 0 个沿，A 发出新数据；同一时刻，B 正在抓上一个周期的旧数据。新数据如果跑得太快，在 B 还没抓稳的时候就到了 D 端，就会把旧值冲掉。

text
第0个沿 = 发射沿 = 捕获沿（同一个）  │  ├── Tcq ──┤  │ 0.10    ├── Tlogic_min ──┤  │         │      0.04      │  ▼         ▼                ▼ t=0      0.10             0.14  ← 新数据到达 B 的 D 端                            │                     Thold 0.06                            │                            ▼                          0.06  ← 旧值必须保持到这个时刻之后

要求只有一句：新数据到达的时刻，必须晚于"捕获沿 + 保持时间"。

text
T_launch + Tcq + Tlogic_min ≥ T_capture + Thold

代入 skew 定义（Tskew = T_capture − T_launch）：

text
Tcq + Tlogic_min ≥ Tskew + TholdThold ≤ Tcq + Tlogic_min − Tskew

slack 形式：

text
hold slack = Tcq + Tlogic_min − Tskew − Thold

这条式子里没有 Tclk。 这不是推导时漏掉了，是物理上真的不出现：发射沿和捕获沿是同一个沿，周期怎么变，两个沿都一起移动，它们之间的相对关系一点没变。

hold 的敌人是"最短的那条延迟"。同一对触发器之间有多条路径时，工具检查最快的那一条——因为它最容易冲到前面去。

对照一下两条式子，会发现它们像镜像：

setuphold
看哪条路径最慢（Tlogic_max）最快（Tlogic_min）
捕获沿下一个周期同一个周期
公式里有周期吗有没有
与频率的关系频率越高越容易违例完全无关
时钟晚到的效果帮忙（多给时间）添乱（更早被冲）
违例的后果跑到某个频率以下就正常任何频率都错
Slack裕量点击看解释

"实际时间 − 要求时间"。正数表示还有余量，负数表示违例。
setup slack = Tclk + Tskew − Tcq − Tlogic_max − Tsetup − Tunc
hold slack = Tcq + Tlogic_min − Tskew − Thold
报告里按数值排序，最差的那个叫 WNS（Worst Negative Slack）。WNS 为负就不能签核。

Skew时钟偏斜点击看解释

同一个时钟到达两个触发器的时间差。本课统一用 Tskew = T_capture − T_launch，捕获端晚到为正。
正 skew：对 setup 有利（多给时间），对 hold 不利（旧值更早被冲）。
负 skew：反过来。
有些教材用相反的符号定义。看别人的公式前，先确认他那句"正 skew"指的是哪一端晚到——符号搞反是新手算错时序的第一原因。

工作中怎么用：看到 hold 违例先看 Tskew，别先看 Tlogic_min。hold 违例里时钟的贡献通常比数据路径大——一棵没平衡好的树能让几十条短路径同时违例，而数据路径的问题一般只影响一两条。

04

同一条路径，setup 看最长、hold 看最短

到这里很多人会产生一个错觉：一条路径要么"太慢"（setup 违例），要么"太快"（hold 违例），修一头就行。

真实情况是：同一条路径，在工艺、电压、温度不同的情况下延迟能差一倍，于是它同时被两头夹。

把"数据到达 D 端的时刻"画成一个区间：左端是最快情况（Tmin），右端是最慢情况（Tmax）。两次检查各看一端。

text
① setup 看右端（最慢的那次）   0        0.30                                      1.90   2.00  │          │                                         │      │  ├──────────██████████████████████████████████████████──────┤  │         Tmin                                      Tmax   capture 沿  │                                       1.85 │  │                                            ▼ Tsetup = 0.15  │                          数据必须落在这条线左边 → 1.90 越界，违例 50ps ② hold 看左端（最快的那次）   0     0.08      0.30  │      │         │  ├──────┼─────────████████████████████ ...  │      │         Tmin  │      ▼ Thold = 0.08  │   数据必须落在这条线右边 → 0.30 满足，余量 220ps

一条路径的延迟必须落在一个窗口里：

text
下界（hold）：数据到达 ≥ Thold + Tskew上界（setup）：数据到达 ≤ Tclk + Tskew − Tsetup窗口宽度 = Tclk − Tsetup − Thold

窗口宽度只跟周期有关。周期越短，窗口越窄；窄到比"延迟的变化范围"（Tmax − Tmin）还小时，这条路径就无解了——不管你怎么调，它要么太快要么太慢。

这就是先进工艺的难点：Tmax / Tmin 的比值随工艺进步不断变大（低压下更明显），而周期在缩短，两头一起挤。

用数字感受一下。周期 2.0ns，Tsetup=0.15，Thold=0.08：

text
窗口 = 2.0 − 0.15 − 0.08 = 1.77ns延迟变化范围（上例）= 1.90 − 0.30 = 1.60ns余量 = 1.77 − 1.60 = 0.17ns   ← 只剩 170ps 可以分给 skew 和 uncertainty

如果周期降到 1.6ns：

text
窗口 = 1.6 − 0.23 = 1.37ns变化范围还是 1.60ns > 1.37ns  →  物理上无解

这时候不是"修得不够好"，是这条路径在这个频率下不可能收敛。 唯一出路是减少延迟的变化范围（减少逻辑级数、缩短线长）或者换更快的单元。

记住这句话：setup 限制"最慢"，hold 限制"最快"，所以修 setup（让最慢的变快）经常顺手把 hold 弄坏——因为你把整条路径都推快了。

工作中怎么用：判断一条路径"还有没有救"，就算窗口宽度和延迟变化范围这两个数。窗口减范围小于 0 是物理无解，别再让人加班换单元；大于 0 但很小（<100ps），说明这条路径对 corner 极其敏感，签核时要重点盯。

05

手算两个完整例子

两个例子来自同一个设计，条件先列清楚：

参数值说明
时钟周期1.25ns800MHz
Tcq0.10~0.12ns触发器时钟到输出（不同单元不同）
Tsetup0.09ns建立时间
Thold0.06ns保持时间
Tunc0.07ns时钟不确定性（jitter + OCV 余量）

例子一：setup 违例

一条从 u_alu/reg_a 到 u_alu/reg_b 的路径，最慢 corner 下：

  • Tlogic_max = 0.95ns（cell 0.62 + net 0.33）
  • Tskew = −0.03ns（捕获端早到 30ps，对 setup 不利）

代入：

text
setup slack = 1.25 + (−0.03) − 0.12 − 0.95 − 0.09 − 0.07            = 1.22 − 1.23            = −0.01ns        ❌ 违例 10ps

差得不多，但签核不认"差不多"。10ps 在下一版提取后可能变 −40ps。

修法有三个方向，代价不同：

手段怎么算结果代价
逻辑链上一级 upsizeTlogic 0.95 → 0.90slack +0.04ns面积 +2%，功耗 +1%
缩短那根 0.33ns 的 netnet 0.33 → 0.25slack +0.07ns要挪位置，可能引新拥塞
把周期放到 1.3ns（降频到 769MHz）Tclk +0.05slack +0.04ns性能下降 3.8%，客户不一定接受

注意第三行：降频确实能"修"setup，因为 Tclk 在公式里。这也是为什么 setup 违例本质上是"性能问题"，而不是"功能问题"。

例子二：hold 违例

同一设计里另一对相邻触发器，短路径：

  • Tcq = 0.10ns（这颗触发器驱动能力更强，Tcq 比例子一那颗小 20ps）
  • Tlogic_min = 0.04ns（几乎直连，只有一小段线）
  • Tskew = +0.12ns（捕获端晚到 120ps——它的时钟在树里深了一级）

代入，逐项写清楚（容易把 Tcq 和 Tskew 混在一起）：

text
Tcq          = 0.10ns   （这颗触发器的时钟到输出）Tlogic_min   = 0.04ns   （最短路径延迟）Tskew        = +0.12ns  （捕获端晚到）Thold        = 0.06ns hold slack = 0.10 + 0.04 − 0.12 − 0.06           = 0.14 − 0.18           = −0.04ns     ❌ 违例 40ps

两个例子对照着看，能读出三件事：

  1. setup 违例的路径和 hold 违例的路径通常不是同一条。前者是长逻辑链，后者是短直连。
  2. hold 违例的元凶常常是时钟（Tskew = +120ps 一项就吃掉了 120ps 的余量），而不是数据路径。所以见到大面积 hold 违例，先看时钟树，而不是先插 delay cell。
  3. 两条式子里 Tcq 的位置不同：setup 里它在"成本"一侧，hold 里它在"收益"一侧。同一个参数，两个方向。

修 hold 只有两条路：给数据路径加延迟（插 delay cell），或者让捕获时钟早点到（减 skew）。前者每条路径几十 ps，后者要动时钟树。

如果给这条路径插一个 0.08ns 的 delay cell：

text
hold slack = 0.10 + (0.04 + 0.08) − 0.12 − 0.06 = +0.04ns  ✅

但代价是 setup 变差 0.08ns——如果这条路径的 setup slack 只有 +0.05，插完就变 −0.03。这就是下一课"先修 setup 再修 hold"的全部理由。

常见坑 · hold 违例靠降频解决

现象：hold slack −0.04ns，新人把周期从 1.25ns 改成 2.5ns，重跑报告，发现 hold 还是 −0.04ns。

原因：hold 公式 Tcq + Tlogic_min − Tskew − Thold 里没有 Tclk。周期翻倍，五个量一个都没变，slack 当然一个字都不变。

更迷惑的是：降频之后 setup 从 −0.01 变成 +1.24，整体报告"变绿了"，让人误以为 hold 也好了。绿的只是 setup 那一栏。

正确做法：hold 只能靠"给数据加延迟"或"减小时钟 skew"修，见下一课。

判断依据（面试常问）：看公式里有没有周期。有 → 降频有效；没有 → 降频无效。

工作中怎么用：手算的意义不是替代工具，是让你能核对工具。工具报 −0.01ns、你手算 −0.01ns，说明你理解它的口径；差 50ps 以上，就要查 corner、derate 或时钟路径的口径是不是不一样。

06

为什么 hold 不能靠降频解决

上面给了结论，这里补三条论证，因为这是最容易被"经验"带偏的一条。

论证一：公式里没有周期。

text
hold slack = Tcq + Tlogic_min − Tskew − Thold

五个量全部与 Tclk 无关。数学上，改 Tclk 不改变这个式子的值。这不是"影响很小"，是"精确地没有影响"。

论证二：物理上两个沿一起动。

hold 检查的是"第 N 个沿发射、第 N 个沿捕获"。周期变长，这两个沿在时间轴上都往后挪了同样的距离，它们之间的间隔恒等于 0。而 setup 检查的是"第 N 个沿发射、第 N+1 个沿捕获"，间隔恰好是一个周期——所以周期一变，setup 立刻变。

用一个类比：hold 是"两个人同时出门，谁先到路口"；setup 是"一个人先走，另一个人一个小时后才出门"。把"一小时"改成"两小时"，同时出门的两个人还是同时到。

论证三：数值上可以验证。

把例子二的周期从 1.25ns 改到 12.5ns（降频 10 倍），其他四个量不变：

text
hold slack = 0.10 + 0.04 − 0.12 − 0.06 = −0.04ns   ← 一模一样setup slack = 12.5 − 0.03 − 0.12 − 0.95 − 0.09 − 0.07 = +11.24ns   ← 早就过了

十倍周期换来 hold 上 0ps 的改善。这就是"用错了工具"的典型。

还有一个反直觉的补充：降频经常伴随降压（DVFS，动态电压频率调节）。电压降低后单元变慢，Tlogic_min 变大，hold 反而变好了。于是有人得出"降频能修 hold"的错误结论——真正起作用的是电压，不是频率。把电压调回去，hold 立刻回到 −0.04。

同理，升频也不会让 hold 变差。hold 违例在 fastest corner（FF、高压、低温）最严重，跟你跑多少兆赫兹无关。

PVT Corner工艺角点击看解释

Process（工艺）、Voltage（电压）、Temperature（温度）三者的组合。芯片必须在所有组合下都正确工作，所以同一版设计要跑很多个 corner。
常见命名如 ss_0p99v_125c：slow-slow 工艺、0.99V、125°C。setup 用最慢的 corner，hold 用最快的 corner，两者永远不是同一个文件。

工作中怎么用：这条结论最常见的用途是挡住错误的需求。产品问"降频能不能解决 hold"，你要能当场用公式回答"不能，只有延迟和电压能"；说不清，团队就会花一周做一次注定无效的降频验证。

07

PVT corner 与 OCV：为什么要算好几遍

一条路径的延迟不是一个数，是一个范围。范围和两件事有关：芯片制造出来"有多快"，以及同一条路径上不同单元"快得一致不一致"。

PVT 决定整体快慢。

维度极端对谁最不利
Process（工艺）SS（慢） / FF（快）setup 怕 SS，hold 怕 FF
Voltage（电压）标称 −10% / +10%setup 怕低压，hold 怕高压
Temperature（温度）高温 / 低温传统上 setup 怕高温；先进节点低压下可能反过来

于是同一个设计至少跑两个方向的 corner：

text
setup 看：ss corner + 低电压 + 高温（最慢）hold  看：ff corner + 高电压 + 低温（最快）

为什么不能只跑一个 corner？ 因为 setup 要"发射慢、捕获快"，hold 要"发射快、捕获慢"，两个要求方向相反，任何一个 corner 都不可能同时是最悲观。

text
setup 需要的悲观组合：launch 最慢  +  capture 最快hold  需要的悲观组合：launch 最快  +  capture 最慢

这是 OCV 的起点。OCV（On-Chip Variation，片上偏差）说的是：同一颗芯片上，不同位置的单元速度有 ±5% 左右的差异（典型值），签核时必须假设"最坏的那种搭配"。

具体做法是给延迟乘系数（derate）：

tcl
# 作用：设置 OCV 悲观系数——发射路径按 1.05 变慢，捕获路径按 0.95 变快# 用法：STA 工具里读入库和网表之后设置；数值来自工艺厂建议，不是自己拍的set_timing_derate -late  1.05        ;# 慢的往更慢算（发射侧、setup 用）set_timing_derate -early 0.95        ;# 快的往更快算（捕获侧、hold 用）

手算一次 derate 的影响。一条 setup 路径：数据路径 1.50ns，时钟路径 0.60ns，derate ±5%：

text
数据路径变慢：1.50 × 1.05 = 1.575   →  +75ps捕获时钟变快：0.60 × 0.95 = 0.570   →  −30ps合计损失：75 + 30 = 105ps

105ps 的损失，相当于把 slack 直接扣掉一个数量级。 一个原本 +0.10ns 的设计，加上 OCV 就变 −0.005ns。这就是为什么"没加 OCV 时全绿，加了 OCV 全线飘红"是每个新人都要经历一次的事。

更精细的做法是 AOCV（按逻辑深度给不同 derate）和 POCV/LVF（按统计分布算），原理是"路径越长，相对偏差越小"，细节在阶段六的 STA 深水区课。这里只需要记住一句：derate 不是保守主义，是物理事实的数学表达。

常见坑 · 用 typ corner 看时序，报告全绿，签核挂掉

现象：place 之后跑 report_timing，WNS +0.35ns，心情很好。签核时 STA 用 ss_0p99v_125c 加 OCV 重跑，WNS −0.28ns。

原因：typ（typical）corner 是"标称速度"，真实芯片一定比它慢或快；再加上 OCV 的双向扣减，0.35 到 −0.28 差 0.63ns 完全正常。

处理：中间过程可以用 typ 看趋势，但任何"能不能收敛"的判断都必须用 signoff corner。项目开工时就要问清楚：签核用哪几个 corner、derate 多少、要不要 AOCV——这三个问题答不上来，你做的所有时序判断都是猜的。

工作中怎么用：每个阶段的时序报告必须标明 corner 和 derate，否则数字没有意义。交接时写"ss_0p99v_125c + OCV 5%"，不要只写"WNS +0.1"——前者别人能复现，后者只能猜。

08

时钟不确定性（uncertainty）从哪来

Tunc 是公式里最"虚"的一项，但它经常是压死骆驼的最后一根稻草。它的来源有四个：

  1. PLL 抖动（jitter）：时钟源本身不是完美的，每个周期的长度会有几十 ps 的随机波动。PLL 的数据手册会给 period jitter 和 cycle-to-cycle jitter。
  2. 时钟树上的 OCV 残余：CTS 之后 skew 是一个确定值，但同一棵树上不同分支的延迟还会随工艺波动，这部分没有被 skew 完全覆盖。
  3. 电源噪声：IR drop 让单元供电电压瞬时下降，延迟变长。开关活动密集的区域，这个效应能到几十 ps。
  4. 建模误差：提取的寄生参数、库的查表插值、时钟树的耦合电容估算，都有误差。

它和 skew 的区别必须分清：

skewuncertainty
性质确定的空间差随机 + 未建模
能不能测能（CTS 报告里有）不能直接测，只能估
能不能消除CTS 可以压到几十 ps永远存在
怎么进公式单独一项，带符号单独一项，恒为不利

给多少？经验值是周期的 5%~10%（典型值）。2ns 周期给 100~150ps 很常见。给的时候要区分 setup 和 hold：

tcl
# 作用：给时钟设不确定性（jitter + OCV 余量），setup 和 hold 分开给# 用法：SDC 里 create_clock 之后设置；数值来自 PLL 手册 + 项目余量约定set_clock_uncertainty 0.10 [get_clocks clk_core]          ;# setup 用 100ps（周期 2ns 的 5%）set_clock_uncertainty -hold 0.05 [get_clocks clk_core]    ;# hold 用 50ps，通常比 setup 小

为什么 hold 给小一些？因为 hold 检查已经用了 fastest corner（最保守的延迟），jitter 在同一个沿上的影响远小于跨周期的影响。但"给小"不等于"给 0"——给 0 等于假设时钟完美，硅片上一定会打脸。

给多了的代价：白修时序，多插 buffer，面积功耗上涨，甚至把一个本来能收敛的设计判死。 给少了的代价：硅片上偶发失效，测试覆盖不到，客户手上出事。

这一项的取值必须由项目组统一定，不能由个人拍。 你在报告里看到 Tunc = 0.10，要能说出它可能由哪几块拼成。

常见坑 · 为了让 WNS 好看，把 uncertainty 设成 0

现象：WNS −0.06ns，你把 set_clock_uncertainty 改成 0，报告立刻变 +0.04，签核"通过"。

原因：uncertainty 是给物理世界留的余量。设成 0 只是把"未知"从账本上划掉，芯片上的 jitter、IR drop、提取误差一个都没消失。

后果：这个设计在实验室常温常压下能跑，量产后在高温低压的片子上偶发算错，而且测试程序很难复现——因为你把唯一的保护垫抽掉了。

处理：uncertainty 只能由项目统一规定（问 STA 负责人或查时序约束规范）。个人改这个数等于改签核标准，比改时序本身严重得多。

工作中怎么用：这一项是签核争议的高发区。PR 觉得给多了修不动，STA 觉得给少了不保险。解决方式不是吵，是把来源拆开算：jitter 多少（PLL 手册）、树上的 OCV 残余多少、电源噪声多少（IR 分析），加起来看合不合理。

Clock Uncertainty时钟不确定性点击看解释

时序公式里为"时钟不完美"预留的余量，包含 PLL 抖动、时钟树 OCV 残余、电源噪声引起的延迟变化、建模误差。
它在 setup 和 hold 里取值不同，且恒为不利项（不像 skew 有正负）。给多少由项目统一规定，通常 5%~10% 周期。

09

setup 和 hold 冲突时，谁优先

冲突有两种，性质完全不同。

第一种：同一条路径两头夹。 前面"窗口"那一节讲过——Tmax 太长导致 setup 违例，Tmin 太短导致 hold 违例。这种冲突的根源是"延迟变化范围 > 窗口宽度"，通常出现在周期已经逼近工艺极限、或者这条路径的逻辑级数太多的时候。

这种冲突没有修复顺序能救，只能改结构：减少级数、缩短线长、换更快的单元，把 Tmax − Tmin 压下来。如果压不下来，就是频率定高了。

第二种：修一头会弄坏另一头。 这才是日常遇到的：

动作对 setup对 hold为什么
插 delay cell（修 hold）变差变好净加延迟，Tmax 和 Tmin 同时变大
upsize / 换 LVT（修 setup）变好变差净减延迟，Tmax 和 Tmin 同时变小
缩短线长 / 挪近变好变差同上
让捕获时钟晚到（useful skew）变好变差Tskew 变大，两个公式符号相反
让捕获时钟早到变差变好同上

表格里每一行都是同一件事的两面：延迟只有一个，setup 和 hold 对它的要求相反。

所以优先级不是"哪个更重要"，而是"哪个必须先做"。答案是：

先修 setup，再修 hold。

三条理由，按强度排序：

  1. 修 hold 的动作一定恶化 setup，所以它必须排在最后。 插进去的 delay cell 会同时抬高 Tmax，如果先修 hold，后面修 setup 时又要把这些延迟拆掉重来。这是一个逻辑上必然返工的顺序。
  2. 修 setup 的动作会消耗 hold 余量，所以 hold 必须在"网表定稿"之后修一次。 你先修 setup，hold 余量被吃掉一部分，然后一次性把剩下的 hold 违例修掉；反过来做，hold 修完就被 setup 修复全部推翻。
  3. 两者的量级不同。 setup 违例往往几十上百条、分布在长路径上，要动网表结构；hold 违例往往集中在少数短路径上，用 delay cell 局部解决。先做影响面大的，后做影响面小的，这是所有工程流程的通用原则。

有一条硬禁忌：不要用"全局牺牲一头"的方式修另一头。 比如给整个时钟域加 100ps latency 去修 setup——那会让这个域所有路径的 hold 一起变差 100ps。也不要用降频"修" hold（无效），或者用升压"修" setup（会毁掉 hold 的 corner 假设）。

最后是签核标准：不是"两个 slack 都 ≥ 0"，而是两个都留出余量：

text
setup 目标：WNS ≥ +50~100ps（在 signoff corner + OCV 下）hold  目标：WNS ≥ +30~50ps

刚好 0 的设计，任何一点提取误差、任何一次 ECO，都会让它变负。签核是"留出安全边际"，不是"压线通过"。

工作场景 · 为什么组长坚持"先 setup 后 hold"

你花了两小时把 12 条 hold 违例修干净，每条插了 60~80ps 的 delay cell。组长看了一眼说："setup 那 47 条还没动呢，你这活儿白干了。"

你不服：hold 不是更严重吗？功能错啊。

他说：你去修 setup，修完再看 hold。

你 upsize 了 30 个单元、挪了 8 个位置、删了 5 个 buffer。重跑：

text
hold WNS: −0.04 → −0.11    （12 条变 31 条）

原因很直接：upsize 和删 buffer 都在减延迟，Tmin 一起变小，你刚加的那点余量被吃光了。

这不是"谁更重要"的问题，是"顺序决定要不要返工"的问题。

工作中怎么用：排修复计划时把"谁先谁后"写进脚本注释，并给每一步留门槛（setup 到 −20ps 才准动 hold）。这样即使换人接手，也不会有人半夜心血来潮先修 hold。

动手动手：写一个能算两头的时序计算器

任务：把两条公式写成脚本，验证三件事——降频救 setup 不救 hold；skew 符号对两头的影响相反；hold 违例需要多少 delay cell。

bash
# 作用：算一条路径的 setup/hold slack，并做三组对照实验# 用法：任意目录 python3 直接跑；改参数看结论怎么变python3 - <<'EOF'def slacks(tclk, tcq, tlogic_max, tlogic_min, tsu, th, skew, unc):    setup = tclk + skew - tcq - tlogic_max - tsu - unc      # setup：捕获端晚到为正，帮忙    hold  = tcq + tlogic_min - skew - th                     # hold：同样的 skew，添乱    return setup, hold base = dict(tcq=0.12, tlogic_max=0.95, tlogic_min=0.04, tsu=0.09, th=0.06, skew=-0.03, unc=0.07)for tclk in (1.25, 2.50, 12.5):                              # 三档周期：800M / 400M / 80M    s, h = slacks(tclk, **base)    print("Tclk=%5.2f  setup=%+.3f  hold=%+.3f" % (tclk, s, h)) print("--- 只改 skew 符号 ---")for skew in (-0.03, 0.0, +0.03):    s, h = slacks(1.25, **{**base, "skew": skew})    print("skew=%+.2f  setup=%+.3f  hold=%+.3f" % (skew, s, h)) print("--- 修 hold 需要多少 delay cell ---")s, h = slacks(1.25, **{**base, "skew": +0.12})print("当前 hold=%+.3f，需要插入 %.3f ns 才能到 0" % (h, -h))EOF

预期：第一组三行里，setup 从 −0.010 变成 +1.240 再到 +11.240，而 hold 三行恒为 +0.130——周期根本不进这个公式；第二组 skew 从 −0.03 加到 +0.03 时，setup 从 −0.010 升到 +0.050，hold 从 +0.130 降到 +0.070，两个方向正好相反；第三组算出 hold = −0.020，至少要插 0.02ns 才能到 0，实战要留余量，插 0.05~0.08ns。

再走一步：把 unc 从 0.07 改成 0.15，看 setup 掉多少；再想想真实项目里这 80ps 差价意味着多少条违例。

过关标准：能指着输出说出三句话——"周期变 10 倍 hold 一点没动"、"skew 对两头符号相反"、"修 hold 的延迟会原封不动加到 setup 上"。

自测：先自己想，再点开答案
setup 和 hold 分别检查什么？用照相机比喻说一遍。
setup 检查按快门前数据是否已稳定足够久（来得够早）；hold 检查快门关闭前数据是否保持稳定（别太早变）。前者限制频率上限，后者决定功能对不对。
写出 setup slack 与 hold slack 的完整表达式，并指出哪个含周期。
setup = Tclk + Tskew − Tcq − Tlogic_max − Tsetup − Tunc；hold = Tcq + Tlogic_min − Tskew − Thold。只有 setup 含 Tclk。
为什么 hold 公式里没有时钟周期？
因为发射和捕获是同一个时钟沿，周期变化时两个沿一起移动，相对关系不变；hold 检查的是同一沿附近的竞争，不是跨周期传递。
正 skew（捕获端晚到）对 setup 和 hold 各有什么影响？为什么？
对 setup 有利：捕获沿推后等于多给数据时间；对 hold 不利：捕获沿推后意味着数据更早于"沿+Thold"这个界限到达。
同一条路径为什么会同时担心"太长"和"太短"？
不同 corner 下延迟差别很大（Tmax 到 Tmin 可能差一倍）。setup 用最慢的 Tmax，hold 用最快的 Tmin；周期不够时窗口比变化范围还窄，两头同时违例。
降频为什么救不了 hold？给两条理由。
一是公式里没有周期，数学上无影响；二是物理上两个沿同时移动，间隔恒为 0。数值上把周期从 1.25 改到 12.5，hold slack 一个字不变。
为什么 setup 用 ss corner、hold 用 ff corner？
setup 的最坏情况是"发射慢 + 捕获快"，ss（慢工艺、低压、高温）最接近；hold 的最坏情况是"发射快 + 捕获慢"，ff（快工艺、高压、低温）最接近。方向相反，不能共用一个 corner。
OCV derate 1.05/0.95 会吃掉多少余量？举例说明。
数据路径 1.5ns ×1.05 多 75ps，捕获时钟 0.6ns ×0.95 少 30ps，合计损失 105ps，相当于把 slack 直接扣掉 105ps。
uncertainty 和 skew 有什么区别？
skew 是确定的空间时间差，CTS 能压、报告能测；uncertainty 是随机和未建模的部分（jitter、OCV 残余、电源噪声、模型误差），永远存在，只能预留。
修 setup 和修 hold 的动作为什么会互相破坏？
两者都通过改延迟实现，而 setup 要"最慢的变快"、hold 要"最快的变慢"，方向相反。插 delay cell 同时抬高 Tmax 和 Tmin，upsize 同时压低两者。

  • 能用照相机比喻讲清 setup / hold / Tcq 三个参数，并说出各自物理来源
  • 能不看资料写出两条 slack 表达式，且知道 skew 的正负号定义
  • 能用波形图说明"一条路径的延迟必须落在窗口里"，并算出窗口宽度
  • 能手算一个 setup 违例和一个 hold 违例，给出数字、结论和至少两种修法
  • 能给出三条论证说明"降频救不了 hold"，包括数值验证
  • 能说清 setup 和 hold 为什么用不同 corner，以及 OCV derate 的算法
  • 能说出 uncertainty 的四个来源，并解释它和 skew 的区别
  • 能论证"先修 setup 后修 hold"，并说出为什么反过来一定返工
