02

ECO 为什么是 1-2 个月的长周期

原文第一句就给了一个令人印象深刻的事实，这句话本身就是最重要的信息。

为什么一个「局部修改」要一两个月？新手容易以为 ECO 就是「改几个 cell、连几根线」。实际不是。原因有四：

① 每一轮 ECO 都要跑完整验证。 改了一条线，走线变了 → 寄生变了 → 所有时序要重算；单元换了 → 布局变了 → 局部密度和拥塞要重查；新插了 buffer → DRC 和 LVS 要重跑。所以每一轮都是「小改动 + 全量验证」，一天能跑完的轮数有限。

② 问题是分批暴露的。 时序违例不是一次全暴露。第一轮修完可能又冒出新的一批（修 A 影响了 B），所以要反复迭代。

③ 多方交接。 原文提到的 FCT 负责出顶层 ECO 脚本，PV 部门需要一版 LVS 能过的数据。一个 ECO 要经过「发现 → 提工单 → 出脚本 → 吃脚本 → 验证 → 反馈」，每一环都有等待时间。

④ 后期改动风险高。 到了 ECO 阶段版图已接近冻结，任何改动都可能引入新问题，所以每次都要谨慎评估、完整回归，快不起来。

「每天需要起 eco 的 run」说明了什么

这句话说明 ECO 是按天迭代的：每天都有一轮新的 run，修一批、验证、第二天再来。

这也解释了为什么 ECO 需要严格的可追溯性——几十轮下来如果没记录清楚「哪一轮改了什么」，出问题根本追不回来。

03

周期与内容总览

原文这一段把周期和修复内容一起列了出来。

九、ECO

ECO的时间（1-2个月）

ECO需要修复的内容

每天需要起eco的run

这段话里最关键的三个信息：时间是 1-2 个月（不是几天）、要修的是一批内容（不是单项）、每天要起 eco 的 run（按天迭代）。

「每天起 run」意味着 ECO 是流水线式的：今天修一批，明天验证完再修下一批。所以每一轮的可追溯性极其重要——几十轮下来，如果没记录清楚「哪一轮改了什么、为什么改」，出了问题根本追不回来。

下面五节按原文顺序，逐类讲这六类修复内容。

为什么 DRV 排第一？因为 DRV 会掩盖时序问题。transition 太缓的单元延迟模型不准确——工具算出来的延迟和实际差很多，在这种情况下修时序等于在错误的基础上优化。

原文列的 DRV 清单逐项解释：

项含义
SI transition串扰导致的边沿恶化（信号完整性）
longnet走线太长
min_pulse最小脉宽，时钟高低电平太短
dontuse用了被禁用的单元
short短路
open开路

注意 short 和 open 也在这里：它们严格说是「连通性」问题而不是「规则」问题，但在 ECO 阶段通常和 DRV 一起处理，因为都要改版图。

原文最后一句很关键：PV 的部门需要一版 LVS 能过的数据。

这句话说明 DRV 阶段的交付物不是「DRV 清零」，而是「能通过 LVS 的数据」。因为 LVS 验证的是版图和网表是否一致——如果 ECO 改了单元但没同步网表，LVS 就过不了。

常见坑 · DRV 修完但 LVS 不过

典型原因：ECO 插了 buffer，版图有了但网表没更新。LVS 会比较版图提取的连接关系和网表，多一个单元就报 mismatch。

所以每次 ECO 之后必须同步网表，这不是「顺手的事」，是交付条件。

top 层 timinginternal 内部 timing

为什么 top 层不用修到 0？top 层时序涉及多个模块，单靠改自己这块可能修不动；而且 FCT 的脚本是全局折中方案。

为什么 internal 要修到 0 还要留 15 ps margin？这是「安全垫」，原因有三：提取精度有误差（SPEF 和实际硅片有差异）、OCV derate 可能没完全覆盖、后续还有改动避免「刚过又违例」。

「多个 corner 一起修，尽量避免 conflict」这句是高级功能的核心价值：多工艺角修时序最怕「修好 FF 角把 SS 角搞坏」。工具能同时看多个角，找出一组不冲突的改动，比人工逐角修快得多也可靠。

常见坑 · 吃脚本不检查前后变化

原文特别提醒：注意吃的脚本前后，时序的变化。

别人给的脚本基于他们的版图状态生成。你的版图如果已经和他不同（之前修过别的东西），脚本里的单元位置、网络名可能对不上。

正确流程：吃前存基线（数据库+时序报告）→ 吃脚本 → 立刻跑时序对比 → 变差就回退并反馈。

「如果变得很差，需要反馈」—— 这句话说明反馈是被鼓励的，不是必须自己扛。

Metal DRC 金属层 BASE DRC (overlap VT不一致)

short 和 open：靠手动改

四种手段各有适用场景和风险：

手段适用风险
手动拉线局部断开，补一段线连通可能违反 DRC 或引入串扰
剪断 net短路：剪掉落误连的那段剪错会导致开路
挪 cell两单元挤在一起导致短路挪动可能违反布局约束
删除 power电源线压到信号线导致短路删了可能造成供电不足

为什么 short/open 要手动改？因为工具自动修的能力有限——它能修规则违例，但「这两根线为什么撞在一起」往往需要人判断（floorplan 问题？某条网绕太远？），修法取决于根因。

手动改的纪律：每改一处立刻验证连通性。不要连续改十处再一起验——出问题不知道是哪一处。

DRC：两类规则

原文的分法很实用，逐项拆：

BASE DRC 的两个典型：overlap（两个图形重叠了不该重叠的地方）、VT 不一致（相邻单元阈值电压类型不匹配，某些工艺要求同类相邻）。

规则记号的读法：M1.A.S1 拆开是 M1（第 1 层金属）+ A（Area 面积）+ S1（第 1 条相关规则）。VIA.S. 是过孔间距规则。

为什么 DRC 排第四而不是第一？因为 DRC 违例不影响功能正确性（版图做不出来是制造问题，不是逻辑问题），而 DRV 和时序影响功能。顺序是先保功能、再保可制造。

不过实际项目里 DRC 通常和 short/open 一起处理，因为都是改版图的操作。

IR Drop 两个修法：用高层走线（高层金属更厚更宽、电阻小）、加 power（加电源条带或加宽现有条带）。

crosstalk 加 shielding：在受害网两侧打地线。原理前面 CTS 那课讲过——耦合对象从「会翻转的信号线」变成「不动的地线」。

Dynamic 用 size down：原文例子 D12 → D6 是驱动强度从 12 档降到 6 档。为什么降驱动能省功耗？驱动越强单元内部晶体管越大，充放电电容越大，动态功耗 P ∝ C·V²·f 越高。

但降驱动有代价：驱动弱了边沿变缓，transition 违例可能回来。所以这是功耗与时序的权衡。

常见坑 · size down 降过头

D12 → D6 省了功耗，但如果这条路径原本余量就不多，降到 D6 可能直接违例。

正确做法：降一档，立刻查时序；过了再看能不能再降一档。逐步试，不要一次降到底。

VSI：一个很具体的检查

原文：VSI — 检查 Tie cell 不能连接两个 cell。VSI 是 Voltage Signal Integrity 相关检查。

含义：一个 tie cell（提供恒定 0 或 1 的单元）不能同时驱动两个以上的单元。

为什么？tie cell 的驱动能力很弱（它就是个小小的恒压源）。驱动太多负载时输出电压会被拉偏——本来该是稳定的 1，可能变成 0.7，导致下游误判。

怎么修？拆开——多加几个 tie cell，每个只驱动一个或少数几个负载。

这条规则很容易漏

因为它不在常规 DRV 列表里（不是 transition/fanout/cap/length），是工艺相关的特殊规则。

而且只在特定条件下报——某些工艺库、某些 tie cell 类型才检查。看 DRC/LVS 报告时要专门找 VSI 这一项。

08

进阶：有意改变功能的 ECO 怎么验收

前面六类修的都是「让设计符合原有规格」。但 ECO 还有一类更难的：有意改变功能。下面这段是原文之外的站点原创练习，保留了原文的算例表格和手工核对答案。

这类 ECO 的风险完全不同——前六类改错了，验证能查出来（时序/DRC/LVS 会报）；功能 ECO 改错了，可能所有检查都通过，但芯片做出来功能就是错的。

以下为站点原创纸面案例，不属于上传 Word 原文。批准单 EC-27 要求已唤醒的模块在 req=1 时，仅当 enable=1 才输出 grant=1。旧功能是 grant = req，新参考 REF_B 是 grant = req AND enable。本题只比较唤醒后的正常模式；复位、扫描和低功耗模式不能靠这张真值表推断，真实项目须另按批准范围验证。

核对：旧新参考只允许在 (req, enable) = (1, 0) 改变，共 1 组；OR 候选在 (0, 1) 和 (1, 0) 错，共 2 组。LVS 匹配说明版图忠实实现了错接网表，不证明实现了获批新功能；DRC 只检查几何规则。不能为了让逻辑等价通过而屏蔽 grant。修正后保留批准单和差异范围，拿最终网表对 REF_B 做逻辑等价，并验证批准单规定的功能范围；再用同一候选的最终网表、流出版图和新寄生做受影响的时序、电气及物理签核回归，传给逻辑、实现、物理验证三方确认。

下一步：ChipFinish 桌面实训：整理回归证据并决定放行。

一个真实的验收陷阱

场景：批准单要求把 grant = req 改成 grant = req AND enable。

如果实现时错接成 grant = req OR enable：LVS 会通过（版图和网表一致）、DRC 会通过（几何没问题）、时序可能也通过。

但功能是错的。 唯一能发现的方法是逻辑等价检查（formal equivalence），用最终网表对新参考做比对。

所以功能 ECO 的验收必须包含：逻辑等价 + 批准单规定的功能范围验证 + 受影响的时序/电气/物理签核回归。

09

检查清单

过关标准（都能做到才算学完）
  • ECO 的改动范围有工单/批准单记录，不是口头传达
  • 吃外部脚本前存了基线（数据库 + 时序报告）
  • 吃脚本后立刻跑时序，与基线对比；变差已反馈而非硬吃
  • internal 时序修到 0 且留了 margin（如 15 ps）
  • 多工艺角一起检查，没有「修好一个角搞坏另一个角」
  • DRV 六项都查过：transition / SI transition / longnet / min_pulse / dontuse / short / open
  • short/open 每改一处立刻验连通性，没有攒着一起验
  • DRC 的 BASE（overlap、VT 不一致）和 Area/Spacing 都查过
  • PA 三类都评估过：IR Drop、EM、Dynamic
  • size down 是逐步试的，每步都查了时序
  • VSI 检查过 tie cell 没有驱动多个负载
  • 每次 ECO 后网表已同步（LVS 能过）
  • 功能 ECO 做过逻辑等价检查，不是只看 LVS/DRC

自测

自测
为什么 ECO 一个「局部修改」要 1-2 个月？
每轮改动都要跑全量验证（重提取、重算时序、重跑 DRC/LVS）；问题分批暴露需反复迭代；涉及 FCT、PV 多方交接有等待时间；后期改动风险高必须谨慎。
为什么 DRV 要排在时序之前修？
transition 太缓会让延迟模型不准确，工具算的延迟和实际差很多，在这种基础上修时序等于在错误基础上优化。
top 层 timing 和 internal timing 的修法为什么不同？
top 层涉及多模块，FCT 从全局视角出脚本，单个模块可能修不动；internal 完全自己掌控，所以要修到 0 并留 margin。
internal 时序为什么留 15 ps margin 而不是修到 0 就算？
提取精度有误差、OCV derate 可能没完全覆盖、后续还有改动。留余量避免「刚过又违例」。
吃外部 ECO 脚本前后必须做什么？
吃前存基线（数据库+时序报告），吃后立刻跑时序对比。变差就回退并反馈，不要硬吃。
short/open 为什么主要靠手动改而不是工具自动修？
工具能修规则违例，但「两根线为什么撞在一起」需要人判断（floorplan 问题？某条网绕太远？），修法取决于根因。
DRV 阶段的交付物为什么是「LVS 能过的数据」而不是「DRV 清零」？
ECO 改了单元必须同步网表，否则版图提取的连接关系和网表不一致，LVS 报 mismatch。交付看能否过 LVS。
M1.A.S1 这个规则名怎么读？
M1 是第 1 层金属，A 是 Area 面积，S1 是第 1 条相关规则。整条表示第 1 层金属的面积规则 1 不满足。
修 Dynamic 功耗为什么用 size down？代价是什么？
驱动越强单元晶体管越大、充放电电容越大，动态功耗 P∝C·V²·f 越高。代价是边沿变缓，transition 违例可能回来。
VSI 检查「tie cell 不能连接两个 cell」的原因？
tie cell 驱动能力弱，驱动多负载时输出电压被拉偏，本来稳定的 1 可能变 0.7，导致下游误判。
功能 ECO 为什么 LVS 和 DRC 都过也可能是错的？
LVS 只证明版图忠实于网表，DRC 只证明几何合法。若网表本身错接（AND 写成 OR），两者都会通过。必须用逻辑等价检查发现。
功能 ECO 的完整验收包括哪三项？
逻辑等价检查（对最终网表和新参考）、批准单规定的功能范围验证、受影响范围的时序/电气/物理签核回归。
