04

文本处理三件套：grep / sed / awk

grep, sed, awk

后端的报告全是文本。学会从几十万行报告里精确捞出"哪条路径违例、差多少"，是效率分水岭。

约 45 分钟 课表学时 3.5 Linuxgrepsedawk管道
01

后端的一天，就是在文本里捞针

时序报告动辄几十万行，DRC 报告几万条，日志几百兆。你不可能用眼睛找。

真实场景长这样：

  • 早上看时序：report_timing 出来 30 万行，你只想知道"最差的那条差多少"。
  • 中午看 DRC：calibre 报告 8000 条违例，你想知道"有几类、各多少条"。
  • 下午看日志：跑了 4 小时的流程挂在某一步，你要在 200MB 日志里找到第一个 Error。

这三个动作对应三个命令：awk 取数、grep 过滤、sed 改写。

Pipeline管道点击看解释

把上一个命令的输出，直接当成下一个命令的输入。写法是一个竖线 |。
cat a.log | grep error | wc -l 读作："把 a.log 的内容，交给 grep 筛出含 error 的行，再交给 wc 数行数"。
管道是 Unix 最伟大的设计：每个工具只做一件小事，串起来就能干大事。

02

重定向：把输出送到该去的地方

默认情况下，命令的输出打在屏幕上（标准输出 stdout），报错也打在屏幕上（标准错误 stderr）。

bash
ls > filelist.txt# > 覆盖写入：把 ls 的结果写进 filelist.txt，屏幕什么都不显示 ls >> filelist.txt# >> 追加写入：接在文件末尾，不覆盖 run.sh > run.log 2>&1# 把正常输出和错误输出都写进 run.log# 2>&1 的意思是"把 2 号（stderr）指向 1 号（stdout）该去的地方"# 这是跑批最常见的写法，一定要背下来 run.sh > /dev/null 2>&1# 全部丢掉（/dev/null 是系统的黑洞），只关心成功与否
常见坑 · > run.log 会清空文件

如果你本来想追加，用了 >，之前 3 小时的日志瞬间没了。

  • 想追加：>>
  • 想保留现场再重跑：先 mv run.log run_$(date +%m%d_%H%M).log，再跑
03

grep：把想要的行挑出来

bash
grep error run.log# 打印所有含 "error" 的行（区分大小写，Error 不会被匹配） grep -i error run.log# -i = ignore case，忽略大小写。日志里 Error / ERROR / error 混着出现时必须加 grep -n error run.log# -n = number，带上行号。方便回头用 vim 跳到那一行 grep -c error run.log# -c = count，只输出命中多少行，不输出内容 grep -v error run.log# -v = invert，反过来：打印"不含 error"的行 grep -A 3 "Error" run.log# -A 3 = after，命中行后面再带 3 行。看报错上下文必用 grep -B 2 "Error" run.log# -B 2 = before，前面带 2 行 grep -E "setup|hold" timing.rpt# -E = 扩展正则，用 | 表示"或"。这一行等价于筛出含 setup 或 hold 的行 grep -rn "create_clock" scripts/# -r = 递归整个目录，-n 带行号。找"哪个脚本里定义了这个时钟"
Regular Expression正则表达式点击看解释

一种描述"文本模式"的小语言。常用的几个：
| 写法 | 含义 |
|---|---|
| ^abc | 以 abc 开头 |
| abc$ | 以 abc 结尾 |
| . | 任意一个字符 |
| .* | 任意多个字符 |
| [0-9] | 一个数字 |
| \|（在 -E 下是 |） | 或 |
不用一次学全。先会 ^、$、[0-9]，就够应付 80% 的报告提取。

工作场景 · 在 200MB 日志里找第一个错误
bash
grep -n -m 1 -i "error" run.log# -m 1 = max count，找到第一个就停（日志大时必须加，否则要扫完） grep -n -A 5 -i "error" run.log | head -40# 带上下文看前 40 行，基本能定位病因

老手不看最后一个错误，看第一个错误——后面的错误常常是第一个引起的连锁反应。

04

sed：替换和筛选行

bash
sed -n '10,20p' timing.rpt# -n 加 p：只打印第 10 到 20 行（p = print） sed -n '/Startpoint/,/Endpoint/p' timing.rpt# 打印从 "Startpoint" 到 "Endpoint" 之间的所有行# 这是读时序报告最实用的一条命令：一条路径的完整信息全在这两行之间 sed 's/old/new/' file# 把每行第一个 old 换成 new（只换第一个） sed 's/old/new/g' file# g = global，一行里全部替换 sed -i 's/0\.5/0.6/g' config.tcl# -i = in-place，直接改文件（小心，先不加 -i 看一眼输出） sed '/^#/d' config.tcl# d = delete，删掉所有以 # 开头的注释行 sed -i 's/\r$//' run.sh# 去掉 Windows 换行符。从 Windows 拷脚本过来必用
常见坑 · sed -i 没有撤销

sed -i 是直接改磁盘上的文件，改错了没法 Ctrl+Z。

保命做法：先去 -i 跑一遍看输出，确认替换对了再加 -i。

bash
sed 's/0.5/0.6/g' config.tcl | head -20     # 只看，不改sed -i.bak 's/0.5/0.6/g' config.tcl         # 改，同时留一份 config.tcl.bak
05

awk：按列取数，做小计算

awk 把每一行按空格（或指定分隔符）切成若干列，$1 是第一列，$2 第二列，$NF 是最后一列，$0 是整行。

bash
awk '{print $1}' file# 打印每行第一列 awk '{print $NF}' file# NF = number of fields，最后一列 awk '{print $1, $3}' file# 打印第 1 和第 3 列，中间用空格分隔 awk 'NR==5' file# NR = 行号，只打印第 5 行 awk 'NR>=10 && NR<=20' file# 打印 10 到 20 行，效果同 sed -n '10,20p' awk '/setup/ {print $2}' report# 只对含 setup 的行，打印它的第 2 列 awk '{sum+=$2} END {print sum}' num.txt# 把第 2 列累加，最后打印总和 awk '{print $2}' num.txt | sort -n | tail -1# 取第 2 列，按数值排序，取最大的那个 → 一行拿到"最差 slack"
Field字段 / 列点击看解释

一行文本里被分隔符（默认空格、Tab）切开的一段。$1 是第一段。
报告类文本的规律很强：同一个位置的数字含义固定。所以 awk '{print $2}' 这种"取第 2 列"的写法，在报告提取里极其常用。

模拟终端试：grep slack timing.rpt、awk '{print $1}' paths.rpt、cat drc.rpt
[autumn@eda ~]$
这里跑的是浏览器里的模拟环境：命令、输出、报错都按真实 Linux 的行为写，练手够用；真机上的路径与权限另有差异。
06

组合技：从时序报告里提取最差 slack

真实报告长这样（report_timing 的摘录）：

shell
Startpoint: u_core/u_reg[3]            (rising edge-triggered flip-flop clocked by clk)Endpoint:   u_core/u_alu/out_reg[7]            (rising edge-triggered flip-flop clocked by clk)Path Group: clkPath Type:  max...slack (VIOLATED) -0.213

想一句话回答"最差 slack 是多少"：

bash
grep "slack" timing.rpt | awk '{print $NF}' | sort -n | head -1# grep 挑出所有 slack 行 → awk 取最后一列（数字） → 数值排序 → 取最小# 输出：-0.213

想统计各类违例数：

bash
grep -c "VIOLATED" timing.rpt        # 违例路径条数grep -o "slack (VIOLATED)" timing.rpt | wc -l   # 同上，另一种写法

想看所有违例路径的起点：

bash
grep -A 2 "slack (VIOLATED)" timing.rpt | grep "Startpoint" | awk '{print $2}' | sort | uniq -c | sort -rn | head# 输出形如： 12 u_core/u_reg[3]  ← 说明这个寄存器贡献了 12 条违例
工作场景 · 这段脚本组长真的会用

布局布线跑完，报告 30 万行。组长问："最差多少？有几条违例？集中在哪？"

你把上面三条命令贴过去，30 秒回答完。这就是"会用 Linux"和"不会用"的差距——不是知识差距，是效率差距。

动手动手：自己造一份报告并分析
bash
cd ~/demo 2>/dev/null || { mkdir -p ~/demo && cd ~/demo; } # 造一份假的时序报告cat > timing.rpt <<'EOF'Startpoint: u_core/u_reg[3]Endpoint:   u_core/u_alu/out_reg[7]slack (VIOLATED) -0.213Startpoint: u_core/u_reg[9]Endpoint:   u_core/u_alu/out_reg[1]slack (VIOLATED) -0.087Startpoint: u_core/u_reg[9]Endpoint:   u_core/mem/rd_reg[2]slack (MET) 0.412EOF # 1. 有几条违例grep -c VIOLATED timing.rpt # 2. 最差 slackgrep slack timing.rpt | awk '{print $NF}' | sort -n | head -1 # 3. 违例集中在哪个起点grep -A 1 "VIOLATED" timing.rpt | grep Startpoint | awk '{print $2}' | sort | uniq -c

预期输出：

shell
2-0.213      1 u_core/u_reg[3]      1 u_core/u_reg[9]

过关标准：不改脚本，把第 3 条改成"按起点统计违例数并从多到少排序"（提示：末尾加 | sort -rn）。

过关标准（都能做到才算学完）
  • 能写出"输出和错误都进日志"的那一行（> run.log 2>&1）
  • 会用 grep -n -i -c -v -A/-B 五个选项
  • 会用 sed -n '/A/,/B/p' 截取一段报告
  • 会用 awk '{print $NF}' 取最后一列并配合 sort -n | head -1 找最小值
  • 知道 sed -i 有风险，会先不加 -i 验证
自测：先自己想，再点开答案
run.sh > run.log 2>&1 里 2>&1 是什么意思？
把标准错误（文件描述符 2）重定向到标准输出（1）当前指向的地方，也就是同一个日志文件。
grep -A 3 Error 和 grep -B 3 Error 有什么区别？
-A 是命中行之后多显示 3 行（after），-B 是之前多显示 3 行（before）。
怎么打印一份报告里从 Startpoint 到 Endpoint 之间的内容？
sed -n '/Startpoint/,/Endpoint/p' report
awk '{print $NF}' 里的 NF 是什么？
Number of Fields，当前行的字段总数，所以 $NF 就是最后一列。
为什么在 200MB 日志里找错误要加 -m 1？
-m 1 命中第一个就停止，避免扫完整个文件；而且第一个错误通常才是根因。
