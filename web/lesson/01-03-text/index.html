文本处理三件套：grep / sed / awk

grep, sed, awk

后端报告全是文本。学会用重定向、管道、grep/sed/awk 从几十万行里捞出"哪条路径违例、差多少"，并用一条命令回答"最差 slack 是多少、有几条违例、集中在哪"。

约 45 分钟 课表学时 3.5 Linuxgrepsedawk管道
01

后端的一天，就是在文本里捞针

本章目标学完这一课，你能写出"从报告里捞出最差 slack 一行"的完整管道，并逐段解释每个命令在做什么、去掉它会怎样。

时序报告动辄几十万行，DRC 报告几万条，日志几百兆（都是 40nm 量级项目的典型值）。你不可能用眼睛找。

算一笔账：30 万行的报告，人眼平均 1 秒看 1 行，看完要

300,000 ÷ 3,600 ≈ 83 小时

而且看完你还记不住。工具跑一次只要 3 小时，你看报告要 83 小时——这就是为什么"会不会文本处理"是后端的效率分水岭，不是知识差距。

真实场景长这样：

  • 早上看时序：report_timing 出来 30 万行，你只想知道"最差的那条差多少"。
  • 中午看 DRC：calibre 报告 8000 条违例，你想知道"有几类、各多少条"。
  • 下午看日志：跑了 4 小时的流程挂在某一步，你要在 200MB 日志里找到第一个 Error。

这三个动作对应三个命令：grep 过滤、sed 改写、awk 取数。而把它们串起来的东西叫管道。

Pipeline（管道）管道点击看解释

把上一个命令的输出，直接当成下一个命令的输入。写法是一个竖线。
cat a.log | grep error | wc -l 读作："把 a.log 的内容，交给 grep 筛出含 error 的行，再交给 wc 数行数"。
管道是 Unix 最伟大的设计：每个工具只做一件小事，串起来就能干大事。你不需要写一个大程序，只需要会拼积木。

02

重定向：把输出送到该去的地方

默认情况下，命令的输出打在屏幕上。但"屏幕"其实只是三个标准流之一：

编号名字装什么默认去哪
0stdin（标准输入）你敲进去的内容键盘
1stdout（标准输出）正常结果屏幕
2stderr（标准错误）报错信息屏幕

关键点：1 和 2 是两个不同的管道，虽然都显示在屏幕上。 这就是为什么 run.sh > run.log 之后，错误还是会刷在屏幕上——你只重定向了 1 号，2 号还在往屏幕走。

bash
# 作用：四种重定向写法；在任意目录执行，run.log 会生成在当前目录ls > filelist.txt               # > 覆盖写入：清空原文件再写，屏幕什么都不显示ls >> filelist.txt              # >> 追加写入：接在末尾，不覆盖run.sh > run.log 2>&1           # 正常输出和错误输出都进 run.log（最常用的跑批写法）run.sh 2> err.log               # 只把错误单独收进 err.log，正常输出还在屏幕上run.sh > /dev/null 2>&1         # 全部丢掉（/dev/null 是系统的黑洞），只关心成功与否run.sh 2>&1 | tee run.log       # 既进日志又显示在屏幕上（tee = 三通，真机命令）

2>&1 到底在说什么，拆开看：

  • 2> 是"把 2 号（stderr）重定向到某个地方"。
  • &1 是"1 号当前指向的地方"（不是"1 号这个文件"，& 表示引用而不是文件名）。
  • 连起来：把错误流接到输出流正在去的那个地方。

顺序不能反。 > run.log 2>&1 是"先把 1 指向文件，再让 2 跟着 1"，两个都进文件。而 2>&1 > run.log 是"先让 2 跟着当前的 1（屏幕），再把 1 指向文件"，结果是错误还在屏幕上。这一个字符的顺序，坑过无数人。

三个符号在屏幕上的实际效果是这样的：

要看出的是：管道不落盘，重定向落盘。 所以"只想看一眼"用管道，"要留证据"必须重定向到文件。跑 3 小时的任务，日志不落盘等于没跑。

常见坑 · > run.log 会清空文件

如果你本来想追加，用了 >，之前 3 小时的日志瞬间没了。

  • 想追加：>>
  • 想保留现场再重跑：先 mv run.log run_$(date +%m%d_%H%M).log，再跑

判断依据：> 是"打开并截断"，>> 是"打开并定位到末尾"。跑批脚本里 90% 的场景应该用 >> 或带时间戳的新文件名，而不是 >。

03

grep：把想要的行挑出来

grep 是"按行过滤"：只要这一行里出现了你给的模式，就把整行打出来。

bash
# 作用：grep 的九个常用选项；在报告所在目录执行grep error run.log              # 打印所有含 "error" 的行（区分大小写，Error 不匹配）grep -i error run.log           # -i = ignore case，忽略大小写（Error/ERROR/error 混着出现时必加）grep -n error run.log           # -n = number，带行号，方便回头用 vim 跳到那一行grep -c error run.log           # -c = count，只输出命中多少行，不输出内容grep -v error run.log           # -v = invert，反过来：打印"不含 error"的行grep -w error run.log           # -w = word，只匹配整词，避免 error_code 被算进来grep -o "slack.*" timing.rpt    # -o = only，只打印匹配到的那一段，不打印整行grep -A 3 "Error" run.log       # -A 3 = after，命中行后面再带 3 行（看上下文必用）grep -B 2 "Error" run.log       # -B 2 = before，前面带 2 行grep -C 3 "Error" run.log       # -C 3 = 前后各 3 行（context）grep -m 1 -n -i error run.log   # -m 1 = 找到第一个就停（大日志必加）grep -E "setup|hold" timing.rpt # -E = 扩展正则，用竖线表示"或"grep -F "reg_b[3]" paths.rpt    # -F = fixed string，把模式当纯文本，不解释 [ ] 等正则符号grep -rn "create_clock" scripts/  # -r = 递归整个目录，-n 带行号，找"哪个脚本里定义了这个时钟"

其中 -F 是后端最被低估的选项。路径里全是 [ ] . *，这些在正则里都有特殊含义。想搜 u_core/u_alu/reg_b[3] 这一行，不加 -F 会被当成"reg_b 后面跟一个 3 的字符类"，匹配不到。搜路径、搜带括号的实例名，一律加 -F。

三个工具在屏幕上各干一段，最后串成一条管道：

要看出的是：没有哪条命令"很聪明"，是组合让它们能干复杂的事。 你以后写的每条分析命令，都是这三样的重新排列——所以先把单个练熟，再练拼。

Regular Expression（正则表达式）正则表达式点击看解释

一种描述"文本模式"的小语言。grep 默认用基本正则，-E 用扩展正则。
| 写法 | 含义 |
|---|---|
| ^abc | 以 abc 开头 |
| abc$ | 以 abc 结尾 |
| . | 任意一个字符 |
| .* | 任意多个字符 |
| [0-9] | 一个数字 |
| [^0-9] | 一个非数字 |
| \b | 单词边界 |
| 竖线（-E 下） | 或 |
不用一次学全。先会 ^、$、[0-9]，就够应付 80% 的报告提取。

grep -E 三个能直接用的例子

-E 的价值在"或"和"量词"上。下面三条是后端报告里最常用的，直接抄：

bash
# 作用：三个 grep -E 实用例子；在报告所在目录执行grep -E "^(Startpoint|Endpoint):" timing.rpt        # ① 只取每条路径的起点和终点grep -E "u_(alu|mul)/.*(VIOLATED|slack)" timing.rpt # ② 只看两个模块的违例grep -E "slack +-?[0-9]+\.[0-9]+" timing.rpt        # ③ 只匹配"后面真的跟数字"的 slack 行

逐条说清每段在干什么：

  1. ^(Startpoint|Endpoint): —— 行首锚定 + 二选一。报告里起点、终点各占一行，中间夹十几行计算。想快速看"谁到谁"，这两行够了。比 grep -A 稳，因为它不依赖"中间隔几行"。
  2. **u_(alu|mul)/.*(VIOLATED|slack)** —— 两个"或"叠在一起：先限定模块，再限定状态。.* 不能省，因为模块名和状态必须在同一行；如果报告是"路径占几十行"的格式，这条会漏，得改用 -A 或 awk 记状态。
  3. slack +-?[0-9]+\.[0-9]+ —— 关键词 + 空格 + 可选负号 + 数字。-? 让 0.31 和 -0.35 都能匹配。这是"报告里有标题行、小节名也叫 slack"时的通用解法：只认后面真的跟数字的那一行。
常见坑 · 用了 -E，带方括号的实例名就搜不到了

现象：grep -E "u_alu/reg_b[3]" timing.rpt 一行都没输出，但报告里明明有 u_alu/reg_b[3] 这一行。

原因：[3] 在正则里是字符类，意思是"一个字符 3"，所以这个模式实际要求的是 reg_b3。-E 不会把 [ 当字面量——它只会让 + ? | ( ) 变成元字符，字符类规则照旧。

怎么查、怎么改：去掉 -E 再跑一次（基本正则里 [3] 同样是字符类，所以还是搜不到）；直接加 -F。要保留正则又要字面括号，就写 reg_b\[3\]。

判断依据：实例名、路径、带方括号的信号名，一律 -F。 这些名字里 [ ] . * + ? 全是元字符，写正则是在给自己挖坑。

工作场景 · 在 200MB 日志里找第一个错误
bash
# 作用：在大日志里定位第一个错误及其上下文；在日志所在目录执行grep -n -m 1 -i "error" run.log          # 找到第一个错误，带行号，找到就停grep -n -A 5 -i "error" run.log | head -40   # 带后 5 行上下文，只看前 40 行

盯日志的窗口长这样：

要看出的是：这个窗口要一直开着，直到出现你自己写的结束标记（比如 [DONE]）。 Ctrl+C 退出是正常操作，不代表任务失败；反过来，日志不动也不代表进程死了，先用 ps 确认。

老手不看最后一个错误，看第一个错误——后面的错误常常是第一个引起的连锁反应。

举个真实例子：第一个错误是 Cannot open library file 'slow.db'（库读不到），后面 800 条 Cannot resolve reference 全是它引起的。你要是从最后一条开始查，会查一整天。

常见坑 · grep 一个目录，报 Is a directory

现象：你想在整个 reports 目录里找 slack，敲了

text
$ grep "slack" reports/grep: reports/: Is a directory

原因：grep 默认只处理文件。给它一个目录，它不会自己进去翻，而是直接告诉你"这是个目录"。

怎么查、怎么修：想递归整个目录就加 -r（同时建议加 -n 保留行号）：

bash
# 作用：在整个目录里递归搜索；在 reports 的上一层执行grep -rn "slack" reports/            # -r 递归，-n 带行号，输出形如 reports/timing.rpt:32:...grep -rn --include="*.rpt" "slack" . # 只搜 .rpt 文件，避免把 .log/.db 也扫一遍

判断依据：报错里出现 Is a directory、omitting directory、cannot read 这一类词，先想"我是不是少加了一个递归选项"。

04

sed：替换和筛选行

sed 是"流编辑器"：一行一行读进来，按你的规则改，再输出。它不改原文件（除非加 -i）。

bash
# 作用：sed 的读取与替换；在报告或配置文件所在目录执行sed -n '10,20p' timing.rpt              # -n 加 p：只打印第 10 到 20 行（p = print）sed -n '10p;20p' timing.rpt             # 打印第 10 行和第 20 行sed -n '/Startpoint/,/Endpoint/p' timing.rpt   # 打印从 Startpoint 到 Endpoint 之间的所有行sed -n '/VIOLATED/p' timing.rpt         # 只打印含 VIOLATED 的行（等价 grep VIOLATED）sed 's/old/new/' file                   # 把每行第一个 old 换成 newsed 's/old/new/g' file                  # g = global，一行里全部替换sed 's/old/new/2' file                  # 只替换每行的第 2 个匹配sed -n 's/^slack.*:\s*//p' rpt          # 替换 + 只打印被改过的行（提取数字的常用组合）sed 's/^[ \t]*//' file                  # 去掉行首空白（对齐乱的报告很有用）sed '/^#/d' config.tcl                  # d = delete，删掉所有以 # 开头的注释行sed '/^$/d' config.tcl                  # 删掉所有空行sed -i 's/0\.5/0.6/g' config.tcl        # -i = in-place，直接改文件（危险，见下面的坑）sed -i.bak 's/0\.5/0.6/g' config.tcl    # 改的同时留一份 config.tcl.baksed -i 's/\r$//' run.sh                 # 去掉 Windows 换行符（上一课讲过）

三个必须理解的细节：

  1. -n 和 p 是一对。sed 默认会把每一行都打印出来；-n 关掉默认打印，p 才显式打印你要的行。只用 p 不加 -n，每行会打印两遍。
  2. /A/,/B/p 是区间匹配，从含 A 的行开始，到含 B 的行结束。如果 A 出现多次、B 只出现一次，会打印出好几段——这在时序报告里正好是你要的（每条路径一段）。
  3. s/// 里 / 是分隔符，如果模式里有 /（比如路径），换成别的分隔符更清楚：sed 's|/home/wei|/home/lisi|g'。
常见坑 · sed -i 没有撤销

sed -i 是直接改磁盘上的文件，改错了没法 Ctrl+Z。更糟的是：如果正则写错，它可能把整个文件改乱，而你还没备份。

保命三步：

bash
# 作用：安全地做一次批量替换；在配置文件所在目录执行cp config.tcl config.tcl.bak                  # 第一步：先备份（比 -i.bak 更早，连"改错文件名"都能救）sed 's/0\.5/0.6/g' config.tcl | head -20      # 第二步：不加 -i，只看前 20 行输出，确认替换对不对sed -i.bak 's/0\.5/0.6/g' config.tcl          # 第三步：确认无误再改，并自动留 .bak

判断依据：凡是 sed -i，前面必须有备份，后面必须有 diff 验证：diff config.tcl.bak config.tcl | head 只应该看到你预期的几行变化。

05

awk：按列取数，做小计算

awk 把每一行按分隔符（默认空格 / Tab）切成若干列，$1 是第一列，$2 第二列，$NF 是最后一列，$0 是整行。

bash
# 作用：awk 的取列与小计算；在报告所在目录执行awk '{print $1}' file               # 打印每行第一列awk '{print $NF}' file              # NF = number of fields，最后一列（列数不定时最有用）awk '{print $1, $3}' file           # 打印第 1 和第 3 列，中间用空格分隔awk '{print NF}' file               # 每行有多少列（排查"格式变了"很快）awk 'NR==5' file                    # NR = 行号，只打印第 5 行awk 'NR>=10 && NR<=20' file         # 打印 10 到 20 行，效果同 sed -n '10,20p'awk 'NR>1' file                     # 跳过第 1 行（表头），报告提取的标配awk '/setup/ {print $2}' report     # 只对含 setup 的行，打印它的第 2 列awk -F: '{print $1}' /etc/passwd    # -F 指定分隔符为冒号（默认是空格）awk -F, '{print $2}' data.csv       # CSV 用逗号分隔awk 'NR>1 {s+=$2; n++} END {printf "n=%d sum=%.3f avg=%.4f\n", n, s, s/n}' paths.rpt# ↑ 跳过表头，累加第 2 列、计数，最后打印条数 / 总和 / 平均值awk 'NR>1 && $2<0 {c++} END {print c+0}' paths.rpt    # 统计第 2 列为负的行数（+0 保证空结果输出 0）

$NF 值得单独说：时序报告的列数不固定（层级深的名字会把字段推来推去），但 slack 那个数字永远在最后一个字段。所以 '{print $NF}' 比 '{print $3}' 稳得多。这是老手和新手的区别：新手数第几列，老手用 $NF。

NR>1 也是标配。报告第一行通常是表头（# endpoint slack cells length），表头参与计算会让 n 多 1、avg 偏掉。所有统计都要先想"表头怎么办"。

Field（字段 / 列）字段点击看解释

一行文本里被分隔符（默认空格、Tab）切开的一段。$1 是第一段，$NF 是最后一段。
报告类文本的规律很强：同一个位置的数字含义固定。所以"取第 2 列""取最后一列"这种写法，在报告提取里极其常用。

模拟终端试：grep slack timing.rpt、awk '{print $1}' paths.rpt、cat drc.rpt
[autumn@eda ~]$
这里跑的是浏览器里的模拟环境：命令、输出、报错都按真实 Linux 的行为写，练手够用；真机上的路径与权限另有差异。
06

组合技：从时序报告里提取最差 slack

真实报告长这样（report_timing 的摘录，本站模拟终端里的 timing.rpt 就是这个格式）：

text
Startpoint: u_core/u_alu/reg_a[3]  (rising edge-triggered flip-flop clocked by clk)Endpoint:   u_core/u_alu/reg_b[3]  (rising edge-triggered flip-flop clocked by clk)  data arrival time                               0.32  data required time                              1.90  slack (MET)                                     1.58

先手算一次 slack，把公式钉死：

slack = required − arrival = 1.90 − 0.32 = 1.58 ns

正数表示还有 1.58ns 余量（MET）；如果是 -0.213，就表示晚了 213ps（VIOLATED）。所有时序报告都是这个结构，看懂这一处，所有报告都能读。

想一句话回答"最差 slack 是多少"：

bash
# 作用：从 report_timing 输出里取最差（最小）slack；在报告目录执行grep "slack (" timing.rpt | awk '{print $NF}' | sort -n | head -1# grep 挑出所有 slack 行（含 VIOLATED / MET）# awk 取最后一列，也就是那个数字# sort -n 按数值排序（不要用字典序，否则 -0.9 会排在 -0.1 后面）# head -1 取第一个，也就是最小值# 本站 timing.rpt 只有一条 slack，输出 1.58；真实报告有几百条，输出的就是最负的那个值

把每一段的中间结果摊开看。左边是本站这份只有一条路径的报告，右边是真实报告（几百条）跑同一条命令的样子：

段本站 timing.rpt 的输出真实报告的输出去掉它会怎样
grep "slack ("1 行： slack (MET) 1.58几百行，每行一条路径标题行、小节名也叫 slack，会被一起送进下一段
awk '{print $NF}'1.58几百个数字，一行一个sort 按整行字符串排，行首缩进也参与比较
sort -n1.58从小到大，最负的排第一head -1 只是"文件里第一条"，不是最差
head -11.58一个数，就是 WNS拿到一整列数字，还得人眼看

注意第二段为什么用 $NF 而不是 $3：真实的路径名字有长有短，列数会被推着变，但"数字永远在最后一列"这个规律不变。这是新手和老手最容易拉开差距的一处细节。

注意 sort 必须加 -n。默认的字典序会把 -0.9 排在 -0.1 前面（因为字符 9 > 1），你会拿到一个错误答案，而且看起来"很像对的"。这是文本处理里最隐蔽的坑。

如果手上是"每条路径一行"的摘要表（paths.rpt 那种四列格式），最差 slack 更简单：

bash
# 作用：从摘要表里取 slack 最差的一行；paths.rpt 第 2 列是 slackgrep -v '^#' paths.rpt | sort -k2 -n | head -1# grep -v '^#'  去掉 # 开头的表头（否则表头会被排进结果）# sort -k2 -n   按第 2 列做数值排序# head -1       取最差的一行# 输出：u_core/u_mul/reg_p[7]             -0.35     57     203.8

想统计各类违例数：

bash
# 作用：统计违例条数的三种写法；任选一种，在报告目录执行grep -c "VIOLATED" timing.rpt                    # 违例行数（一行一条路径时可用）grep -o "slack (VIOLATED)" timing.rpt | wc -l    # 一行里出现多次时按出现次数算grep -v '^#' paths.rpt | awk '$2<0' | wc -l      # 摘要表里第 2 列为负的行数

想看所有违例路径的起点，并按"谁贡献最多"排序。这里不能简单用 grep -A：Startpoint 在 slack 上面，而中间隔几行是不固定的。正确做法是用 awk 记住"最近一个起点"，读到违例行时把它打出来：

bash
# 作用：按"起点"统计违例条数；适合"一条路径占几十行"的 report_timing 输出awk '/^Startpoint:/{sp=$2} /slack \(VIOLATED\)/{print sp}' timing.rpt | sort | uniq -c | sort -rn | head# /^Startpoint:/{sp=$2}    遇到起点行，把第 2 列（实例名）存进变量 sp# /slack \(VIOLATED\)/     遇到违例行，打印"当前记住的 sp"# sort | uniq -c | sort -rn  按出现次数从多到少排# 输出形如： 12 u_core/u_reg[3]  ← 说明这个寄存器贡献了 12 条违例

这个"状态变量"的思路比 -A/-B 可靠得多：报告里两个信息的距离不固定时，就别数行数，让 awk 帮你记。

工作场景 · 这段脚本组长真的会用

布局布线跑完，报告 30 万行。组长在群里问："最差多少？有几条违例？集中在哪？"

你把上面三条命令贴过去，30 秒回答完。这就是"会用 Linux"和"不会用"的差距——不是知识差距，是效率差距。

更实际的一点：这三个数决定了下一步干什么。最差 -0.35ns 且集中在 u_mul，说明是乘法器那片布局太挤，而不是全局问题；这时候该回 floorplan 看 macro 间距，而不是盲目插 buffer。

配角三件套：sort / uniq / wc

三个"看起来不重要、但每个管道里都有"的命令。

bash
# 作用：排序、去重计数、统计；在报告所在目录执行sort -n nums.txt                # -n = numeric，按数值排（不加就是字典序，-0.9 会排错）sort -k2 -n paths.rpt           # -k2 = 按第 2 列排序sort -k2 -n -r paths.rpt        # -r = reverse，倒序（找最大值用）sort -u names.txt               # -u = unique，排序的同时去重grep -v '^#' paths.rpt | awk '{print $1}' | cut -d/ -f2 | sort | uniq -c   # 按模块名聚合计数wc -l paths.rpt                 # 行数wc -lw paths.rpt                # 行数 + 单词数wc -c paths.rpt                 # 字节数（判断文件是不是空的第二招）cut -d: -f1 /etc/passwd         # -d 指定分隔符，-f1 取第 1 段（简单取列比 awk 快）cut -d' ' -f1-3 paths.rpt       # 取第 1 到第 3 段

uniq -c 有个必须记住的前提：它只合并"相邻"的重复行。所以永远是 sort | uniq -c，不能 uniq -c 单独用——单独用的时候，中间隔了一行的重复项算不出来，而结果看起来完全正常。

手算一次"违例率"：paths.rpt 里 8 条路径，slack 依次是

-0.12, 0.31, -0.35, 0.04, -0.08, 0.22, -0.21, 0.15

负数的有 4 条（-0.12、-0.35、-0.08、-0.21），所以违例率 4 ÷ 8 = 50%。

平均 slack：(-0.12 + 0.31 - 0.35 + 0.04 - 0.08 + 0.22 - 0.21 + 0.15) ÷ 8 = -0.04 ÷ 8 = -0.005 ns

也就是平均还差 5ps。这个数很有用：如果平均是 -5ps、最差是 -350ps，说明只有个别路径烂，整体健康；如果平均是 -200ps，说明是整个设计的问题，改约束比修路径更有效。

在真机上用 awk 一次算出来（跳过表头）：

bash
# 作用：一次算出条数、总和、平均值；真机执行（模拟终端不支持累加）awk 'NR>1 {s+=$2; n++} END {printf "n=%d sum=%.3f avg=%.4f\n", n, s, s/n}' paths.rpt# 输出：n=8 sum=-0.040 avg=-0.0050

awk 的 SUM / AVG：三种写法，一个坑

最短的写法是 awk '{s+=$1} END{print s/NR}'。它只对"没有表头、每一行都要算"的文件成立；而报告几乎都有表头，所以真实写法要处理三件事：跳表头、累加、用参与计算的行数当分母。

bash
# 作用：SUM / AVG 的三种写法，从最简到能上生产# 用法：在报告目录执行；paths.rpt 第 2 列是 slack，第 1 行是表头awk '{s+=$1} END{print s/NR}' nums.txt              # 最简：无表头时才成立，NR 正好是行数awk 'NR>1 {s+=$2} END{print s/(NR-1)}' paths.rpt    # 有表头：跳过第 1 行，分母也要减 1awk 'NR>1 {s+=$2; n++} END{printf "n=%d sum=%.3f avg=%.4f\n", n, s, s/n}' paths.rpt# 最稳：自己数 n，分母永远等于"真正参与计算的行数"

第二种写法就是那个坑：NR>1 只跳过了表头，NR 仍然是总行数（含表头），所以 s/NR 的分母多 1。结果不是报错，是"看起来很正常的一个错数"。

拿上一节那 8 条路径算一遍，把三种分母的差别摊开：

  • 参与计算的行：8 条（第 1 行是表头，不算）
  • 总和：-0.12 + 0.31 - 0.35 + 0.04 - 0.08 + 0.22 - 0.21 + 0.15 = -0.040
  • 正确平均：-0.040 ÷ 8 = -0.005 ns
  • 用错分母：-0.040 ÷ 9 ≈ -0.0044 ns

差 0.0006ns 看着无所谓，但它说明统计口径错了。等你算"违例路径的平均值"时，分母从 4 变 5，误差就是 20%，结论直接反过来。

再给一个能上生产的版本，一次输出条数、总和、均值、最差：

bash
# 作用：一份摘要表的四件套统计；min 用第一条数据做初值，避免 0 干扰# 用法：paths.rpt 第 2 列是 slack，第 1 行是表头awk 'NR==2 {min=$2} NR>1 {s+=$2; n++; if ($2<min) min=$2} END {printf "n=%d sum=%.3f avg=%.4f min=%.3f\n", n, s, s/n, min}' paths.rpt# NR==2  先把第一条数据当成"当前最小值"# NR>1   从第 2 行开始累加、计数、比较# END    一次输出四个数：条数 / 总和 / 均值 / 最差

预期输出：n=8 sum=-0.040 avg=-0.0050 min=-0.350。

为什么 min 要单独处理初值？awk 的变量默认是 0。 如果所有 slack 都是正的，从 0 开始比较就永远得到 0——"最差是 0"这种结论比算错更危险，它会让你以为还有余量，直接签核。

一条命令的解剖：从 30 万行到一行

真正干活时，你拼出来的命令往往有四五个管道。看不懂不可怕，可怕的是不知道哪一段出了问题。

把最常用的那条命令逐段拆开：

bash
# 作用：从 report_timing 全量输出里，找出最差 slack 出现在第几行# 用法：在 pnr/reports 下执行；timing.rpt 是 report_timing 的重定向输出grep "slack (" timing.rpt | awk '{print $NF}' | sort -n | head -1 | xargs -I{} grep -n -- "{}" timing.rpt# 最后一段的 -- 不能省：-0.213 以减号开头，不加 -- 会被 grep 当成选项，报 invalid option
段在干什么去掉它会怎样
grep "slack ("只留 slack 行（( 避免匹配到别处出现的 slack 字样）所有行都进管道，后面全乱
awk '{print $NF}'取最后一列，也就是数值排序时按整行字符串排，结果错
sort -n按数值升序不排序则 head -1 只是第一行
head -1取最小值（最差）没有"最差"这个概念
xargs -I{}把上一步的结果填到下一段的 {} 位置无法把数字当作参数传给下一条命令
grep -n -- "{}"拿这个数回原文件找它出现在第几行只得到一个数字，不知道是哪条路径

拆管道的方法：每加一段就回车看一次输出。

bash
# 作用：逐段验证，定位是哪一段出错；在报告目录执行grep "slack (" timing.rpt | head -3        # 第一段：确认能捞到行grep "slack (" timing.rpt | awk '{print $NF}' | head -3   # 第二段：确认取到的是数字... | sort -n | head -3                    # 第三段：确认排序方向对（最差在最前）

这是最实用的调试方法：管道越长，越要分段看。一次性写完再回车，报错信息只会告诉你"最后一段没输入"，不会告诉你哪一段断了。

管道没输出时的五种断点

"命令跑完了，什么都没显示"是最常见的困惑。按这个顺序查，五种原因覆盖 95% 的情况：

#原因怎么验证怎么修
1真的没有匹配去掉管道单独跑第一段换关键词；确认大小写
2文件不对/是空的wc -l 文件检查路径；上游是否真的产出了报告
3大小写不一致加 -i 试一次报告里是 Slack，你搜的是 slack
4特殊字符被当正则加 -F 试一次搜 reg_b[3] 这类名字必须 -F
5上一条命令的错误流没进来加 2>&1错误在 stderr，管道只接 stdout

第 5 条最隐蔽：工具 | grep Error 什么都没捞到，因为工具的报错走的是 stderr（2 号），而管道只接 stdout（1 号）。正确写法是 工具 2>&1 | grep Error。

还有一个更工程化的做法：在脚本开头加 set -o pipefail。默认情况下，管道的返回码是最后一段的返回码——grep 没匹配到返回 1，但后面的 wc -l 成功返回 0，整条管道就算"成功"，你的脚本会带着空结果继续往下跑。加了 pipefail，任何一段失败整条管道就失败。

bash
#!/bin/bash# ↑ shebang 必须在第一行，前面不能有任何注释或空行# 作用：让管道里的失败不被吞掉；放在脚本开头set -e              # 任何命令失败就退出set -o pipefail     # 管道中任意一段失败，整条管道算失败（默认只看最后一段）set -u              # 用到未定义变量就报错，防止 $DIR 为空导致 rm -rf /
动手动手：自己造一份报告并分析

任务：造一份假的时序摘要，回答三个问题：几条违例、最差多少、集中在哪。

bash
# 作用：造数据 + 三步分析；在 ~/demo 下执行（没有就 mkdir -p ~/demo）cd ~/demo 2>/dev/null || { mkdir -p ~/demo && cd ~/demo; } cat > paths.rpt <<'EOF'# endpoint                        slack    cells  length(um)u_core/u_alu/reg_b[3]             -0.12     42     118.4u_core/u_alu/reg_c[0]              0.31     28      76.2u_core/u_mul/reg_p[7]             -0.35     57     203.8u_core/u_ctrl/state_reg[2]         0.04     19      41.6u_ram/u_sram/DO[31]               -0.08     33      92.5u_core/u_alu/reg_a[5]              0.22     24      63.1u_core/u_mul/reg_p[6]             -0.21     51     187.3u_dma/u_fifo/wr_ptr[4]             0.15     26      70.9EOF grep -v '^#' paths.rpt | awk '$2<0' | wc -l      # 1. 有几条违例 → 4grep -v '^#' paths.rpt | sort -k2 -n | head -1   # 2. 最差 slack → -0.35，在 u_mul/reg_p[7]grep -v '^#' paths.rpt | awk '$2<0 {print $1}' | cut -d/ -f2 | sort | uniq -c | sort -rn# 3. 违例集中在哪个模块 → 按路径第 2 段（模块名）统计

自测：先自己想，再点开答案
run.sh > run.log 2>&1 里 2>&1 是什么意思？
把标准错误（文件描述符 2）重定向到标准输出（1）当前指向的地方，也就是同一个日志文件。顺序不能反，写成 2>&1 > run.log 错误仍会留在屏幕上。
grep -A 3 Error 和 grep -B 3 Error 有什么区别？
-A 是命中行之后多显示 3 行（after），-B 是之前多显示 3 行（before），-C 是前后各 3 行。
怎么打印一份报告里从 Startpoint 到 Endpoint 之间的内容？
sed -n '/Startpoint/,/Endpoint/p' report，-n 关掉默认打印，p 只打印区间内的行。
awk '{print $NF}' 里的 NF 是什么？
Number of Fields，当前行的字段总数，所以 $NF 就是最后一列。列数不固定时用它比写死列号稳。
为什么在 200MB 日志里找错误要加 -m 1？
-m 1 命中第一个就停止，避免扫完整个文件；而且第一个错误通常才是根因，后面的多是连锁反应。
sort 不加 -n 会发生什么？
按字典序排序，-0.9 会排在 -0.1 前面（因为字符 9 大于 1），你会拿到错误的"最差值"，而且结果看起来很正常。
uniq -c 为什么必须先 sort？
uniq 只合并相邻的重复行。不排序时，中间隔了别的行的重复项不会被合并，计数会偏小且毫无提示。
搜 u_core/u_alu/reg_b[3] 为什么搜不到，怎么修？
[3] 在正则里是"匹配字符 3 的字符类"，实际被匹配成 reg_b3。加 -F 按纯文本搜索。
awk 'NR>1 {s+=$2} END {print s}' 里的 NR>1 为什么要加？
跳过第 1 行表头。表头第 2 列是文字（如 slack），参与计算会让条数多 1、平均值偏掉。
工具报错为什么用管道 grep 捞不到？
工具的报错走 stderr（2 号），管道只接 stdout（1 号）。要写成 工具 2>&1 再接 grep。
