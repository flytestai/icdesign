Placement：几万个单元怎么摆

Placement

布局是在四个互相打架的目标之间找平衡：线长、拥塞、时序、电源。这一课讲清三个指标怎么读、density 与 target_density 的关系、参数逐个什么意思、扫描链为什么必须重排，以及什么时候该认输回去改 floorplan。

约 45 分钟 课表学时 4 Innovusplacement拥塞密度HPWL
01

布局在权衡什么

本章目标学完这一课，你能读懂 place 之后的密度、拥塞、HPWL 三份数据，判断这一版该继续优化、该调参数、还是该回 floorplan 重来，并且说得出判断依据。

先想一个场景：两百人的考场，认识的同学习惯性坐一起。让他们随便坐，凑得近的那几堆没路可走；按学号散开坐，路是通了，但要传纸条得跨三个区。

布局（placement）就是排这个座位。几万个标准单元，有连线的想凑近（线短），但不能挤到没地方走线（拥塞），同时"快交卷的那几位"（关键路径）还得单独照顾（时序），最后整片还不能局部过热（电源）。

四个目标，两两冲突：

想改善通常牺牲为什么
线长更短拥塞单元挤在一起，局部走线需求超过轨道数
拥塞更松线长、时序单元摊开，连线变长，延迟变大
时序更好面积、功耗、拥塞关键路径加 buffer、换大驱动单元
电源更稳面积降密度、拉大间距、加去耦单元

所以布局没有"最优解"，只有"这一版在四个目标上的取舍"。工具给你的是它认为的加权最优，你要判断的是权重给对了没有。

把常见动作单独拎出来看，四个目标各自怎么变，一目了然：

动作线长拥塞时序功耗
提高 target_density（挤紧）变好变差先好后差（挤到绕线就崩）略好
降低 target_density（摊开）变差变好变差（线长涨）变差
提高 timing_effort略差变差变好变差（多插 buffer）
提高 cong_effort变差变好略差略差（绕线变长）
关键路径加 buffer / 换大驱动略好变差变好明显变差
扫描链重排明显变好明显变好不变（false path）变好
局部加禁放区略差变好（局部）略差略差

这张表只有一个目的：让你放弃"找一个只改善一件事的旋钮"这个念头。 它不存在。每调一个参数，至少有一个目标会变差，问题是那个"变差"你能不能接受。

所以真正的决策顺序是分层的，不是四个目标平权：

  1. 时序是门槛：setup/hold 违例不能留到签核，这一条不满足，其他三项再好也没用。
  2. 拥塞是硬约束：布不通，后面全部作废，所以 overflow 超过阈值时必须先解决它。
  3. 线长和功耗是优化项：在 1、2 都满足的前提下，谁的余量大就先优化谁。

新手常犯的错是把四项平权，结果"每项都还行，但没有一项达标"。评审要看的是"哪一项已经到红线"，不是"四项的平均分"。

工具内部走三步：

  1. 全局布局（global placement）：先解一个连续优化问题，允许单元重叠，目标是最小化总线长（用 HPWL 近似）。
  2. 合法化（legalize）：把重叠的单元挪开，落到合法的行（row）和站点（site）上。
  3. 详细布局（detail placement）：在合法位置上做小范围微调，顺手修站点对齐、pin access 之类的问题。

时序驱动是怎么加进去的？靠线网加权（net weighting）：给关键路径上的连线更高的权重，工具在最小化线长时会优先把这几个 net 拉短。这就是 timing_effort 参数在控制的东西。

Legalize合法化点击看解释

把单元的连续坐标调整到"行"上、对齐到"站点"网格、且互不重叠的过程。
没合法化的位置叫 illegal，工具不能布线。合法化一定会让线长变差一点（因为不能停在最优位置），这部分损失是必须付的。

工作场景 · 周二下午，overflow 3200

place 跑完，你打开 reportCongestion，总 overflow 3200，热点集中在两个 SRAM 之间那条通道里。同时 density 热图很均匀，平均只有 0.68。

组长的三个问题：

  1. "调 cong_effort 能救吗？"——你不能凭感觉答，得知道 overflow 是"分配不均"还是"空间不够"。
  2. "现在改 floorplan 要多久？"——两天。所以你得先证明"不改不行"。
  3. "如果先往下走 CTS，最坏会怎样？"——CTS 会往里插几千个 buffer，密度再涨一截，现在 3200 会变成多少？

这三个问题的答案决定这一版是"调参数"还是"回退"。这一课最后两节就是回答它们。

工作中怎么用：place 是 PR 工程师的主战场，通常跑 2~3 轮。第一轮看趋势（哪里挤），第二轮调参数，第三轮才追时序。布局阶段定下全片 70%~80% 的线长，后面 CTS 和 route 只能在这个基础上微调。所以布局做完必须存盘 + 存报告，因为它是后面所有对比的基线。

02

三个关键指标

三个数，三种问法：放得下吗（密度）、走得通吗（拥塞）、绕得远吗（线长）。

指标一：利用率（utilization）

标准单元总面积 ÷ 可放置标准单元的面积。它的完整定义和两种口径在第 13 课讲过，这里只说 place 阶段的新问题：place 之后的利用率一定比 floorplan 时高。

原因是工具在布局时会顺手插一些 buffer（修 DRV、隔离、时钟预缓冲），实例数增加 5%~15%。所以 floorplan 时按 0.62 起，place 完看到 0.70 是正常的；如果 place 完直接看到 0.80，说明 floorplan 时算少了。

密度高不高，最终要看版图上"单元行被填满"的样子。

从图里要看出什么：密度问题在版图上是"成片"的，拥塞问题是"顺着通道"的。这张图上红色成片出现，说明是那一整块区域的可用 row 不够；如果红条是细长地贴着某条通道，那是走线需求的问题（下一节）。两种红的修法完全不同。

指标二：拥塞（congestion）

把芯片切成很多小格子（grid），每个格子统计"要过多少根线"和"有几条轨道"：

text
overflow = 走线需求（demand） − 可用轨道（capacity）

单格 overflow 大于 0 就叫溢出，全片加起来就是 Total Overflow。它是个"预估值"——此时还没真布线，工具用统计模型估每条 net 会走哪、要多宽。

判断标准（40nm 量级，典型值）：

Total Overflow判断动作
0理想直接往下走
1~500可接受布线工具能消化，记下来
500~2000危险先调参数/加局部禁放区，再看
> 2000不可接受基本要回 floorplan

关键不是总数，是分布。 3200 均匀撒在全片，可能只是密度略高，加 3% 面积就解决；3200 全挤在一条 6µm 的通道里，那是物理空间不够，调任何参数都没用。

"分布"这件事看热图最快：

从图里要看出什么：红斑的位置就是问题的地址。红斑贴着两条 macro 之间 → 通道宽度问题，回 floorplan；红斑在标准单元区中间、形状不规则 → 密度问题，调 target_density 或加局部禁放区。这就是"为什么说拥塞大多是上游造成的，不是布线器不努力"——布线器只能在既有空间里绕，空间不够它也没办法。

指标三：HPWL（半周长线长）

HPWL（Half-Perimeter Wirelength，半周长线长）是最常用的线长估计：对每根 net，画一个能把所有引脚包住的最小矩形，取它周长的一半。

text
HPWL(net) = (max_x − min_x) + (max_y − min_y)全设计 HPWL = Σ HPWL(每根 net)

手算一根三引脚 net：引脚坐标 (10,20)、(30,50)、(45,25)。

text
max_x − min_x = 45 − 10 = 35max_y − min_y = 50 − 20 = 30HPWL = 35 + 30 = 65 µm

这根 net 的真实布线长度通常是 HPWL 的 1.2~1.5 倍（典型值）——因为线要绕障碍、要换层、要在引脚处逃逸。所以 HPWL 只适合做相对比较：这一版比上一版降了 8%，说明布局变好了；不能拿它当"这一版线长 65µm"去报数。

HPWL 的两个盲区必须知道：它看不见障碍（一根 net 跨过 SRAM，HPWL 算得很短，实际要绕一大圈），也看不见层（不知道这根线能不能用上层）。所以它和拥塞要一起看。

HPWL半周长线长点击看解释

Half-Perimeter Wirelength。把所有引脚包住的最小外框，周长的一半。
它是估计值，不是测量值，真实线长通常还要乘 1.2~1.5。用途只有一个：同一设计不同版本之间比大小。

Bin网格点击看解释

工具把 core 切成的小方格，常见 5~20µm 见方。密度、拥塞都按 bin 统计，报告里的"热点"就是某个 bin 超标。
bin 越小，定位越准，但统计噪声越大；bin 越大，趋势越清楚，但会漏掉局部尖峰。

工作中怎么用：三个指标要一起报。只报 overflow 0 不报密度，等于说"路不堵"但没说"车停哪"；只报 HPWL 降了不报 overflow，等于说"路修短了"但没说"路是不是变窄了"。

03

密度和 target_density 到底是什么关系

这两个词经常被混着说，其实是两件事。

密度（density）是结果：某个 bin 里，标准单元占了多少可用面积。

text
bin_density = bin 内标准单元面积 ÷ bin 内可用 row 面积

target_density 是输入：你告诉布局工具"我希望整体摊到多密"，它会按这个目标去决定单元之间的平均间距。

text
place 时的平均间距 ≈ f(target_density)target_density 0.65 → 单元之间平均留 35% 空隙target_density 0.85 → 平均只留 15% 空隙

所以 target_density 调高，工具会把单元挤得更紧，局部 density 随之升高，overflow 跟着涨。这就是"省面积"和"布得通"之间的那个旋钮。

为什么不能设到 0.95？三个硬约束：

  1. row 是按 site 切的，一个 bin 里可用面积本来就只有 80%~90%（row 边界、tap cell、去耦单元占位），0.95 的目标实际上无解。
  2. 后面还要塞东西：CTS 插 buffer（实例数 +20%~30%）、route 插 repeater、ECO 修 hold 插 delay cell。place 时 0.70，CTS 后可能就 0.85 了。
  3. pin access 需要空隙：单元贴太紧，布线连引脚都接不出来，会出现"密度不高但布不通"的怪现象。

手算一次，看清"预留"这件事。core 可用 row 面积 77419µm²，标准单元 48000µm²：

text
place 时密度 = 48000 ÷ 77419 = 62%CTS 后实例增加 25%（插 buffer）→ 有效面积 48000 × 1.25 = 60000CTS 后密度 = 60000 ÷ 77419 = 77.5%route 再插 5% → 63% → 81%

62% 起步，最后落到 80% 左右，这是健康曲线。如果你 place 时就按 0.80 起步，CTS 后必然 95%+，布线阶段只能拆线。

这张"起步该给多少"的取舍，图里画得更直观：

从图里要看出什么：利用率的风险不是线性的，0.60 到 0.75 之间几乎没差别，0.75 以上每加 5 个点，风险陡增。而且图上的手算告诉你分母是谁——是"可用 row 面积"，不是 die 面积，更不是 core 面积。

Target Density目标密度点击看解释

给布局工具的输入参数，控制单元平均摊多开。不是结果，是"我希望多密"。
它和 utilization 的区别：utilization 是事后统计的实际占用比例，target_density 是事前给的优化目标，两者通常差 3~8 个百分点（工具会为了时序/拥塞在局部偏离目标）。

一个是全局参数，一个是局部结果

这两个词被混用，根源是它们中文都叫"密度"。用"全局 / 局部"切开就清楚了：

对比项target_densitydensity
性质输入参数（你给工具的目标）输出结果（工具算出来的）
有几个数全局 1 个，整个设计共用一个每个 bin 一个，几万个数
谁产生你在 setPlaceMode 里设工具布局完之后统计
怎么判断好坏看这个值合不合理看分布、看峰值，不看平均
发现问题怎么改改参数重跑改不了它，只能改参数或改布局
典型误用拉到 0.90 想省面积只看平均值就签字

"全局一个数"和"局部几万个数"的差别，正是所有误判的来源。

工具拿到 0.68 这个全局目标，会尽量让整个设计的平均密度落在 0.68 附近。但它是"平均"——有的 bin 是 0.55（留白多），有的 bin 是 0.92（几乎塞满），平均下来正好 0.68。平均达标，不代表每个地方都达标。

手算一次这个偏差有多大：core 切成 10µm 见方的 bin（以本课后面实验用的 3mm 模块为例），3000×3000µm 就是 9 万个 bin。假设平均密度 0.68、标准差 0.08（典型量级），那么按正态分布，超过 0.68 + 3×0.08 = 0.92 的 bin 约占 0.13%，也就是一百多个 bin 已经塞死。这 100 多个 bin 就是布线时最先爆的地方。

所以布局后的判断标准必须是两条：

  • 平均值：report_area 的 utilization，用来和 floorplan 的目标对；
  • 峰值和分布：密度热图里最红的那块是多少，红色占多大面积。

只报平均值的人，等于说"这栋楼平均每间住 2 人"，却不提有一间住了 8 个。评审要看的是最挤那间。

常见坑 · 把 target_density 拉到 0.9 想省面积

现象：为了不改 die 尺寸，把 -place_global_max_density 0.90。place 跑完 overflow 4000，density 热图一片深红。

原因：0.9 意味着平均只留 10% 空隙，而 bin 内可用面积本来就只有 85% 左右，实际局部密度直接冲到 0.95+。单元挤在一起，每个 bin 的走线需求都超过轨道数。

处理：target_density 一次只调 0.03~0.05，调完立刻看 overflow。真正该做的是承认面积不够——省下来的那 8% 面积，要用两三天布线调试来换，而且经常换不回来。

工作中怎么用：target_density 是少数"调一下立刻看到效果"的参数，所以最容易被拿来救火。规矩是：一次只动 0.03，动完同时看 overflow 和 HPWL——只降一个说明你只是把问题挪了地方。

04

命令与参数

Innovus 的主力命令是 place_opt_design，纯布局用 placeDesign。

tcl
# 作用：时序/拥塞双驱动的全局布局 + 合法化 + 初步优化（插 buffer、换单元）# 用法：floorplan 与电源规划之后执行；参数先逐条 setPlaceMode 设好，再跑 placesetPlaceMode -place_global_timing_effort high      ;# 时序优化力度：high 更慢，但关键路径更短setPlaceMode -place_global_cong_effort   high      ;# 拥塞缓解力度：high 会主动把单元摊开setPlaceMode -place_global_place_io_pins false     ;# 不动 IO 引脚：位置是 floorplan/封装定的setPlaceMode -place_global_reorder_scan  true      ;# 布局时顺手重排扫描链（下一节详说）setPlaceMode -place_global_max_density   0.72      ;# 目标密度 72%，给 CTS 留 20 个点余量 place_opt_design                                   ;# 真正执行：全局布局 → 合法化 → pre-CTS 优化

注意：Tcl 里换行要用 \ 结尾，而 \ 后面不能再跟注释。所以这里拆成多条 setPlaceMode（它们会累加），每条行尾用 ;# 接注释——这是 Tcl 唯一安全的行尾注释写法。

参数逐个解释：

参数含义给错的后果
timing_effort high关键路径加权更重、迭代更多跑得慢（可能 2~3 倍），但 WNS 通常好 5%~15%

place_io_pins false不移动 IO 引脚设 true 会把引脚挪位置，和封装对不上，等于白做 floorplan

max_density 0.72目标密度太高布不通，太低浪费面积（<0.55 基本等于 die 做大了一档）

place_opt_design 和 placeDesign 的区别要记牢：

命令做什么什么时候用

place_opt_design -incremental在当前布局基础上做增量优化第二轮微调，不想全推翻

timeDesign 会一次生成一整套报告（summary、最差路径、DRV），比一条条 report_timing 省事，也更接近签核口径。

05

扫描链重排：一个容易忽略的步骤

DFT（可测性设计）会把几千个触发器串成一条长链，用于测试时逐位灌数据。问题是：这条链的顺序由综合工具按逻辑层次决定，和物理位置毫无关系。

一条 3000 个触发器的扫描链，按逻辑顺序连，物理上可能从芯片左上角一路窜到右下角再折回来。它是一根人为造出来的超长 net，占布线资源、制造拥塞、还会引起天线违例。

扫描链重排（scan chain reorder）就是把链的顺序按物理位置重排：物理上相邻的触发器串在一起。

tcl
# 作用：布局之后按物理位置重排扫描链# 用法：place 完成之后、CTS 之前执行；也可以让 placer 顺手做（见上一节的 reorder_scan）scanReorder                        ;# 全设计重排：读实例坐标，重连 scan chaincheckScanChain                     ;# 检查重排后链是否完整（长度、lockup 顺序、时钟域）# 上面这条在不同版本里可能叫 checkScanChain 或 reportScanChain，敲之前 man 一下确认

为什么这一步最容易被忽略？ 三个原因：

  1. 它不报错。不重排，流程照样跑完，DRC 也可能清干净，只是线更长、更挤。
  2. 它不改功能。测试模式下链的顺序无所谓，所以功能验证不会发现任何问题。
  3. 它不在"时序"报表里。扫描链是测试路径，通常被设成 false path，STA 报告里根本看不到它的延迟。

后果是可以量化的。3000 个触发器，逻辑顺序连 vs 物理顺序连（课程环境实测的那组数据里，这一类链的线长差 30%~50%）：线长降 40%，等于少占 40% 的轨道。一条链占的资源和 3000 根普通 net 差不多，不做重排等于白扔一片区域的布线空间。

重排有两类约束不能破：链的顺序语义（前一级的输出必须进下一级的输入，中间不能插东西）和时钟域（跨时钟域的链要靠 lockup latch，重排时不能把两个域的触发器串到一起）。所以重排完一定要 checkScanChain，不能只看线长。

Scan Chain Reorder扫描链重排点击看解释

按物理位置重新排列扫描链中触发器的连接顺序，缩短线长、降低拥塞。
它只改测试链的连接，不改功能逻辑；但改完必须重跑链完整性检查，因为顺序和锁存器位置有硬约束。

工作场景 · 不做扫描链重排的后果

一条 3000 个触发器的扫描链，逻辑顺序连，飞线图上是满片乱窜的蜘蛛网。

布线跑到一半，这条链所在区域 overflow 一直降不下来。你以为是密度问题，加了一堆禁放区，结果只是把拥塞推到了旁边。

关掉扫描链（临时设成 ideal 或直接删掉）再跑一次，overflow 立刻掉 30%——问题找到了，但已经浪费了半天。

工作中怎么用：重排放 place 之后、CTS 之前，跑完把线长数字记进交接记录。如果 DFT 团队后面还要改链（加测试点、改压缩结构），必须重跑一次——链一变，重排结果就废了。

五份报告，各看一行

上面五项对应五份要归档的东西。每一份只需要先看一行——那一行不对，后面几百行不用看：

#报告生成命令先看哪一行判据

5线长 place_wl.rptreportWirelengthTotal HPWL不比上一版涨 15%

三条使用纪律：

  • 第 2 和第 4 必须存完整报告，其余存一行数字就够。因为 CTS 和 route 出问题时，第一件事是拿现在的拥塞和时序跟布局时对比——没有完整报告，你只能看到"变差了"，看不到"从哪一项开始变差"。
  • 报告文件名带版本号和日期，否则一周后分不清哪份对应哪一版数据库（第 10 课讲过这个坑）。
  • 第 1 项不过，后面四项都不用看。 合法性是 0 与 1 的关系，不是"差不多就行"——有违例的布局，工具连布线都不会启动。

第 4 项有个纪律：先确认约束，再怀疑布局。 布局"看起来不错但时序一塌糊涂"，八成是约束问题——时钟周期写错、false path 漏设、setup 用了 fast corner。查约束的顺序是：report_clocks 看周期 → report_timing -path_group 看违例集中在哪个域 → 抽一条路径看延迟构成。

常见坑 · 布局"看起来很整齐"，但时序一塌糊涂

现象：reportDensityMap 很均匀、reportCongestion overflow 接近 0，但 reportTiming 有 200 条 setup 违例，最差 −0.4ns。

原因通常是三类：约束错（周期写短了、false path 没设）、库 corner 错（用 FF 快 corner 算 setup）、时序没参与布局（timing_effort 给 low，工具只优化线长）。

排查顺序（照这个顺序，别跳）：

  1. report_clocks：周期、波形、端口对不对。
  2. report_timing -path_group：违例是不是全集中在某一个时钟域。
  3. 抽一条 report_timing -from ... -to ... -path_type full_clock_expanded：看延迟是 cell 多还是 net 多。
  4. 以上都正常，才回去看 setPlaceMode 的 timing_effort 是不是被设成了 low。

不要一上来就改布局参数——约束错了，改什么参数都是在错的地基上盖楼。

工作中怎么用：五项里第 2、4 项要存报告，第 1、3、5 项存数字。因为 CTS 和 route 出问题时，第一件事就是拿现在的数和布局时的数对比——没有基线，你连"变差了"都说不清。

07

什么情况要回退改 floorplan

这是布局阶段最重要的判断，也是最难开口的判断（因为回退意味着两天）。

判据只有一句话：问题是"分配不均"还是"空间不够"？

  • 分配不均 → 能在 place 里解决（调参数、加局部禁放区、局部降密度）。
  • 空间不够 → 必须回 floorplan（加 die、改通道、挪 macro）。

五种典型症状，对应五种结论：

症状数据特征结论代价
拥塞集中在宏单元之间的通道热点坐标落在两条 macro 边之间，通道宽度 < 估算值回退：通道物理不够，任何参数都救不了高：改 floorplan，2 天
拥塞均匀分布全片热点几十处，每处 overflow 一两百，density 普遍 0.85+回退：整体面积不够高：加 die 或提利用率
局部一小片特别挤热点 1~2 处，范围几十微米，周围 density 正常不回退：加 partial blockage 或局部降密度低：半天
时序差且路径横跨全片最差路径的起点终点在芯片对角，flyline 显示中间被 macro 隔断回退：macro 把相关逻辑分开了中高：挪 macro，1 天
长宽比 >1.5 导致单向拥塞overflow 集中在短边方向的通道回退：die 形状问题高：改长宽比

判断流程可以固化成四步：

  1. 打开拥塞热图，把热点坐标抄下来，对照 floorplan 图看它落在哪。
  2. 落在 macro 通道里 → 量通道宽度，和课程 13 的公式算出来的值比。小于估算值 80% → 回退。
  3. 落在标准单元区内部，且该区域 density > 0.9 → 看全片平均 density。全片都高 → 回退加面积；只有这里高 → 加禁放区摊开。
  4. 都不符合，看时序：最差路径跨全片 → 这个问题 place 解决不了，是 macro 摆错了。

最后一条经验：改 floorplan 的成本是 2 天，硬扛着往下走的成本通常是 3~5 天，而且风险更高。 因为 CTS 会往里插 20%~30% 的实例，现在 3200 的 overflow，CTS 后往往变 5000。你在 place 阶段看到的拥塞，是"最好的情况"。

工作中怎么用：回退的决定要在 review 会上做，不要一个人扛。带上三样东西——拥塞热图、通道宽度与估算值的对比、以及"继续往下走"的最坏估计。组长要听的不是"我觉得布不通"，而是"批我两天，能换回什么"。

Net Weighting线网加权点击看解释

给不同 net 设不同权重，引导布局工具优先缩短重要的线。关键路径上的 net 权重高，普通 net 权重低。
timing_effort 调的就是这套权重的激进程度。权重给得太高，工具会为了几条关键路径把周围单元全拽过来，造成局部拥塞——时序和拥塞的冲突，本质是权重的冲突。

常见坑 · 用 place 参数硬扛 floorplan 的问题

现象：overflow 3200，你连续调了 cong_effort、max_density、加了三块禁放区，overflow 降到 1800，看起来"解决了"。

代价：线长涨了 12%，WNS 从 −0.05 变成 −0.22，密度热图从"一处红"变成"到处浅红"。CTS 一跑，overflow 回到 4000。

原因：所有 place 参数都是在"既定空间里重新分配"，空间本身没变。你把拥塞从 A 推到 B，总量没减少。

判断方法：调完参数后看总 HPWL。如果 overflow 降了但 HPWL 涨了 10% 以上，说明你只是把问题摊平了，不是解决了。这种情况该回 floorplan。

动手动手：读一份拥塞报告，判断该不该回退

任务：给一份 place 后的拥塞报告和三条信息，判断下一步动作。

bash
# 作用：造一份典型的 reportCongestion 摘录，练"看分布不看总数"# 用法：任意目录 bash 直接跑，生成 cong.rpt 再用 awk 统计cat > cong.rpt <<'EOF'Layer    Total Capacity   Total Usage   OverflowM2       120000           118900        0M3       120000           122500        2500M4       120000           119200        0M5       120000           117800        0Region (1200 800) (1800 1400): overflow 1800Region (300 2600) (700 3000): overflow 700EOF # 哪一层最拥塞awk 'NR>1 && $4 ~ /^[0-9]+$/ && $4>0 {print $1, "overflow="$4}' cong.rpt   # 只打 overflow>0 的层# 总 overflow（只累加数字行，跳过 Region 行）awk 'NR>1 && $4 ~ /^[0-9]+$/ {s+=$4} END {print "total:", s}' cong.rpt

预期：M3 overflow 2500，total 2500。

已知条件：

  • 设计 core 是 3000µm × 3000µm，热点 (1200,800)-(1800,1400) 正好在两个 SRAM 之间，通道实际宽度 12µm。
  • 按课程 13 的公式，这条通道应该留 45µm。
  • 全片平均 density 0.68，热点区域 density 0.71。

回答四个问题：

  1. 总 overflow 2500 属于哪一档？（对照本课的判断表）
  2. 问题是"分配不均"还是"空间不够"？依据是什么？
  3. 调 cong_effort high 有用吗？为什么？
  4. 下一步动作是什么，代价多大？

参考答案：2500 属于"不可接受"；空间不够——因为热点精确落在 macro 通道，且实际宽度 12µm 只有需求 45µm 的 27%，而周围 density 正常（0.71），说明不是单元太多，是通道太窄；调参数无用，因为 place 只能在既定空间里重分配，通道宽度的上限是物理的；下一步是回 floorplan 把这条通道加宽到 45µm（可能要挪 SRAM 或加 die），代价约 2 天。

过关标准：能说出"为什么 density 正常却拥塞"——因为拥塞是走线需求除以轨道数，和单元密度不是一回事：引脚密集的地方，单元不多也会拥塞。

自测：先自己想，再点开答案
布局在权衡哪四个目标？举一组互相冲突的例子。
线长、拥塞、时序、电源。比如把有连接的单元凑近能缩短线长，但局部走线需求超过轨道数就拥塞。
为什么 place 之后的利用率一定比 floorplan 时高？
布局时会插 buffer/隔离单元/时钟预缓冲，实例数增加 5%~15%，分子变大；同时分母（可用 row）没变。
overflow 是什么？总数大就一定要回退吗？
overflow = 走线需求 − 可用轨道，单格大于 0 就是溢出。不一定：要看分布，均匀分布可能只是密度略高，集中在 macro 通道才是空间不够。
HPWL 怎么算？为什么不能当真实线长报数？
把所有引脚包住的最小外框，周长的一半。它看不见障碍和层，真实布线长度通常是它的 1.2~1.5 倍，只能做版本间相对比较。
target_density 和 density 的区别？
target_density 是给工具的优化目标（输入），density 是事后统计的实际占用（结果），两者通常差 3~8 个百分点。
为什么 target_density 不能设 0.9？
bin 内可用 row 面积本来只有 85% 左右，0.9 的目标局部会冲到 0.95+；而且后面 CTS/route/ECO 还要插 25%~35% 的单元。
place_io_pins 为什么要设 false？
IO 引脚位置由 floorplan 和封装决定，布局工具挪动它会导致封装对不上，等于把 floorplan 的工作废掉。
扫描链重排为什么容易被忽略？
它不报错、不改功能、扫描路径通常设成 false path 不在时序报告里，所以三条线索都看不见它，只有拥塞和线长会受影响。
什么情况下必须回退改 floorplan？
拥塞集中在 macro 通道且宽度不足、全片密度过高、最差路径横跨全片被 macro 隔断、长宽比过大导致单向拥塞——这些都是"空间不够"或"位置不对"，place 参数解决不了。

  • 能用 (max_x − min_x) + (max_y − min_y) 手算一根 net 的 HPWL
  • 知道 overflow 要看分布而不是只看总数，能说出四个档位
  • 能解释 target_density 与 density 的区别，以及为什么不能设 0.9
  • 能逐个解释 timing_effort / cong_effort / place_io_pins / max_density 四个参数
