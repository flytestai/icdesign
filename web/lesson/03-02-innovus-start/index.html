Innovus 的使用

Using Innovus

两课时沿用同一个 40nm 案例：先从终端启动并认清界面、V/S 与对象属性，再准备输入、导入验证、保存检查点并在新会话恢复。没有工具也能用原图和教学数据完成练习。

预计学习 ≈50 分钟 课表学时 2 Innovus启动-log-files-no_gui-cpusSetMultiCpuUsageTabhelp
01

课程导入：从启动到可恢复的设计

本课沿用阶段三的同一个 40nm 案例：第一课时把工具打开、看清并选中对象；第二课时把同一设计的输入导进来，核对后保存，并在新会话中恢复。能启动、导对了、能恢复，是三个不同的验收点。

原图用于认界面，不是本课的实机验证记录。本站不提供该案例的商用软件、PDK、网表或检查点下载；有授权工具、许可证和获准使用的项目资料才执行命令，否则按每课时的桌面练习走。

02

第一课时：从 Linux 终端启动并留下日志

原图 01 是 Linux 文件管理器与终端：能看到 data/、library/、logs/、reports/、scripts/ 等，以及创建 work/ 的示例。它不是 Innovus 启动后的画面；也不需要照图使用 root 或照跑 start.sh。

  1. 登录团队提供的图形 Linux 会话，按项目说明加载工具环境，进入获准使用的个人练习目录。先看 pwd 和 ls：确认当前位置、输入从哪读、输出写到哪里；不在公共输入目录写日志或覆盖文件。
  2. 在 Linux shell 依次检查工具入口和启动帮助；任何一步出错就先停下来排查。
bash
pwdlscommand -v innovusinnovus -help

确认本版本支持 -log 后再启动 GUI；示例日志名应换成本次 run 未使用的名称。

bash
innovus -log use_lesson01.log
  1. 从启动横幅或日志确认版本，不要把 command -v 返回的路径当版本号。到 innovus ...> 提示符后才进入 Innovus 命令环境；项目 Tcl 命令应在这里输入，不是在 Linux shell 输入。日志名、实际生成位置和文件后缀以这次启动结果为准。
  2. 起不来先按现象分流：找不到命令，核对项目环境和 PATH；许可证报错，记录原文并走团队支持流程；无法开窗，核对是否在获准的图形会话。首次上手不加 -files，避免把启动故障和脚本故障混在一起。

进阶阅读：目录怎么分工、Run 与 Queue；本页另保留旧版启动资料、日志文件、启动选项和帮助用法。

03

第一课时：认主界面，分清看见与选中

看原图 09，从上往下定位：标题栏显示截图所用的 Innovus 20.1，其下是菜单和工具栏；中间黑底为版图区，右侧是对象类别、层和显示/选择控制。图中已经载入设计，红箭头标注了布局规划阶段与布局及之后的视图入口，不是空会话的启动结果。图中没截到 innovus ...> 提示符；命令输入与输出请到本次会话的终端或控制台找。

把鼠标停在图标上读提示，不按“从左数第几个”记忆。不同版本、布局和显示宽度下，位置和图标可能变动。图 02–04 是工具栏入口，不是打开工具窗口后的截图；图 05 则是右侧控制区的局部。

跟做顺序：适配全图 → 缩放局部 → 切换 V/S → 核对对象属性。 有已获准载入的同一案例只读设计或个人副本才动手；空会话无法演示对象选择，可先读图，第二课时导入后补做。

  1. 用菜单或工具栏执行 Fit，再框选放大一个区域，最后回到全图。旧资料记载 f 适配全图、z 放大、Shift+z 缩小、q 打开对象属性；先查本版本菜单或快捷键设置，并将焦点置于版图区。若不一致，用菜单或工具提示，不反复试按。
  2. 在右侧找到目标对象的类别，例如 Instance。保持 V 开、暂关 S：这类对象仍可见，但不能在版图区选中。再打开 S，清除旧选择后重选同一对象；试关 V 时只观察显示变化，隐藏不等于删除，做完恢复原设置。
  3. 在版图区选中一个已知实例，通过本版本的属性入口查看，记录实例名和引用单元名，并用 Design Browser 或项目清单交叉核对。选到的是 net 而非 instance 时，属性字段不同；先核对对象类型，不急着改设计。

进阶阅读：旧版快捷键原文与原站的界面分区说明。

第一课时：桌面练习与验收

动手无工具也能做：读图和排错

在纸上标注：图 01 的个人工作目录、图 09 的版图区和右侧控制区、图 02–04 的三个工具栏入口，以及图 05 的 V/S 两列。再写一份启动记录：工作目录、工具入口、版本证据、日志名分别从哪里取得；用两行描述“可见但点不中”的观察与下一步。最后列出对象属性里应抄下的两个字段。不要把图上的版本或路径当作自己机器的结果。

过关标准（都能做到才算学完）
  • 上机：能指出实际 run 目录、版本出处与日志位置，区分 Linux shell 和 Innovus 提示符；能完成一次缩放与 Fit、一次 S 关/开对照，并给出实例名和引用单元名。只有空会话时，把对象操作标为待补，第二课时补验。
  • 桌面：能用图号指出上述操作从哪进入，准确写出 V/S 对照和属性字段，并从“找不到命令、许可证报错、无图形显示”中选一例说明先查什么。记录标明“读图演练”。
自测
command -v innovus 找到路径，但没看到 GUI。能否据此报版本并判定启动成功？
解析：不能。路径只证明 shell 找到了入口，可能还是包装脚本。版本从启动横幅或日志确认；开窗失败先读启动诊断，区分许可证与图形会话问题。
某实例看得见却选不中，同位置一点击反而选到 net。如何做最小排查？
解析：先清除旧选择，核对 Instance 类别及其 S 列；保持 V 开，把 S 打开后重选，再用属性中的实例名和引用单元名确认对象类型。先不改设计，也不把缩放当作修复。
05

第二课时：为同一个 40nm 案例准备输入

这节仍用上一课的 40nm 案例，不换到其他工艺。把项目发布清单当作对照表，先填写“输入路径、发布版本、预期结果”，再开一个干净会话。原图 08 的 leon 是历史资料中的顶层实参；上机以手头同一案例的发布清单为准，不凭截图猜路径、库名或电源网名。

准备项上机前核对
门级网表与顶层网表可读，顶层名和大小写以网表及发布清单为准；记下预期端口/实例规模以及一个可抽查的实例。
Tech LEF 与 Cell/Macro LEF来自同一 40nm 发布；按项目清单排列，Tech LEF 在前，核对标准单元及用到的宏是否有物理定义。
MMMC 配置及其依赖核对各分析视图、Liberty、RC 技术数据、SDC 和配置内引用的实际路径；记下预期视图、时钟或合理的无时钟预期。
电源/地网与可选 DEF按项目指定的电源域和网名填写，不能默认 VDD/VSS；仅在项目要求接续已有物理数据时才用同一发布的 DEF。
环境与留档核对授权、项目指定版本、可读输入和可写个人 run 目录；约定日志、报告和检查点名称。不复制或分享受限资料。
06

第二课时：按对照表配置并导入

操作顺序有工具时做什么完成的标志
1. 确认起点从独立 run 目录打开空会话并记录日志；确认项目指定的命令模式和版本。日志可追踪，未在现有设计里重做初始化。
2. 填输入用经过审核的项目脚本填入网表/顶层、LEF、MMMC 及项目所需的 PG 设置。GUI 仅用于认输入项，不另做一次重复导入。每组配置都能指回同一发布清单；路径的解析基准已经核对。
3. 执行初始化在支持旧版命令的会话里执行 init_design；项目确需 DEF 时按项目脚本和当前版本帮助另行处理。能在日志里找到初始化的位置、返回和第一条关键异常；还不能据此宣布通过。

下面是 旧版命令骨架，不是本站可直接运行的项目脚本。netlist_files 等变量必须由已审核的本地项目配置提供；在授权的个人空会话中先查本版帮助（如支持，可用 help init_design），确认命令和参数再逐条执行。若项目用另一套命令接口，走该项目批准的脚本，不把两套写法混用。source 和 -files 会执行整个脚本，不加载来历不明的文件。

tcl
set init_verilog    $netlist_filesset init_top_cell   $top_cellset init_lef_file   [linsert $cell_lefs 0 $tech_lef]set init_mmmc_file  $mmmc_file# 仅在项目要求由这些旧版变量指定 PG 时设置set init_pwr_net    $power_netsset init_gnd_net    $ground_netsinit_design

进阶阅读：脚本和 GUI 的对比、数据清单、旧版脚本拆解。进阶页的其他工艺、路径或核数例子不照搬到本案例。

07

第二课时：用证据验证，再保存并恢复

先验再存。 对照开工前的预期，记录下面三类证据；不拿“能 Fit 到图形”或“没有 ERROR”当验收。

检查项看哪些证据不符合时先查什么
设计身份与链接用 Design Browser 或汇总报告核对顶层、端口/实例规模、一个实例及其引用单元；旧版若支持 dbGet top.name，可用它查顶层。网表发布版、顶层名、缺失的 LEF/时序库定义。
约束与视图核对预期 MMMC 视图是否启用，时钟名、周期和单位是否相符；用该版本的报告或团队脚本取证。MMMC 的分析视图绑定、SDC 路径、约束引用的端口及当前观察的视图。
日志与设计检查读第一条有因果关系的异常及上下文；若帮助确认支持，可用 checkDesign -all 做旧版设计检查，并区分此阶段预期的提示与阻断项。先处理未解析引用、缺库、错误顶层或必需视图/时钟缺失；修正输入后从干净会话重跑并留新日志，不覆盖原 run。

三项符合项目预期后，在个人可写目录用一个尚未使用的基名保存。以下是旧版会话示例；先确认 saveDesign 的用法和实际写出的产物。checkpoint_path 是你事先设定的完整 .enc 路径，不是课程文件。

tcl
saveDesign $checkpoint_path

记录同一次保存生成的入口和配套数据，例如 .enc 与 .enc.dat（后者可能是目录）；搬运时保留配套数据与所需依赖。另开一个干净的兼容会话，在当前版本帮助和项目手册确认后，二选一使用可信的 .enc 入口，或用 restoreDesign 指定配套数据及真实顶层。下面的三个变量须在新会话用自己的实际路径和顶层重新设置，两条命令不要连跑。

tcl
# 方式 A：仅 source 自己生成或明确获得信任的 .enc 入口source $checkpoint_path# 方式 B：改用同次保存的配套数据，顶层名以发布清单为准restoreDesign $checkpoint_data_path $top_cell

恢复后再比对顶层、端口/实例规模、抽查实例及其引用单元、预期视图或时钟，并检查恢复日志。任何一项不一致都不能算恢复通过；优先核对 .enc 与配套数据是否来自同一次保存、路径依赖是否可访问，以及版本和顶层是否匹配。

进阶阅读：导入后检查、报错对照、保存和恢复的原文。验收后，可选学给检查点配上可追溯的验收记录和用 dbGet 核对对象关系。

第二课时：桌面演练与验收

动手无工具也能做：判读三份记录

同一个 40nm 案例的练习基线：顶层 leon，预期实例数 18,240，抽查实例 u_ctrl 引用 CTRL_X1，指定分析视图应有 clk_core，周期 10 ns。这些计数、实例和时钟是教学设定，不是原项目的报告。

  • 记录 A（初次导入）：顶层、实例数和抽查对象均匹配；指定视图为 0 clocks。
  • 记录 B（在新 run 修正输入后）：各项匹配，指定视图可见 clk_core，周期 10 ns；练习设定日志无阻断项，随后保存了检查点。
  • 记录 C（恢复尝试）：日志提示找不到配套 .enc.dat，没有得到可复核的设计对象。

将三条记录分别标为“可保存／需先修复／恢复未通过”，各写一条证据和下一步；再把图 07、08 对应到两种恢复入口。只需纸笔或文本编辑器，不生成或运行 Tcl。

过关标准（都能做到才算学完）
  • 上机：交一张输入清单和一份前后对照记录，含 run/版本、导入及恢复日志、顶层、端口或实例规模、抽查实例与引用单元、视图/时钟证据、检查点入口及配套数据。新会话复核一致且阻断项已处理，才算通过。
  • 桌面：A 先查 MMMC 视图、SDC 路径与端口绑定，不保存为已验证检查点；B 可保存；C 尚未恢复，先核对配套数据和依赖，只凭图 07–08 的命令行不能打勾。写清三项证据并标明“桌面演练”。
自测
指定视图里没有时钟，但顶层、实例数都对，而且没有 ERROR。下一步是继续布局还是停下来？
解析：先停下来。本案例有预期时钟，逐项核对视图是否激活、对应 SDC 是否读到、约束是否命中正确端口；修正后在新 run 复核。结构证据不能替代约束证据。
图 07 和图 08 分别把什么交给工具？看完两张图，能说原课已证明恢复成功吗？
解析：图 07 把可信的 .enc 入口交给 source；图 08 把 .enc.dat 路径和顶层 leon 交给 restoreDesign。两图只显示输入命令，实际成功仍需会话输出和恢复后的复核。
把 .enc 拷到另一处后恢复失败；同名 .enc.dat 刚好在另一份 run 里。能否把它补进来直接重试？
解析：不能凭同名配对。先找同次保存的入口、配套数据与它们需要的路径，确认版本和顶层一致，再在干净会话选一种方式恢复，复核设计身份、规模与约束。

为什么是 Innovus / ICC2

本章目标能说出 Innovus/ICC2 各自替代的老工具与换代原因；能用一条命令完成"无界面启动 + 自动跑脚本 + 写 log"；能解释 -log / -files / -no_gui / -wait / -cpus 五个选项的真实语义与风险；能用 which、nproc、help *关键字* 三件事把环境摸清。
时代CadenceSynopsys适用工艺
老一代EncounterICC90nm 及以上
主流InnovusICC265nm 及以下，28/16/7nm

文档给的理由很实在："工艺越来越先进，原有的架构已经无法满足新的架构"，具体对比就是运行时间。

老引擎的几个硬伤，在先进工艺下会直接暴露：

  • 一次跑不完几十万 instance 的优化，跑一天还没到 route；
  • 不支持多重曝光（double patterning）的染色约束；
  • 时序/拥塞/功耗三者不能联合优化，只能一轮轮手调。

所以你在招聘要求里看到"熟悉 Innovus 或 ICC2"，指的是这一代工具；只会 Encounter/ICC，在 28nm 以下基本没有用武之地。本课程后面所有实操都用 Innovus。

which innovus 的返回值一举两得，文档说得很清楚："结果会显示 innovus 所在目录以及 innovus 的版本"：

text
/opt/cadence/INNOVUS201/innovus      ← 目录里带 201，说明是 Innovus 20.1 版本

为什么第一件事是查版本？ 因为不同版本的命令行为有差异（尤其 ccopt、setPlaceMode 的参数），网上抄来的脚本报错，八成是版本不匹配。项目里也会明确要求"用 21.1 及以上"，出了问题才有人背书。

小技巧

三种常见情况：

  1. command not found → PATH 没配，找 source /xxx/setup.csh 或 module load innovus；
  2. 报 license 相关错误 → license 服务器不通或没有空闲 license，找 IT/管理员，不是你的脚本问题；
  3. 启动卡在 Loading... 很久 → 磁盘 IO 慢或家目录配额满，df -h ~ 看一眼。
license许可证

EDA 工具的授权凭证，按工具、按功能、按核数计量。启动失败里最常见的一类就是拿不到 license——它和脚本写错是两回事，先分清再排查。抢不到时可以带 -wait 排队等。

GUI图形界面模式

带版图窗口的运行模式（默认）。与之相对的 -no_gui 只跑命令、不加载图形引擎。GUI 用来 debug，脚本用来干活——这是 PR 工作的基本分工。

九个常用启动选项

文档列了九条，我按"一定会用到的程度"重排，并补上实际工作中的注意点。

1. -log：把这一趟的全部输出记下来

bash
# 启动时指定 log 文件名，工具的所有输出都会写进 test.loginnovus -log test.log
log运行日志

记录这一趟运行中所有内容：你在界面上做的操作、输入的每条命令、命令的返回结果、warning 与 error。它是唯一能事后追溯的证据。

为什么这条最重要？因为 Innovus 跑到一半崩了、或者同事问你"你昨天那个 run 到底怎么配的"，只有 log 能回答。文档原话："log 内容一般是界面做的操作，以及操作的结果，输入的 cmd 等等。"

实操约定：

  • 文件名带版本和日期，比如 -log pr_v3_1025.log，别都叫 innovus.log 互相覆盖；
  • 界面上的操作也会进 log，所以你点过的每一步都能被还原成命令——这是新人学命令最快的方法：点一遍，然后去 log 里看它对应哪条命令；
  • 报错时先 grep -n "ERROR" pr_v3_1025.log | head，比在滚屏里找快一百倍。

2. -files：启动后自动跑脚本

bash
# 启动完成后自动执行 run.tcl，脚本跑完就停在那儿等你的命令innovus -files run.tcl

文档的说明："脚本的内容可以自己定义，亦或是项目中的一些配置文件。"

这条是自动化的入口。实际项目里没人手点界面，都是：

bash
# 无界面 + 自动跑 init 脚本 + 写 log：一条命令完成整个导入，扔后台等结果innovus -no_gui -files scripts/init_design.tcl -log init.log

一条命令把"启动 → 导入数据 → 检查 → 退出"全做完，扔到后台跑。这是 PR 工程师的日常姿势，界面只是用来 debug 的。

小技巧
  • -files run.tcl：启动时就带上，工具启动完立刻执行；
  • 进去以后 source run.tcl：手动执行，随时可以再来一遍。

两者执行效果一样，区别只是时机。改脚本调试时用 source 反复跑，正式跑用 -files。

3. -no_gui：不开图形界面，快得多

bash
# 无界面启动：只跑命令，不加载图形引擎innovus -no_gui -files run.tcl -log run.log

为什么值得单独记一条？ 图形界面会吃掉大量内存和启动时间（还要连 X server / VNC）。服务器上批量跑 run 时，-no_gui 能省下可观的内存，让同一个节点多跑几个 run。

进去了想再打开界面？文档给了答案：

tcl
# 在 innovus 的命令行里输入，图形界面就出来了（前提是你有可用的显示环境）win on

反过来，想临时关掉界面：

tcl
# 关闭图形界面，回到纯命令模式win off
常见坑 · 在 no_gui 里截图/开窗

现象：win on 报错，提示无法连接 display。 原因：-no_gui 启动的进程通常没有有效的 DISPLAY 环境变量（或者通过 ssh 没带 -X）。 解决：要么用 VNC/远程桌面登录后再启动（课程环境推荐），要么 export DISPLAY=:1 指向你已登录的桌面会话。远程纯 ssh 场景下就别指望开窗了，看 log 和报告文件即可。

4. -wait：等 license 再启动

bash
# license 被占满时，最多等 120 秒再启动innovus -wait 120

文档叫它"定时启动"，实际语义是：license 不够时排队等，而不是直接失败退出。

这个功能在项目冲刺期特别有用——几十个人抢同一批 license，你的脚本半夜排队，等到就自动开跑。不带 -wait 的话，脚本会因为拿不到 license 直接死掉，白排一晚上。

5. -cpus：多核启动

bash
# 用 8 个核启动innovus -cpus 8

文档的提醒非常关键：

实际工作根据需要确定核数，一般最高可以设置 32 或者 16。不要设置过高，否则可能会被 kill。

原因有两个，都要知道：

  1. license 是按核计费的。你申请 32 核，可能消耗 32 份并行 license 额度，管理员看到会来找你；
  2. 集群有空闲核数上限（LSF/SGE 之类调度器会限制每用户/每任务的核数），超了直接被调度器 kill，跑了几小时的 run 白费。

文档还提到一个现场细节："可以看到有 28 个 cpu，每个 cpu 有 4 核"——意思是物理机 28 路、每路 4 核。看核数别只看 CPU 个数，nproc 才是你能用的逻辑核数：

bash
# 看这台机器到底能给我多少逻辑核nproc # 看物理 CPU 路数与每路核数lscpu | grep -E "^CPU\(s\)|Thread|Core|Socket"

6. 启动后调整核数：SetMultiCpuUsage

已经进去了才发现核给少了，不用退出重开：

tcl
# 改成 32 核，并允许工具根据当前任务自动调整实际使用核数setMultiCpuUsage -localCpu 32 -cpuAutoAdjust true
setMultiCpuUsage多核使用设置

Innovus 里控制并行线程数的命令。-localCpu 指定本机可用核数，-cpuAutoAdjust true 让工具在不同阶段自动升降（比如 placement 用得多、report 用得少）。

注意大小写：Innovus 的命令是驼峰式（setMultiCpuUsage、setPlaceMode、optDesign），而它内部很多底层命令是小写下划线式（ccopt_design、place_opt_design）。两种都存在，别以为敲错了。

7. -help：不知道参数就查

bash
# 看 innovus 本身有哪些启动选项innovus -help # 看某条命令的完整参数（在 innovus 命令行里执行）ccopt_design -helpplace_opt_design -help

这是最省时间的习惯：任何命令后面加 -help，立刻看到全部参数、默认值、示例。比翻文档快得多。

8. help *关键字*：按关键字搜命令

只记得"跟 place 有关"，不记得命令名？用通配符搜：

tcl
# 搜索所有名字里带 place 的命令，会列出命令名和一行说明help *place* # 搜索所有时序报告相关的命令help *report* # 看某条命令的详细解释（等价于 cmd -help）help setPlaceMode
小技巧
入口用来查
innovus -help启动选项（-log -files -cpus 这些）
cmd -help某条命令的完整参数表
help *kw*只记得关键字，找命令名

9. Tab 键补全

文档把"TAB 键"单独列成一条，因为它真的能救命：

  • 敲 setPlace + Tab → 自动补成 setPlaceMode；
  • 敲 setPlaceMode - + Tab → 列出所有可用参数；
  • 路径也能补：source scr + Tab → source scripts/。

养成"敲一半就按 Tab"的习惯，能避掉大量拼写错误。Innovus 命令长、驼峰多，手打几乎必错。

自测
Innovus 与 ICC2 分别属于哪家公司？它们替代的老工具是什么？
Innovus 是 Cadence 的，替代 Encounter；ICC2 是 Synopsys 的，替代 ICC。老一代适用于 90nm 以上，先进工艺必须用新一代。
为什么每次上机第一件事是 which innovus？
它同时给出工具所在目录和版本号；版本不同命令行为有差异，脚本报错常因版本不匹配。
-log 和 -files 分别做什么？
-log 把这一趟的所有输出（界面操作、输入命令、结果、warning/error）写进指定文件；-files 让工具启动后自动执行指定 tcl 脚本。
-no_gui 有什么好处？进去后怎么再打开界面？
省内存、省启动时间，适合服务器批量跑 run；进去后执行 win on 打开，win off 关闭。
-cpus 为什么不能设太高？
会消耗大量并行 license，且可能超过集群每任务核数上限被调度器 kill，导致长时间 run 白跑。
进去之后怎么改核数？
setMultiCpuUsage -localCpu 32 -cpuAutoAdjust true。
想找所有名字里带 place 的命令，怎么做？
help *place*；看某条命令的完整参数用 cmd -help；看启动选项用 innovus -help。
Tab 键有两个什么用法？
补全命令/路径名；在命令后加空格再按 Tab 列出该命令的所有可用参数。
过关标准（都能做到才算学完）
  • 能说出 Innovus/ICC2 对应替代的老工具，以及换代的核心原因（运行时间与先进工艺约束）
  • 能用一条命令完成"无界面启动 + 自动跑脚本 + 写 log"
  • 能解释 -wait 的真实语义（license 排队）
  • 能说出 -cpus 给太高会被 kill 的两个原因
  • 能用 which / nproc / lscpu 三个命令确认环境
  • 能说出三个帮助入口各自查什么
  • 能把界面分成版图区、命令行、输出窗、层次树四块并说出各自用途
