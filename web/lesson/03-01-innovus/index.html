Innovus 起步：一个后端工具到底在管什么

Getting Started with Innovus

后端工具不是"画图软件"，它管的是一个巨大的数据库、一个优化引擎和一堆报告。这一课讲清数据库里存了什么、为什么必须用命令行、第一个能跑通的命令序列，以及 Innovus 与 ICC2 的十六组命令对应。

约 35 分钟 课表学时 2 Innovus工具数据库
01

工具在管什么

本章目标能说出 Innovus 里"设计、库、约束"三类数据各自存在哪、用一条 dbGet 查出来，并用纯命令行跑通一次初始化到存盘。

一个布局布线工具（Innovus / ICC2）本质是三样东西：

  1. 一个数据库：几万个单元、几十万条连线、几百层几何图形，全在里面。
  2. 一个优化引擎：决定"放哪、怎么连、插不插缓冲器"。
  3. 一堆报告：时序、拥塞、DRC、面积、功耗。

你敲的每条命令，都是在改数据库或者让引擎干活，然后读报告判断下一步。三件事循环，就是整个后端工作。

数据库里其实装的是"一设计 + 三份资料"：

组成内容从哪来少了会怎样
设计（design）单元实例、连线、引脚、电源网络.v 网表 + .def没有东西可摆
库（library）每个单元的尺寸、引脚、延迟.lef + .lib/.db不知道单元长什么样
约束（constraint）时钟、IO 延迟、例外.sdc / MMMC不知道要多快，优化没目标
工艺（tech）层、线宽、间距、viatech LEF + TLU+不知道怎么画线
InnovusCadence 的布局布线工具点击看解释

数字后端两大主流 PR（Place & Route，布局布线）工具之一，另一个是 Synopsys 的 ICC2。命令语言是 Tcl，所有操作都能写成脚本。
课程阶段三用 40nm 走 Innovus，阶段四用 32nm 走 ICC2。两套工具，一套方法论：先想清"这一步在改什么数据"，再查命令名。

Instance实例点击看解释

网表里"用了一个单元"这件事的实体。U1234 是一个实例，它的类型（cell）是 NAND2_X1，位置是 (120.5, 340.2)。
cell 是"图纸"，instance 是"按图纸造出来的那一颗"：一个 INV_X1 可以被实例化一万次，库里的定义只有一份。

02

GUI 和命令行：到底用哪个

新手最容易犯的错：以为要用鼠标拖。

真实情况：

  • GUI 用来"看"：看布局、看拥塞热图、看某条路径的走向、看 flyline。
  • 命令行/脚本用来"做"：所有设置、所有流程，都写成 .tcl 脚本跑。

原因不是"显得专业"，是四个很实际的工程需求，每条一句话：

1. 可重复。 同一份脚本今天跑和下周跑结果一样，换同事跑也一样；用鼠标点的流程第二次复现不出来，你不知道自己当时点了哪几个按钮。

2. 可存档。 脚本是文本，能进 git、能随项目归档；数据库存档（.enc）是二进制，只能整体回退，看不出改了什么。

3. 可批量。 想试 6 组利用率（0.60/0.65/0.70/0.75/0.80/0.85），脚本套一层循环就跑完；用 GUI 你要点 6 遍，还得手工记每次结果。

4. 可对比（diff）。 两个版本差在哪，git diff 一行行告诉你"改的是 max_density，从 0.72 到 0.68"；两次 GUI 操作之间没有"差异"这个东西，只能靠回忆。

一句话总结：GUI 负责"看"，脚本负责"做"；凡是需要"再做一次"的事，都必须落到脚本里。 这不是纪律要求，是因为人记不住自己点过什么。

bash
# 作用：两种启动方式，批处理跑脚本 vs 带界面调试# 用法：在 pnr/ 目录下执行；run.tcl 里写完整流程，日志重定向到 log/innovus -no_gui -files run.tcl -log log/run_0901.log -overwrite   # 无界面跑脚本，服务器上跑批用这个innovus                                                          # 带 GUI 启动，交互式调试用；进去后 source run.tcl

参数逐个说：

  • -no_gui：不启动图形界面。省内存、能在没有显示器的服务器上跑，这是正式跑流程的唯一方式。
  • -files run.tcl：启动后自动执行这个脚本。可以跟多个文件，按顺序执行。
  • -log log/xxx.log：把终端输出写进日志。必须给，否则出问题没有证据。
  • -overwrite：允许覆盖同名日志（不加时工具会拒绝写已存在的日志，批处理会直接退出）。
Batch Mode批处理模式点击看解释

不给图形界面、直接跑脚本的运行方式（-no_gui）。特点是可排队、可并行、日志完整。
公司里的常规做法：本地 GUI 调脚本，提交到计算集群用批处理跑全流程。你写的脚本要能在两种模式下都跑通，这是基本要求。

工作场景 · 凌晨两点，GUI 断了，跑了 5 小时的流程没了

你在自己电脑上开着 GUI 跑布线，跑了 5 小时到 80%。凌晨两点 VPN 断了一下，X11 转发断开，进程跟着被杀。日志只写到一半，数据库没存。

第二天早上你面对两个选择：重跑 5 小时，或者跟组长解释为什么延期。

老手的做法从一开始就不一样：

bash
# 作用：把长任务丢到后台，断线也不影响# 用法：在服务器上执行；nohup 让进程脱离终端，日志照样落盘nohup innovus -no_gui -files run_route.tcl -log log/route_0901.log -overwrite > /dev/null 2>&1 &

公司里更常见的是提交到作业队列（LSF 的 bsub、SGE 的 qsub）：进程跑在计算节点上，本来就不跟着你的终端。命令不同，原则一样——长任务不能挂在你的一次 SSH 会话上。

配合脚本里每阶段 saveDesign，最坏情况也只是从上一个存档重跑一小时，而不是从零开始。

03

GUI 上每个面板叫什么

GUI 不是用来"操作"的，但你必须认识它——因为所有 review、所有排错，最后都要回到这张图上看一眼。先认脸。

从图里要看出什么：三个区域各管一件事——左边回答"设计里有什么"，中间回答"它长在哪"，底部回答"我让它做什么"。后面所有课里说的"打开飞线看一眼""放大到那个 macro"，指的都是中间这块。

小技巧

不知道某个操作对应的命令是什么？在 GUI 里点一次，命令日志会把等价 Tcl 打出来，复制到脚本里就行。

这是学 Innovus 命令最快的方法：先会点，再抄命令，最后忘掉怎么点。 但要注意，GUI 点出来的命令往往带一堆默认参数，抄的时候要删掉你不需要的那些，否则脚本会变得又长又难读。

数据库里有什么

打开一个设计后，数据库里至少存了这些：

内容说明对应报告
单元实例每个标准单元的类型、坐标、朝向report_area
连线（net）谁连谁、走哪层、多长reportCongestion -hotSpot
引脚（pin/terminal）IO 位置、方向、所在层dbGet top.terms
电源网络ring / stripe / railverifyPowerVia
时序图每条路径的门延迟、线延迟report_timing
约束时钟、IO 延迟、false pathreport_clocks

用 dbGet 直接查数据库

Innovus 的所有数据都能用 dbGet 查。它的语法是 dbGet 对象.属性，可以在 Tcl 里当普通命令用：

tcl
# 作用：不打开 GUI，直接从数据库里数单元、查坐标、找特定实例# 用法：init_design 之后在 Innovus 命令行里敲；输出格式随版本略有差异，语义一致 dbGet top.insts                    # 返回所有实例的句柄列表（一长串 0x... 的指针）llength [dbGet top.insts]          # 数一数有多少个实例，这是"单元数"的来源dbGet top.insts.name               # 只要名字，返回 u_core/u_alu/u_alu/add_1 这样的列表dbGet -p top.insts.name u_sram0    # 按名字过滤，只返回叫 u_sram0 的那个实例句柄dbGet [dbGet -p top.insts.name u_sram0].box   # 再取它的坐标框，四个数：llx lly urx urydbGet top.nets.name                # 所有连线的名字，用来确认某个 net 在不在

dbGet 的输出长什么样、报错长什么样，下面这张图是真实会话的摘录。

从图里要看出什么：dbGet 返回的是"对象"，不是"值"。想要值必须再点一层属性（.name、.box、.numTerms）。这也是新手最常卡的地方：拿到一串 0x 指针，以为命令失败了。最后那个 can't read 报错，说明属性名必须精确到拼写。

为什么要会这个：报告不够用时，dbGet 是唯一能"自己造一份报告"的办法。比如"列出所有面积大于 1000µm² 的实例"，报告命令里没有，一行 dbGet 加 foreach 就能出来。

dbGet数据库查询命令点击看解释

Innovus 的 Tcl 数据库接口：dbGet 对象.属性 取数据，dbSet 对象.属性 值 改数据，-p 用来按值过滤。
它相当于直接读内存里的数据库，比报告命令灵活，也比报告命令危险：dbSet 改错了不会有人拦你。

05

第一个能跑通的序列

下面这一串是 Innovus 的"最小可运行流程"：从零到有一个能存盘的设计。顺序不能乱，每一段的作用写在注释里。

tcl
# 作用：Innovus 从零初始化一个设计的完整序列（MMMC 流程）# 用法：innovus -no_gui -files init.tcl；所有相对路径以 pnr/ 为当前目录 # ---- 1. 读设计数据（此时还没有数据库）----read_verilog ../syn/netlist/ipa_top.v            # 读门级网表，建立逻辑连接关系read_lef ../lib/lef/tsmc40_tech.lef              # 先读 tech LEF：有哪些层、线宽、间距、viaread_lef ../lib/lef/tsmc40_stdcell.lef           # 再读单元 LEF：每个单元的尺寸和引脚位置read_lef ../lib/lef/sram_2048x64.lef             # 宏单元 LEF，用不到 SRAM 时可以省read_mmmc ../constraints/mmmc.tcl                # 读 MMMC：库集合、约束模式、分析视图三件套 # ---- 2. 建数据库（把上面这些绑成一个设计）----set init_top_cell ipa_top                        # 指定顶层单元名，必须和网表里的 module 一致init_design                                      # 建立内部数据库；这一步之后才能真正操作设计 # ---- 3. 灌入已有的物理信息（可选）----read_def ../def/02_fp.def                        # 有现成 floorplan 就灌进来；没有则从空 die 开始 # ---- 4. 自检：确认读对了 ----report_area                                      # 总面积、单元数；为 0 说明网表或库没读进来report_clocks                                    # 时钟列出来了吗？没有就是 MMMC/SDC 没生效checkDesign -all                                 # 一致性检查：悬空引脚、未连接端口、非法实例check_timing -include unconstrained              # 有没有完全没约束的端点 # ---- 5. 存盘：这一步不做，前面全白干 ----saveDesign db/01_init.enc                        # 二进制存档，实际生成的目录叫 01_init.enc.dat/

几点必须解释清楚：

  • read_lef 要读两次：tech LEF 定"规则"，cell LEF 定"形状"。只读后者，工具知道单元多大但不知道怎么画线。
  • read_mmmc 替代了 read_sdc：MMMC（Multi-Mode Multi-Corner，多模式多工艺角）把"用哪套库 + 用哪份约束 + 看哪个 corner"打包成分析视图。小项目也可以直接 read_sdc，但公司流程基本都用 MMMC。
  • read_def 必须在 init_design 之后：init_design 建空数据库，read_def 往里灌坐标。顺序反了会报"没有设计"。
  • checkDesign 不要跳：它会把"某个输入端口没接驱动"这种问题提前暴露，比在布线阶段发现便宜一百倍。
常见坑 · 忘了 saveDesign，几小时白干

Innovus 不会自动存。跑到一半崩溃、或者你自己想回退，没有存盘就只能从零开始。

规矩：每完成一个阶段就 saveDesign db/NN_阶段名.enc。 出问题可以 restoreDesign db/05_cts.enc.dat ipa_top 回到上一个可用状态。

NN 用序号，方便排序和回退。存档目录会越来越大（一个设计几个 GB），定期清理中间版本，但每个阶段的最后一版必须留。

.encInnovus 设计数据库点击看解释

Innovus 自己的二进制存盘格式，实际是一个目录（01_init.enc/ 里面若干文件）。存了设计的完整状态：布局、布线、约束、工具设置。
和它对应的是 ICC2 的 block 数据库（NDM 库 + save_block）。格式不同，作用相同：给流程留一个可回退的锚点。

常见坑 · 脚本里用了相对路径，换个目录就跑不了

现象：在 pnr/ 下跑得好好的脚本，cd 到别处再跑，报 Cannot open file ../lib/...。

原因：路径是相对当前工作目录的。批处理系统提交任务时，工作目录经常不是你以为的那个。

怎么改：脚本开头统一 set PRJ [pwd]，所有路径写成 $PRJ/../lib/...；或者在启动脚本里先 cd 到固定目录。路径问题占了新手报错的一半，一次性写对能省很多时间。

06

第一次打开设计：8 步操作清单

上一个序列讲的是"脚本里写什么"。这一节讲"人第一次接手一个设计时，按什么顺序点"——顺序错了，后面每一步的报错都会把你带到错的方向。

步动作目的这步失败的典型表现
1pwd + 建 log/ db/ rpt/确认工作目录，日志有地方落日志写到别处，出问题找不到证据
2读 tech LEF先有"层规则"：有哪些层、线宽、间距、via后面报"没有层定义"，画不出线
3读 cell LEF + macro LEF再读"形状"：每个单元多大、引脚在哪单元没尺寸，placeInstance 报非法
4读网表建立逻辑连接关系（谁连谁）顶层名找不到、report_area 为 0
5读 MMMC / SDC把库、约束、corner 绑成分析视图report_clocks 空，全部 unconstrained
6set init_top_cell + init_design建内部数据库报"design not found"，多半是顶层名不一致
7四项自检面积/时钟/一致性/未约束，四项都要过某一项异常却往下走，错误会在布线阶段放大
8saveDesign db/01_init.enc留一个可回退的锚点后面任何一步崩了，只能从零开始

几条纪律：

  • 第 2、3 步的顺序不能反。 tech LEF 是"地方法规"，cell LEF 是"占地证"。先有法规才知道怎么量地；反过来，工具会先读进一堆没有归属的矩形。
  • 每一步之后看一次消息窗口。 不要一口气跑完 8 步再回头找 error——那时你分不清是哪一步出的。
  • 第 8 步之前不要点任何优化按钮。 没存盘就 point-and-click 是最典型的翻车：点错一个，前面全要重来。

8 步走完，你应该能回答三个问题：设计里有多少个实例（report_area）、有几个时钟（report_clocks）、有没有没约束的端点（check_timing）。三个都答得出，才算"打开了设计"，而不是"启动了软件"。

MMMC多模式多工艺角点击看解释

Multi-Mode Multi-Corner。把"用哪套时序库（library set）+ 用哪份约束（constraint mode）+ 看哪个 corner（analysis view）"组合成若干分析视图，一次性管住所有场景。

自测：先自己想，再点开答案
为什么后端流程强调"写脚本"而不是用 GUI 点？
因为要可复现、可存档、可批量：一次运行几小时、参数几十个，只有脚本能重跑、能 diff、能循环扫参数。
-no_gui 和 -files 分别是什么意思？
-no_gui 不启动图形界面（服务器批处理）；-files 启动后自动执行指定的 Tcl 脚本。
saveDesign 为什么每个阶段都要做？
工具不会自动存盘，崩溃或需要回退时没有存档就得从头再来；每个阶段留一版才能精确回退。
Innovus 的 .enc 和 ICC2 的数据库有什么区别？
格式不同（Cadence 私有目录 vs Synopsys NDM + block），作用相同：保存设计的完整状态。
init_design 做了什么？
把网表、物理库、时序库、约束绑定在一起，建立可操作的内部数据库；之后才能读 DEF、做布局。
为什么 read_def 要放在 init_design 之后？
init_design 建空数据库，read_def 往已有设计里灌坐标；反了就没有设计可灌。
dbGet top.insts 和 dbGet top.insts.name 有什么区别？
前者返回实例句柄列表（对象指针），后者返回名字列表；要取坐标得先拿句柄再取 .box。
