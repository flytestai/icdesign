PrimeTime 签核：自己给自己签字不算数

PrimeTime Signoff

布局布线工具自己算的时序不能作为签核依据。这一课讲 PT 怎么读设计、约束怎么写、报告怎么读、OCV 为什么要更悲观，以及违例怎么反馈回 PR。

约 65 分钟 课表学时 14 PTSTASDCOCV签核
01

为什么要用 PT 再算一遍

布局布线工具内部也有时序引擎，为什么还要 PrimeTime？

原因说明
独立性自己检查自己不可信，同一套引擎的系统性偏差会被继承
精度PT 的延迟计算模型更严格（尤其是 OCV、串扰）
行业标准流片签字用的是 PT 报告，foundry 也认这个
约束解析PT 对 SDC 的解析最严格，能暴露约束写法问题
STA静态时序分析点击看解释

Static Timing Analysis。不跑仿真，靠遍历所有路径 + 计算延迟来判断时序是否满足。
优点是快（几分钟覆盖几百万条路径）、完备（不漏路径）；缺点是不能验证功能，只能验证时序。

02

读入三件套

tcl
# pt_shell 里执行set link_path "* /pdk/db/tsmc28_tt.db /pdk/db/sram_2048x64.db"# link_path 里必须包含所有用到的库，否则单元解析不出来 read_verilog ./final.vlink_design# 读网表并解析单元 read_sdc ./ipa.sdc# 读约束 read_parasitics -format SPEF ./final.spef# 读寄生参数（这一步决定时序精度） # 检查check_timing# 会报：没有时钟、没有输入延迟、未约束的路径…… 必须清干净
常见坑 · link_path 漏库，时序全错

现象：PT 报一堆 Cannot find cell 'SRAM_2048x64'，或者把这些单元当成黑盒（延迟按 0 算），时序看起来"特别好"。

时序看起来过于乐观，第一反应就该怀疑库没读全。

检查：report_design -library 看实际用了哪些库，和网表里的单元列表对比。

03

约束怎么写（SDC 核心五条）

tcl
# 1. 定义时钟：周期 2.0ns，占空比 50%create_clock -name clk_core -period 2.0 [get_ports clk] # 2. 时钟不确定性：给 jitter 和 skew 留余量（签核时更保守）set_clock_uncertainty -setup 0.15 [get_clocks clk_core]set_clock_uncertainty -hold  0.08 [get_clocks clk_core] # 3. 输入延迟：数据从芯片外进来，要算上游器件的延迟set_input_delay -clock clk_core -max 1.2 [get_ports data_in*]set_input_delay -clock clk_core -min 0.3 [get_ports data_in*] # 4. 输出延迟：数据出去后要在外部器件建立前到达set_output_delay -clock clk_core -max 1.0 [get_ports data_out*] # 5. 例外路径：这些路径不用按单周期算set_false_path -from [get_ports rst_n]            # 复位不需要时序set_multicycle_path 2 -setup -from [get_cells u_slow/*] -to [get_cells u_slow/*]# 多周期：这条路径允许 2 个周期完成（慢速模块）
Clock Uncertainty时钟不确定性点击看解释

约束里给时钟加的"额外悲观量"。包含两部分：时钟源抖动（jitter）和时钟树偏斜（skew）的残余。
set_clock_uncertainty -setup 0.15 的意思是：算 setup 时，假设时钟比理想情况早到 0.15ns，逼工具留出余量。

常见坑 · false_path 用多了，等于骗自己

set_false_path 是告诉工具"这条路径不用检查"。用对了是效率（复位、测试逻辑），用错了是掩盖问题。

真实事故：有人为了让报告变绿，把一条真实的跨时钟域路径设成 false path。流片后功能错，几百万打水漂。

规矩：每一条 false_path 都要写注释说明理由，并且 Review 时逐条过。

04

报告怎么读

tcl
report_timing -max_paths 20 -slack_lesser_than 0 > rpt/viol.rpt# 只报 slack < 0 的路径 report_qor > rpt/qor.rpt# 汇总：WNS / TNS / 违例路径数 / 面积 / 单元数 report_constraint -all_violators > rpt/all_viol.rpt# 所有类型的违例（setup / hold / max_transition / max_cap ...）

一条路径报告的骨架：

shell
Startpoint: u_core/u_reg[3]/CK          ← 起点（时钟引脚）Endpoint:   u_core/u_alu/out_reg[7]/D   ← 终点（数据引脚）Path Group: clk_corePath Type:  max                          ← max = setup 检查   Point                     Incr     Path  -------------------------------------------------  clock clk_core (rise)     0.00     0.00  u_core/u_reg[3]/CK        0.00     0.00  u_core/u_reg[3]/Q         0.12     0.12     ← 单元延迟  u_core/u_alu/U12/Z        0.85     0.97     ← 组合逻辑  u_core/u_alu/out_reg[7]/D 0.00     0.97  data arrival time                  0.97   clock clk_core (rise)     2.00     2.00     ← 下一个时钟沿  clock uncertainty        -0.15     1.85  library setup time       -0.08     1.77     ← T_setup  data required time                 1.77  -------------------------------------------------  data required time                 1.77  data arrival time                 -0.97  -------------------------------------------------  slack (MET)                        0.80

读报告的三步：

  1. 看 slack：正负、多少。
  2. 看 data arrival 和 required 的差在哪一段：是单元延迟太大，还是时钟余量吃太多。
  3. 看路径上的单元：哪一级贡献最大（Incr 列）。
工作场景 · WNS 是负的，怎么回答组长

组长问："WNS −0.12ns，为什么？"

错误回答："工具优化不够，我再跑一遍。"（等于没说）

正确回答："最差路径在 u_core/u_alu 到 out_reg[7]，arrival 1.89、required 1.77，差 0.12。看 Incr 列，中间那条 32 位加法器占了 0.85ns，是主因。修法有两个：拆进位链，或者把这段逻辑往上游挪，减少线延迟。"

能定位到具体单元和具体原因，才叫会看报告。

05

OCV：签核为什么更悲观

真实芯片里，同一个单元在不同位置、不同批次的延迟会有偏差。OCV（On-Chip Variation）就是把这个偏差算进去。

tcl
set_timing_derate -early 0.95     # 早路径（hold 检查用）快 5%set_timing_derate -late  1.05     # 晚路径（setup 检查用）慢 5%

效果：setup 检查时把数据路径算慢 5%、时钟路径算快 5%（更悲观）；hold 相反。

模式含义复杂度
OCV统一 derate简单，偏悲观
AOCV按逻辑深度分级 derate中等
POCV / LVF按统计分布算最准，先进工艺必用
Derate降额系数点击看解释

在计算延迟时乘一个系数，模拟工艺偏差。1.05 表示"实际可能比标称慢 5%"。
derate 加得越狠，签核越保守：容易过不了，但过了就真能工作。

06

违例怎么反馈回 PR

PT 发现违例，不能直接改版图。流程是：

  1. PT 输出 ECO 清单（哪些单元要换、哪些要插 buffer）。
  2. PR 工具读入 ECO，做局部修改。
  3. 重新导出网表/SPEF，回 PT 复算。
tcl
# PT 侧生成 ECOfix_eco_timing -type setup -methods {size_cell}write_changes -format icctcl -output eco.tcl # PR 侧应用（ICC2）source eco.tcl
小技巧

第一轮修掉 80%，第二轮修掉剩下的一半，第三轮处理边角。

如果三轮还收敛不了，说明问题不在时序优化，而在约束、库、或架构（比如频率定得太高）。

07

签核标准

指标要求说明
setup WNS≥ 0（建议留 50~100ps）最差路径不能违例
hold WNS≥ 0（建议留 30~50ps）hold 更危险，必须留余量
TNS0所有违例之和
max_transition全部达标信号边沿不能太慢
max_capacitance全部达标负载不能超过驱动能力
过关标准（都能做到才算学完）
  • 知道为什么必须用 PT 复签
  • 会读入网表/约束/SPEF 并跑 check_timing
  • 能写出 SDC 五条核心约束
  • 能读懂一条路径报告并定位瓶颈
  • 理解 OCV/derate 的作用
  • 知道 ECO 流程和签核标准
自测：先自己想，再点开答案
为什么布局布线工具自己算的时序不能签核？
缺乏独立性（同一引擎的系统偏差会被继承），且精度和约束解析不如 PT 严格；流片签字以 PT 为准。
check_timing 报"没有时钟"说明什么？
约束没读进去，或时钟端口名写错，后面所有时序结果都不可信。
set_clock_uncertainty -setup 0.15 的含义？
算 setup 时假设时钟提前 0.15ns 到达，逼工具留出余量。
一条路径 arrival 1.89、required 1.77，slack 是多少？
−0.12ns（违例）。
PT 发现违例后怎么让版图改？
生成 ECO（换单元/插 buffer），PR 工具读入执行，再导出网表/SPEF 回 PT 复算，通常 2~3 轮收敛。
