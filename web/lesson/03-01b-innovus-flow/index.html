Innovus 项目流程：每个阶段到底交付什么？

Innovus Flow Handoffs

从项目准备到 ECO，按阶段核对数据库、报告和验收条件，学会定位失败应该回退到哪里。

预计学习 ≈4 分钟 课表学时 0 Innovus项目流程检查点
01

开工前：让同事能复跑你的 Run

资料来源

本讲参考钉钉目录第 05 项的主题安排，正文和练习为原创教学内容，不是钉钉原文、截图或项目案例的转载。

先冻结输入清单：顶层网表、技术与单元物理库、时序库、时序约束，以及预定的模式与工艺角。再记录 Innovus 版本、入口脚本、运行目录和日志位置。工具启动成功不等于导入正确；导入后用日志和数据库核对顶层名、单元引用、约束读取情况。交给下一阶段的是可恢复的初始数据库和输入清单，而不是一张 GUI 截图。详见 项目环境、工具启动和初始化检查。

02

Floorplan 到 Place：检查能否摆得下、接得通

  • Floorplan：交付含 Die、Core、宏、端口及布局约束的检查点。验收时查看宏朝向和重叠、剩余未分配端口、通道与可摆放区域，按项目要求记录例外。见 Floorplan。
  • PowerPlan：交付有电源网络和供电结构的检查点，以及供电连接和几何检查记录。电源线看起来完整，不代表每个电源域、宏电源脚都接到了对应电源网。见 PowerPlan。
  • Place：交付标准单元布局数据库，以及合法性、时序和拥塞报告。既看全局时序摘要，也核对热点；放得合法，不代表接下来一定布得通。见 Place。
03

CTS 到 ECO：记录每轮到底改了什么

CTS 保存时钟树后的数据库并核对时钟覆盖、偏斜、插入延迟及相关时序。Route 保存已布线版本并检查开路、短路和布线规则；OptRoute 用布线后的寄生信息重新评估时序与电气约束，比较优化前后变化。ECO 保存修复后的实现、变更记录和回归报告；若改动涉及功能逻辑，还应按项目要求核对等价性或验证结果。各阶段的工具报告不能替代最终签核。见 CTS、Route、OptRoute和 ECO。

04

练习：验收失败后回到哪一站？

题目：Route 报告有三条开路，复查发现其中两条经过 Floorplan 留下的窄通道。能否直接进入 ECO？下一轮至少保留哪些材料？

参考作答：不能仅凭开路数量就跳到 ECO。先核对断点、网络和附近的布局及电源资源，确认窄通道是否真是根因。若需要移动宏或扩宽通道，就回到 Floorplan 检查点，重新验证受影响的供电、布局、时钟和布线。至少保留变更说明、变更前后数据库、同设置的开路与拥塞报告，以及受影响阶段的回归结果。
