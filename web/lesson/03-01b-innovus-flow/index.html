Innovus 项目流程：每个阶段到底交付什么？

Innovus Flow Handoffs

从项目准备到 ECO，按阶段核对数据库、报告和验收条件，学会定位失败应该回退到哪里。

预计学习 ≈14 分钟 课表学时 0 Innovus项目流程检查点
01

开工前：让同事能复跑你的 Run

这一讲在流程里的位置

项目流程交接 · 从导入到 ECO 的每一站。本讲给你一张全局地图。看完再进具体工序，每次都知道"现在在第几站、上一站的产出是什么"。

资料来源

本讲参考钉钉目录第 05 项的主题安排，正文和练习为原创教学内容，不是钉钉原文、截图或项目案例的转载。

先冻结顶层网表、技术与单元物理库、时序库、时序约束，以及预定的模式与工艺角。运行清单还要记录 Innovus 版本、入口脚本版本、运行目录、日志位置和输入校验值。输入目录不要一边跑一边覆盖，否则重跑时即使脚本没变，也未必使用同一套库。详见 项目环境、工具启动和初始化检查。

工具启动成功不等于导入正确。用日志核对顶层名、未解析引用、被忽略的约束，并在数据库中确认预期模式和工艺角确实启用。没有约束的路径不能当成时序通过。初始交接不以 GUI 截图为准，应让接手人能恢复数据库、查看摘要，并找到产生它的原始输入。

02

Floorplan 到 Place：检查能否摆得下、接得通

Floorplan 交付含 Die、Core、宏、端口及布局约束的版本。除了看重叠和朝向，还要看剩余未分配的端口、宏外禁放区与摆放行，以及总线从哪一边进入通道。环境相同的两次布局，即使宏总面积不变，窄通道和零散摆放行也可能让局部资源不足。见 Floorplan。

PowerPlan 交付有电源网络和供电结构的检查点，以及连接和几何检查记录。电源线看起来完整，不代表每个电源域、宏电源脚都接到了对应网络；例如相邻的两块 Memory 可能属于不同域，不能因几何相近而推断应接同一电源。见 PowerPlan。

Place 交付标准单元布局数据库和合法性、时序及拥塞报告。报告中先分清「没摆上」「摆得不合法」和「能摆但可能走不通」三类问题，再决定回退。只给平均利用率，无法说明需要穿过宏通道的网络能否绕出。见 Place。

03

CTS 到 ECO：记录每轮到底改了什么

CTS 保存建树后的数据库并核对时钟覆盖、偏斜、插入延迟和相关时序。复核时钟覆盖时，要拿约束定义的端点集合与实际建树记录对照；有意不纳入的对象要有解释。Route 保存已布线版本并检查开路、短路和布线规则。OptRoute 基于布线后寄生信息重新评估时序与电气约束，比较优化前后变化。预布线和布线后的数值可用于了解阶段差异，不能视为一组同口径 A/B 对照。

ECO 交付修复后的实现、变更记录和回归报告；若改动涉及功能逻辑，还应按项目要求核对等价性或验证结果。时钟、供电或宏位置若因修复而改变，应重新执行受影响的检查，不能借用旧报告。阶段工具报告不替代最终签核。见 CTS、Route、OptRoute和 ECO。

04

四个检查点各要留什么证据

每次交接都写清「父版本、变更、检查、结论」，让接手人知道报告是否与数据库配套。同一阶段的不同试跑各用独立目录；不要让后一次生成的报告覆盖原基线。检查状态至少区分通过、失败、未跑和获准例外；例外要写明受影响对象、判断依据及负责人，不要把未跑当成通过。

从日志找到验收记录还不够：查看报告标题中的阶段、数据库版本或生成时间，再核对场景与筛选条件。只有确认报告来自正确版本，才值得分析问题本身。比如把基线的早期拥塞图拼接到修改后的布线报告上，看似能解释开路，实际可能指出已经不存在的热点。

第一次接手时，先恢复一个检查点做只读抽验：看固定宏坐标、报告所列的关键场景，以及输出目录里的对象名能否在数据库查到。若连恢复都需要原运行者机器上的临时环境，就先修交接清单。阶段之间可以保留轻量的索引，详细报告仍放在生成它的分支中；复制一份改名容易弄丢生成来源。

05

三条开路先按断点位置归类

练习使用纸面合成案例，基础设置是同一网表、分析视图和布线配置。路线图上，两组跨宏侧的总线位经过同一个窄通道，第三条网络的开路点在远离通道的顶边。R0 的 Route 正常结束，但连接性检查报三条开路。先根据网络名找断点坐标、所在层和相邻可达金属，不要只看一条汇总数字。

text
教学位置示意（不按比例）+-- 顶边 VIN[0]：端口接入开路 ------------------+|                                                  ||  [ MEM_A ] | 12 um | [ MEM_B ]                  ||             DATA[2]、DATA[3]：通道内开路         |+--------------------------------------------------+

先按断点位置对照宏禁布区、供电占轨和引脚附近可接入区。练习已知这两条 DATA 网络的断点在同一层同一侧，局部报告还显示该方向可用轨道不足。这支持通道假设，但并不能解释 VIN。对 VIN 单独核对端口坐标和接入标记；若标记落在非接入区，应修正端口定义并独立回归，不能把它算成扩通道的功劳。

06

扩通道只改一个变量，重跑四个阶段

从 D0 分支只调整 MEM_B 的横向位置，把通道从 12 µm 扩到 20 µm，不改约束、宏朝向和端口配置。按父子关系重新跑 PowerPlan、Place、CTS 和 Route：电源连接与几何先通过，才值得看后续结果。对比来自相同布线阶段、场景和统计范围的报告。如果只恢复 R0 直接移动宏，原供电、布局和时钟结果已不再对应当前几何，无法用来验收。

R1 的两条开路和相邻窗口溢出同时消失，通道假设得到支持；第三条仍需按端口问题回退，得到 R2。即使 R2 连接检查通过，功能慢角最差裕量仍为负，本例不能宣称时序签核完成。保留该违例的路径和场景，交给下一轮有明确目标的优化。

07

证据链断了从哪一站接回

  • 如果扩通道后供电连接失败，停止后续阶段，回到该分支 Floorplan 核对宏供电脚和电源接入；保留失败日志。
  • 如果开路数下降但邻区新增短路或规则违例，不合入 R1；恢复基线，从同一父版本改一个变量重试。
  • 如果改动没有改善局部指标，复核轨道统计范围及阻挡来源；不要连续挪宏后再用最后一张图倒推原因。
  • 回归包至少留输入清单、变更前后数据库、同设置的开路与拥塞报告、受影响阶段结果和仍未通过的事项。
08

Route 报三条开路，该退回哪一步

Route 有三条开路，其中两条经过 Floorplan 留下的窄通道。不能仅凭数量直接跳到 ECO；先核对断点、网络和附近的布局及电源资源。若需要调整宏或扩通道，就回到 Floorplan，重新验证供电、布局、时钟和布线。把第三条当成独立假设处理，才知道每次改动究竟修了什么。

自测
工具导入结束后为什么仍要核对分析视图？
导入可完成但预期场景未启用或约束被忽略，后续时序结果会缺少应检查的路径。
R1 消除了 DATA 开路但 VIN 仍开路，下一步是什么？
保留 R1 及对照报告，对 VIN 单独核对端口接入并回到受影响阶段，不把它当成同一根因。
R2 开路、短路和 DRC 都为零，能否宣布最终通过？
不能，本例 WNS 仍为负，且最终签核还须使用项目规定的流程和规则。
09

流出重试拿了旧数据库：哪些产物作废

这是原创纸面案例，不是 Innovus 运行输出。收尾时有两个候选数据库 B6 与 B7；B7 仅把一段绕线缩短，最终逻辑网表未变。一次流出任务失败后重试，调度器把输出目录设为 release/B7，但只有版图流出步骤仍从旧的 latest.db 链接恢复 B6。最终出现同目录、不同父版本的工件。

用三条箭头标注数据库到产物的实际依赖。已知 OA6 已被 DRC 和 LVS 使用，逻辑等价检查读取 NV5，静态时序分析读取 NV5 + PX7；后两项的其余输入与检查范围均符合要求。先数必重出的工件和必重跑的检查，再指出回退发生在哪一站。

核对：必重出 1 个表中工件（OASIS），必重跑 2 类检查（DRC 和 LVS）。回到 B7 的流出任务入口，把重试输入锁定到数据库的实际校验值，不需要退回布线改几何。回归时给新 OASIS 独立指纹和运行号；不要把 OA6 改名交付。若提取其实也读了 OA6，则还须重提寄生并重跑时序，不能照抄本题的保留结论。
