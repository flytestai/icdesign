OptRoute：布线后优化到底在优化什么

Post-route Optimization

布线后为什么必须优化；timing、DRC、short、open 四类目标怎么排优先级；PreRoute 与 PostRoute 脚本的分工；PR 流程终点与 ECO 的交界。附原始资料对照。

预计学习 ≈14 分钟 课表学时 1 Innovus40nm项目实操OptRoute
01

为什么要单独有一步"布线后优化"

上一课说过，Route 的首要任务是把所有线连上。这是一个"约束满足"问题：只要连上，就算完成。

但"连上"和"连得好"是两件事：

  • 为了绕开拥堵，工具可能选了很长的路径 → 时序变差；
  • 为了塞进窄通道，工具可能用了最小间距 → SI 风险升高；
  • 为了强制连通，工具可能用了勉强合法的 via → DRC 边缘；
  • 局部资源紧张的地方，可能出现少量短路或开路。

所以布线跑完，得到的是一个"技术上连通"的版图，不是"可以交付"的版图。OptRoute 就是在不改连接关系的前提下，把上面这些问题往下压。

OptRoute布线后优化

在已完成详细布线的版图上，通过调整走线路径、换层、插入/移动缓冲器等方式，改善时序、DRC 和布通率，但不改变逻辑连接关系。

02

四类优化目标，优先级不是并列的

原始资料列了四个方向：timing、DRC、short、open。它没说谁先谁后，但顺序其实是有硬约束的。

第一优先：open 和 short（连通性）

这两项不通，后面全都无意义。

  • open（开路）：该连的没连上，功能直接错误。时序分析甚至无法给这条路径算值。
  • short（短路）：不该连的连上了，功能直接错误，而且可能造成电源短接。

一项都不许留。这不是"优化目标"，是"合格门槛"。

第二优先：DRC（可制造性）

DRC 违例意味着这个版图做不出来。哪怕时序全绿，工厂也造不出。

但这里有个现实权衡：极少数 DRC 违例（比如某些特殊规则）在项目里可能被豁免（waiver），需要签核确认。但"能豁免"和"现在就先不管"是两件事——先修，修不掉再走豁免流程。

第三优先：timing（性能）

时序在前面两者都过关之后才有意义。

原因很直接：修 timing 的手段（插 buffer、加宽线、换层）会增加布线资源占用，可能反过来制造 DRC 或 short。所以必须先把连通和规则做干净，再动时序。

常见坑 · 一上来就修时序

新手常见操作：Route 完看到 WNS 是负的，立刻跑时序优化。结果优化过程插了一堆 buffer，把原本干净的布线搞出一片 DRC 和 short，最后连通性都保不住，只能回退重跑。

正确顺序永远是：连通 → 规则 → 时序。

03

PreRoute 与 PostRoute：同一套 tune，两个挂载点

原始资料提到两种 tune：

text
PreRoute.tcl   在绕线之前执行的脚本PostRoute.tcl  在绕线之后执行的脚本

它说"具体的优化设置取决于工程师自己的配置，加在 tune 里面"。这句话是对的，但要展开一下——同一个参数放在哪个脚本里，效果完全不同。

PreRoute.tclPostRoute.tcl
执行时机详细布线之前详细布线之后
能改什么布线策略、层分配偏好、间距偏好、禁布区已有走线的调整、局部重布、缓冲器插入
影响范围全局（影响工具怎么规划所有线）局部（只动被点名的网或区域）
典型用途让工具一开始就往正确的方向走修补工具没做好的个别地方
风险改错会影响整个布线结果改错只影响局部，好回退

经验法则：能在 PreRoute 解决的，不要留到 PostRoute。

原因：PreRoute 是"告诉工具怎么做"，成本低；PostRoute 是"在成品上动刀"，每改一处都要重新做局部提取和检查，成本高，而且可能引入新问题。

举个具体例子：如果一个设计中大量网需要走 M5 以上层，那应该在 PreRoute 里设置层偏好，让工具一开始就这么规划。如果留到 PostRoute，就得一条一条网去改，工作量爆炸，而且改完之后层间的 via 结构可能不合法。

小技巧

PreRoute.tcl / PostRoute.tcl 必须放进版本管理，并且能被同一条流程脚本调用。写在 GUI 里点出来的设置，下次重跑就没了——这是"结果无法复现"的头号原因。

04

PR 流程的终点在哪里

原始资料有一行很关键：

text
===========================PR流程结束==============================FinalPR  最后一轮PR，fp不能在调整！进入ECO修复阶段,(如果结果很差，没法eco修复，只能RePR)

这行字里藏着两个重要判断：

1. "fp 不能再调整"是什么意思

走到 FinalPR，意味着 floorplan 已经冻结。宏的位置、Die 的尺寸、端口的分配都不能再动。

为什么？因为前面所有阶段的结果（place、CTS、route、所有报告）都是基于这个 floorplan 产生的。一旦 floorplan 变了，前面所有报告全部作废，必须从头重跑。这个代价在项目后期是不可接受的。

所以 FinalPR 阶段的优化手段被严格限制在"不动 floorplan"的范围内：改走线、换层、插 buffer、局部重布。

2. "没法 ECO 修复只能 RePR"是什么意思

ECO（Engineering Change Order）是在已有版图上做局部修改。它的前提是：问题局部化，改动不影响全局。

如果出现下面这些情况，ECO 就救不了了：

  • 布线资源整体不够（大面积溢出的后果）；
  • 时序违例遍布所有路径组（不是局部问题）；
  • 电源网络本身设计不足（IR drop 超标）。

这些都必须回到 PR 流程重跑（RePR），甚至回到 floorplan。

判断能不能 ECO 的方法

看违例的分布，不是看数量。

  • 100 个违例集中在 3 个区域 → 大概率能 ECO；
  • 20 个违例散布在 20 个区域，且分属不同路径组 → 可能需要 RePR。

数量少但分散，往往比数量多但集中更难修。

05

优化之后怎么验收

OptRoute 跑完，不能只看"优化报告说改善了"。要按下面的顺序自己核一遍：

  1. 连通性：open = 0，short = 0。注意要看最终版图的报告，不是优化过程中的中间报告。
  2. DRC：违例数下降，且剩余违例有明确豁免依据。要确认 DRC 跑的是最终版图 + 最终层映射。
  3. 时序：对比优化前后的 WNS / TNS，必须同场景、同工艺角、同路径组。跨场景比较没有意义。
  4. SI：优化改了走线，耦合关系变了，串扰要重算。
  5. 寄生提取：走线变了，寄生必须重新提取，否则时序数字是旧版图的。
常见坑 · 拿优化前的时序报告当结论

OptRoute 改了走线 → 寄生变了 → 时序必须重算。如果直接拿优化前的 SPEF 去看时序，看到的是"旧版图的时序"，跟实际交付的版图对不上。

顺序永远是：改版图 → 重提取 → 重算时序 → 重跑 DRC。

07

动手：判断该 PreRoute 还是 PostRoute

动手三个场景，各自该放哪个脚本

下面三个需求，判断应该写进 PreRoute.tcl 还是 PostRoute.tcl，并说明理由：

  1. 这个设计里所有时钟网必须走 M6 以上层，且用 2W2S 规则。
  2. Route 跑完发现某个宏附近有 5 条短路，集中在 200 µm × 200 µm 的窗口里。
  3. 全局布线显示某个区域纵向拥塞严重，需要减少那里的纵向布线需求。

提示：想清楚"这个设置是告诉工具怎么规划，还是在成品上打补丁"。

自测
OptRoute 的四类目标为什么必须按 open/short → DRC → timing 的顺序？
连通性不通功能直接错；DRC 不过版图造不出来；修 timing 的手段会增加布线资源，可能破坏前两者。
PreRoute 和 PostRoute 的核心区别是什么？
PreRoute 在布线前影响工具的全局规划，成本低影响面大；PostRoute 在成品上做局部修补，成本高但好回退。
FinalPR 阶段为什么不能再调 floorplan？
前面所有阶段结果和报告都基于该 floorplan，一旦改动全部作废需从头重跑。
什么情况下 ECO 救不了，必须 RePR？
布线资源整体不足、违例遍布多个路径组、电源网络本身设计不足等非局部问题时。
OptRoute 改了走线之后，为什么时序必须重算？
走线变化导致寄生参数变化，旧 SPEF 对应的是旧版图，算出来的时序与交付版图不符。
违例 100 个集中在 3 个区域，和 20 个散布在 20 个区域，哪个更难修？
后者。ECO 依赖问题局部化，分散违例往往涉及全局结构问题，可能需要 RePR。
