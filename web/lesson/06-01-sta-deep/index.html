STA 深水区：时钟组、跨时钟域与悲观度

Advanced STA

会算 setup/hold 只是入门。真实项目里最难的是"哪些路径该查、该怎么查"：时钟组为什么必须写、false path / multicycle / max_delay 三者怎么选、OCV / CPPR / AOCV 各自消除什么、2.5ns 的周期怎么分给逻辑和余量，以及 report_timing 的三个高级用法。

约 50 分钟 课表学时 6 STACDCOCV约束
01

一、时钟组：异步时钟之间不该比

本章目标学完这一章，你能看着一份 SDC 说出"哪两组时钟之间必须写 set_clock_groups -asynchronous"，并解释漏写之后报告会变成什么样。

两个人对表。你在北京，同事在纽约。你说"九点前把文件发我"，他按纽约时间九点发过来——晚了十二个小时。不是他不守时，是你们用的不是同一把尺子。

异步时钟就是这两个人。clk_core 由一颗 PLL（锁相环，phase-locked loop）产生，clk_ddr 由另一颗产生，两者频率不成整数比，相位关系每次上电都可能不同。它们之间没有"第几拍对第几拍"这回事，所以任何"周期减逻辑延迟"的计算都没有物理意义。

但工具不知道这件事。它默认把所有时钟当成同源同步时钟，会去扫两者的相位组合，取最坏的那一组来算 required。于是你会看到一条永远修不好的违例。

Clock Group时钟组点击看解释

用 set_clock_groups 把时钟分成若干组，声明组与组之间的时序关系。最常用的是 -asynchronous（异步）：任意两组之间的路径不做时序检查，但同一组内部的路径照常检查。这一句必须记牢——组内仍然是同步的。

不写会怎样：三个后果，一个比一个隐蔽

第一，报出修不掉的违例。 一条跨域路径 slack −1.28ns，你换单元、加 buffer、挪位置，全都收效甚微，因为它本来就不该被比较。它会占据 WNS 榜首，让整个项目的 QoR 看起来很差。

第二，优化器会为假路径浪费资源。 PR 工具的优化引擎看到违例就去修：给跨域路径插 buffer（缓冲器）、把单元 upsize（加大驱动）。这些动作真实发生，面积和功耗真金白银地涨，而真正该修的同步路径反而抢不到优化预算。

第三，报告之间不可比。 加了 clock group 和没加，WNS 可能差 1ns 以上。两个人拿着两份报告开会，会吵一下午"到底谁的数字对"。

手算一次这个差距。clk_core 周期 2.5ns，clk_ddr 周期 1.25ns，两个 PLL 独立。一条 core→ddr 的路径：发射时钟延迟 0.60ns，数据路径 1.10ns，捕获时钟延迟 0.50ns，setup 0.08ns。

  • 工具取"刚好赶上下一个 ddr 沿"：required = 1.25 + 0.50 − 0.08 = 1.67，arrival = 0.60 + 1.10 = 1.70，slack = −0.03。
  • 工具再扫相位漂移，最坏情况捕获沿几乎提前一整拍：required = 0.50 − 0.08 = 0.42，slack = 0.42 − 1.70 = −1.28。

同一对时钟，同一条路径，slack 从 −0.03 变到 −1.28。这个数字不是设计的性质，是约束缺失的产物。

tcl
# 作用：把三组互不相关的时钟声明为异步，组内仍然互相检查# 用法：写在所有 create_clock 之后、出报告之前；三组必须列全set_clock_groups -asynchronous \    -group {clk_core} \    -group {clk_ddr} \    -group {clk_usb}          ;# 任意两组之间不检查，组内照常检查# 说明：-group 里写 create_clock -name 起的时钟名，不是端口名# 说明：同一个时钟只能出现在一个组里，重复出现工具会报错# 说明：漏掉某一组，那一组和其余所有组之间仍然会被当成同步

三种 exclusive，别用错

set_clock_groups 除了 -asynchronous，还有两个容易混的选项：

选项含义典型场景用错的后果
-asynchronous相位无关，永远不会同步两个独立 PLL、外部晶振与内部 PLL用得过多 → 真实同步路径被放过
-logically_exclusive逻辑上不可能同时存在时钟 mux 的两路输入用错 → 把真实路径整片关掉
-physically_exclusive物理上不可能同时存在不同封装/不同测试模式的时钟用错 → 同上，且更难发现

三者都是"不检查"，但理由不同。评审时被问"为什么这两组是异步的"，你要能答出物理依据（不同 PLL、不同晶振、频率比非整数），不能答"因为报了违例"。

和 set_false_path 的区别：一个双向，一个单向

维度set_clock_groups -asynchronousset_false_path
方向双向：A→B 和 B→A 都不查单向：只关掉 -from 到 -to 这一个方向
覆盖一次声明，组内新增的时钟/寄存器自动适用是"快照"，新逻辑加进来要重写
可读性一眼看出"哪些域互不相关"散落在 SDC 各处，容易重复或冲突
适用整块域之间异步单个信号、单条路径、复位/测试

结论：域与域之间用 clock group，单个信号用 false path。 用 false path 处理跨域，你要写两条（A→B、B→A），漏一条就漏一半。

CDC跨时钟域点击看解释

Clock Domain Crossing。信号从一个时钟域传到另一个时钟域。后端不做 CDC 设计，但必须看懂：单比特控制信号用两级同步器（synchronizer），多比特数据用异步 FIFO（asynchronous FIFO）或握手（handshake）。
关键认知：设成异步只是"不检查"，不等于"安全"。 前端的同步器没做，STA 全绿也会在硅片上偶发采错。

工作场景 · 周一评审，WNS 榜首是一条跨域路径

项目例会，QoR 页面第一行写着 WNS −1.28ns，起点 u_core/u_fifo/wptr_reg[3]/CK，终点 u_ddr/u_sync/rptr_sync_reg[1]/D。组长问："这条为什么修不掉？"

你翻 SDC，发现只有 create_clock，一条 set_clock_groups 都没有。三个时钟 clk_core / clk_ddr / clk_usb 全被工具当成同源。

你要在五分钟内回答三件事：这条路径是不是真违例、依据是什么、加了约束之后 WNS 会变成多少。答案不在报告里，在 SDC 里。

常见坑 · 为了消违例，把同步路径也设成异步

现象：加了 set_clock_groups -asynchronous -group {clk_core} -group {clk_ddr} 之后，WNS 从 −1.28 变成 +0.35，报告全绿。

但设计里 clk_ddr 有一路是 clk_core 三分频后经 PLL 倍频回来的，和 core 存在固定相位关系，那部分路径本来是同步的，现在全被关掉了。

原因：把"看起来是两个时钟"当成"一定异步"。分频/倍频关系、同源 PLL 的不同输出，都属于同步或半同步，必须按同步检查（或用 -logically_exclusive 说明真实关系）。

怎么查：report_clocks 看每个时钟的 source；对每个 generated clock 确认它的上游是不是同一个根。有共同根的，先按同步处理，确实要放松必须有波形或规格依据。

02

二、false path 与 multicycle：该松的松，该紧的紧

三条命令长得很像，语义完全不同。先看一张定位表：

约束一句话语义还检不检查检查基准
set_false_path这条路径永远不用查完全不查无
set_multicycle_path N允许 N 个周期完成查，但放宽到第 N 拍时钟周期 × N
set_max_delay D绝对延迟不许超过 D查，用绝对值D 本身，与周期无关

记法：false path 是"删掉"，multicycle 是"往后挪"，max_delay 是"换个尺子量"。

False Path假路径点击看解释

物理上连通、功能上永远不会有有效信号通过的路径。典型：异步复位、测试逻辑、扫描链旁路、被 mux 永久屏蔽的分支。
风险不对称：多写一条，真实违例会消失；少写一条，只是多几条假违例。所以每一条 false path 都要有书面依据。

false path：最常见的写法错误是"只写一半"

set_false_path 的两个端点参数都是可选的。省略 -to 的意思是"到所有终点"，省略 -from 是"从所有起点"。于是这一行：

tcl
# 作用：演示一个危险写法——只写 -from，等于关掉整个时钟域# 用法：不要这样写；这里只是给你看漏写 -to 的后果set_false_path -from [get_clocks clk_core]# 说明：语义是"从 clk_core 出发到任何地方都不检查"# 说明：包括 clk_core → clk_core 的真实同步路径，全部消失

写完之后 WNS 立刻变好，因为最差的那一大批路径被整片删掉了。识别方法很直接：跑 report_timing -from [get_clocks clk_core] -to [get_clocks clk_core]，如果返回 No paths，而设计里明明有 core 域内部的同步逻辑，那就是这条约束写宽了。

正确的写法只有两种：成对写 -from 和 -to，或者用 clock group 表达域间关系。

multicycle：必须成对，且 N 要有依据

tcl
# 作用：声明一条路径允许 2 拍完成，并把 hold 检查点拉回正确位置# 用法：必须有前端书面确认"第 2 拍才采样"，否则就是放水set_multicycle_path 2 -setup -from [get_pins u_mul/*/Q] -to [get_pins u_acc/*/D]# 说明：setup 检查点从第 1 个沿后移到第 2 个沿set_multicycle_path 1 -hold  -from [get_pins u_mul/*/Q] -to [get_pins u_acc/*/D]# 说明：-hold 写 N−1，把 hold 的检查沿拉回第 1 个沿# 说明：不写这一行，hold 检查沿会跟着 setup 一起后移，位置就错了

为什么 hold 也要写：setup 的检查沿一挪，hold 的检查沿默认跟着挪。挪错之后有两种表现——一种是 report_timing -delay_type min 里那条路径的 required 变成一个奇怪的整周期数（比如 1.25 而不是 0.05），另一种是干脆一条 hold 都不报。两种都是"检查位置错了"，不是"没有 hold 问题"。

判断 N 对不对，只有一个办法：回到 RTL 数拍子。看使能信号是第几拍拉高的、数据在寄存器里停了几拍。工具永远猜不出你的设计意图，N 是人给的。

max_delay：跨异步域的唯一正确工具

异步域之间不做时序检查（clock group），但有些跨域信号仍然需要"有界偏斜"：比如 8 位配置总线配合一个握手信号，要求数据和有效信号之间的偏斜不超过 1ns，否则接收端会在有效沿上采到半新半旧的值。

这种"不按周期、只按绝对时间"的要求，就是 set_max_delay 的场景。

tcl
# 作用：给跨异步域的数据总线限制绝对延迟和最小延迟# 用法：与握手协议配套；max 和 min 成对写，理由写进注释set_max_delay 1.0 -from [get_pins u_apb/data_reg*/Q] -to [get_pins u_core/cfg_reg*/D]# 说明：最晚 1.0ns 内必须到达，超过就报违例set_min_delay 0.2 -from [get_pins u_apb/data_reg*/Q] -to [get_pins u_core/cfg_reg*/D]# 说明：最早不能早于 0.2ns，防止数据比同组有效信号早太多

三种误用，各漏掉一类真实违例

误用表面现象漏掉了什么真实违例
set_false_path -from [get_clocks clk_core]（漏 -to）WNS 突然变好、报告全绿core 域内部所有同步路径，包括真正的关键路径
set_multicycle_path 3 -setup（本该 2 拍）那条路径 slack 变正第 2 拍就该采样的真实违例；芯片上累加结果错
set_max_delay 5（周期才 2.5ns）跨域路径一条违例都没有偏斜超过 1ns 的真实风险；接收端采样错位

第三种的隐蔽性最高：5ns 看起来是个"很严"的数，实际比两个周期还宽。max_delay 的数值必须来自协议，不能来自"设大一点比较安全"。

Multicycle Path多周期路径点击看解释

功能上允许用超过一个时钟周期完成的路径。必须成对声明 setup 和 hold：setup 写 N，hold 写 N−1。
典型场景：乘法器、除法器、慢速配置寄存器、带使能的累加器。没有使能信号保护的路径不能设 multicycle——工具不检查，功能上就会在第 1 拍采到中间值。

常见坑 · 把"时序修不动"当成"可以设 false path"

现象：一条路径修了两周还是 −0.4ns，有人在 SDC 里加了一行 false path，WNS 归零，项目"收敛"。

流片后症状：某个功能在特定输入组合下算错，概率约百万分之一，实验室复现不了。

原因：false path 不改逻辑，只改检查。物理上的竞争还在，硅片上照样发生。

规矩：false path 的依据必须是"功能上不可能"，不能是"时序上修不动"。 修不动就走 waiver 流程，写清风险和批准人，而不是偷偷改约束。

03

三、悲观度：签核要多保守

05-02 已经讲过 derate（降额系数）的基本公式和 5% 吃掉多少，这里不重复推导。这一章换个角度：把三种悲观度当成三笔账，看每一笔在修什么问题。

买电阻的类比还记得：标称 100Ω、精度 ±5%，一盒里实际是 95~105Ω。如果你拿 20 个串联，最坏是不是 20×5Ω？不是——误差有正有负，全同向的概率极低。但签核必须按最坏算，因为要量产几百万颗。

OCV 就是"全按最坏算"。它的问题也在这里：太粗。

机制在消除什么消除不了什么代价
OCV / derate给随机偏差留余量（覆盖，不是消除）分不清深路径和浅路径深路径过度悲观
CPPR公共路径被 late/early 各算一次的虚假悲观分叉之后的真实偏差需要工具支持，计算稍慢
AOCV深路径上"统一系数"的过度悲观同一深度内不同单元的真实差异需要 foundry 给表
POCV / LVF线性相加的过度悲观（改方差相加）模型本身的误差文件巨大、跑得慢

一句记法：OCV 是"一刀切"，CPPR 是"把重复扣的还回来"，AOCV 是"按深度分级"，POCV 是"按分布算"。

CPPR公共路径悲观度消除点击看解释

Common Path Pessimism Removal。发射时钟和捕获时钟从同一个根出发，在分叉前走过同一段物理路径。这段路径在发射侧按 late（×1.05）、在捕获侧按 early（×0.95）各算了一遍，产生了一个物理上不存在的差值。CPPR 把这段加回来。
报告里对应 clock reconvergence pessimism 这一行，通常是正数（加回）。

手算：一条 2.5ns 路径，四种模式

设定：周期 2.5ns，发射时钟路径 0.70ns，捕获时钟路径 0.90ns，数据路径（CK→Q + 组合 + 线）1.30ns，setup 0.10ns，uncertainty 0.15ns，公共路径 0.60ns。

① 不开 OCV

  • arrival = 0.70 + 1.30 = 2.00
  • required = 2.5 + 0.90 − 0.15 − 0.10 = 3.15
  • slack = 3.15 − 2.00 = 1.15ns

② 开 5% derate（数据侧和发射时钟 ×1.05，捕获时钟 ×0.95）

  • arrival = 0.70×1.05 + 1.30×1.05 = 0.735 + 1.365 = 2.10
  • required = 2.5 + 0.90×0.95 − 0.25 = 2.5 + 0.855 − 0.25 = 3.105
  • slack = 3.105 − 2.10 = 1.005ns

③ 打开 CPPR

公共段 0.60ns 被算了两次：发射侧 0.63、捕获侧 0.57，差 0.60 × (1.05 − 0.95) = 0.06。

  • slack = 1.005 + 0.06 = 1.065ns

④ 换成 AOCV（depth=10，late 1.02 / early 0.98）

  • arrival = 0.70×1.02 + 1.30×1.02 = 2.04
  • required = 2.5 + 0.90×0.98 − 0.25 = 3.132
  • slack = 3.132 − 2.04 = 1.092
  • 加回 CPPR：0.60 × 0.04 = 0.024 → 1.116ns

四步走下来：1.15 → 1.005 → 1.065 → 1.116。OCV 吃掉 0.145，CPPR 还回 0.06，AOCV 又比 OCV 少悲观约 0.05。 这三个数就是评审时"为什么你的 WNS 和别人差 0.1ns"的全部答案。

AOCV先进片上偏差点击看解释

Advanced OCV。把 derate 从常数改成查表，两个维度：depth（路径上的级数） 和 distance（物理距离）。级数越多、距离越近，相对偏差越小，derate 越接近 1。
28nm~16nm 的主力方案。表由 foundry 提供，不要自己造。

三条纪律

  1. 四个组合写全：late/early × cell/net。只写 -cell_delay 的话，线延迟完全没有 derate，长线路径的悲观度会不足。
  2. 异步域之间不需要 derate，因为它们根本不检查。先确认 clock group，再谈悲观度。
  3. 不要为了让报告变绿而改 derate。 每一个值的调整都要有依据（foundry 表、实测 skew、评审结论），并写进签核记录。改 derate 是改结论，不是改参数。
工作场景 · 三个人，三份报告，三个结论

同一版网表，三个人各跑一次 PT：

跑法setup WNS结论
不开 OCV+0.35ns"这设计很宽松"
5% derate−0.12ns"要修两周"
AOCV + CPPR+0.08ns"可以签核"

会上吵起来的根本不是设计，是悲观度。所以签核会的第一页必须是"本次使用的模式与参数"，而不是 WNS 数字。没有参数说明的 WNS 没有意义。

四、时序预算：把周期分给谁

时序预算（timing budget）就是"一个周期怎么花"。它的作用和家庭预算一样：先定各项上限，超了就知道该砍哪一项，而不是月底看账单发呆。

基本式子（setup 视角）：

text
T_period = T_ckq + T_logic + T_setup + T_skew + T_uncertainty + T_margin

这个式子画成一条路径的解剖图，就是下面这张：

从图里要看出什么：预算表的每一行，都能在图里指到一个具体的位置。28 级还是 38 级的争论，本质上就是 T_logic 这一段能不能塞进它的预算。

每一项都要有人负责：

项目谁负责怎么定
T_ckq库查 lib，触发器 CK→Q 的延迟
T_logic前端 + 后端逻辑级数 × 单级延迟；这是唯一能大幅压缩的一项
T_setup库查 lib，且随 transition 变化（见第六章）
T_skewCTS目标值，CTS 后用实测替换
T_uncertainty签核jitter + 残余 skew + 建模误差

2.5ns 的预算表

手算：两条路径，一条过一条不过

单级 NAND2 在 28nm 约 50ps（典型值，含线分摊）。预算给逻辑 1.55ns，能放 1.55 / 0.05 = 31 级。

路径 A：28 级

  • arrival = 0.12 + 28×0.05 = 0.12 + 1.40 = 1.52
  • required = 2.5 − 0.15 − 0.10 = 2.25
  • slack = 2.25 − 1.52 = 0.73ns → 余量充足

路径 B：38 级

  • arrival = 0.12 + 38×0.05 = 0.12 + 1.90 = 2.02
  • slack = 2.25 − 2.02 = 0.23ns → 账面为正，但没扣 OCV

再扣 5% derate（数据侧约 1.9×0.05 ≈ 0.095）：

  • slack ≈ 0.23 − 0.095 = 0.135ns
  • 再扣布线恶化 0.1 → 0.035ns

结论：38 级在预算表里已经是"擦线过"。 想稳，逻辑级数要压到 33 级以内，或者把关键路径上的单元换成 LVT（低阈值电压，low-Vt）——代价是漏电上升（见 08-01 第 9 个坑）。

预算表的三个使用时机

  1. 综合前：把"单级 50ps、最多 31 级"告诉前端，让他知道哪段 RTL 必须拆。这是预算表最有价值的时刻——在设计还没定型时干预，比在版图上补救便宜一个数量级。
  2. CTS 后：把 skew 从"预算 80ps"换成"实测 62ps"，把省下的 18ps 还给逻辑或余量。这一步叫"预算回收"，很多项目忘了做，白留了余量。
  3. 签核时：margin 只保留模型误差，不再保留"给后期改动"的那一份——因为已经没有后期了。
常见坑 · 预算表加总超过 100%

现象：各项单独看都合理，加起来 2.68ns，比周期 2.5ns 多 0.18ns。报告上却"没有违例"。

原因：工具不会拿你的预算表算 slack，它用的是 SDC 里的周期和库里的真实参数。预算表只是人看的文档，加总超标不会报错，只会让你的判断全部偏乐观。

怎么查：预算表最后一行必须是求和，且等于周期。每次改任何一项，重算总和。多出来的部分要么砍逻辑，要么明确写成"负余量，已知风险"并由组长签字。

五、report_timing 的三个高级用法

report_timing 有几十个参数，但真正改变"你能看到什么"的只有三个：-through、-from/-to、-path_type。默认输出把时钟路径折叠成一行，很多问题因此看不见。

tcl
# 作用：三种高级用法，分别对应"经过谁""只看这一条""skew 从哪来"# 用法：定位阶段用第一条，ECO 复验用第二条，查时钟用第三条report_timing -through [get_pins u_alu/U1188/Z] -max_paths 20# 说明：-through 只保留经过该引脚的路径，用来数"这个单元拖了多少条违例"# 说明：出现在 200 条违例里的单元，换掉它比修 200 条路径划算 report_timing -from [get_pins u_ctrl/state_reg[2]/CK] -to [get_pins u_dp/acc_reg[7]/D]# 说明：-from/-to 精确锁定一对端点；改完 ECO 只看这一条，避免被别的路径干扰# 说明：-from 写 CK 引脚表示"由这个触发器的时钟沿发射"，写 cell 则包含它的所有起点 report_timing -from [get_pins u_ctrl/state_reg[2]/CK] -to [get_pins u_dp/acc_reg[7]/D] \              -path_type full_clock_expanded -max_paths 1# 说明：full_clock_expanded 把时钟路径逐级展开# 说明：默认只给一行 "clock network delay 0.90"，展开后能看到每一级 buffer 的 Incr

这三种用法捞出来的报告长什么样，先看一张逐行注解的全景：

从图里要看出什么：报告不是只读最后那个 slack，是读中间每一行的 Incr。三个高级用法全是在帮你把"哪一级"定位出来。

-through：找"惯犯单元"

一个问题单元往往会出现在很多条违例里。-through 就是筛子。

用法上有两个细节：

  • 多个 -through 表示"按顺序经过"（先 A 后 B），不是"经过任意一个"。想表达"或"，要跑多次或用 -through 加通配。
  • 配合 -max_paths 200 再 grep -c 数条数，比一条条看快得多。

工作中怎么用：修 setup 之前先跑一次 -through 统计，排出"出现在最多违例里的前五个单元"。这五个通常是真正的瓶颈；换掉它们，比按 slack 排序一条条修有效得多。

-from/-to：ECO 复验的唯一正确方式

改完一处，全量重跑要十几分钟，而且新冒出来的违例会干扰判断。用 -from/-to 锁定一条，30 秒就能确认"这一条好了没有"。

注意端点写法：

写法含义什么时候用
-from [get_pins .../CK]从该触发器的时钟引脚出发精确定位一条路径
-from [get_cells ...]从该 cell 的所有起点出发一整个寄存器组
-to [get_pins .../D]到该数据引脚精确定位
-to [get_clocks clk]到该时钟域所有终点看整个域

-path_type full_clock_expanded：skew 的唯一证据

默认报告里，时钟只占一行：

text
clock network delay (propagated)         0.9000     0.9000

你只知道总数是 0.9ns，不知道这 0.9 里有多少是主干、多少是叶子、有没有某一级特别慢。加 -path_type full_clock_expanded 之后，每一级 buffer 都会列出来，Incr 列一眼就能看出瓶颈。

这也是 CTS 工程师和 STA 工程师吵架时唯一的事实依据。 "我觉得时钟树挺平衡的"不是证据，"展开报告里第 4 级 buffer 的 Incr 是 0.21ns，其他级都是 0.06"才是。

06

六、transition 为什么会让 setup 变差

Transition转换时间点击看解释

也叫 slew（斜率）。信号从低到高（或从高到低）跨越阈值区间所花的时间。库里的每一张延迟表、每一张约束表，都以它为自变量之一。
transition 差 = 边沿"爬"得慢 = 波形不再是陡直的台阶。

库里触发器的 setup 时间不是一个常数，是一张二维表：

时钟 transition数据 transitionsetup 时间
50ps50ps0.080ns
100ps50ps0.095ns
150ps50ps0.120ns
150ps100ps0.140ns
250ps150ps0.180ns

（数值是典型趋势示意，具体查你项目库的 .lib。趋势是确定的：两个 transition 越慢，setup 越大。）

为什么慢边沿会让 setup 变差

触发器内部是一对背靠背的反相器（锁存环）。时钟沿到来时，它要"关门"。关门需要时间，而这个时间取决于时钟沿有多陡：

  1. 关门过程本身变长：慢边沿意味着时钟在阈值附近停留更久，内部传输门处于"半开"状态的时间更长，数据更容易在关门过程中被改动，所以库要求数据更早稳定。
  2. 数据边沿也慢：数据在 D 端爬得慢，同样需要更长时间才能被正确识别，两项叠加。
  3. 延迟表要外插：库表的自变量范围是有限的（比如 transition 到 200ps）。超过之后工具只能外插，算出来的延迟不准，可能偏乐观。

第三条最危险：你以为在修时序，其实是在用错误的延迟数字修时序。 这就是 03-08 里"先修 DRV 再修时序"的物理依据。

手算：一次 transition 恶化吃掉多少

某条路径原本 slack = +0.05ns，时钟树上一级 buffer 驱动不足，clock transition 从 100ps 恶化到 250ps。

  • setup 从 0.095 涨到 0.180，多扣 0.085ns
  • 该 buffer 自身延迟也从 0.06 涨到 0.09，arrival 多 0.03ns
  • 合计：0.05 − 0.085 − 0.03 = −0.065ns

一个 transition 违例，把一条"刚好过"的路径变成了违例。 而它不会出现在 setup 报告的"原因"里——报告只告诉你 slack 是负的。

反过来也成立：修 setup 时如果只 upsize 数据侧单元，而时钟树 transition 依然很烂，你换来的那点收益会被 setup 变大吃掉一部分。先看 report_constraint -all_violators -max_transition，再决定修哪边。

07

七、例外约束的纪律：四条，缺一条就出事

例外约束（exception）是 SDC 里唯一能"让违例消失"的东西。所以它也是唯一需要流程管控的东西。

四条纪律：

  1. 每条例外都要有注释，写清依据：设计规格第几节、前端谁的确认、哪封邮件。没有依据的 false path 等于在签核报告上造假。
  2. 每条例外都要能被复查。写法上尽量用 clock group 和 -from/-to 成对，避免"只写 -from"这种覆盖整个域的写法。
  3. 改动要留 diff。SDC 进版本管理，每次改动一个 commit，message 写"为什么"。评审时看 diff 比看全文快十倍。
  4. 数量要能解释。一个中等项目的例外约束通常几十条；如果你的 SDC 里有三百条 false path，那不是约束，是掩盖。

自测：先自己想，再点开答案
为什么异步时钟之间不应该做时序检查？
两者相位关系不固定，不存在"第几拍对第几拍"，required 的计算没有物理意义；强行比较会得到从 −0.03 到 −1.28 不等的假数字。
set_clock_groups -asynchronous 和 set_false_path 的核心区别？
前者双向、按域生效、可维护；后者单向、按端点、是快照。域间用前者，单信号用后者。
只写 set_false_path -from [get_clocks clk_core] 会发生什么？
等于"从 core 出发到所有终点都不检查"，包括 core 域内部的真实同步路径，WNS 会假性变好。
set_multicycle_path 2 -setup 之后为什么必须写 -hold 1？
setup 检查沿后移会让 hold 检查沿跟着错位；-hold N−1 把它拉回正确位置，否则真实 hold 违例会被藏起来或凭空出现。
set_max_delay 5 用在 2.5ns 周期上，问题在哪？
5ns 比两个周期还宽，等于没有约束；跨域总线的偏斜风险完全不被检查。数值必须来自协议而不是"设大点安全"。
OCV、CPPR、AOCV 各自在消除什么？
OCV 给随机偏差留余量（但一刀切）；CPPR 消除公共路径被 late/early 各算一次的虚假悲观；AOCV 消除深路径上统一系数的过度悲观。
为什么 derate 要写 cell 和 net 两组？
只写 -cell_delay 时线延迟完全没有 derate，长线路径的悲观度不足，报告会偏乐观。
2.5ns 周期里，逻辑预算 1.55ns、单级 50ps，最多几级？
31 级。38 级时账面 slack 只剩 0.23ns，扣 OCV 和布线恶化后基本擦线。
为什么修 setup 之前要先修 transition？
transition 超标时库的 setup 值变大、延迟表要外插，工具算出来的延迟本身不准；在错的数字上修时序没有意义。
